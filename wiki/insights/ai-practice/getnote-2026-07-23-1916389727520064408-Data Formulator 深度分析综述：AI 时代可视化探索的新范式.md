## 一、一句话定位

**Data Formulator 是把"自然语言 + UI 拖拽"混合驱动数据可视化的开源工具，核心创新是"概念层（Concept）+ 数据线程（Data Thread）+ 沙箱 Python Agent"三件套 —— 让 AI 在不接管用户控制权的前提下完成"数据 → 图表"的迭代。**

它不是 BI 工具的 AI 化，也不是 ChatGPT 加图表 —— 它是一个新范式：**"专业领域的 Vibe Coding"**。

---

## 二、解决的真问题

### 传统可视化工具的两难困境

```
传统 BI（Tableau/PowerBI）
  ✅ 完全可控
  ❌ 操作复杂、学习曲线陡
  ❌ 表达意图 ≠ 选字段拖面板

AI 直接生成（ChatGPT + Code）
  ✅ 表达自然
  ❌ 不可控：用户看不到过程
  ❌ 不可改：调整必须重新 prompt
  ❌ 不可分享：结果散落在对话里

Data Formulator
  ✅ UI 提供结构化输入（字段绑定）
  ✅ NL 补充细节（指令）
  ✅ 中间产物可回溯、可修改
  ✅ 图表自带"可调旋钮"（生成式 UI）
```

**真痛点**：分析师明知想看什么，但用 BI 要点 10 分钟，用 ChatGPT 要重新描述 3 次。

## 三、4 大核心创新（独家）

### 创新 1：Concept Encoding Shelf — 概念层

**本质**：把"字段名"提升为"语义字段"（Field + Concept）。

**50+ 预定义 Semantic Type**（来自 `semantic_types.py`）：

```
时序：DATETIME / DATE / TIMESTAMP / YEAR / MONTH / WEEK
测量：AMOUNT / PRICE / QUANTITY / TEMPERATURE / PERCENTAGE
符号：PROFIT / PERCENTAGE_CHANGE / SENTIMENT / CORRELATION
离散：RANK / SCORE / BOOLEAN / STATUS / DIRECTION
地理：LATITUDE / LONGITUDE / COUNTRY / STATE / CITY / REGION
分类：CATEGORY / NAME / RANGE
```

**配套元数据**：`intrinsic_domain`（值域）、`unit`（单位）、`sort_order`（自然排序）。

**为什么这是创新**：传统 BI 的"字段"只是列名；这里的"Concept"是**带语义 + 上下文**的领域实体。这正是 Data Formulator 比 Tableau 智能、比 ChatGPT 可控的根源。

### 创新 2：Data Threads — 可回溯的对话式探索

**本质**：每次生成的图表 = `chart spec + 衍生数据 + 数据变换代码` 三元组，全部持久化。

```
Thread 1: line chart → country 排序
Thread 2:   └── top 5 CO2 国家  ← 用户点击 Thread 1，加新指令
Thread 3:      └── 改成 bar chart + 加 tooltip  ← 可回跑、可改指令
```

**4 个用户操作**：(a) rerun (b) follow up (c) revise (d) branch。

### 创新 3：Generative UI — 自带可调控件的图表 ⭐⭐⭐

每次生成图表，**LLM 同时返回 2-4 个"follow-up 控件"**：

```json
{
  "vlSpec": {...},
  "label": "dark theme",
  "configUI": [
    {"key": "opacity", "type": "continuous",
     "min": 0.2, "max": 1, "defaultValue": 0.9,
     "path": ["mark", "opacity"]},
    {"key": "grid", "type": "binary",
     "defaultValue": true, "path": ["encoding", "y", "axis", "grid"]},
    {"key": "scheme", "type": "discrete",
     "defaultValue": "tableau10",
     "path": ["encoding", "color", "scale", "scheme"]}
  ]
}
```

**神奇之处**：控件描述的是 **"spec 中的位置 + 类型 + 默认值"**，不是代码。应用层直接渲染。

**对比**：
- Tableau：固定控件
- ChatGPT：无控件
- Data Formulator：**每次新图表自带定制控件**

### 创新 4：Chart Intent Router — 意图路由

把图表编辑请求智能分流：

```
用户说："改一下颜色"        → STYLE agent（不改数据）
用户说："按 region 分组"    → DATA agent（要重算数据）
```

把"图表迭代"拆成"轻量操作"和"重量操作"，避免 LLM 把简单需求做得过重。

### 4.2 沙箱设计（最值得借鉴）⭐⭐⭐

Data Formulator **真正能上生产**，关键是 **Python Audit Hook**（Python 3.8+ 解释器层拦截）：

```python
# 拦截的"危险事件"
✅ Block: open(mode != "r")           # 禁止写文件
✅ Block: open(path 不在工作空间)     # 禁止越界读
✅ Block: subprocess / shutil / winreg
✅ Block: os.system / os.exec / os.fork
✅ Block: socket.connect / bind / sendto
✅ Block: ctypes.dlopen / dlsym       # 防绕过 audit hook
✅ Block: import subprocess / socket / requests
```

**两层防御**：Python 解释器层（audit hook）+ 可选 Docker 沙箱层。

## 五、Data Thread 回放算法 ⭐⭐⭐

### 5.1 节点数据结构

每个 derived table 在 workspace 里存一个 `Derivation` 对象：

```python
@dataclass
class Derivation:
    source_tables: list[str]   # 父表 ID 列表（依赖图边）
    description: str           # LLM 当时的人类语言解释
    code: str                  # 实际执行的 Python 代码
    created_at: datetime
```

### 5.2 回放算法的 5 步执行

```
Step 1 触发回放（auto-refresh / manual / cascade）
Step 2 依赖图遍历（前端 refreshDerivedTables）
       derivedTables = tables.filter(t => t.derive?.source?.includes(sourceTableId))
Step 3 构造签名请求（HMAC 契约）
       { input_tables, code, code_signature, output_variable, virtual, output_table_name }
Step 4 后端验证 + 沙箱执行（refresh_derived_data）
       5 重防御：input_tables/code/code_signature/MAX_CODE_SIZE/verify_code
Step 5 批量更新 store（一次性 dispatch）
```

### 5.3 HMAC 代码签名 — 最值得借鉴的安全设计

**问题**：LLM 生成的代码存在前端，用户可能篡改后重发。

**解决**：服务端每次生成代码都签名，前端重发必须带签名。

```python
def sign_code(code: str) -> str:
    return hmac.new(_get_secret(), code.encode("utf-8"), hashlib.sha256).hexdigest()

def verify_code(code: str, signature: str) -> bool:
    return hmac.compare_digest(sign_code(code), signature)
```

**Secret 的 3 层优先级**：
1. `DF_CODE_SIGNING_SECRET` 环境变量（多实例部署一致）
2. Dev 模式固定 key（--dev 启动，重载不破签）
3. Flask `app.secret_key` 派生（生产默认）

**对 AI Agent 团队的启示**：**任何让 LLM 生成可执行代码的系统，都必须有 HMAC 签名机制**。

### 5.4 3 层 Context 设计（多线程场景的"信息分层"）

```
Tier 1: PRIMARY TABLE(S) + OTHER AVAILABLE TABLES（数据上下文）
Tier 2: [FOCUSED THREAD] 步骤详情（当前关注线程）
Tier 3: [OTHER THREADS] 一行摘要（外围线程）
```

**这是一个"信息密度梯度"设计**：当前关注 = 完整上下文；其他线程 = 一行摘要；不相关 = 完全省略。

### 5.5 回放的 3 个关键性质

1. **回放 ≠ 重跑 LLM**：回放 = `sandbox.run_python_code()`，快、便宜、确定
2. **Code is the Source of Truth**：Python 代码（确定性）比自然语言（不确定性）真值
3. **级联性 vs 递归性**：当前是级联（直接子节点并行刷新），非递归

### 6.2 核心区分："探索器" vs "生成器" vs "查询器"

```
       可控性
       ▲
       │
Tableau ●
       │
       │     ● Data Formulator  ← 甜蜜区
       │
PowerBI ●
       │
       │
       │           ● Vibe Coding
       │           ● ChatGPT+Code
       │
       │   ● ChatBI
       │
       └────────────────────────────► 表达自由度
```

**DF 处于"高可控 + 高表达自由度"的甜蜜区** —— 这是它的护城河。

### 6.3 与每个对标产品的本质区别

- **vs Tableau**：DF 的"概念层"是 Tableau 没有的 —— Tableau 不知道 `temperature` 字段值域是 [-50, 50]°C
- **vs PowerBI**：PowerBI 的 DAX 是"另一门语言"，门槛高；DF 的 NL = "show me top 5 regions by revenue YoY"
- **vs ChatBI**：ChatBI 是查询工具（Q&A），DF 是探索工具（Exploration）
- **vs ChatGPT+Code**：ChatGPT 输出代码（用户读不懂），DF 输出可视化 + UI 控件（用户会点）
- **vs Vibe Coding**：Vibe Coding 是应用生成器，DF 是数据探索器；DF 有 Data Thread 和 Workflow Distill，Vibe Coding 没有

## 七、5 个方法论沉淀（核心）⭐⭐⭐

### 方法论 1：**概念层抽象（Concept Layer）** 🏆

**原理**：任何"字段"都不只是"列名"，而是"语义化的领域实体"。

**可复用模式**：
```
原始字段名              概念层
─────────────────────────────────
"amt"            →    "Amount [unit: CNY, domain: ≥0]"
"rate"           →    "Percentage [domain: [0,1]]"
"created_at"     →    "Timestamp [granularity: ms]"
"customer_name"  →    "Name [entity: Person, language: zh]"
```

### 方法论 2：**路由分发（Intent Routing）** 🏆

**原理**：不要让一个 agent 处理所有事。先分类，再分发。

```
用户指令 → Intent Router → [Agent A | Agent B | Agent C]
                          ↓
                  每个 agent 单一职责
```

### 方法论 3：**生成式 UI（Generative UI）** 🏆

**原理**：UI 不是 hardcode 的，而是每次 AI 输出时动态生成。

```
LLM 输出 = { content: spec, controls: [2-4 个可调控件] }
                                ↓
                        前端渲染控件
                                ↓
                        用户调节 → 直接写回 spec
```

### 方法论 4：**持久化上下文（Persistent Context）**

**原理**：不要让用户每次重新描述需求。

DF 的 Data Thread = `chart + 衍生数据 + 变换代码`，全部持久化。用户可以 rerun / revise / branch / continue。

### 方法论 5：**沙箱优先（Sandbox-First）**

**原理**：让 LLM 生成代码不可怕，可怕的是直接 exec()。

DF 的 Python audit hook + 可选 Docker 沙箱 + URL 白名单 + 文件路径限制 + 危险模块黑名单 —— **生产级 5 重防御**。

## 八、局限性与风险

### 8.1 模型兼容性门槛高 🔴

来自 Chenglong-MS（作者）2026-06-17 实测：

| 模型 | 成功率 | 质量 | 评价 |
|:---|:---:|:---:|:---|
| **gpt-5.5 / gpt-5-mini** | 100% | 89-91 | ceiling |
| qwen3.6:27b | 100% | 87 | 最佳开源 |
| gpt-oss:120b | 96% | 82-84 | 第二强 |
| qwen2.5:72b / coder:32b | 80% | 74-80 | 中等可用 |
| 7-14B 模型 | 失败 | - | "Unknown action" |

**结论**：本地部署至少需要 32B 模型 + 80GB GPU。

### 8.2 错误处理不友好 🔴

Issue #398：ChartInsightAgent 无条件发送 base64 PNG 给 LLM，非视觉模型直接失败，用户看到的错误是 `LLM_UNKNOWN_ERROR`。

### 8.3 Docker 构建复杂 🟠

Issue #371/#372：`canvas` 原生编译失败、Vite heap OOM。

### 8.4 不适合的场景

| 场景 | 是否适合 | 原因 |
|:---|:---:|:---|
| 实时数据流监控 | ❌ | 是探索工具，非 dashboard |
| 企业级权限管理 | ❌ | 没有 row-level security |
| 大数据集（> 100GB）| ⚠️ | DuckDB 支持，但需本地大内存 |
| 多用户协作 | ⚠️ | 主要是单人 |
| 移动端 | ❌ | 只支持桌面浏览器 |

## 九、对 AI PM / Agent 工作的启示

### 9.1 三个可立刻落地的借鉴

| 借鉴 | 应用场景 | 落地难度 |
|:---|:---|:---:|

### 9.2 Vibe Coding 趋势判断

```
Vibe Coding（通用）         →  生成完整应用
Vibe Visualization（DF）  →  生成数据图表     ← DF 的位置
Vibe Analysis（未来方向）  →  生成完整分析报告
```

**未来 12 个月演进**：
- 2026 H2：Data Thread 标准化（让其他 BI 工具接入）
- 2027 H1：知识蒸馏（Workflow Distill）成为标准
- 2027 H2：多模态数据融合（图像/视频/音频 + 结构化数据）
- 2028+  ："AI 数据分析师" 角色标准化

### 9.3 真正的机会

不是**重复造 DF 轮子**，而是 **"垂直领域的 DF 变体"**（金融 / 消金 / 营销）。

掌握这套范式，比做一个仿制品更有价值。
