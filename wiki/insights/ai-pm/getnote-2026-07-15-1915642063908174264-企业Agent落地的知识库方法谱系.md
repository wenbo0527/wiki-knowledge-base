## 十三、我们的知识库：从"文档仓库"到"认知基础设施"

### 13.1 起点：四个痛点，一个根因

2026年4月，文博的Agent小队启动Wiki知识底座建设时，面对的不是"要不要建知识库"的问题，而是"知识散在5个地方，每次决策都要切5个App"的日常痛苦：

**痛点一：信息分散，多源无法统一检索。** RSS情报（234源跨AI/金融/产品）、Get笔记（15个知识库互不联通）、飞书文档、本地文档、Obsidian Wiki——五个系统各自为政，决策时无法跨源联想。

**痛点二：重复决策，方法论不沉淀。** 6月8日派单4次口头承诺未落盘；7月1日到14日ETF估值18天失真（hardcoded预设）；Get笔记同步静默50天——同一类问题反复发生，每次都从零排查。

**痛点三：Agent协作无共享知识。** 17个Agent各有独立workspace，Agent间方法论不共享，派蒙调度时无法让Agent共享上下文。每个Agent都重复建设工具和方法论。

**痛点四：检索召回率不稳定。** 早期RAG命中率低于0.6，关键词检索和语义检索两极分化，长文档chunk切分不当（早期固定512字符）。

四个痛点看起来是四个问题。但踩完13个坑之后我们发现，根因只有一个：**系统在"假装成功"。**

ETF推送每天报告"✅ 成功"，但数据是18天前的。Get笔记同步脚本输出"✅ 同步完成"，但50天没有新笔记进来。launchd健康检查每天09:00跑，但44天只输出`Operation not permitted`，没人发现。13个INC中，11个的根因可以归结为同一句话——**"系统说成功了，但实际没成功"**。

这不是检索精度的问题，不是架构设计的问题，是反馈闭环的问题。你的知识库可能也坐在同样的火山口上——那些"✅ 成功"的日志背后，有多少是真正的成功？

### 13.3 技术选型：每个决策背后的理由

每个选型都遵循"列候选（≥3个）→ 评估维度 → 决策记录"三步法：


| 组件        | 选型                     | 核心理由                      | 放弃的方案                          |
| --------- | ---------------------- | ------------------------- | ------------------------------ |
| 文档存储      | Obsidian Markdown      | 本地.md · 双链 · Git友好 · AI友好 | Notion（封闭）/ Confluence（重）      |
| 向量库       | Chroma                 | 轻量 · 嵌入式 · 零部署 · 离线可用     | Milvus（过度工程）/ Pinecone（数据出海）   |
| Embedding | Ollama bge-m3          | 本地推理 · 多语言 · 离线           | OpenAI（API依赖+成本）/ Qwen（复杂度高）   |
| Agent框架   | OpenClaw v1.0.63       | 原生cron/heartbeat/5契约/派蒙集成 | LangChain（重）/ AutoGen（配置复杂）    |
| 通讯        | 飞书 lark-cli            | 消息实时 · 文档一体 · 生态完整        | 企微（接口限制）/ Slack（国内不便）          |
| 文档格式      | Markdown + Frontmatter | 纯文本 · 跨平台 · 元数据可被RAG过滤    | HTML/Word（不便编辑）/ Notion DB（耦合） |


**选型方法论**：不做选型记录的选型，6个月内14个重复（L-13治本）。每个INC的"修复方向"都列3方案A/B/C。

## 十四、用方法谱系审视我们的实践

把我们的实践放进综述篇和详细篇的框架里，能看到什么？

### 14.1 范式定位：我们在哪个象限

**当前定位：RAG为主，LLM Wiki元素初现。**


| 范式特征           | 我们的实践                                               | 匹配度 |
| -------------- | --------------------------------------------------- | --- |
| RAG：查询时检索      | ✅ 核心检索方式。向量+BM25+RRF融合，MRR@10=1.0                   | 高   |
| RAG：实时性        | ✅ Wiki写完即索引（RAG自动ingest），文档变更即时生效                   | 高   |
| RAG：溯源能力       | ✅ 每个chunk带来源文档ID、元数据、标签                             | 高   |
| LLM Wiki：摄入时编译 | ⚠️ 部分实现。Get笔记同步到Wiki时做了结构化沉淀（加标签、归入主题目录），但不是LLM自主编译 | 低   |
| LLM Wiki：知识复利  | ⚠️ 通过INC/Lesson机制实现了"经验回写"，但不是自动编译                  | 中   |
| LLM Wiki：矛盾显式化 | ❌ 未实现。不同来源的矛盾信息没有显式标注                               | 无   |
| 融合架构：人机分离      | ⚠️ Wiki层人可编辑（不是LLM独占），RAG层人主导                       | 部分  |


**核心判断**：我们的知识库本质上是一个**RAG系统，叠加了手动版的"经验回写"机制**。INC/Lesson解决了"经验往哪写"的问题，但没解决"谁来编译"的问题——人写的是记录，LLM编译的才是知识。这两步之间，差的是自动化。

### 14.2 对标综述篇的决策树

按综述篇的决策树走一遍：

```
我们的知识是否涉及私有数据？ → 是
知识变更频率如何？ → 高频（RSS每天/ETF每天/Wiki持续更新）
答案是否需要溯源到原文？ → 是（INC/Lesson必须可溯源）
→ 推荐范式：RAG为主 ✅ 吻合
```

但有一个分支值得注意：

```
是否需要跨文档综合推理？ → 是（Agent协作需要跨主题关联）
→ LLM Wiki有价值 ✅ 但尚未落地
```

**结论**：当前RAG为主的选型是正确的——我们的知识高频变更、需要溯源、17个Agent需要实时检索。但跨文档综合推理的需求真实存在（Agent协作时需要理解多个主题之间的关联），这是LLM Wiki可以补充的。

### 14.3 对标详细篇：RAG技术方案的完成度

用详细篇第七章的RAG技术方案逐项对照，完成度参差不齐：

**已落地**：四层架构基本吻合（三层知识源+RAG层+Agent层）、混合检索（向量+BM25+RRF融合）、语义访问中台（Get笔记不迁移原数据，只建索引层）。

**关键差距**：


| 缺失组件    | 对标详细篇  | 影响                                            |
| ------- | ------ | --------------------------------------------- |
| 多模态入库   | §7.2.2 | 232个PDF/Excel不可检索，2,500+文件散落                  |
| Query改写 | §7.2.3 | 口语化问题直接查原始query，召回率受限                         |
| 知识分层存储  | §7.2.6 | 单层Chroma向量库，缺图数据库做确定性关系查询                     |
| 完整评估体系  | §7.2.9 | 只有MRR@10=1.0，缺Recall/Precision/Faithfulness三层 |


**完成度判断**：基础架构和混合检索已落地，但多模态入库、Query改写、知识分层存储、完整评估体系四个关键组件缺失。这些不是"锦上添花"，而是RAG从"能用"到"好用"的必经之路。

### 14.4 对标详细篇：Agent集成的完成度

Agent集成是实践最扎实的部分——17个Agent的协作架构、5契约机制、派蒙调度、INC/Lesson沉淀，已经跑通。

**关键差距**：隐式反馈采集。详细篇第九章说"80%的优化信号在隐式反馈里"，我们只做了显式反馈（INC/Lesson），没有从Agent的日常行为中挖掘优化信号。这也是"静默失败"能持续那么久的原因——系统不会主动告诉你它失败了，你必须主动去问。

## 十五、踩过的坑与沉淀的教训

1年多，13个INC（事件），25个Lesson（教训）。按类型梳理，每一条都对应详细篇中的一个理论问题。

### 15.1 "反思≠实证"：最深刻的教训

**INC-2026-07-14-001：ETF估值18天失真。**

6月25日写死了8只ETF的分位数据。18天里，每天推送"✅ 推送成功"，但推送的是6月25日的旧数据。半导体真实分位29.4%，预设82.1%——差异52.7个百分点，"减仓"信号变成了"加仓"信号。

**根因**：fetcher失败时静默fallback到预设数据。系统报告"成功"，但数据是假的。

**这对应详细篇的哪个理论问题？** → 第七章7.3.2"忠实度是最危险的指标"：模型忠实复述了检索到的错误信息，这是最危险也最难被发现的失败模式。我们的实践给出了一个更极端的版本：**不是LLM复述了错误信息，而是整个系统在"成功"的假象下持续输出错误数据。**

**教训沉淀**：

- L-28：多源兜底必须raise，不能静默fallback
- L-29：自检必须区分"输出成功"和"输入真实"（exit 0 ≠ 数据真实）

### 15.2 "路径错位=等于没写"：知识库的索引问题

**INC-2026-07-14-003：7天review-log真空。**

INC和Lesson写在`/05_AgentOutput/`而不是`review-logs/`——路径错位导致Wiki索引不到，等于没写。

**这对应详细篇的哪个理论问题？** → 第七章7.2.8"数据治理"和第九章9.2"知识更新"：知识写入了但索引不到，和没写没有区别。增量更新的前提是文档有正确的元数据和路径。

**教训沉淀**：

- L-31：INC/Lesson必须立即归档到review-logs子目录（写错路径=等于没写）

### 15.3 "同步静默"：最隐蔽的失败模式

**INC-2026-07-14-004：Get笔记同步静默50天。**

同步脚本hardcode了5条笔记ID（不拉新），try/except吞掉了AttributeError，输出"✅ 同步完成"——50天没有新笔记同步，但系统报告一切正常。

**这对应详细篇的哪个理论问题？** → 第九章9.3"Agent反馈回写"中的"隐式反馈"问题：80%的优化信号在隐式反馈里，但大多数团队只做了显式反馈。我们的同步脚本连显式反馈都没做好——它吞掉了错误信号，让"静默失败"成为可能。

**教训沉淀**：

- L-32：同步脚本3必检——不hardcode / 不swallow / 必对账

### 15.4 "cron 25个fail-closed"：Agent调度的系统性风险

**INC-2026-07-15-001：OpenClaw cron 25个全部fail-closed。**

25个定时任务全部投递失败（16个投递配置错误 + 5个脚本不存在 + 1个退出码判定过严 + 4个过期任务未清理）。凌晨假设的根因（"Target=main vs isolated"）被验证后推翻——真实根因是三层叠加。

**这对应详细篇的哪个理论问题？** → 第九章9.3"单Agent vs 多Agent"：17个Agent的调度复杂性已经超出了单点配置能管理的范围。编排价值公式在这里的体现是：**当调度成本（25个cron的配置维护）超过了领域隔离收益（17个Agent各自独立），说明调度层本身需要重新设计。**

**教训沉淀**：

- L-34：cron argv必须随scripts改造同步
- L-35：cron投递必须显式指定channel=feishu + to=user:ou_xxx
- L-36：推送脚本退出码=0当主通道lark-cli成功

### 15.5 教训模式总结


| 模式         | 出现次数 | 对应理论问题    | 核心教训          |
| ---------- | ---- | --------- | ------------- |
| 静默失败       | 4次   | 忠实度/隐式反馈  | 系统报告"成功"≠数据真实 |
| 路径错位       | 3次   | 数据治理/索引   | 写错位置=等于没写     |
| 配置漂移       | 3次   | 知识更新/增量同步 | 脚本改了配置没同步     |
| Hardcode陷阱 | 2次   | 数据治理      | 预设数据会过期       |
| 根因误判       | 1次   | 效果评估      | 凌晨假设≠验证结论     |


**核心洞察**：13个INC中，11个的根因可以归结为同一句话——**"系统说成功了，但实际没成功"**。这不是技术问题，是反馈闭环的问题。详细篇说"80%的优化信号在隐式反馈里"，我们的实践验证了这一点：显式的"✅ 成功"是靠不住的，必须从系统行为中挖掘真实状态。

### 16.3 LLM Wiki在我们场景中的可行性判断

按综述篇的决策树，LLM Wiki适合我们的哪些场景？


| 场景               | 变更频率 | 需要溯源？ | 需要跨文档综合？ | 推荐范式           |
| ---------------- | ---- | ----- | -------- | -------------- |
| Agent方法论沉淀       | 低频   | 否     | 是        | **LLM Wiki** ✅ |
| 技术知识体系（AI/架构/产品） | 低频   | 否     | 是        | **LLM Wiki** ✅ |
| RSS情报            | 高频   | 是     | 否        | RAG            |
| ETF/投资数据         | 高频   | 是     | 否        | RAG            |
| INC/Lesson       | 中频   | 是     | 否        | RAG            |


**判断**：LLM Wiki最适合沉淀Agent方法论和技术知识体系——这两块知识稳定、需要跨文档综合、不涉及合规溯源。当前这两块内容在Wiki的`methodologies/`和`insights/`目录下，但维护靠人工，LLM编译可以大幅降低维护成本。

**但有一个前提**：LLM Wiki的Wiki层必须LLM独占，人只做审阅。当前我们的Wiki层人可以自由编辑——如果要引入LLM Wiki，需要划定"LLM编译区"和"人编辑区"的边界，避免人机混写导致一致性问题（详细篇失败模式第17条）。

### 16.4 诊断器项目的知识库需求

文博的Agent小队诊断器（萃取虾→诊断虾→Demo虾→结构化虾→Roadmap虾→校准虾）对知识库有特殊需求：


| 诊断器阶段          | 知识库需求      | 推荐范式                        |
| -------------- | ---------- | --------------------------- |
| 萃取虾（需求追问）      | 历史案例库+行业知识 | RAG（实时检索案例）                 |
| 诊断虾（五维打分）      | 评估标准+行业基准  | RAG（精确匹配标准）+ LLM Wiki（综合判断） |
| Demo虾（代码生成）    | 技术文档+模板    | RAG（检索模板）                   |
| 结构化虾（能力定义）     | 能力模型+案例    | LLM Wiki（跨案例综合）             |
| Roadmap虾（路线规划） | 行业趋势+落地路径  | LLM Wiki（综合推理）              |
| 校准虾（质量校验）      | 评估标准+历史反馈  | RAG（精确匹配）                   |


**判断**：诊断器是一个典型的"混合场景"——萃取和诊断阶段需要RAG的实时检索和溯源能力，结构化和Roadmap阶段需要LLM Wiki的跨文档综合能力。这验证了综述篇的融合架构判断：**不是二选一，而是分层。**

## 十七、给同路人的三个建议

### 建议一：先跑通反馈闭环，再追求检索精度

这是全篇最想说的。

我们的13个INC中，11个的根因是"系统说成功了，但实际没成功"。检索精度、向量模型、chunk策略——这些当然重要，但它们解决的是"找到了对不对"的问题。而"系统在假装成功"解决的是"找没找到"的问题。前者是精度问题，后者是闭环问题。闭环断了，精度再高也是空中楼阁。

落地方法：给每个关键链路加"对账机制"——不是检查"输出成功"，而是检查"输入真实"。ETF推送不能只看"推送成功"，要看"数据是不是今天的"；同步脚本不能只看"同步完成"，要看"笔记数有没有变化"。

**判断标准**：如果你无法区分"系统真的成功了"和"系统假装成功了"，你的反馈闭环就是断的。

### 建议二：INC/Lesson机制比任何技术选型都重要

5契约（输入/边界/输出/失败处理/经验回写）是我们踩了13个坑后沉淀出来的最小可行治理机制。它不是理论框架，是血泪教训。

每个INC包含：问题描述、根因分析、解决方案、教训沉淀。每个Lesson是一条可执行的规则（如"不hardcode""不swallow""必对账"）。

这个机制对应详细篇第九章的"Agent反馈回写"——但我们不是从Agent的视角做的，而是从"组织知识管理"的视角做的。效果一样：**让错误不白犯，让经验可复用。**

### 建议三：别急着上LLM Wiki，先用RAG把反馈闭环跑通

Karpathy说"Compile, don't retrieve"，很多团队听了就想把RAG换成LLM Wiki。但我们的实践表明：**如果你连RAG的反馈闭环都没跑通，LLM Wiki只会让问题更隐蔽。**

RAG的"静默失败"至少还有日志可查——推送记录、检索命中率、chunk覆盖度。LLM Wiki的编译是LLM自主完成的，如果编译出了错，你连"哪里错了"都看不到。编译错误的Wiki页面看起来和正确的没有区别，但结论可能是错的。

正确顺序：先用RAG把知识库的反馈闭环跑通（对账机制+INC/Lesson+效果评估），确认你的系统能区分"真成功"和"假成功"，再考虑引入LLM Wiki做知识编译。
