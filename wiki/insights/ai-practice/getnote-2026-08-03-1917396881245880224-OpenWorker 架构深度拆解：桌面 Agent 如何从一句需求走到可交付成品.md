### 🏗️ OpenWorker 整体架构分几层？

按源码职责可拆为**四层运行架构**，官方原描述为三层部署关系。

| 层级 | 核心职责 | 关键技术/模块 |
| :--- | :--- | :--- |
| 交互层 | 桌面界面与用户交互 | React + Tauri |
| Agent 运行层 | 任务循环与工具编排 | cowork.py / agent.py / engine.py |
| 控制层 | 风险分类、权限与审计 | risk.py / permissions.py / inbox.py / audit.py |
| 资源与执行层 | 真实工作环境执行 | tools / connectors / aisuite / LocalExecutor |
- **六条运行线**：任务线 + 模型线 + 工具线 + 权限线 + 状态线 + 交付线
- **数据流向**：请求向下变成动作 → 进度、审批、记录、交付物向上回到桌面

### 🔄 一次任务怎样走完整个执行闭环？

从目标到交付物共经历**六个阶段**，每一步都有运行时控制。
- **第一步：目标下发**：桌面端建立会话与工作区 → 交给本地 Python Agent 服务
  - 桌面端 = 界面层（Surface），Python 服务 = 运行时，底层引擎可复用给多入口
- **第二步：建立可见进度**：Agent 先用 `todo_write` 拆步骤，始终只有 1 个 `in_progress`
  - 解决桌面 Agent 「长时间无反馈」的常见问题
- **第三步：模型提议 + 工具执行**：模型只输出工具调用建议，Engine 统一调度执行
  - 自带**二十多种连接器**，支持 MCP 协议
  - 执行策略：低风险读取**并行**，有副作用的写入/命令**串行**
- **第四步：风险分类与权限判定**：所有动作先过 Permission Engine
  - 四类风险等级：
    - `READ`：读文件/搜索/查询 → 无副作用，直接执行
    - `WRITE_LOCAL`：写文件/改内容 → 受允许目录约束
    - `EXEC`：运行命令 → 检查命令内容与允许规则
    - `EXTERNAL`：发消息/改日历 → 需明确授权
  - 五种工作模式：
    - Discuss / Plan → 拒绝有后果的动作
    - Interactive（默认）→ 允许读取，写入/命令/外部操作需确认
    - Custom → 按配置放行指定工具
    - Auto → 直接放行有副作用动作，但写入仍受目录约束
  - 命令检查会处理 `;`、`&&`、管道、重定向、命令替换等 shell 操作符
- **第五步：前台审批 + 后台 Inbox**：人工介入统一走一套机制
  - 前台：审批卡片直接出现在当前会话
  - 后台：任务暂停在 Inbox，等人处理后继续
  - Inbox = 跨会话的人类注意力队列，不是单纯通知列表
- **第六步：交付物 + 审计记录**：一次完成对应三份状态
  - **Progress**：任务走到哪了
  - **Artifacts**：交付物在哪（用 `artifact:` 链接交付）
  - **Audit**：执行过什么、谁批准的（敏感字段脱敏）

### 🔌 模型可以随便换吗？

模型可替换，但**运行时合同保持稳定**，不随模型更换而改变。
- **支持模型**：OpenAI、Anthropic、Gemini、GLM、DeepSeek、Kimi、Qwen、MiniMax，也可通过 Ollama 本地运行
- **适配层**：基于 `aisuite` 构建统一接口，复用工具、Toolkit、MCP 能力
- **模型不直接绑定**文件系统和外部服务，只看到工具定义、输出调用建议
- **六份不变的运行时合同**：
  - 工具参数与返回值
  - 风险分类和权限策略
  - 工作区和可写目录
  - 进度状态
  - 审批与 Inbox
  - 交付物链接和审计记录

### 🧩 Skills 是干什么的？

Skills 负责**任务方法**，不自动扩大工具权限。
- 组织形式：`SKILL.md` = YAML 元数据 + Markdown 指令 + 可选资源
- 加载方式：渐进式加载 → 会话开始只放名称描述，需要时才用 `load_skill` 加载完整内容
- 权限边界：即使 Skill 写了「发 Slack」，发送动作仍要经过连接器配置、风险分类和审批
  说白了，Skill 只是教方法，不是给通行证，能不能干还得运行时说了算。

### ⚠️ 有哪些必须知道的边界？

三个边界要分开看，**不能混为一谈**。

| 边界类型 | 解决什么问题 | 当前状态 |
| :--- | :--- | :--- |
| local-first | 状态优先放哪 | 会话/密钥/循环在本机，云模型和连接器仍可能出网 |
| 审批 | 谁同意哪次动作 | 授权点不能代替隔离、幂等和结果核对 |
| Executor | 动作在哪执行 | 当前只有 LocalExecutor，容器/VM 执行器是预留接口 |
- **LocalExecutor 特点**：维持持久 shell，`cd`、环境变量、虚拟环境可跨命令保留
- **重要结论**：当前版本**不能直接按「已有沙箱」理解**，审批 ≠ 命令安全

### 🆚 和腾讯 WorkBuddy 有什么不一样？

目标相似，都是「从一句指令到可验证交付物」，但**架构路线不同**。

| 维度 | 腾讯 WorkBuddy | OpenWorker |
| :--- | :--- | :--- |
| 产品形态 | 腾讯云企业级产品 | MIT 许可开源桌面应用 |
| 模型账号 | 平台提供模型与服务 | 用户自带模型/密钥，支持 Ollama |
| 工具接入 | 腾讯生态与平台能力 | 本地文件/终端/连接器/MCP |
| 运行基础 | Agent Runtime + 安全沙箱 | 本地 Python 服务 + LocalExecutor |
| 观察重点 | 企业级工作台与托管运行 | 桌面 Agent 的模块、协议与源码 |

### 🎯 适合先试哪四类任务？

从**低风险场景**切入，逐步验证架构能力。
- **工作类**：读取会议纪要/数据表 → 生成简报 → 检验文件读取、进度、交付物
- **生活类**：整理零散行程 → 生成计划 → 检验「生成文件」与「改日历」的风险差异
- **架构类**：汇总 ADR/接口/事故记录 → 输出评审草稿 → 检验 Skill 复用能力
- **研发类**：读取仓库/Issue/测试 → 生成发布风险清单 → 最完整的全链路验证

### 💡 第一次用怎么写任务说明？

按「目标 + 输入 + 权限 + 禁止 + 交付 + 例外」模板写，**边界越清楚越稳**。
```
目标：根据本目录资料生成本周项目简报
输入：只使用 ./meeting-notes 和 ./metrics
允许访问：可读上述目录，可写 ./output
不要做：不发邮件、不改日历、不读其他目录
交付物：./output/项目周报.html
完成条件：含进展/风险/下周计划/来源清单，可直接打开
遇到以下情况先问我：资料矛盾、需运行命令、需访问外部系统
```
