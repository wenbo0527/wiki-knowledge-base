# 产品文档走查与项目代码走查机制

> 保障产品文档质量和项目代码质量的标准化流程
> 
> **定位**: Wiki健康走查机制的子流程
> **维护者**: 尼克·弗瑞（文档） + 托尼·斯塔克（产品）/ 钟离（代码）

---

## 一、机制概述

### 1.1 目标

| 机制 | 目标 |
|------|------|
| **产品文档走查** | 保障产品文档的完整性、一致性、可操作性 |
| **项目代码走查** | 保障代码质量、安全性、可维护性 |

### 1.2 核心原则

#### 产品文档原则

1. **MECE文档结构**: 相互独立、完全穷尽
2. **可追溯**: 从需求到实现到文档
3. **活文档**: 文档与代码同步更新
4. **用户导向**: 站在读者角度写作

#### 项目代码原则（基于Karpathy Coding Guidelines）

1. **Think Before Coding**: 明确假设，呈现权衡
2. **Simplicity First**: 最少代码解决问题
3. **Surgical Changes**: 精准修改，只改必要的
4. **Goal-Driven Execution**: 目标驱动，可验证成功

## 二、产品文档走查机制

### 2.1 文档类型定义

| 类型 | 说明 | 示例 |
|------|------|------|
| **PRD** | 产品需求文档 | 产品功能详细说明 |
| **Spec** | 规格说明书 | 业务规则、边界条件 |
| **API文档** | 接口定义 | 接口参数、返回值 |
| **用户手册** | 使用指南 | 操作步骤、FAQ |
| **决策记录** | ADR | 技术决策、业务决策 |

### 2.2 走查检查清单

#### PRD走查清单

```
□ 文档信息
  □ 文档版本号正确
  □ 作者和日期准确
  □ 关联的Epic/Issue编号

□ 需求完整性
  □ 背景和目标清晰
  □ 用户故事完整（角色-场景-价值）
  □ 功能需求描述清晰
  □ 非功能需求明确（性能/安全/可用性）

□ 逻辑一致性
  □ 业务流程图存在且准确
  □ 状态机/决策树完整
  □ 边界条件已识别

□ 可操作性
  □ 验收标准明确
  □ 测试用例可执行
  □ 依赖关系清晰

□ MECE检查
  □ 无遗漏的需求场景
  □ 无重复的章节或内容
  □ 章节之间无矛盾
```

#### Spec走查清单

```
□ 规格完整性
  □ 业务规则完整
  □ 边界条件覆盖
  □ 异常处理说明

□ 一致性检查
  □ 与PRD一致
  □ 与API文档一致
  □ 与数据库设计一致

□ 可验证性
  □ 每个规则有对应测试
  □ 验证方法明确
```

## 三、项目代码走查机制

### 3.1 代码走查分层模型

基于Wiki中AI代码审查框架：

```
┌─────────────────────────────────────────────────────────────┐
│              Human Review（人类终审）                          │
│   - 架构决策      - 安全关键      - 业务逻辑                   │
├─────────────────────────────────────────────────────────────┤
│              AI Deep Review（AI深度审查）                      │
│   - 逻辑正确性    - 边界条件      - 性能分析                   │
├─────────────────────────────────────────────────────────────┤
│              AI Quick Review（AI快速审查）                    │
│   - 代码风格      - 命名规范      - 简单bug                   │
└─────────────────────────────────────────────────────────────┘
```

### 3.2 代码走查检查清单

#### AI快速审查（自动化）

```
□ 静态分析通过
  □ ESLint / TSLint 无error
  □ 类型检查通过
  
□ 测试覆盖达标
  □ 覆盖率 > 80%
  □ 关键路径覆盖
  
□ 安全扫描通过
  □ 无硬编码凭证
  □ 依赖无高危漏洞
```

#### AI深度审查（Claude Code）

```
□ 功能正确性
  □ 实现与Spec一致
  □ 边界条件处理
  □ 错误处理适当

□ 性能检查
  □ 无N+1查询
  □ 适当缓存
  □ 索引考虑

□ 安全审查
  □ 输入验证存在
  □ SQL/注入防护
  □ 敏感数据保护
```

#### 人类终审

```
□ 架构合规
  □ 分层架构遵守
  □ 依赖方向正确
  □ 无循环依赖

□ 业务逻辑
  □ 核心流程正确
  □ 异常场景处理
  □ 日志充分

□ 可维护性
  □ 代码可读
  □ 文档更新
  □ 测试完整
```

### 3.3 代码走查流程

```
┌─────────────────────────────────────────────────────────────┐
│                    代码走查流程                                │

│                                                              │

│     ▼                                                       │
│  4. AI深度审查（Claude Code）                                 │
│     │  □ 逻辑正确性                                         │

│     │  □ 性能分析                                          │
```

### 3.4 走查角色定义

| 角色 | 职责 | 触发条件 |
|------|------|----------|
| **AI-Pair (Quick)** | 风格、命名、简单bug | PR创建自动触发 |
| **Claude Code (Deep)** | 逻辑、性能、安全 | PR规模>100行 |
| **钟离** | 架构、技术决策 | 涉及核心模块 |
| **托尼·斯塔克** | 业务逻辑、产品一致性 | 功能变更 |

## 四、问题分级与处理

### 4.1 问题分级

| 级别 | 标识 | 说明 | 处理时限 |
|------|------|------|----------|
| **P0** | 🔴 | 阻塞性问题（安全漏洞、数据丢失风险） | 立即修复 |
| **P1** | 🟠 | 重要问题（功能缺失、严重性能问题） | 24小时内 |
| **P2** | 🟡 | 一般问题（代码风格、可维护性） | 计划内修复 |
| **P3** | 🟢 | 优化建议 | 后续迭代 |

### 4.2 问题处理流程

```
发现问题
    │
    ▼
判断级别
    │
    ├─ P0 → 立即修复，PRBlocker
    │
    ├─ P1 → 当天修复，进入审查重点
    │
    ├─ P2 → 计划修复，标记为tech debt
    │
    └─ P3 → 记录，后续处理
```

## 七、复杂项目走查原则

### 7.1 核心框架（Karpathy四大原则）

| 原则 | 说明 | 走查检查点 |
|------|------|-------------|
| **Think Before Coding** | 明确假设，呈现权衡 | 代码变更前是否明确了假设？是否有更简单的方案？ |
| **Simplicity First** | 最少代码解决问题 | 是否添加了不必要的功能？是否有200行可以变成50行的？ |
| **Surgical Changes** | 精准修改，只改必要的 | 是否"顺便改进"了无关代码？是否匹配了现有风格？ |
| **Goal-Driven Execution** | 目标驱动，可验证 | 是否有可验证的成功标准？每步是否有检查点？ |

### 7.2 复杂项目特殊检查

| 检查项 | 说明 | 通过标准 |
|--------|------|----------|
| **依赖方向** | 只能外层依赖内层 | 禁止反向依赖 |
| **循环依赖** | 模块之间无循环 | A→B→C→A 必须消除 |
| **接口稳定性** | 核心接口变更 | 必须向后兼容或有迁移方案 |
| **数据迁移** | 数据库变更 | 必须有迁移脚本和回滚方案 |
| **回滚方案** | 变更失败时 | 回滚步骤必须明确且可执行 |

### 7.3 反模式警示（Simon Willison Anti-patterns）

| ❌ 禁止项 | ✅ 正确做法 |
|---------|-----------|
| 提交未审查的代码 | 先自审，确保代码能工作 |
| 过大PR（数千行） | 拆分成多个小PR（<500行） |
| PR无上下文说明 | 说明变更目的，关联Issue |
| 让审查者猜意图 | 提供测试记录、截图等证据 |

### 7.4 活文档原则

| 检查项 | 标准 |
|--------|------|
| **文档与代码同步** | 代码变更后24小时内更新文档 |
| **文档可验证** | 验收标准明确，可直接对照检查 |
| **知识沉淀** | 踩坑记录→Wiki，形成组织资产 |
