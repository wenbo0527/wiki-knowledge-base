## 第1章：现状诊断——为什么需要 LangGraph 接管编排

### 1.1 PM 是人肉编排引擎——三重角色冲突

当前 v1.7.2.1 的实际编排者不是 LangGraph，不是 OpenClaw Gateway，而是 **PM 自己**。PM 同时承担三个角色：

1. **编排者**：派单、盯进度、1h cron 提醒、双向 grep 校验
2. **执行者**：PM 自接活 fallback、5 单 P0 漏 update、doc 文档 PM 自写
3. **质量检查者**：5min 自评 checklist、5 维评估标准、综合评分 A/B/C/D/F

这三重角色冲突导致 PM 成为系统最大瓶颈——任务板 31 单 in_progress，PM 自己就是过载点。

### 1.2 四组数据实证

v1.7.2.1 的 10h14m 实战数据揭示了四个架构矛盾：


| 数据                 | 数值                          | 工程缺口                                  |
| ------------------ | --------------------------- | ------------------------------------- |
| PM 任务板 in_progress | 31 单（P0 8 + P1 14 + P2 9）   | 无自动派单机制，PM 手动分配是唯一入口                  |
| PM 派单 vs 接活速度差     | 5min vs 4h4min = 20 倍       | 无超时自动重试，PM 手动 cron 是唯一兜底              |
| 任务板 status vs 交付脱钩 | 12 单脱钩 = 100%               | 无 checkpoint 状态快照，SQLite status 字段不可信 |
| 4 Agent 失联时长       | arch 4d / dev 13h / doc 13d | 无心跳检测 + 故障转移，Agent 失联无人知道             |


PM 还出现了 2 次"假性自循环"（4h46m + 3h31m 空白期）——编排者空白期等于系统停摆。

### 1.3 5 件套是质量门雏形，但靠人肉

v1.7.2.1 的 5 件套是 Harness 质量门的雏形，但全部依赖 PM 手动执行：


| 5 件套            | 对应 Harness 层 | 当前实现               | 目标实现                        |
| --------------- | ------------ | ------------------ | --------------------------- |
| 派单 4 件套硬约束      | L02 准入层      | PM 手动写 description | LangGraph 条件边质量门            |
| 双向 grep 校验      | L04 运行时层     | PM 手动跑脚本           | checkpoint 自动校验             |
| PM 自评 checklist | L05 交互层      | PM 5min 手动         | LangGraph interrupt + 质量门节点 |
| PM 自身治理         | L03 编排层      | PM 手动 update       | LangGraph 自动状态流转            |
| 投递验证            | L04 运行时层     | PM 手动 grep 网关日志    | OpenClaw Hook 自动验证          |


更值得注意的是：v1.7.2.1 的 5 维评估标准已经具备了 Anthropic 评测方法论的核心概念——


| v1.7.2.1 评估维度 | Anthropic 术语     | 当前实现       | 目标实现            |
| ------------- | ---------------- | ---------- | --------------- |
| 派单 4 件套完成率    | Task（测试用例）       | PM 手动统计    | 自动化 Task 定义     |
| 双向 grep 脱钩率   | Grader（评分器）      | PM 手动 grep | 自动化 Grader      |
| PM 自评全过率      | Trial（试验）        | PM 5min 手动 | 自动化 Trial 执行    |
| PM 漏 update 数 | Transcript（执行轨迹） | PM 手动 grep | checkpoint 自动记录 |
| 投递成功率         | Outcome（最终结果）    | PM 手动 grep | 自动化 Outcome 记录  |


5 维评估是"人肉评测"到"自动化评测"的过渡态——框架有了，执行还靠人。

### 1.4 三个架构矛盾

从数据中提炼出三个结构性矛盾：

**矛盾 1：双重编排冲突**。OpenClaw Gateway 自带 Agent Loop + 消息路由 + 子 Agent 调度，LangGraph StateGraph 也自带节点 + 边 + 条件路由 + checkpoint。两层编排叠加，导致状态管理分裂（MEMORY.md vs State）、任务追踪分裂（SQLite vs checkpoint vs TaskFlow）、错误恢复分裂（Hook vs interrupt）。本质是控制权争夺——谁才是任务流程的真正编排者？

**矛盾 2：SQLite 定位模糊**。task_tool.py 当前是"外挂"的，角色不清晰：如果只是 CRUD，checkpoint 已经能做状态持久化，SQLite 冗余；如果是状态引擎，和 LangGraph StateGraph 功能重叠；如果是依赖解析，这个能力应该属于编排层。SQLite 需要明确职责边界。

**矛盾 3：Spec Coding 断层**。OpenClaw 有 7 个 Bootstrap Files 做 Spec（AGENTS.md / SOUL.md / TOOLS.md 等），但 LangGraph 的编排逻辑没有对应 Spec——State 定义是代码级的 TypedDict，条件边是 Python 函数，不是声明式 YAML。Spec 只覆盖了 Agent 层，没有覆盖编排层。

### 1.5 OpenClaw Lobster 为什么不够

排除 Lobster 继续做编排的 4 条理由：

1. **状态持久化弱**——MEMORY.md 是纯文本，不支持 checkpoint 式的状态快照、版本链、时间戳索引。v1.7.2.1 的 12 单 status 脱钩 100% 就是状态持久化弱的直接后果
2. **条件路由能力有限**——workflow.yaml 支持条件分支但嵌套深度有限，诊断器的 7 Agent 协作 + 质量门 + 回退重试需要更复杂的条件路由
3. **人机协同不原生**——Barrier 确认机制是自定义实现，不如 LangGraph 的 interrupt 标准化。v1.7.2.1 的文博拍板是人工触发，不是 interrupt 式的暂停 + 恢复
4. **OpenClaw 处于修复爬坡期**——P0 级启动崩溃、SubAgent 静默丢消息、Gateway 内存泄漏频发，把编排权交给还在修基础问题的框架风险太高

### 1.6 结论：三层分工


| 层       | 组件                   | 职责                                          |
| ------- | -------------------- | ------------------------------------------- |
| **编排层** | LangGraph StateGraph | 节点编排、条件路由、checkpoint 持久化、interrupt 人机协同、质量门 |
| **执行层** | OpenClaw Agent       | Agent 执行、Skill 加载、工具调用、记忆管理、沙箱隔离            |
| **查询层** | SQLite Task Tool     | 任务 CRUD、跨工作流查询、依赖 DAG、历史统计                  |


PM 从编排者退位为 interrupt 节点——日常编排由 LangGraph 自动执行，只在关键决策点介入拍板。

## 第2章：架构对接——LangGraph StateGraph × OpenClaw Agent

### 2.1 三层架构总览

第 1 章诊断了为什么做，本章讲怎么做。编排权只有一个主人。LangGraph 做编排，OpenClaw 做执行，SQLite 做查询。

**调用链路**：LangGraph 节点 → MCP/ACP → OpenClaw Agent → 节点函数末尾 → SQLite Task Tool。三层按顺序调用，LangGraph 不直接调 SQLite。

### 2.2 六个对接点

LangGraph 和 OpenClaw 不是"并行运行"，而是"分层调用"。以下是 6 个核心对接点：


| LangGraph 层       | OpenClaw 层                | 对接方式                                                  | 实现路径                                                  |
| ----------------- | ------------------------- | ----------------------------------------------------- | ----------------------------------------------------- |
| **StateGraph 节点** | OpenClaw Agent            | 节点函数通过 OpenClaw CLI/API 调用 Agent                      | 短期：`openclaw agent run <agent_name>`；中期：MCP tool_call |
| **State 字段**      | Agent 间 JSON Schema 交接    | LangGraph State 的 TypedDict 字段对应 Agent 交接 JSON Schema | State 字段名 = JSON Schema 的 key                         |
| **条件边质量门**        | OpenClaw 准入层（config.yaml） | 质量标准从 OpenClaw Spec 提取，嵌入 LangGraph 条件边函数             | 从 AGENTS.md / SOUL.md 提取硬约束 → 写入条件边逻辑                 |
| **interrupt**     | Barrier 确认机制              | LangGraph interrupt 替代 OpenClaw 的 Barrier 确认          | interrupt 暂停 → 人工审批 → Command 恢复                      |
| **checkpoint**    | MEMORY.md + SQLite        | checkpoint 做状态持久化，SQLite 做查询辅助                        | checkpoint 自动保存 → 节点末尾同步写 SQLite                      |
| **Subgraph**      | OpenClaw SubAgent         | LangGraph 子图对应 OpenClaw 的 SubAgent 调用                 | 子图编译 → SubAgent sessions_spawn                        |


### 2.3 OpenClaw Gateway 降级职责清单

Gateway 从"编排 + 执行"降级为"纯执行运行时"。移除的职责由 LangGraph 接管，保留的职责是 OpenClaw 的核心能力：


| 原职责                   | 降级后            | 说明                                                                                |
| --------------------- | -------------- | --------------------------------------------------------------------------------- |
| Agent 路由 + 任务分发       | ❌ 移除           | LangGraph StateGraph 接管节点编排和任务流转                                                  |
| 消息分发 + 通信协议           | ❌ 移除           | LangGraph State + 条件边接管 Agent 间信息传递                                               |
| 准入层（质量门）              | ⚠️ 保留为 Spec 来源 | config.yaml 的 Guardrail + Tool Policy 仍定义质量标准，但执行逻辑迁移到 LangGraph 条件边              |
| 预加载层（Bootstrap Files） | ✅ 保留           | 7 个 Bootstrap Files（AGENTS.md / SOUL.md / TOOLS.md 等）仍是 Agent 定义的核心，LangGraph 不触碰 |
| 工具调用 + Skill 加载       | ✅ 保留           | OpenClaw 的 Skill 系统（SKILL.md 渐进式加载）仍是 Agent 执行的核心                                 |
| 记忆管理                  | ✅ 保留           | MEMORY.md + Chroma 向量存储 + memory_search 仍是 Agent 记忆的核心                            |
| 沙箱 + Hook             | ✅ 保留           | OpenClaw 的 Docker 沙箱 + Steering Hook 仍是运行时安全的核心                                   |


**关键原则**：LangGraph 不替代 OpenClaw 的执行能力，只替代编排能力。OpenClaw 的 6 层 Harness（预加载→准入→编排→运行时→交互→时序）中，L03 编排层由 LangGraph 接管，其余 5 层保留在 OpenClaw。

### 2.4 State 定义——对应 Agent 间 JSON Schema 交接

LangGraph 的 State 是整个编排流程的"共享内存"，每个节点读写 State 的不同字段。State 的字段设计直接对应 OpenClaw Agent 间的 JSON Schema 交接规范：

```python
from typing import TypedDict, Annotated, Literal
from langgraph.graph import add_messages

class DiagnosticState(TypedDict):
    """诊断器 State —— 对应 7 只虾的 Agent 间 JSON Schema 交接"""
    
    # ---- 流程控制字段 ----
    workflow_id: str                    # 工作流实例 ID，关联 SQLite task
    mode: Literal["fast", "full"]       # 快模式（萃取虾直通）或完整模式
    
    # ---- Agent 产出字段（对应 JSON Schema 交接） ----
    clarification_result: dict          # 澄清虾输出 → 需求定义虾输入
    requirement_output: dict            # 需求定义虾输出 → 交互设计虾输入
    interaction_output: dict            # 交互设计虾输出 → Demo 虾输入
    demo_output: dict                   # Demo 虾输出 → Playwright 测试输入
    
    # ---- Harness 字段 ----
    sufficiency_scores: dict            # 充分度评分（五维加权）
    quality_gate_passed: bool           # 当前质量门是否通过
    retry_count: int                    # 当前节点的重试计数
    human_approval: Literal["approve", "modify", "reject"]  # 人工审批结果
```

**设计要点**：

- 每个字段对应一个 Agent 交接环节，字段名 = JSON Schema 的 key
- `workflow_id` 是 SQLite 和 checkpoint 的关联键
- `sufficiency_scores` / `quality_gate_passed` / `retry_count` 是 Harness 层的状态，不在 Agent 交接中传递，只在条件边中读写

### 2.5 StateGraph 定义——对应诊断器传统 Demo 路线

```python
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.sqlite import SqliteSaver

# ---- 构建图 ----
builder = StateGraph(DiagnosticState)

# ---- 添加节点 ----
# 每个 Agent 节点 = 调用 OpenClaw Agent + 同步写 SQLite
builder.add_node("clarify", clarify_agent_node)
builder.add_node("quality_check_clarify", quality_gate_clarify)
builder.add_node("define_requirement", requirement_definer_node)
builder.add_node("quality_check_requirement", quality_gate_requirement)
builder.add_node("design_interaction", interaction_designer_node)
builder.add_node("quality_check_interaction", quality_gate_interaction)
builder.add_node("build_demo", demo_builder_node)
builder.add_node("playwright_test", playwright_test_node)
builder.add_node("human_review", human_review_node)

# ---- 添加边 ----
builder.add_edge(START, "clarify")
builder.add_edge("clarify", "quality_check_clarify")
builder.add_conditional_edges("quality_check_clarify", route_after_quality_check,
    {"next_step": "define_requirement", "retry": "clarify", "human_review": "human_review"})
builder.add_edge("define_requirement", "quality_check_requirement")
builder.add_conditional_edges("quality_check_requirement", route_after_quality_check,
    {"next_step": "design_interaction", "retry": "define_requirement", "human_review": "human_review"})
builder.add_edge("design_interaction", "quality_check_interaction")
builder.add_conditional_edges("quality_check_interaction", route_after_quality_check,
    {"next_step": "build_demo", "retry": "design_interaction", "human_review": "human_review"})
builder.add_edge("build_demo", "playwright_test")
builder.add_edge("playwright_test", END)

# ---- 编译 + checkpoint ----
with SqliteSaver.from_conn_string("./diagnostic_checkpoint.db") as checkpointer:
    graph = builder.compile(
        checkpointer=checkpointer,
        interrupt_before=["human_review"]  # human_review 节点前自动暂停
    )
```

**设计要点**：

- 每个 Agent 节点后面紧跟一个 `quality_check_*` 节点——质量门是编排层的职责，不是 Agent 层的
- `add_conditional_edges` 的 3 个出口：`next_step`（通过继续）、`retry`（回退重试）、`human_review`（interrupt 等人工）
- `interrupt_before=["human_review"]` 让图在 human_review 节点前自动暂停，等人工 Command 恢复
- checkpoint 用 SqliteSaver（开发阶段），生产环境切换 PostgresSaver

### 2.6 Agent 节点函数——调用 OpenClaw Agent + 同步写 SQLite

每个 LangGraph 节点函数做两件事：调用 OpenClaw Agent 执行任务，然后把结果同步写入 SQLite。

```python
def clarify_agent_node(state: DiagnosticState) -> dict:
    """澄清虾节点：调用 OpenClaw 澄清 Agent + 同步写 SQLite"""
    
    # ---- Step 1: 调用 OpenClaw Agent ----
    # 短期方案：通过 OpenClaw CLI 调用
    result = call_openclaw_agent(
        agent_name="clarifier",
        input_data=state.get("clarification_result", {}),
        timeout=120  # 对应 Lobster 的 120s 超时
    )
    
    # ---- Step 2: 同步写 SQLite ----
    task_tool.update_task(
        workflow_id=state["workflow_id"],
        step_id="clarify",
        status="completed",
        output_path=result["output_path"]
    )
    
    # ---- Step 3: 返回 State 更新 ----
    return {
        "clarification_result": result,
        "retry_count": 0  # 重试计数归零
    }


def call_openclaw_agent(agent_name: str, input_data: dict, timeout: int = 120) -> dict:
    """OpenClaw Agent 调用封装——短期用 CLI，中期升级 MCP"""
    
    import subprocess
    cmd = f"openclaw agent run {agent_name} --input-json '{json.dumps(input_data)}'"
    
    try:
        proc = subprocess.run(cmd, shell=True, capture_output=True, timeout=timeout)
    except subprocess.TimeoutExpired:
        # Agent 超时 → SQLite 写 failed + 返回 retry 信号给 State
        task_tool.update_task(
            workflow_id=input_data.get("workflow_id", ""),
            step_id=agent_name,
            status="failed",
            error="timeout"
        )
        return {"_timeout": True}  # 质量门读到 _timeout=True → 自动走 retry 或 interrupt
    
    if proc.returncode != 0:
        raise AgentExecutionError(f"OpenClaw Agent {agent_name} failed: {proc.stderr}")
    
    return json.loads(proc.stdout)
    
    # 中期方案（待实现）：MCP tool_call
    # return mcp_client.call_tool(agent_name, input_data)
```

**设计要点**：

- 短期用 OpenClaw CLI 调用 Agent，中期升级为 MCP tool_call——接口不变，只改 `call_openclaw_agent` 内部实现
- 每个节点函数末尾都有 `task_tool.update_task`——这是 checkpoint 和 SQLite 双写的触发点

**短期 CLI 对接实操步骤**——今天就能跑：

```bash

openclaw --version  # 确认版本 ≥ 2026.7.1

# 2. 验证 Agent 注册
openclaw agent list  # 应看到 clarifier / requirement-definer / interaction-designer / demo-builder

# 3. 单步调用测试
openclaw agent run clarifier --input-json '{"topic": "测试输入"}'
# stdout 返回 JSON dict，节点函数用 json.loads(proc.stdout) 解析

# 4. 集成到 LangGraph 节点函数
# 调用 call_openclaw_agent("clarifier", input_data, timeout=120)
# 成功 → json.loads(stdout) → 返回 State 更新
# 超时 → subprocess.TimeoutExpired → 见下方异常处理
```

### 2.7 SQLite 与 checkpoint 的对接触发机制

checkpoint 擅长状态持久化和恢复，但不擅长跨工作流查询、依赖 DAG、历史统计。SQLite 补上这些缺口：


| 操作        | checkpoint                     | SQLite        |
| --------- | ------------------------------ | ------------- |
| Agent 执行完 | 自动保存状态快照                       | 同步写入任务记录      |
| 状态恢复      | `checkpoint.get_state_history` | SQLite 查询任务列表 |
| 跨工作流查询    | ❌ 不擅长                          | ✅ 主力          |
| 依赖 DAG 查询 | ❌ 不擅长                          | ✅ 主力          |
| 任务历史统计    | ❌ 不擅长                          | ✅ 主力          |


**双写触发机制**：在 2.6 的每个节点函数末尾统一调用 `task_tool.update_task`，避免双写不一致。checkpoint 由 LangGraph 自动保存，SQLite 由节点函数主动写入——两者通过 `workflow_id` 关联。

## 第3章：质量门迁移——v1.7.2.1 的 5 件套怎么变成 LangGraph 条件边

### 3.1 5 件套 → LangGraph 条件边的映射

v1.7.2.1 的 5 件套是质量门的雏形，但全部依赖 PM 手动执行。LangGraph 条件边把这些质量门从 PM 层迁移到编排层——自动化执行，不依赖 PM 自觉：


| v1.7.2.1 件套         | 对应 Harness 层 | PM 手动实现                                               | LangGraph 自动化实现                               |
| ------------------- | ------------ | ----------------------------------------------------- | --------------------------------------------- |
| **派单 4 件套硬约束**      | L02 准入层      | PM 写 description 时手动检查清单+依赖+验收+时间窗                    | `quality_gate_*` 条件边函数检查 Agent 输出完整性          |
| **双向 grep 校验**      | L04 运行时层     | PM 跑 `pm-task-board-2way-grep.sh` 手动比对 status vs tmp/ | checkpoint 自动比对 State 字段 vs SQLite 记录         |
| **PM 自评 checklist** | L05 交互层      | PM 5min 手动跑 5 项 checklist                             | `quality_gate_*` 节点自动评分，interrupt 只在质量门不通过时触发 |
| **PM 自身治理**         | L03 编排层      | PM 手动 update 5 单 P0/P1                                | LangGraph 自动状态流转，PM 不需要手动 update              |
| **投递验证**            | L04 运行时层     | PM 手动 grep 网关日志确认 sessions_send 成功                    | OpenClaw Hook 自动验证 + 节点函数返回值校验                |


### 3.2 条件边质量门代码框架

每个 Agent 输出后经过质量门节点，不合格则回退重试或 interrupt 等人工决策。这替代了 v1.7.2.1 的 PM 派单 4 件套硬约束——"description 缺任一 → Agent 拒绝接单"变成了"质量门不通过 → 回退或 interrupt"。

```python
def route_after_quality_check(state: DiagnosticState) -> str:
    """质量门路由：通过→继续，不通过→回退或 interrupt
    
    替代 v1.7.2.1 的 PM 派单 4 件套硬约束：
    - 原来：description 缺任一 → Agent 拒绝接单 + 飞书 ping PM
    - 现在：质量门不通过 → 自动回退或 interrupt 等人工决策
    """
    if state["quality_gate_passed"]:
        return "next_step"
    elif state["retry_count"] < 2:
        # 回退到上一个 Agent 重试，最多 2 次
        return "retry"
    else:
        # 重试次数用完，interrupt 等人工决策
        return "human_review"


def quality_gate_clarify(state: DiagnosticState) -> dict:
    """澄清 Agent 质量门
    
    检查项（替代 v1.7.2.1 的派单 4 件套）：
    1. 充分度评分 ≥ 0.7（对应"验收标准"）
    2. 无未确认点（对应"清单完整性"）
    3. 输出包含 JSON Schema 结构化字段（对应"依赖关系"）
    """
    # 阈值来源：workflow-spec.yaml nodes[].quality_checks
    # P0 阶段硬编码，P1 阶段从 Spec 动态读取
    scores = state["sufficiency_scores"]
    unconfirmed = state["clarification_result"].get("unconfirmed_points", [])
    has_schema = "schema_fields" in state["clarification_result"]
    
    # 三项全部通过 = 质量门通过
    passed = (
        scores["weighted_total"] >= 0.7 
        and len(unconfirmed) == 0 
        and has_schema
    )
    
    return {"quality_gate_passed": passed}


def quality_gate_requirement(state: DiagnosticState) -> dict:
    """需求定义 Agent 质量门
    
    检查项（对应 v1.7.2.1 的派单 4 件套）：
    1. 硬约束覆盖率 ≥ 80%（对应"验收标准覆盖"）
    2. JSON Schema 交接完整性（对应"清单完整性"）
    3. 上下游依赖声明（对应"依赖关系"）
    """
    req = state["requirement_output"]
    
    passed = (
        req.get("hard_constraint_coverage", 0) >= 0.8
        and "schema_fields" in req
        and "dependencies" in req
    )
    
    return {"quality_gate_passed": passed}
```

**设计要点**：

- 每个质量门函数检查 3 项——对应 v1.7.2.1 派单 4 件套的 4 项硬约束（清单+依赖+验收+时间窗），时间窗由 LangGraph 的 timeout 参数自动管理，不需要质量门检查
- `route_after_quality_check` 是通用的路由函数，所有质量门节点共用同一个路由逻辑
- 重试最多 2 次——对应 Lobster 的 `retry: 1`（1 次重试 + 1 次原始执行 = 2 次尝试）

### 3.3 interrupt 人机协同——替代文博拍板 + PM 手动 Barrier

v1.7.2.1 的文博拍板是人工触发的——PM 写完 SOP 后等文博回复。LangGraph 的 interrupt 是自动触发的——质量门不通过 + 重试次数用完时，图自动暂停，等人工 Command 恢复。

```python
from langgraph.types import interrupt, Command

def human_review_node(state: DiagnosticState) -> dict:
    """人工审批节点：替代 v1.7.2.1 的文博拍板
    
    原来：PM 写 SOP → 等文博回复 → 文博拍板确认/修改/拒绝
    现在：质量门不通过 + 重试用完 → 图自动暂停 → 人工审批 → Command 恢复
    """
    decision = interrupt({
        "question": "是否批准当前 Agent 输出？",
        "agent_name": "requirement-definer",
        "output": state["requirement_output"],
        "quality_score": state["sufficiency_scores"]["weighted_total"],
        "retry_count": state["retry_count"],
        "risk_level": "中等"
    })
    
    # interrupt 返回后，通过 Command 恢复图的执行
    if decision == "approve":
        return {"human_approval": "approve", "quality_gate_passed": True}
    elif decision == "modify":
        # 人工修改内容合并后传给下游 Agent
        return {
            "human_approval": "modify",
            "requirement_output": decision.get("modified_output", state["requirement_output"]),
            "quality_gate_passed": True
        }
    else:  # reject
        return {"human_approval": "reject", "quality_gate_passed": False}
```

**恢复图的执行**（对应 v1.7.2.1 的文博拍板后 PM 继续派单）：

```python
# 人工审批后，通过 Command 恢复图的执行
for event in graph.stream(
    Command(resume="approve"),  # 或 "modify" + 修改内容
    config={"configurable": {"thread_id": state["workflow_id"]}},
    stream_mode="values"
):
    print(event)  # 图继续执行下一个节点
```

**设计要点**：

- interrupt 暂停时，checkpoint 自动保存当前 State——即使人工审批耗时几小时，图恢复后 State 不丢失
- `Command(resume=...)` 是 LangGraph v1.0 的标准恢复机制，替代了 v1.7.2.1 的"文博拍板 → PM 继续派单"
- PM 退位为 interrupt 节点——日常编排由 LangGraph 自动执行，只在质量门不通过 + 重试用完时介入

### 3.4 PM 退位为 interrupt 节点——三重角色变成一个角色


| PM 当前角色                | LangGraph 替代                            | PM 退位后       |
| ---------------------- | --------------------------------------- | ------------ |
| 编排者（派单+盯进度+1h cron）    | LangGraph StateGraph + 条件边 + checkpoint | ❌ 不再做        |
| 执行者（自接活 fallback）      | LangGraph 节点函数调用 OpenClaw Agent         | ❌ 不再做        |
| 质量检查者（5min 自评+双向 grep） | LangGraph 条件边质量门 + checkpoint 校验        | ❌ 不再做        |
| **拍板者**（文博拍板）          | LangGraph interrupt + Command 恢复        | ✅ **保留这个角色** |


PM 从"人肉编排引擎"变成"interrupt 节点"——只在质量门不通过 + 重试用完时介入拍板，日常编排全部自动化。

## 第4章：三步迁移路径——从 PM 手动 SOP 到 LangGraph StateGraph

### 4.1 三步总览


| 步骤         | 起点                    | 终点                    | 核心动作                                                             | 预估工期  |
| ---------- | --------------------- | --------------------- | ---------------------------------------------------------------- | ----- |
| **Step 1** | PM 手动 SOP（v1.7.2.1）   | Lobster workflow.yaml | 将 8 步 SOP 转化为 YAML 声明式编排，PM 从人肉编排退位为 Lobster 执行                  | 1-2 周 |

### 4.2 Step 1：PM 手动 SOP → Lobster workflow.yaml

**目标**：让编排从 PM 人肉变成机器执行。PM 的 8 步 SOP 转化为 Lobster 的 workflow.yaml，Lobster 接管任务流转和超时控制。

**转化对照**：


| v1.7.2.1 SOP 步骤        | Lobster workflow.yaml 对应             | 说明                                 |
| ---------------------- | ------------------------------------ | ---------------------------------- |


### 4.3 Step 2：Lobster workflow.yaml → LangGraph StateGraph

**目标**：从声明式 YAML 编排升级到 Python StateGraph 编排，增加条件边质量门、interrupt 人机协同、checkpoint 状态持久化。

**转化逻辑**：


| Lobster workflow.yaml      | LangGraph StateGraph 对应                     | 说明                                 |
| -------------------------- | ------------------------------------------- | ---------------------------------- |
| `steps[].id`               | `builder.add_node(name, func)`              | 每个 step 变成一个节点                     |
| `steps[].agent`            | `call_openclaw_agent(agent_name)`           | 节点函数内部调用 OpenClaw Agent            |
| `steps[].timeout`          | `subprocess.run(timeout=N)`                 | 节点函数内部设置超时                         |
| `steps[].retry`            | `retry_count < N` 条件边逻辑                     | 条件边控制重试次数                          |
| `steps[].barrier: true`    | `interrupt_before=["human_review"]`         | interrupt 替代 Barrier               |
| `steps` 顺序执行               | `builder.add_edge(from, to)`                | 显式边定义顺序                            |
| 无质量门                       | `builder.add_node("quality_check_*", func)` | **新增**：每个 Agent 后面加质量门节点           |
| Lobster TaskFlow stateJson | LangGraph checkpoint SqliteSaver            | **升级**：checkpoint 替代 TaskFlow 状态管理 |


**转化后的 StateGraph**（即第 2 章 §2.5 的完整代码，不再重复）。

**最小可运行转化示例**——YAML 每个字段怎么变成 Python 的哪一行：

```python
# ---- §4.2 的 workflow.yaml → §2.5 的 StateGraph，5-8 行关键转化注释 ----

# steps[0].id='clarify', steps[0].agent='clarifier'
#   → builder.add_node("clarify", make_agent_node("clarifier", 120))
builder.add_node("clarify", clarify_agent_node)

# steps[0].quality_gate=true (新增，YAML 里没有，Step 2 新加)
#   → builder.add_node("quality_check_clarify", quality_gate_clarify)
builder.add_node("quality_check_clarify", quality_gate_clarify)

# steps[0].barrier=true → interrupt_before=["human_review"]
#   → builder.add_conditional_edges("quality_check_clarify", route_after_quality_check, ...)
builder.add_conditional_edges("quality_check_clarify", route_after_quality_check,
    {"next_step": "define_requirement", "retry": "clarify", "human_review": "human_review"})

# steps 顺序执行 → builder.add_edge("clarify", "quality_check_clarify")
builder.add_edge("clarify", "quality_check_clarify")
```

转化是**机械化的、可自动化的**——YAML 的每个字段对应 Python 的一行代码。这就是 §5.4 的 `build_graph_from_spec` 生成器为什么可行：YAML→Python 的映射规则是确定的，不需要人工判断。

1. **条件边质量门**——每个 Agent 输出后经过 `quality_check_*` 节点

3. **checkpoint 状态持久化**——SqliteSaver 替代 MEMORY.md + TaskFlow stateJson

## 第5章：Spec Coding 覆盖编排层——workflow-spec.yaml

### 5.1 编排层 Spec 断层的根因

OpenClaw 有 7 个 Bootstrap Files 做 Spec（AGENTS.md / SOUL.md / TOOLS.md / IDENTITY.md / USER.md / HEARTBEAT.md / MEMORY.md），覆盖了 Agent 层的定义规范。但 LangGraph 的编排逻辑没有对应 Spec：

- State 定义是代码级的 TypedDict，不是声明式 YAML
- 条件边是 Python 函数，不是人可审查的声明式规则
- 节点编排顺序写在 `builder.add_edge()` 里，不是结构化文档

**后果**：编排逻辑不可审查、不可迭代、不可热加载。每次改编排流程都要改 Python 代码、重新编译 StateGraph——这就是 v1.7.2.1 从 v1.5 到 v1.7.2.1 迭代 6 个版本的根因：PM 每次手动改 SOP，而不是改 Spec 自动生效。

### 5.2 workflow-spec.yaml——编排层的声明式 Spec

**5 分钟读懂 workflow-spec.yaml**：

1. **State Schema**：对应 `DiagnosticState` TypedDict——定义编排流程的共享内存字段
2. **nodes**：对应 `builder.add_node()`——定义哪些 Agent 参与编排，每个 Agent 的超时、重试、质量检查标准
3. **edges**：对应 `builder.add_edge()` 和 `add_conditional_edges()`——定义节点之间的流转规则，质量门通过→继续，不通过→回退或 interrupt
4. **quality_checks**：对应 `quality_gate_*` 函数的检查阈值——从 SOUL.md 提取，嵌入条件边
5. **改 Spec 即改系统**：`build_graph_from_spec()` 从 YAML 生成 StateGraph，不需要改 Python 代码

引入 workflow-spec.yaml，让编排逻辑变成人可读、可审查、可迭代的声明式定义：

```yaml
# workflow-spec.yaml — 编排层的 Spec 文档
workflow:
  name: "诊断器 Demo 路线"
  version: "1.0.0"
  mode: "traditional_demo"
  
  # ---- State Schema（对应 DiagnosticState TypedDict） ----
  state_schema:
    fields:
      - name: workflow_id
        type: string
        description: "工作流实例 ID，关联 SQLite task"
      - name: mode
        type: enum
        values: ["fast", "full"]
        description: "快模式或完整模式"
      - name: clarification_result
        type: object
        description: "澄清虾输出 → 需求定义虾输入"
        ref: "schemas/clarification-output.json"
      - name: requirement_output
        type: object
        description: "需求定义虾输出 → 交互设计虾输入"
        ref: "schemas/requirement-output.json"
      - name: interaction_output
        type: object
        description: "交互设计虾输出 → Demo 虾输入"
        ref: "schemas/interaction-output.json"
      - name: demo_output
        type: object
        description: "Demo 虾输出 → Playwright 测试输入"
        ref: "schemas/demo-output.json"
      - name: sufficiency_scores
        type: object
        description: "充分度评分（五维加权）"
      - name: quality_gate_passed
        type: boolean
        description: "当前质量门是否通过"
      - name: retry_count
        type: integer
        description: "当前节点的重试计数"
      - name: human_approval
        type: enum
        values: ["approve", "modify", "reject"]
```

### 5.4 LangGraph 从 workflow-spec.yaml 生成 StateGraph

workflow-spec.yaml 是声明式定义，LangGraph 从 Spec 生成 StateGraph——实现"改 Spec 即改系统"：

```python
import yaml

def build_graph_from_spec(spec_path: str) -> StateGraph:
    """从 workflow-spec.yaml 生成 LangGraph StateGraph"""
    
    with open(spec_path) as f:
        spec = yaml.safe_load(f)
    
    # ---- Step 1: 从 state_schema 生成 DiagnosticState ----
    state_fields = {}
    for field in spec["state_schema"]["fields"]:
        state_fields[field["name"]] = infer_type(field)
    DiagnosticState = TypedDict("DiagnosticState", state_fields)
    
    # ---- Step 2: 从 nodes 生成节点 ----
    builder = StateGraph(DiagnosticState)
    for node in spec["nodes"]:
        if node["type"] == "interrupt":
            builder.add_node(node["id"], human_review_node)
        elif node["type"] == "automated":
            builder.add_node(node["id"], automated_node(node))
        else:
            # Agent 节点 = 调用 OpenClaw Agent + 同步写 SQLite
            builder.add_node(node["id"], make_agent_node(node["agent"], node["timeout"]))
            # 质量门节点
            if node.get("quality_gate"):
                builder.add_node(
                    f"quality_check_{node['id']}",
                    make_quality_gate(node["id"], node["quality_checks"])
                )
    
    # ---- Step 3: 从 edges 生成边 ----
    for edge in spec["edges"]:
        if edge.get("condition"):
            # 条件边
            builder.add_conditional_edges(
                edge["from"],
                make_route_func(edge),
                {
                    "next_step": edge["to"],
                    "retry": edge.get("else_to"),
                    "human_review": edge.get("interrupt_to")
                }
            )
        else:
            # 固定边
            builder.add_edge(edge["from"], edge["to"])
    
    return builder
```

**设计要点**：

- `build_graph_from_spec` 是 Spec→Code 的生成器——改 workflow-spec.yaml 即改编排逻辑，不需要改 Python 代码
- `make_agent_node` / `make_quality_gate` / `make_route_func` 是工厂函数，从 Spec 参数动态生成节点和边

**Spec 校验逻辑**（生成器运行前必须校验）：

```python
def validate_spec(spec: dict) -> list[str]:
    """校验 workflow-spec.yaml 的合法性，返回错误列表"""
    errors = []
    registered_agents = get_registered_agents()  # 从 AGENTS.md 读取
    
    for node in spec["nodes"]:
        # 1. Agent 名必须存在于 AGENTS.md 注册表
        if node.get("agent") and node["agent"] not in registered_agents:
            errors.append(f"节点 {node['id']} 的 agent '{node['agent']}' 不在 AGENTS.md 注册表中")
        
        # 2. 阈值格式必须合法（数字或 'exists'）
        for check in node.get("quality_checks", []):
            if check["threshold"] != "exists" and not isinstance(check["threshold"], (int, float)):
                errors.append(f"节点 {node['id']} 的阈值 '{check['threshold']}' 格式错误")
        
        # 3. 边的 from/to 必须指向存在的节点 ID
        # ...（省略，逻辑类似）
    
    return errors
```

**边界说明——什么时候不该用生成器**：

- **条件边逻辑嵌套 > 3 层**：YAML 的 `condition` + `else_condition` + `interrupt_to` 只支持 2 层分支。如果质量门路由需要 3 层以上嵌套条件（比如：A 通过→继续，A 不通过但 B 通过→降级继续，A 和 B 都不通过→interrupt），应该手写 Python 条件边函数，而不是用生成器
- **动态路由逻辑**：如果条件边的路由规则需要根据运行时数据动态变化（比如：根据 Agent 输出的某个字段值决定走哪条路），生成器无法表达——手写 Python
- **生成器负责标准节点和边，手写函数负责复杂条件逻辑**——两者共存：生成器生成骨架，手写函数覆盖特定节点

**生产环境还需要增加 Spec 变更测试 + 回滚机制**（参考 OpenSpec 的 delta 设计管理）。

## 第7章：风险与应对——LangGraph 方案的 6 条局限不回避

### 7.1 六条局限


| #   | 局限/风险                          | 影响                                                                                          | 应对方案                                                           | 对应章节     |
| --- | ------------------------------ | ------------------------------------------------------------------------------------------- | -------------------------------------------------------------- | -------- |
| 1   | **技术栈复杂度增加**                   | 从 OpenClaw 单栈变成 OpenClaw + LangGraph 双栈，团队需要学习 LangGraph 的 State / Node / Edge / Checkpoint | 短期先启用 Lobster 跑通闭环（Step 1），中期再引入 LangGraph（Step 2）             | §4.2     |
| 2   | **编排逻辑是 Python 代码**            | StateGraph 的节点和边是 Python 函数，不是声明式 YAML——编排逻辑不可审查、不可热加载                                      | 引入 workflow-spec.yaml 做 Spec 驱动，LangGraph 从 Spec 生成 StateGraph | §5.2-5.4 |
| 3   | **OpenClaw 编排能力闲置**            | Gateway 的 Agent 路由 + 子 Agent 调度 + 消息分发能力被 LangGraph 接管后闲置                                   | Gateway 降级为执行运行时，保留准入 + 预加载 + 工具调用 + 记忆管理                      | §2.3     |
| 4   | **LangGraph 与 OpenClaw 的对接成本** | 需要开发 MCP / ACP 协议适配层                                                                        | 先用 OpenClaw CLI / API 做简单对接，后续升级为 MCP 标准                       | §2.6     |
| 5   | **checkpoint 与 SQLite 双写**     | 每个节点执行完需要同时写入 checkpoint 和 SQLite，可能不一致                                                     | 在节点函数末尾统一触发 SQLite 写入，避免双写不一致                                  | §2.7     |
| 6   | **团队学习成本**                     | 团队需要学习 LangGraph 的核心概念                                                                      | 参考 LangGraph 教程 2026 版和 LangGraph 工程落地手册，本文就是落地手册              | §2.5     |


### 7.2 最关键的两条风险

**风险 2（编排逻辑是 Python 代码）** 是最需要重视的。如果不引入 workflow-spec.yaml，编排逻辑就藏在 Python 函数里——PM 改编排流程需要改代码，而不是改 Spec。这和 v1.7.2.1 的问题一样：PM 改 SOP 是改 Markdown，改 LangGraph 编排是改 Python——本质没变，只是从 Markdown 换成了 Python。

workflow-spec.yaml 是解决这个风险的关键——让编排逻辑从"改代码"变成"改 Spec"，Spec→Code 生成器自动把 YAML 转化为 StateGraph。**但 workflow-spec.yaml 是 P1 优先级**——P0 阶段先手写 Python 跑通闭环，验证编排逻辑正确后再反推成 Spec。不要在 P0 阶段就急着写 Spec，增加落地阻力。

**风险 5（checkpoint 与 SQLite 双写）** 需要在架构设计时就解决。双写不一致会导致 SQLite 的任务记录和 checkpoint 的状态记录不同步——这和 v1.7.2.1 的"status vs 交付脱钩 100%"是同一类问题。

解决方案：在节点函数末尾统一触发 SQLite 写入，不在 Agent 内部写。checkpoint 由 LangGraph 自动保存，SQLite 由节点函数主动写入——两者通过 `workflow_id` 关联，不需要同步锁。

### 7.3 一句话总结

**LangGraph 方案不是完美方案，但它是当前最优解——6 条局限都有应对方案，且应对方案都在本文的技术框架内。编排权归属、质量门自动化、Spec 驱动是三个核心跃迁点，PM 从人肉编排引擎退位为 interrupt 拍板者，日常编排全部自动化。**
