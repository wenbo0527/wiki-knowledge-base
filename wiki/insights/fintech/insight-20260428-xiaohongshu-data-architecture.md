## 数据架构四次演进

### 1.0 时代：ClickHouse即席分析

**架构**：Spark → ClickHouse

**特点**：
- 解决即席查询性能问题
- 秒级响应查询

**局限性**：
- 实时和离线分离
- 数据一致性问题

### 2.0 时代：存算分离Lambda架构

**架构**：Flink + Spark + ClickHouse

**特点**：
- 实时和离线计算分离
- 存算分离提升灵活性

**痛点**：
- 两套代码维护成本高
- 数据口径可能不一致

### 3.0 时代：Lakehouse湖上建仓

**架构**：Flink + Iceberg + Spark + StarRocks

**特点**：
- 湖仓一体架构
- 统一数据存储
- P90时延5秒

**关键技术**：
- Apache Iceberg作为数据湖格式
- StarRocks作为OLAP引擎
- 物化视图优化查询

### 4.0 时代：增量计算（当前）

**架构**：Dynamic Table（增量计算框架）

**核心突破**：
- 用增量计算替代Lambda架构
- 一套代码解决实时和离线
- 架构复杂度降低 **1/3**

### 三大成本降低

| 维度 | 降低幅度 |
|------|----------|
| 架构复杂度 | 降低 **1/3** |
| 资源成本 | 降低到 **1/3** |
| 开发成本 | 降低到 **1/3** |

### 性能提升

| 指标 | 提升幅度 |
|------|----------|
| 实时汇总任务资源 | 约为Flink的 **1/4** |
| 查询性能 | **3倍**提升 |
| P99时延 | 从15s降至5s |

### 增量计算的定义与标准

**核心思想**：只处理变化的数据，而非全量数据

**三大特性**：
1. **Change Data Capture (CDC)**：捕获数据变化
2. **Incremental Computation**：增量计算
3. **Dynamic Table**：动态表抽象

---

## 核心技术点

### 1. 自动Z-Order排序

**效果**：
- 80-90%的查询能命中Z-Order索引
- 查询性能提升 **10倍**

**原理**：
- 对高频查询字段进行预排序
- 利用Z-Order曲线优化多维查询

### 2. 物化视图

**效果**：
- 数据量从6000亿压缩到200亿
- 存储空间节省 **30倍**

**应用场景**：
- 高频聚合查询
- 预计算复杂指标

### 3. 倒排索引

**效果**：
- Date Skipping效率提升 **10倍**

**原理**：
- 建立字段值到数据行的倒排映射
- 快速定位满足条件的数据

### 4. Json Flatter

**应用场景**：
- 非结构化JSON数据优化
- 嵌套字段查询加速

## 行业启示

### 1. 增量计算是趋势

Lambda架构的痛点（双代码、低一致性、高成本）在AI时代被放大，增量计算提供了更优雅的解决方案。

### 2. 湖仓一体成为标配

从3.0到4.0，小红书始终坚持Lakehouse方向，说明湖仓一体架构经受住了大规模生产验证。

### 3. 智能化是下一个方向

**Data+AI融合**：
- 智能数据治理
- 自动SQL优化
- 自适应Z-Order

### 4. 性能优化无止境

即使达到P99<5s，小红书仍在探索进一步优化，说明数据平台的性能提升是持续工程。
