### **🏆 核心背景：Demo级方案的面试痛点**

绝大多数候选人对Agent意图识别的初始回答停留在Demo阶段：将全部Intent（意图）和Intent Description（意图描述）直接写入Prompt，让大模型返回对应意图名称。该方案仅适配Intent数量极少的简单场景，完全无法应对生产环境中企业Copilot的真实情况——这类系统通常包含HR、财务、合同、OA、审批、CRM等数十个Agent，每个Agent下又有数十个Intent，整体规模可达数百级。

面试官针对Demo方案提出的四大灵魂拷问，本质是指向生产环境的三大核心难题：
1.  **Token爆炸问题**：若单条Intent描述占300Token，100个Intent的总Token量将达到30000，直接导致调用成本飙升、响应速度变慢，系统完全不具备可扩展性。
2.  **准确率衰减问题**：Intent数量越多，意图边界越容易重叠混淆，大模型的分类准确率会随意图规模扩大持续下降。生产环境要求Intent设计必须满足**互斥性**，意图描述清晰无大量重叠。
3.  **误识别兜底问题**：大模型无法保证100%分类正确，不能依赖单次分类结果，必须引入**Confidence（置信度）**机制，低置信度场景下主动反问用户澄清，避免错误路由带来的业务风险。
---
### **📊 生产级核心架构：多阶段Intent Routing分层体系**

该架构通过「规则过滤 → 语义召回 → LLM精排 → 澄清兜底」的分层流程，在成本、速度、准确率三者间实现最优平衡，完整流程以歧义query「苹果多少钱？」为例拆解如下：

| 分层阶段 | 核心能力 | 实现细节 | 架构价值 |
| :--- | :--- | :--- | :--- |
| **第一层：规则匹配** | 快速处理确定性请求 | 基于Regex正则、关键词匹配、黑白名单规则，命中后直接返回结果或跳转对应Agent | 零大模型调用，速度最快、成本最低，过滤大量固定表达类请求 |
| **第二层：Embedding语义召回** | 缩小意图候选范围 | 对用户输入和全量Intent做语义相似度计算，从100个Intent中召回Top-K（通常取5个）最相关候选 | 大幅减少后续LLM需要处理的意图数量，核心作用是**降本提速** |
| **第三层：LLM精准分类** | 小候选集下的意图判定 | 仅让大模型在Top-5候选Intent中做选择，同时输出三个结果：最终Intent、Confidence置信度、Reason判断依据 | 避免大模型在海量意图中混淆，大幅提升分类准确率，缩短Prompt长度降低Token消耗 |
| **第四层：置信度分流+澄清兜底** | 低置信度场景风险规避 | 置信度≥80%直接进入对应Agent执行业务逻辑；置信度<80%触发Clarify流程，主动向用户确认歧义点（如询问「你说的苹果，是苹果公司，还是水果？」） | 用少量多轮对话的成本，大幅降低误路由带来的业务损失 |

### **🌟 进阶优化：生产级Intent Routing持续迭代闭环**

成熟的企业级意图识别系统绝非单次分类即可完成，必须搭建完整的工程化闭环体系，实现从线上观测到线下优化的全链路迭代：
1.  **全链路Trace（轨迹）建设**
    完整记录每一次请求的全决策链路：用户输入 → Embedding Top-K召回结果 → LLM Prompt → LLM输出（Intent/Confidence/Reason） → 进入Agent → 调用Tool → 最终回复结果。该能力让所有决策过程可回溯、可排查，遇到用户反馈误识别时，能快速定位问题根因（是Embedding漏召回、Prompt缺陷还是置信度阈值不合理）。
2.  **线上可观测体系（Observability）**
    搭建监控仪表盘实时采集全链路运行指标，无需人工介入即可快速发现系统异常：
    - 流量类：QPS请求量
    - 性能类：平均耗时、P95延迟、Embedding耗时、LLM耗时、超时次数
    - 成本类：Token消耗
    - 稳定性类：重试次数、降级次数、澄清次数
    例如当短时间内澄清次数占比突增时，可快速预警系统可能出现了Prompt变更、新增混淆意图或模型置信度分布偏移等异常。
3.  **离线评测（Evaluation）体系**
    从线上生产Trace中抽样真实用户Query，通过「人工标注+LLM-as-a-Judge」的组合方式生成Ground Truth（标准答案），重新运行最新版路由系统后计算Accuracy（准确率）、Precision（精确率）、Recall（召回率）、F1值等核心指标，客观评估模型真实能力，定位易混淆的意图对和高误判Query。
4.  **Benchmark（基准测试集）沉淀**
    长期维护Golden Dataset黄金数据集，覆盖正常请求、歧义请求、错别字、口语表达、中英文混输、未知Intent、长文本输入等全量业务场景。每次修改Prompt、调整Intent、升级Embedding或大模型版本时，必须完整跑通全量Benchmark做回归测试，只有满足「准确率不下降、性能无明显退化、成本符合预期」的上线标准，新版本才能发布，从机制上避免系统迭代后能力退化。

### **📝 关键洞察**

Agent意图识别本质不是单一的Prompt工程问题，而是集Routing路由设计、Observability可观测、Evaluation评测、Benchmark基准测试于一体的复杂工程系统设计。搭建这套持续观测、持续评测、持续优化的闭环体系，才是从「会调用大模型API」的开发者，成长为真正具备生产级Agent系统设计能力工程师的核心标志。
