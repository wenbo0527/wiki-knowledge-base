# 知识库搭建最佳实践 - 2026-06-03

> **方法论沉淀**: 从1年实操中反向倒推
> **方法论编号**: 07（接续6大方法论）
> **维护者**: 尼克·弗瑞 🕵️
> **基于**: Karpathy LLM Wiki Pattern + 1年Wiki运营经验（1048个文档）

---

## 一、核心论断

> **"知识库不是文档仓库，是认知基础设施。"**

搭建知识库的目标**不是存东西**，是**让知识能在你决策时被召回、连接、复用**。

判断标准：搭完半年后，是否还在被使用？是否还在产出新认知？

---

## 二、五阶段建设路径

### 阶段1：定位（Day 1-7）

**先回答3个问题**：

| 问题 | 选项 | 含义 |
|:---|:---|:---|
| **谁用？** | 个人 / 团队 / 公司 | 决定协作机制和权限 |
| **存什么？** | 灵感 / 方法论 / 业务知识 / 代码 | 决定文档分类 |
| **怎么用？** | 检索 / 创作 / 决策 / 教学 | 决定评价标准 |

**陷阱**：上来就建目录、写模板——**先确定北极星指标**。

**我们自己的答案**：
- 谁用：文博+4个Agent（混合团队）
- 存什么：金融+AI+产品方法论+情报
- 怎么用：辅助决策+沉淀方法论+Agent RAG检索

---

### 阶段2：骨架（Week 1-4）

**三层架构（Karpathy LLM Wiki Pattern）**：

```
┌─────────────────────────────────────────┐
│  Layer 3: Schema（规则层）              │
│  → 元数据/命名/Tag体系/评价标准          │
│  → 文档: 元信息头、状态机、四维评价       │
├─────────────────────────────────────────┤
│  Layer 2: Wiki（加工层）                 │
│  → Insight / Topic / Entity / Concept   │
│  → 文档: 模板、写作规范、关联要求        │
├─────────────────────────────────────────┤
│  Layer 1: Sources（输入层）              │
│  → 原始资料/URL/PDF/书籍                 │
│  → 文档: 收集SOP、来源标记、归档规则      │
└─────────────────────────────────────────┘
```

**关键原则**：**先建Schema，再填Wiki，最后才收集Sources**。倒着做 = 垃圾山。

**我们的教训**（2026-04-30健康检查）：
- ❌ **Sources严重不足**（35个），导致Insights无源之水
- ✅ Wiki加工层最先建立，丰富（90+Insights, 236 Topics）
- ⚠️ Schema有但不够强（13个Concepts偏少）

**正确顺序**：Schema → Wiki → Sources（同时建立收集机制）

---

### 阶段3：模板（Week 2-6）

**4类核心模板**（按使用频次）：

| 模板 | 用途 | 关键字段 |
|:---|:---|:---|
| **Insight** | 观点/分析/趋势 | 来源+评级+双向链接+行动建议 |
| **Topic** | 专题深度 | 背景+框架+案例+反思 |
| **Entity** | 公司/人物/产品 | 元信息+关系+时间线+来源 |
| **Concept** | 概念定义 | 定义+演进+应用+边界 |

**元信息头标准**（必须）：

```yaml
---
title: 标题
type: insight | topic | entity | concept
created: YYYY-MM-DD
updated: YYYY-MM-DD
status: active | stale | archived | conflict
maintainer: 维护者
tags: [#capability-xxx, #L4-知识, #domain-xxx]
summary: 一句话概括（必需）
---
```

**4个反模式**：

| ❌ 反模式 | ✅ 正解 |
|:---|:---|
| 复制原文到知识库 | 提取核心+附原文链接 |
| 标题模糊（"笔记1"） | `insight-{date}-{slug}` 命名 |
| 无来源标注 | 必填来源URL/出版物 |
| 无双向链接 | 每个文档至少2个关联 |

### 阶段4：运营机制（Month 2+）

**4大运营机制**：

#### 机制1：Ingest（入站流程）

```
新信息到达
    ↓
Step 1: 类型判断（Insight/Topic/Entity/Project）
    ↓
Step 2: 价值评估（⭐⭐⭐+ 才入库）
    ↓
Step 3: 选模板+提取核心（不复制）
    ↓
Step 4: 加双向链接
    ↓
Step 5: log.md 记录
```

**关键**：
- ⭐⭐⭐ 起步门槛（低于不入库）
- 必须增量更新（不重写已有Topic）
- 矛盾标记 `[[CONFLICT:...]]`

#### 机制2：Lint（健康检查）

**每周一次**，自动+人工结合：

| 检查项 | 频率 | 工具 |
|:---|:---:|:---|
| 孤立页面 | 每周 | 自动脚本 |
| 过时内容（>90天） | 每周 | 自动脚本 |
| 死链 | 每周 | 自动脚本 |
| 空目录 | 每周 | 自动脚本 |
| 双向链接缺失 | 每周 | 抽查10篇 |

**评分标准**：
- 90-100：🟢优秀，跳过
- 75-89：🟡良好，记录下周处理
- 60-74：🟠一般，本周必处理
- <60：🔴紧急，派蒙介入

#### 机制3：保鲜（生命周期管理）

```
创建 → 发布 → 维护 → 评审 → 归档/删除
  │        │        │        │
  ▼        ▼        ▼        ▼
1周内    持续     每季度   按需
```

| 规则 | 触发 | 动作 |
|:---|:---|:---|
| 到期提醒 | review日期-30天 | 自动提醒 |
| 低访问警告 | 6个月无访问 | 标记观察 |
| 过时标记 | 1年未更新 | `[STALE]` |
| 自动归档 | 2年未更新 | 移入`_archive` |

#### 机制4：评价体系（质量门槛）

| 评价对象 | 维度 | 入库阈值 |
|:---|:---|:---:|
| **Insight** | 来源可靠性+价值评级 | ⭐⭐⭐+ |
| **Template** | 完整性30%+可用性25%+规范性25%+实用性20% | ≥60分 |
| **Code Example** | 可运行25%+可读20%+复用20%+文档15%+来源10%+组合10% | ≥60分 |
| **Tool** | 实际使用+可执行+有输出+有文档 | 必填 |

### 阶段5：自动化（Month 3+）

**4个自动化点**：

| 自动化 | 频率 | 工具 | 收益 |
|:---|:---:|:---|:---|
| **RSS抓取** | 每日08:00 | RSS订阅器 | 持续输入 |
| **健康检查** | 每周一09:00 | Lint脚本 | 质量保障 |
| **Git自动提交** | 每30分钟 | LaunchAgent | 版本保护 |
| **月报生成** | 每月1日 | 模板+脚本 | 运营可见 |

**自动化的判断标准**：**人不想干的活，才自动化**。人想干的（如写洞察），别自动。

## 三、关键陷阱（我们踩过的）

### 陷阱1：先囤内容后治理

**症状**：1年下来1000+文档，但Concepts只有13个，找不到东西。

**正解**：**Schema先行**。先定Tag、命名、模板，再填内容。

### 陷阱2：复制粘贴原文

**症状**：文档是"文章摘录"集合，没有自己的观点。

**正解**：**强制要求"认知增量"**——每条Insight必须有自己的判断和行动建议。

### 陷阱3：无来源标注

**症状**：6个月后回来看，不知道这段话从哪来的，不敢用。

**正解**：**没有URL的文档不入库**。来源是知识的"防伪码"。

### 陷阱4：层级过深

**症状**：`wiki/topics/ai-native/business-world-model/jd-pricing-practice/README.md`（5层）

**正解**：**最多3层**。超了就扁平化。

### 陷阱5：缺乏双向链接

**症状**：每篇文档独立，无法形成知识网络。

**正解**：**每篇文档至少2个`[[双向链接]]`**。形成图谱。

### 陷阱6：Sources不足

**症状**：Wiki大但没有原始资料支撑，Insights像"自嗨"。

**正解**：**Sources收集机制**——每产1个Insight，对应1个Source（Karpathy三层架构的核心）。

### 陷阱7：运营节奏中断

**症状**：开始3个月天天写，后来3个月不写，知识库变"废墟"。

**正解**：**自动化优先**（RSS、Git、Lint），让人只做有判断的事。

## 四、5大方法论对齐

我们的6大方法论在知识库场景的应用：

| 方法论 | 知识库应用 | 评价点 |
|:---|:---|:---|
| **技术理解** | 选型Obsidian/Notion/RAG | 工具适配度 |
| **需求决策** | 知识库定位+北极星指标 | 价值清晰度 |
| **产品设计** | 模板+写作流+交互 | 用户体验 |
| **数据驱动** | 健康度评分+访问日志 | 量化运营 |
| **价值闭环** | 知识反哺决策/创作 | ROI衡量 |
| **风险防控** | 来源追溯+矛盾检测 | 可靠性 |

**核心判断**：**知识库是"产品"，不是"项目"**。需要产品思维持续运营。

## 七、避坑总结

> **"知识库的死亡不是建得不够大，是用得不够深。"**

| 死亡方式 | 症状 | 提前防御 |
|:---|:---|:---|
| **废墟化** | 半年不更新 | 自动化运营 |
| **孤岛化** | 文档无关联 | 强制双向链接 |
| **污染化** | 大量低质内容 | 评价+门槛 |
| **失信化** | 来源追溯断裂 | 强制URL |
| **失衡化** | 某类内容过多 | 健康度预警 |
