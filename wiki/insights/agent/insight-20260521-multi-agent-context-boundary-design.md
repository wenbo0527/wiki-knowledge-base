## 核心洞察

> **TL;DR**: 多Agent设计应围绕上下文边界而非角色，要先尝试单Agent，确有必要再引入多Agent协作。

### 关键原则1: Design around context boundaries, not roles

> **来源**: 原文核心观点

**翻译成工程语言**：
- 这两件事，需不需要看到对方的中间过程？
- 这两件事，会不会因为对方做完了某一步就影响自己下一步？
- 如果交给同一个Agent一次性做完，会不会更省心？

**如果答案偏向"是"**，那它们本就该在一起，不该被拆开。

## Sub-Agent vs Agent Team决策框架

### Sub-Agent适用场景

| 特征 | 说明 |
|:---|:---|
| **隔离探索** | 把混乱的探索过程压成一个干净的结论 |
| **压缩信息** | 结果只返回结论和证据 |
| **独立调查** | 任务可独立，不影响主流程 |

### Agent Team适用场景

| 特征 | 说明 |
|:---|:---|
| **持续协作** | 前一个人改完，后面所有人都要立即知道 |
| **共享状态** | 需要处理冲突、可见性、版本化 |
| **实时同步** | 软件项目接口契约变更需即时通知 |

### Agent Team的隐藏成本

| 成本 | 说明 |
|:---|:---|
| **共享状态层** | 不是简单的内存共享，是要能处理冲突、可见性、版本化 |
| **通信协议** | 节点间需要显式协议 |
| **Lead Agent** | 需要仲裁分歧、推动进度、识别阻塞 |
| **调试链路** | 问题可能不在节点，而在节点协作 |

## 多Agent决策检查清单

| 检查项 | 问题 | 如果是 |
|:---|:---|:---|
| **1. 独立调查** | 这段任务是不是独立调查？ | → Sub-Agent |
| **2. 上下文污染** | 会不会污染主上下文？ | → Sub-Agent |
| **3. 只读vs写** | 子Agent是只读还是写共享状态？ | → 只读更适合Sub-Agent |
| **4. 依赖关系** | 子任务之间有没有强依赖？ | → 强依赖慎拆 |
| **5. 结果合并** | 最终结果由谁合并、谁负责写入？ | → 边界清楚有价值 |
| **6. 持续协作** | 前一个完成后，后面所有人要立即知道吗？ | → Agent Team |
| **7. 共享状态** | 是否需要共享、可变的状态？ | → Agent Team |

**决策流程**：
```
单Agent能干完吗？
     │
     ├── 是，体感不差 → 单Agent（结束）
     │
     └── 否 → 检查Sub-Agent 5项
              │
              ├── ≥3项符合 → Sub-Agent
              │
              └── 检查Agent Team 2项
                       │
                       ├── ≥1项符合 → Agent Team
                       │
                       └── 否则 → 优化单Agent
```

## 工具描述设计原则

> **来源**: 原文

**Sub-Agent的description**是路由信号：
- 写得含糊，路由就含糊
- 写得边界清楚，分发也清楚

**写给人看 vs 写给Agent看**：
- 写给人看：注重可读性
- 写给Agent看：注重边界和触发条件

## 常见坑与修复

| 问题 | 原因 | 修复 |
|:---|:---|:---|
| **无限循环** | Supervisor反复调用同一Worker | 设置recursionLimit |
| **上下文污染** | Worker完整历史淹没关键指令 | Worker节点仅返回最后一条结果 |
| **Worker死锁** | A调用B，B调用A导致系统挂死 | 明确Worker prompt：不调用其他Agent |
| **信息差导致动作错** | 上下文在多Agent间不一致 | Agent Team需要共享状态层 |
