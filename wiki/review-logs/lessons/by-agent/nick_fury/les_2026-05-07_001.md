## 教训总结

> **防重复机制需要基于"幂等键"而非"状态日志"**

---

## 问题背景

晨间简报未能正常发送，原因是Pipeline的防重复机制误判：
- 机制设计：检查pipeline_log中是否已有当日记录
- 实际问题：日志状态与实际发送状态不一致
- 结果：误认为已发送，直接跳过

---

## 根因分析

### 技术层面

| 问题 | 说明 |
|:---|:---|
| **状态存储不完整** | pipeline_log只记录"是否执行"，不记录"是否成功" |
| **缺少幂等键** | 没有基于内容哈希的重复检查 |
| **容错机制缺失** | 失败后没有自动重试 |

### 流程层面

```
预期流程：
  检查log → 发现无记录 → 执行发送 → 记录log

实际流程：
  检查log → 发现无记录？ → [这里出了问题]
                    ↓
           误判为"已有记录"
                    ↓
              跳过发送
```

---

## 正确做法

### ✅ 应该做的

1. **基于幂等键判断**
   ```python
   # 用内容哈希作为幂等键
   idempotent_key = hash(content + date)
   if redis.exists(idempotent_key):
       skip()
   else:
       send()
       redis.setex(idempotent_key, 24h, "sent")
   ```

2. **分离"执行状态"和"成功状态"**
   ```python
   pipeline_log = {
       "executed_at": "08:30",
       "status": "success/failed/pending",
       "error": null
   }
   ```

3. **增加心跳检测**
   ```python
   # 发送后等待确认
   # 如果10分钟内没有确认，自动告警
   ```

### ❌ 不应该做的

1. 依赖单一日志文件判断是否执行
2. 没有重试机制的防重复设计
3. 假设"记录了就成功了"

---

## 经验复用

### 可复用的场景

| 场景 | 如何应用 |
|:---|:---|
| 定时任务防重复 | 用内容哈希+日期作为幂等键 |
| 消息队列消费 | 用消息ID作为幂等键 |
| API调用 | 用请求ID追踪 |

### 预防措施

```
1. 所有定时任务增加执行结果确认
2. 失败时立即告警，不等下一次执行
3. 定期清理过期的pipeline_log
```

---

## 关键反思

> **问"How"不问"Why"**
>
> 这个bug是怎么一步步发生的？
> - Pipeline设计时假设"记录=成功"
> - 但网络异常、API超时等情况会导致"记录但未成功"
> - 防重复机制基于这个错误假设
>
> 为什么当时这样设计是合理的？
> - 简化逻辑，最初版本只需要防止重复执行
> - 没有考虑"部分成功"的状态
> - 缺少完善的日志和监控
