# 天猫"胶水编程"实践深度分析

> 来源: Get笔记
> 导入日期: 2026-05-06

### **🏆 核心成果概览**

**胶水编程（Glue Coding）** 是天猫团队提出的AI编码方法论，核心主张"让AI抄代码而非写代码"，通过构建**四层物料体系**（开发规范、代码模式、领域知识、任务规格）实现业务模块的高效组装。实践数据显示，在某大型电商平台业务域试点中，代码采纳率从**50%** 提升至**97.9%**，显著缩短需求交付周期，尤其适用于中后台CRUD场景（列表页、表单页、详情页等）。

### **📊 采纳率提升轨迹**

试点业务域通过三个月物料体系完善，实现采纳率三级跳：

| 时间节点 | 采纳率 | 关键举措 |
| :------- | :----- | :------- |
| 2025.12  | **76.0%** | 引入AGENTS.md静态规范 + 知识库运营 |
| 2026.01  | **93.0%** | 完善代码模式（样板间）体系 |
| 2026.02  | **97.9%** | 四层物料协同 + 上下文延续机制 |

*采纳率定义：周期内CR合并上线的代码总行数中AI生成行数占比（行级加权统计）*

### **🔍 胶水编程设计哲学**

#### **(一) 核心理念：从"生成"到"组装"的范式转变**

传统AI编码将AI定位为"作者"，依赖模型能力从零生成代码；胶水编程将AI定位为"装配工"，核心逻辑是：
- **90%抄**：复用团队已有代码模式、规范和知识
- **10%写**：仅在业务差异点编写"胶水代码"

#### **(二) AI编码演进三阶段**

| 阶段 | 解决问题 | 典型特征 | 可控性 |
| :--- | :------- | :------- | :----- |
| **Vibe Coding** | "能不能用AI写代码" | 自然语言描述，自由生成 | 低（风格随机、不可直接合入） |
| **SPEC Coding** | "AI写的代码对不对" | 结构化方案约束意图边界 | 中（管"做什么"，不管"怎么做"） |
| **Glue Coding** | "AI写的代码像不像我们的" | SPEC+物料双重约束 | 高（风格统一、CR一次通过） |

### **🛠️ 四层物料体系详解**

#### **(一) 开发规范（规矩层）**
- **定位**：仓库级编码底线约束（不可逾越的规则）
- **内容**：物料依赖（如优先使用@internal/admin-components）、请求规范（URL格式key://pathname）、组件规范、页面结构
- **技术实现**：云端域配置系统（agentDomainConfig）自动识别业务域+工作台类型，生成AGENTS.md注入Agent上下文
- **关键价值**：解决组件乱用、规范不守问题，某业务域因缺失businessCode参数导致的导出数据错乱问题彻底解决

#### **(二) 代码模式（骨架层）**
- **定位**：可复用的完整代码骨架（样板间）
- **典型结构**（列表页示例）：
  ```
  ├── index.tsx    // 页面入口
  ├── Form.tsx     // 筛选表单
  ├── Table.tsx    // 数据表格
  ├── services.ts  // 接口定义
  └── constants.ts // 枚举常量
  ```
- **设计原则**：两层继承（架构组维护5个工作台级样板间+域级扩展）
- **效果对比**：相同订单列表需求，无样板间时需50+对话轮次，有样板间后降至15-20轮，且文件结构完全符合团队规范

#### **(三) 领域知识（知识层）**
- **内容构成**：
  - 物料文档（60-70%）：内部组件API（如@internal/admin-components的ProTable用法）
  - 经验知识（20-30%）：踩坑记录（如"ProTable的cacheKey必须全局唯一"）
  - 编码规范（5-10%）：域特有规则
- **技术实现**：MCP协议调用knowledge Server按需检索
- **优化效果**：低效知识条目（高调用率低采纳率）优化后，知识库关联采纳率从18%提升至35%

#### **(四) 任务规格（方案层）**
- **定位**：单次需求的施工图，定义"做什么"
- **模板分类**（6种核心模板）：

| 模板类型 | 核心复杂度 | 特有工具 | 典型场景 |
| :------- | :--------- | :------- | :------- |
| 基础模板 | 标准交互 | 页面布局图 | 常规增删改查 |
| 表单联动 | 字段依赖 | 联动规则表 | 类型选择后子选项变化 |
| 状态流转 | 状态机+权限 | 状态机图 | 审批流、订单状态管理 |
| 复杂校验 | 校验计算 | 校验规则表 | 跨字段校验、价格计算 |

### **📈 实施效果与价值**

#### **(一) 量化收益**
- **采纳率**：从50%提升至97.9%（同一基座模型）
- **新人接入**：配置时间从2小时→30秒（开发规范自动下发）
- **需求交付**：非标子市场询价单管理页从零开发至上线，原创代码仅占10%

#### **(二) 认知转变**
- **投资方向**：从prompt工程→内部物料体系建设
- **质量标准**：从"生成多少代码"→"原创多少代码"（原创越少越好）
- **资产观**：已有代码=样板间资产，需求规格=决策上下文

### **⚠️ 实践误区与避坑指南**
1. **"物料越多越好"** → 需通过"调用率×采纳率"四象限清理低效知识，提升精准度
2. **"样板间写一次就够"** → 需随架构升级同步更新（如请求库迁移）
3. **"有物料就轻视SPEC"** → SPEC管"做什么"，物料管"怎么做"，缺一不可

### **📝 补充细节**
- **MCP协议**：内部知识调用标准协议，支持Agent按检索词精准获取领域知识
- **Track机制**：需求交付后自动在.ai/tracks/目录留存spec.md，实现上下文延续
- **规格保鲜**：通过slash command触发AI辅助同步代码变更至spec.md，保持文档与代码一致性
- **主力用户**：近200名后端工程师，完全依赖该体系交付中后台前端需求
