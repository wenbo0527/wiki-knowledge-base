# Harness Engineering实战指南：从制度化管理到最小可用形态

> **版本**: v1.0

## 核心洞察

> **TL;DR**: AI不是助手，是执行力极强但必须被制度化管理的团队。要给人设计系统，AI负责高强度执行。

### 制度化管理理念

| 理念 | 说明 |
|:---|:---|
| **不是助手** | AI不是助手，是执行力极强的团队成员 |
| **制度化管理** | 不能指望它天生懂规矩，自己长出流程意识 |
| **要给边界** | 给AI边界、分工、门禁、反馈闭环 |
| **人设计系统** | 人负责设计系统，AI负责执行 |
| **人负责结果** | 人对最终结果负责 |

## 四块拼图模型

> **来源**: 原文"第十二章：Harness的全貌"

| 拼图 | 说明 | 作用 |
|:---|:---|:---|
| **约束与流程** | 边界和规则 | 让AI在规矩里干活 |
| **反馈** | 判卷和验证 | 干完以后谁来判卷 |
| **知识库** | 索引和记忆 | 同一功能不被反复重写 |
| **进化** | 持续改进 | 人与AI共同驱动Harness改版 |

### 四块拼图关系

```
约束与流程 → 反馈 → 知识库 → 进化
     ↑                        │
     └───────────←────────────┘
```

### 缺失拼图的症状

| 缺失 | 症状 |
|:---|:---|
| **缺流程** | 即兴发挥，失败日志难收敛 |
| **缺反馈** | 无法判定，流程空转 |
| **缺知识库** | 同类功能反复重写、同类坑反复踩 |
| **缺进化** | 脚本与规则没人收紧，地图与真实脱节 |

## 最小可用形态理念

> **来源**: 原文"第七章"

### 错误的做法

```
✗ 先设计一套完美体系，再照着执行
```

### 正确的做法

```
✓ 先用最小可用形态跑起来
   → 在真实问题里不断补结构、补边界、补门禁、补反馈闭环
```

### 实操步骤

| 步骤 | 动作 |
|:---:|:---|
| **1** | 先看当前最大的痛点在哪里 |
| **2** | 先补最关键的一层 |
| **3** | 让系统先跑起来 |
| **4** | 在真实问题里继续补强 |

## 流程管理要点

### 问题1：下游认为上游产出不合格

| 问题 | 解决方案 |
|:---|:---|
| 下游只能提出阻塞项 | 由PM把流程正式打回给上游 |
| 第一次有了边界感 | "谁负责哪份产物"明确 |

### 问题2：PM太容易越界

| 问题 | 表现 |
|:---|:---|
| PM从流程管理者滑成到处给意见的人 | 顺手说"这个需求我觉得可以这么补" |

### 解决方案：PM守住流程中心

| 角色 | 职责 |
|:---|:---|
| **PM** | 流程管理者，不到处给意见 |
| **越界处理** | 需求不清/方案争议/开发卡点 → 走流程打回 |

---

## 进化机制

### 进化不是泛泛的"项目要写文档"

| 要素 | 说明 |
|:---|:---|
| **人与AI共同驱动** | Harness自身改版的那股力 |
| **人决定改成什么样算好** | 划边界与验收 |
| **AI在规矩内动手** | 规则内执行 |
