### 🏁 项目背景与选型逻辑

数据团队在埋点和指标承接场景中，最核心的痛点并非生成效率低，而是大量精力消耗在分散信息的拼接核对上：反复确认需求动作是否需要采集、回溯历史相似点位、校验指标口径的下游依赖、梳理新增字段的表结构改动链路，以及跨角色确认发布权限。
团队最终选择**Hermes Agent**而非通用智能体OpenClaw，核心原因是其具备持续在线、持久记忆和技能沉淀能力，原生匹配数仓场景的流程痛点，二者核心差异如下：

| 对比维度 | OpenClaw | Hermes Agent |
| :--- | :--- | :--- |
| 核心定位 | 个人通用执行助手 | 面向数据团队的长期协作智能体 |
| 记忆能力 | 窗口级临时记忆 | 面向历史口径、规则包和交付过程的长期沉淀 |
| 协作模式 | 个人桌面助理 | 嵌入飞书等协作平台，支持多人确认 |
| 交付特性 | 无审计链路 | 工作区、看板、系统预演、人工确认点共同生成可回放交付链路 |
| 适用场景 | 个人单次任务执行 | 数仓长期、协作、可审计的全链路流程 |

### 🧩 Hermes 四大原生核心能力

Hermes Agent 针对数仓场景痛点设计了四项原生能力，从底层解决传统智能体“关窗失忆”、经验无法复用等问题：
1.  **分层持久记忆**：采用短期会话/中期交互/长期知识/技能库四层结构，基于本地SQLite+FTS5全文检索实现，彻底避免“窗口关闭后历史口径丢失”的问题。
2.  **技能自动沉淀**：任务完成后自动将经验提炼为Markdown格式的技能文档并持续迭代，为“专家经验资产化”提供框架级支撑，文中的核心“规则包”完全构建在该机制之上。
3.  **多平台统一网关**：原生接入飞书、钉钉、企业微信等主流协作平台，智能体直接嵌入团队现有沟通场景，无需额外搭建独立工作台。
4.  **工具与扩展生态**：内置终端执行、定时任务、浏览器自动化等工具，企业内部系统可通过MCP命令封装实现稳定接入。

### 📊 落地收益与核心构件

基于上述能力底座，团队将埋点需求承接拆解为四个可追踪的工程构件，落地后已验证明确收益：
| 维度 | 落地结论 |
| :--- | :--- |
| 链路基础 | 需求入口接入工作看板，需求材料、讨论记录、预演结果和人工确认全部沉淀到同一独立工作区 |
| 效率收益 | 保守测算下，常规埋点需求的数据承接投入从0.5-1.0人日降至0.1-0.3人日；复杂需求从1-2人日降至0.3-0.6人日 |
| 风险门禁 | 缺材料、缺编码、外部系统异常等问题，可在正式写入生产前被预演和门禁机制提前拦截 |

### 🎯 核心设计边界：AI 做准备，人做决策

Hermes Agent 并非替代人工判断的“埋点生成器”，而是定位为**流程编排者**，核心边界是“把问题整理到足够可判断”：
- **AI 负责的工程化准备四步**：
  1.  把材料收齐：从PRD、飞书话题、会议纪要等多源材料提取上下文，区分已确认事实、待澄清问题和模型推断。
  2.  把历史找出来：自动检索同类点位、复用事件、指标口径、表结构等历史依据，优先判断是否可复用，再决定补充或新增。
  3.  把风险先预演：通过diff确认变更范围、dry-run提前校验写入条件、审计命名冲突等潜在问题，让风险在写入前暴露，避免评审后返工。
  4.  把过程留下来：完整沉淀确认人、变更记录、归档产物，让后续需求可回溯决策依据。
- **人工负责的最终判断**：保留业务语义确认、指标口径定义、风险接受度评估、生产放行四大核心权限，避免AI越权决策。

团队选择从低风险、高频重复的流程动作切入落地，而非直接追求全自动化，核心是提前拦截三类高风险问题：上下文缺失、规则漂移、责任越界，让真实规则在需求推进中被反复验证后，再沉淀到规则包和长期记忆中。

### ⚙️ 架构选型：单 Agent 编排 + 多 Skill 沉淀

团队对比了四类主流方案，最终放弃多Agent拆分模式，选择“单Agent编排+多能力模块+看板确认点”的架构，核心优势是保持统一上下文，避免多智能体场景下上下文同步、状态恢复的高成本问题：
| 方案 | 优势 | 不足 | 适配性判断 |
| :--- | :--- | :--- | :--- |
| 单段提示词 | 启动成本低，适配一次性问答 | 输出结构易漂移，无法沉淀规则和审计记录 | 仅适合局部生成能力，无法承接生产链路 |
| 多Agent拆分 | 角色边界清晰，适配高度并行任务 | 上下文同步、责任归属成本高，易将流程问题转化为协作问题 | 不适配当前场景，该场景更需要统一上下文和状态机 |
| 传统工作流 | 状态和审批可控，系统边界稳定 | 对非结构化文档、历史口径理解能力弱，经验沉淀不灵活 | 仅作为底层门禁和命令接口，不替代Agent |
| Hermes Agent + 能力模块 | 统一上下文、长期记忆、协作确认点可在同链路运行 | 需提前工程化规则包、工具返回和确认点 | 最适配埋点需求向可回放、可确认、可复用的团队流程转型 |

该架构下的Skill（能力模块）并非简单的工具清单，而是严格固化了5项流程契约：输入契约、动作边界、输出产物、失败处理、经验回写，将模型的即时发挥严格约束到可检查的流程中。目前已沉淀5类可跨场景复用的核心Skill：素材采集Skill、历史检索Skill、变更预演Skill、发布确认Skill、经验沉淀Skill，替换事实源和工具接口后，可快速迁移到指标发布、配置变更、数据质量排查等更多数据研发链路。

### 🔒 资产化与风险治理体系

团队将核心能力沉淀为四类可复用资产，让Hermes Agent从“会回答”升级为“能交接”：
1.  **规则资产化**：分层沉淀信息，临时信息留在单任务，可复用经验进入规则包，人工把关内容进入治理记忆，避免后续相似需求从零开始梳理。
2.  **协作可见化**：通过看板暴露阶段、阻断项和责任人，飞书承载澄清、驳回和确认语境，工作区留存全量证据和产物，让AI的每一步执行都可被团队感知。
3.  **上下文与事实源分层**：将任务背景、阶段结论、人工反馈、运行元数据分开存储，明确聊天仅补充语境，工作区负责留证，生产系统作为最终事实源。
4.  **结构化工具接口**：将查询、绑定、发布、验证等生产动作封装为参数明确、返回结构化、过程可审计的接口，越靠近写入环节，越严格执行“先预演、再确认、最后留痕”的流程。

上线前设置三道刚性门禁，任意环节缺失证据都无法推进生产写入：事实源门、预演门、责任门，将人的精力从重复核对中释放，聚焦到口径裁决、风险评估等核心判断环节。

### 🚀 后续落地路径

当前链路已完成需求流转跑通、风险前置拦截、规则资产沉淀的核心主线，下一阶段重点并非叠加更多自动化动作，而是做实证据口径：通过连续样本验证准备时间、交付周期、评审通过率、返工率等核心指标的优化效果，让所有指标与看板、日志、确认记录一一对应，为规模化落地提供工程基础。
