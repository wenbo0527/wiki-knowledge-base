## 一、大型项目架构Agent完整规划方案

### 1.1 核心挑战分析

| 核心挑战 | 问题描述 | 解决方案 |
|---------|---------|---------|
| 上下文爆炸 | 大型项目的文件数量远超200k上下文容量 | 分阶段执行策略，每次只处理一个模块 |
| 任务复杂度高 | 任务拆解粒度需要细化（10-20个子任务） | 多Agent协作分工，每个Agent专注一个子任务 |
| 执行时间长 | 中途容易放弃（速率限制、上下文溢出、中断） | 流式工具执行，模型输出出现tooluse标记立即执行 |
| 风险等级高 | 改完一个Bug，可能引爆三个新Bug | 一次只改一个模块，每改完一层跑完全部测试 |

### 1.2 三种任务类型对比

| 任务类型 | 复杂度 | 风险 | 执行策略 | 分阶段策略 |
|---------|-------|------|---------|-----------|
| Bug修复 | 低 | 高 | 快速响应（实时调度） | 单阶段：定位→修复→验证 |
| 功能开发 | 中 | 中 | 稳定交付（每日调度） | 三阶段：设计→开发→验证 |
| 代码重构 | 高 | 高 | 分阶段执行（每周调度） | 多阶段：10-20个子任务 |

### 1.3 五大核心原则

#### 原则1：一次只改一个模块

> AI在处理单点任务时成功率超过90%，但如果你让它"全面重构"，成功率会降到50%以下。

**执行策略**：
- 每改完一层，跑完全部测试，确认没问题再进下一层
- 严格按优先级一层一层来：P0→采集层→P0→SDK层→P1→Agent编排层→P2→基础设施层

#### 原则2：分阶段执行策略

**核心原则**：
- 大型项目的任务拆解粒度需要细化（拆解为10-20个子任务）
- 每个阶段单独执行，避免上下文爆炸
- 使用`/compact`命令压缩上下文，避免上下文溢出

#### 原则3：流式工具执行

**核心原则**：
- 绝大多数Agent是"等模型把话说完→解析工具→执行工具"
- Claude Code是"模型流式输出中只要出现tooluse标记，立刻就开始执行"
- 这种"流水线"作业的设计，将延迟压缩到了极致

#### 原则4：多Agent协作分工

**核心原则**：
- Claude Code本质上是一个Agent，一次只能专注干一件事
- 大型项目需要多个Agent并行协作（Bug修复Agent、功能开发Agent、代码重构Agent、测试验证Agent）
- OMC（oh-my-claudecode）是一个多智能体编排系统，负责协调、调度、优化

#### 原则5：Karpathy四原则（给AI装上"刹车"）

| 原则 | 问题描述 | 解决方案 |
|------|---------|---------|
| 原则1：Think Before Coding | 过度工程——你让它去修个按钮，它反倒给你搭了一整个组件库 | 先想清楚再动手，禁止过度工程 |
| 原则2：Follow Existing Patterns | 无视现有模式——项目里明明用的是Zustand，它偏要引入Redux | 遵循现有项目的模式，禁止引入无关依赖 |
| 原则3：No Unnecessary Dependencies | 乱加依赖——你从没要求过的npm包，它悄悄就给你装上了 | 禁止添加不必要的依赖 |
| 原则4：Ask When Uncertain | 自信地犯错——在不确定的时候不去询问，直接进行猜测 | 不确定时必须询问，禁止猜测 |

## 二、Claude Code五层架构解析

### 2.1 核心认知

> Claude Code从根本把自己定义为一个**端到端完整的Agent运行时系统**，而不是一个"聊天框 + 代码高亮"。

| 对比维度 | ChatGPT/Copilot | Claude Code |
|---------|-----------------|-------------|
| 定位 | 对话工具 | Agent运行时系统 |
| 架构 | 聊天框 + 代码高亮 | 五层完整架构 |
| 核心循环 | 你问→我答 | TAOR循环（Think-Act-Observe-Repeat） |
| 能力边界 | 只能生成代码片段 | 能完整执行编程任务 |
| 记忆系统 | 单次对话记忆 | 三层记忆（长期语义、情景、工作） |

### 2.2 五层架构详解

> Claude Code的代码量是512,000行，是一个完整的生产级系统。

| 层级 | 名称 | 核心功能 | 架构启示 |
|:---:|:---|:---|:---|
| 第1层 | 入口层（Entrypoints） | 统一路由CLI、桌面端、网页、IDE插件、SDK | 多端产品，入口层抽象决定能否多端协同 |
| 第2层 | 运行层 | REPL循环、状态机、Hook系统，核心是TAOR循环 | 85+个Hook点，覆盖Agent行为每个关键节点 |
| 第3层 | 引擎层 | 系统心脏，负责动态提示词组装，注入数百个提示碎片 | 光安全守则就高达5,677个token |
| 第4层 | 工具与能力层 | 内置约40个独立工具，每个工具均有严格的权限隔离 | 工具权限隔离是核心 |
| 第5层 | 基础设施层 | 管理提示缓存与远程控制，包含远程禁用的"杀向开关" | 安全控制是核心能力 |

### 2.3 TAOR循环

Claude Code运行层的核心是**TAOR循环**：

```
Think → Act → Observe → Repeat
```

- **Think**：理解任务，思考执行计划
- **Act**：调用工具，执行操作
- **Observe**：观察结果，评估状态
- **Repeat**：循环直到任务完成

### 2.4 三层记忆系统

| 记忆类型 | 说明 | 管理策略 |
|:---|:---|:---|
| 长期语义记忆 | 语义知识，容量有限 | 定期压缩清理（2200字符限制） |
| 情景记忆 | 对话序列 | 定期归档历史session |
| 工作记忆 | 当前上下文 | 按需拉取，绝不塞满 |

**Auto-Dream机制**：每24小时或5次会话后，系统会启动子代理进行记忆整合、清理噪声。

## 三、架构Agent的核心定位

### 3.1 定位定义

> 架构Agent是Claude Code的"**架构师+指挥官**"——负责架构决策、任务拆解、Claude Code调用、执行监控、质量验收。

| 定位维度 | 核心职责 |
|:---|:---|
| 架构决策 | 决定用什么架构模式（单体、微服务、MoE等） |
| 任务拆解 | 把复杂编程任务拆解为Claude Code可执行的子任务 |
| Claude Code调用 | 控制Claude Code调用哪些工具、执行哪些命令 |
| 执行监控 | 监控Claude Code的执行进度、错误、风险 |
| 质量验收 | 验收Claude Code的输出质量，决定是否需要重试 |

### 3.2 七层配置文件体系

| 文件 | 说明 |
|:---|:---|
| SOUL.md | 架构Agent的人格定义 |
| IDENTITY.md | 架构Agent的身份标识 |
| USER.md | 架构Agent的用户画像 |
| AGENTS.md | 架构Agent的多代理分工 |
| TOOLS.md | Claude Code工具配置（约40个独立工具） |
| HEARTBEAT.md | 定时任务（记忆整合、噪声清理） |
| MEMORY.md | 记忆存储（三层记忆管理） |

## 四、五个核心风险

| 风险 | 问题 | 解决方案 |
|:---|:---|:---|
| 工具权限隔离 | 不是所有工具都能随意调用 | 必须先授权再调用，filedelete/commandexecute禁止使用 |
| Hook系统覆盖 | 85+个Hook点，每个关键节点都要配置 | pretoolcall/posttoolcall、precommandexecute/postcommandexecute |
| 三层记忆管理 | 容量有限，需要按需拉取 | 长期记忆定期压缩、情景记忆定期归档、工作记忆绝不塞满 |
| 安全边界控制 | 涉及系统级操作、敏感数据访问 | 必须获得用户确认，基础设施层"杀向开关" |
| Token消耗监控 | 光安全守则就5,677个token | 长任务定期汇报Token消耗，优化提示词精简 |

5. **三层记忆管理**：长期语义、情景、工作记忆，按需拉取绝不塞满
6. **Auto-Dream机制**：每24小时或5次会话后记忆整合、清理噪声
7. **安全边界控制**：基础设施层"杀向开关"，防止失控执行
