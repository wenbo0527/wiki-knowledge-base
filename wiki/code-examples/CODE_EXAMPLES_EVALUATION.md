> **制定时间**: 2026-04-30
> **制定者**: 尼克·弗瑞 🕵️
> **定位**: 评估Code Examples质量，指导入库/维护决策
> **适用范围**: `wiki/code-examples/` 目录下所有代码样例

## 1. 评价维度

### 1.1 六角评价模型

| 维度 | 说明 | 权重 |
|------|------|------|
| **🔷 可运行性** | 代码能否实际执行 | 25% |
| **🔷 可读性** | 代码是否清晰易懂 | 20% |
| **🔷 可复用性** | 是否易于应用到其他场景 | 20% |
| **🔷 文档完整性** | README、注释是否充分 | 15% |
| **🔷 来源可靠性** | 来源是否可追溯 | 10% |
| **🔷 组合价值** | 是否易于与其他样例组合 | 10% |

### 1.2 评分标准

| 等级 | 分数 | 说明 |
|------|------|------|
| ⭐⭐⭐⭐⭐ | 90-100 | 卓越，可作为最佳实践 |
| ⭐⭐⭐⭐ | 75-89 | 优秀，满足大多数场景 |
| ⭐⭐⭐ | 60-74 | 良好，可供参考 |
| ⭐⭐ | 45-59 | 一般，需要改进 |
| ⭐ | <45 | 较差，不建议使用 |

## 2. 详细评价标准

### 🔷 可运行性 (25%)

| 等级 | 标准 |
|------|------|
| ⭐⭐⭐⭐⭐ | 有完整依赖声明 + 可运行 + 有输出示例 |
| ⭐⭐⭐⭐ | 有完整依赖声明 + 可运行 |
| ⭐⭐⭐ | 有依赖声明 + 基本可运行 |
| ⭐⭐ | 依赖不完整但可补充 |
| ⭐ | 代码无法运行 |

**检查清单**:
- [ ] `requirements.txt` 或 `pyproject.toml` 完整
- [ ] `main()` 函数存在
- [ ] 运行无报错
- [ ] 输出符合预期

### 🔷 可读性 (20%)

| 等级 | 标准 |
|------|------|
| ⭐⭐⭐⭐⭐ | 变量命名清晰 + 有注释 + 模块化 |
| ⭐⭐⭐⭐ | 命名清晰 + 有注释 |
| ⭐⭐⭐ | 基本可读 |
| ⭐⭐ | 需要努力理解 |
| ⭐ | 难以理解 |

**检查清单**:
- [ ] 变量/函数命名有意义
- [ ] 关键逻辑有注释
- [ ] 代码结构清晰
- [ ] 无magic number/strings

### 🔷 可复用性 (20%)

| 等级 | 标准 |
|------|------|
| ⭐⭐⭐⭐⭐ | 参数化 + 有配置 + 易于修改 |
| ⭐⭐⭐⭐ | 参数化 + 易于修改 |
| ⭐⭐⭐ | 需要小改动可复用 |
| ⭐⭐ | 需要较大改动 |
| ⭐ | 只能原样使用 |

**检查清单**:
- [ ] 硬编码值参数化
- [ ] 配置与逻辑分离
- [ ] 接口有文档
- [ ] 无业务逻辑硬编码

### 🔷 文档完整性 (15%)

| 等级 | 标准 |
|------|------|
| ⭐⭐⭐⭐⭐ | README完整 + 示例丰富 + 更新日志 |
| ⭐⭐⭐⭐ | README完整 + 有示例 |
| ⭐⭐⭐ | README基本完整 |
| ⭐⭐ | 只有代码注释 |
| ⭐ | 无文档 |

**检查清单**:
- [ ] README.md 存在
- [ ] 功能说明清晰
- [ ] 使用示例完整
- [ ] 来源标注明确

### 🔷 来源可靠性 (10%)

| 等级 | 标准 |
|------|------|
| ⭐⭐⭐⭐⭐ | 实际项目 + 来源明确 + 可验证 |
| ⭐⭐⭐⭐ | 来源明确 + 基本可验证 |
| ⭐⭐⭐ | 有来源标注 |
| ⭐⭐ | 来源模糊 |
| ⭐ | 无来源 |

**检查清单**:
- [ ] 标注来源Insight/项目
- [ ] 可追溯到原始需求
- [ ] 可验证真实性

### 🔷 组合价值 (10%)

| 等级 | 标准 |
|------|------|
| ⭐⭐⭐⭐⭐ | 易于组合 + 接口清晰 + 有组合示例 |
| ⭐⭐⭐⭐ | 易于组合 |
| ⭐⭐⭐ | 基本可组合 |
| ⭐⭐ | 组合需要较多改动 |
| ⭐ | 难以组合 |

**检查清单**:
- [ ] 模块化设计
- [ ] 接口定义清晰
- [ ] 提供了组合示例

## 3. 入库决策

### 3.1 入库标准

| 类型 | 入库阈值 | 说明 |
|------|----------|------|
| **正式入库** | ≥60分 | 可进入正式代码样例库 |
| **暂存观察** | 45-59分 | 需要改进后再入库 |
| **不入库** | <45分 | 不符合标准，不入库 |

### 3.2 状态定义

| 状态 | 标识 | 说明 | 分数范围 |
|------|------|------|----------|
| **推荐** | 🟢 | 最佳实践 | ≥80 |
| **标准** | 🔵 | 普通样例 | 60-79 |
| **待改进** | 🟡 | 需改进 | 45-59 |
| **废弃** | 🔴 | 不推荐 | <45 |

### 3.3 状态转换

```
🟡待改进 → 🔵标准: 改进后达到60分
🟡待改进 → 🔴废弃: 30天内未改进
🔵标准 → 🟢推荐: 社区反馈优秀
🔵标准 → 🔴废弃: 发现严重问题
```

## 4. 评价流程

### 4.1 评价时机

| 时机 | 说明 |
|------|------|
| **入库评价** | 新代码样例入库前 |
| **定期复审** | 每季度复审一次 |
| **问题触发** | 发现问题时复审 |
| **贡献者请求** | 贡献者自评 |

### 4.2 评价流程

```
┌─────────────────────────────────────────────────────────────┐
│                    代码样例评价流程                          │
├─────────────────────────────────────────────────────────────┤
│                                                              │
│  Step 1: 自评                                               │
│  └── 贡献者对照检查清单自评                                  │
│                                                              │
│  Step 2: 六角评分                                           │
│  └── 按六个维度打分                                          │
│                                                              │
│  Step 3: 综合评级                                           │
│  └── 计算加权总分，确定等级                                   │
│                                                              │
│  Step 4: 入库决策                                           │
│  ├── ≥60分 → 正式入库                                       │
│  ├── 45-59分 → 暂存，待改进                                 │
│  └── <45分 → 退回                                          │
│                                                              │
│  Step 5: 状态标记                                           │
│  └── 添加状态标签到README                                    │
│                                                              │
└─────────────────────────────────────────────────────────────┘
```
