## 一、产品架构图

### 架构分层逻辑

参考消保行业最佳实践和监管要求（《银行业保险业消费投诉处理管理办法》），消保系统的核心是**投诉全流程闭环管理**——从投诉受理到溯源整改，每个环节对应一层系统架构。


| 层次    | 回答什么     | 对应监管流程                   | 行业实践参考                   |
| ----- | -------- | ------------------------ | ------------------------ |
| 交互层   | 谁在用什么界面  | 各角色在投诉各环节的操作入口           | "畅通投诉渠道"（监管第七条）          |
| 能力层   | 系统提供什么能力 | 受理→分办→处理→答复→归档→溯源整改      | "前端预警→中台调度→后端根治"（仪征农商银行） |
| 数据层   | 数据怎么管    | 投诉数据、业务数据、标签数据、外部数据的统一管理 | "投诉管理信息系统建设"（监管第七条）      |
| 基础设施层 | 依赖什么外部支撑 | 数据来源、外部系统、总行能力           | "投诉管理信息系统建设"（监管第七条）      |


**核心设计原则**：底层能力做通用引擎，上层按角色做交互开发。引擎对前端无感——工单流转引擎同时支撑客服和催收，质检引擎同时覆盖语音和文本，业务执行引擎同时服务坐席和支撑岗。数据层独立管理，每个数据域有且只有一个真相源，避免数据双向同步冲突。

**消保业务分类体系**：消保业务按三个维度交叉分类，所有工单创建时必须打上三个维度的标签。

维度一：工单性质（客户诉求类型）——决定流程深度


| 工单性质 | 流程深度            | 量级占比           |
| ---- | --------------- | -------------- |
| 咨询   | 受理→答复→归档        | 约88.5%（亿联银行数据） |
| 投诉   | 完整六阶段+溯源整改      | 约5%            |
| 外部转办 | 完整六阶段+溯源整改+监管报送 | 约6.6%          |
| 调解   | 受理→对接外部调解→跟踪→归档 | 少量             |
| 信息开具 | 受理→开具→交付→归档     | 中等             |
| 建议   | 记录→归档           | 少量             |
| 表扬   | 记录→归档           | 极少             |


维度二：业务类别（对齐央行标准JR/T 0169-2018，消金裁剪版）——决定监管报送口径


| 业务类别   | 央行标准编码 | 消金映射       |
| ------ | ------ | ---------- |
| 贷款     | 02     | 个人消费贷款（核心） |
| 债务催收   | 12     | 催收合规（核心）   |
| 个人金融信息 | 09     | 数据安全/隐私保护  |
| 定价收费   | 07     | 息费透明/IRR   |
| 支付结算   | 05     | 还款相关       |
| 其他     | 14     | 营销合规等      |


维度三：投诉原因（对齐央行标准12大类，消金聚焦版）——决定溯源引擎标签体系的第一级


| 投诉原因         | 央行标准编码 | 消金权重  |
| ------------ | ------ | ----- |
| 债务催收方式和手段    | 12     | ★★★★★ |
| 定价收费         | 07     | ★★★★  |
| 管理制度、业务规则与流程 | 03     | ★★★★  |
| 信息披露         | 05     | ★★★   |
| 消费者信息安全      | 11     | ★★★   |
| 服务态度及服务质量    | 01     | ★★    |
| 营销方式和手段      | 04     | ★★    |
| 合同条款         | 09     | ★★    |
| 消费者自主选择权     | 06     | ★     |
| 消费者资金安全      | 10     | ★     |


一个工单 = 工单性质 × 业务类别 × 投诉原因。例如：投诉 × 债务催收 × 催收方式和手段。

### 分层逻辑同业对比总览

消保系统的架构设计，不同类型机构因核心驱动力不同，分层逻辑差异显著：


| 维度         | 银行（TRS数星方案）                    | 头部消金（招联）                     | 互金（奇富科技）               | 我们                         |
| ---------- | ------------------------------ | ---------------------------- | ---------------------- | -------------------------- |
| **核心分层**   | 事前审查→事中管控→事后监督（三段式）            | 未病先防→欲病早治→已病综治（三层防线）         | 数据模型驱动→源头管控→协同打击（攻防式）  | 交互层→能力层→底座层（三层架构）          |
| **设计出发点**  | 监管合规驱动，覆盖消保全流程                 | AI驱动，从源头闭环解决投诉隐患             | 黑灰产治理驱动，技术反制为主         | 投诉压力驱动，从投诉工作流倒推            |
| **数据基础**   | 全口径投诉管理大数据平台，整合10+类异构数据，月处理百万级 | 自研智鹿大模型+天罡客户洞察系统，60+业务场景实时洞察 | 数据模型精准识别，年干预黑产用户12万+   | 数仓/Doris+客户中心360，批量提取管道已启动 |
| **AI渗透深度** | 大模型Agent应用于智能审查、投诉处理、诉后分析      | 消保智能体全流程覆盖，客服效率提升80%         | 反欺诈专家策略系统，AI深度学习+大数据分析 | 依赖总行AI能力，自建规则引擎做降级         |


**关键差异**：银行方案以"合规审查"为重心（事前审查模块最重），消金方案以"投诉预防+黑产识别"为重心，互金方案以"技术反制黑灰产"为重心。我们的架构从投诉工作流倒推，与消金同业逻辑更接近，但AI渗透深度和数据整合能力是主要差距。

**我们的选择**：基于三个现实约束——AI能力依赖总行且当前不足、外网云桌面受阻导致外部数据管道不通、年处理监管台账3000-4000条（数据量远不及银行百万级），我们选择从投诉工作流倒推而非从合规审查正推，Phase 1先填断点而非先建AI能力。这不是能力不足的妥协，而是与当前业务痛点和资源约束匹配的务实路径——先把投诉从受理到归档的主干道跑通，再逐步挂上质检、预警、归因等辅助引擎，最后追AI效能。

**第一层：交互层——用户看到什么**

交互层按使用角色分为四个工作台（顶层维度），每个工作台内部按「事前/事中/事后」组织功能（二级维度）。顶层按角色分是因为交互层是给人用的，第一分类维度应该是「谁在用」；二级按阶段分是因为管理者需要看到时间维度的逻辑关系，坐席和支撑岗的功能几乎全是「事中」，不需要拆分。

**坐席工作台**（一线坐席日常使用）——纯事中工作台：

- 事中（接住投诉）：电话工作台[2]、工单创建管理[4]、客户画像查询[3]、知识库检索[1]、消保业务操作[4]、短信/邮件发送[4]、监管转诉建单[3]、IVR自主办理[2]、在线客服[4]
- 核心设计：总行呼叫中心做底座，自研工单系统做上层，在交互层融合为一个界面

**业务执行台**（支撑岗使用）——纯事中工作台：

- 事中（执行业务操作）：证明开具[4]、发票开具[4]、合同出具[4]、纾困方案登记[1]、审批流转[3]、试算查询[4]
- 支撑岗处理坐席流转过来的业务操作，本质上是工单流转引擎驱动的业务执行能力

**管理驾驶舱**（消保管理层+运营管理使用）——横跨事前+事中+事后：

- 事前（防住投诉+搭好舞台）：预警监控[1]、黑名单管理[3]、知识库管理[1]、分单规则配置[3]、预警阈值设置[1]、标签体系维护[1]、权限管理[4]
- 事中（管住过程）：质检管理[1]、审批流转[3]、监管转诉建单[3]、排班管理[1]
- 事后（看住效果）：溯源归因[1]、整改追踪[1]、考核评价[1]、看板管理[1]、月度考核/培训[1]
- 覆盖投诉闭环管理（溯源→整改→考核）和客服运营管理（排班→看板→培训），行业方案中运营管理是驾驶舱的子功能，不独立设入口。事前防线新增「规则配置与系统管理」类功能——管理者搭好舞台让坐席唱戏

**消费者之家**（客户自助使用）——事中为主、事后补充：

- 事中（自助办理）：在线客服[4]、投诉进度查询[4]、IVR自助办理[2]
- 事后（反馈评价）：满意度评价[4]

**第二层：能力层——系统做什么**

能力层抽象为五个通用引擎，对应投诉处理标准流程"受理→分办→处理→答复→归档→溯源整改"：

**①工单流转处理引擎**——投诉从受理到结案的核心链路。能力包括：工单创建/分配、节点流转/审批、状态更新/关单、协办/转办、批量作业。对应监管要求的"受理→分办→处理→答复→归档"全流程。同时支撑客服和催收两个业务线，引擎对前端无感。

**②预警引擎**——投诉异常信号的捕获和处理。能力包括：投诉量异常监测、监管件升级预警、催收频次超限预警、重复投诉预警、规则引擎打底→AI辅助增强。预警是「防投诉」的核心能力，独立于工单流转。

**③溯源引擎**——投诉根因分析与整改闭环。能力包括：三级标签体系（投诉标签→根因标签→整改标签）、整改任务派发→部门认领→完成确认→效果验证、考核评价→部门绩效、知识库更新（整改结论回流）。溯源归因是结案之后的独立动作，不是工单流转的附属品。

**④识别引擎**——黑灰产识别与名单管理。能力包括：黑灰产识别（规则引擎初版→AI模型进阶版）、名单管理（黑名单/投诉特例名单/营销黑名单/异常代理库/敏感词库）。识别和管理是两件事——识别是「发现谁在搞事」，管理是「记住谁搞过事」，但两者强关联，统一在一个引擎内。当前名单分散、定义不统一，需整合后推送到客户中心。

**⑤质控引擎**——覆盖语音和文本两类内容的质检能力。能力包括：语音质检、文本质检、实时质检、关键词识别、情绪识别。依赖总行AI能力，当前总行质检能力不足（存储量少/出结果慢/准确率低），需以"质检中台"名义向总行提需求。

**第三层：数据层——数据怎么管**

数据层独立管理，每个数据域有且只有一个真相源，避免数据双向同步冲突。四条数据管道支撑上层引擎的数据需求。

**投诉数据域**（真相源：工单中心）：工单全生命周期数据、投诉标签、处理记录、满意度数据。

**业务数据域**（真相源：数据中心）：客户信息、借据数据、还款数据、催收记录。批量提取管道（T+1，已启动）和实时数据管道（T+0，待建）是两条核心管道。

**标签数据域**（真相源：溯源中心）：投诉标签→根因标签→整改标签（三级下钻）、整改追踪记录、考核评价数据。

**外部数据域**（真相源：渠道接入层）：监管转办数据、12378/12345数据、黑猫投诉数据、供应商投诉数据。外部数据管道（准实时，待建）依赖外网云桌面启用。

**身份匹配管道**（实时，已含在提取模块）：监管台账明文身份证↔老客服系统掩码身份证的自动转换。

**文件存储**（新增待建设）：工单材料、通话录音、合同文件的统一存储。

**第四层：基础设施层——依赖什么外部支撑**

基础设施层分为三类外部依赖：

**触达能力**（复用总行，不自建）：呼叫中心(华为)——坐席服务/通话录音/软电话；短信平台；IVR平台——语音菜单/自助办理；在线客服平台；通话录音——录音存储/调阅。呼叫底座保留在总行老客服系统，上层功能封装在自研新工单系统。

**核心业务操作接口**（统一封装，客服和催收共用）：核心系统（借据/还款/产品数据，只读不写）；试算系统；票务系统；影像系统（合同/文件影像调阅）；外呼H5（外呼页面嵌入）；催收系统（催收记录/催收标签）；调解/案件管理系统（司法调解+转诉案件管理，公司内部系统）；OA系统（审批流程/资金审批，联动不替代）；外网云桌面（外网数据中转，待启用，账号已批但受阻2个月）。

**合规知识库**（支撑上层知识检索能力）：新产品知识（市场部提供后手动维护）；业务规则（征信/贷后/强制执行规则等，各业务部门提供）；话术模板（各场景标准话术，业务部门+消保部自建）；报送系统（监管报送相关数据）。当前痛点：知识库维护全靠线下Excel，手动向各部门收集更新。新产品上线时，消保审查在OA走流程，但知识库不会自动从OA获取更新信息。

### 交互层详解——四个角色四个工作台

> 交互层顶层按角色分（谁在用），二级按阶段分（事前/事中/事后）。坐席工作台和业务执行台几乎全是「事中」，不需要按阶段拆分；管理驾驶舱横跨三个阶段，按阶段组织更清晰；消费者之家以事中为主、事后补充。

#### 坐席工作台（一线坐席日常使用）——纯事中工作台

坐席工作台是客服坐席的统一作业入口，覆盖从接听到建单到处理的全流程。核心设计：总行呼叫中心做底座，自研工单系统做上层，在交互层融合为一个界面。坐席的日常操作全部是「事中处置」——投诉来了接住、工单来了处理，没有事前预防和事后分析的职责。


| 功能      | 归属      | 说明                                    |
| ------- | ------- | ------------------------------------- |
| 电话工作台   | 总行呼叫中心  | 呼叫底座复用总行（华为），上层做封装，与电销系统架构一致          |
| 工单创建管理  | 自研新工单系统 | 投诉/协商还款类交易工单在新系统创建；简单咨询在老系统建咨询单留档     |
| 客户画像查询  | 自研（待建）  | 客户进线自动展示信息、借据、风险标签；当前仅有零散标签           |
| 知识库检索   | 自研（待建）  | 大模型实时识别客户诉求，推送匹配内容；当前线下Excel          |
| 消保业务操作  | 自研新工单系统 | 停催/停扣/关授信等操作；已迁移                      |
| 短信/邮件发送 | 自研新工单系统 | 坐席与客户沟通的触达出口；已迁移                      |
| 监管转诉建单  | 自研新工单系统 | 监管/12378/12345/黑猫名单建单；当前手动下载Excel逐条建单 |
| IVR自主办理 | 总行IVR平台 | 客户按键自助操作（开证明/查信息）；固定模板，不调知识库          |
| 在线客服    | 自研新工单系统 | APP/小程序在线客服；徐州2名专职人员负责                |


#### 业务执行台（支撑岗使用）——纯事中工作台

支撑岗处理坐席流转过来的业务操作——开证明、开发票、出合同、处理纾困方案。这些功能本质上是工单流转引擎驱动的业务执行能力，全部属于「事中执行」。


| 功能     | 归属      | 说明                                   |
| ------ | ------- | ------------------------------------ |
| 证明开具   | 自研新工单系统 | 已迁移，调用票务系统接口                         |
| 发票开具   | 自研新工单系统 | 已迁移，批量开票半自动化（系统匹配→人工确认→批量生成）         |
| 合同出具   | 自研新工单系统 | 已迁移，调用营销平台接口                         |
| 纾困方案登记 | 自研（待建）  | 当前线下WPS登记→支撑组人工处理；理想：工单系统内直接发起→流转→审批 |
| 审批流转   | OA+自研联动 | 息费减免→OA审批→结果回写工单；当前部分联动              |
| 试算查询   | 自研新工单系统 | 调用核心系统试算接口                           |


#### 管理驾驶舱（消保管理层+运营管理使用）——横跨事前+事中+事后

驾驶舱是唯一横跨三个阶段的工作台。管理者需要同时看到「防住投诉」（事前）、「管住过程」（事中）、「看住效果」（事后），按阶段组织功能让管理视角的逻辑关系更清晰。

**事前防线——防住投诉**

#### 交互层同业对标

**分类逻辑对比**：交互层怎么分，行业有三种做法——按流程阶段分（领雁：事前审查平台→事中处置系统→事后溯源系统）、按功能域分（TRS：审查+投诉+预警各自独立）、按角色分（我们：坐席+支撑+管理+客户四个工作台）。我们选择「角色为主、阶段为辅」——顶层按角色分（谁在用），二级按阶段分（事前/事中/事后）。原因：消金80%的日常操作堆在「事中」，按阶段分顶层会造成「事中」入口过重；管理驾驶舱横跨三个阶段，拆到三个入口反而增加管理者认知负担。

**坐席工作台**：招联已实现智鹿大模型实时话术推荐，客服操作效率提升80%；TRS方案将审查+投诉+预警封装为统一数字化平台入口。我们当前是总行呼叫中心底座+自研工单系统上层融合，AI辅助能力为零，话术推荐和实时质检提示均待建设。Phase 2起以规则引擎打底，Phase 3向总行AI能力对接，与同业从规则到AI的演进路径一致。

**业务执行台**：招联通过智鹿智能体匹配协商方案，已实现客服效率提升80%；马上消费在"消费者之家"中整合延期/分期等还款安排，客户可通过官方渠道自助办理。我们当前纾困方案仍在线下WPS登记，系统化是Phase 1优先事项。

**管理驾驶舱**：招联的"天罡客户洞察系统"实现了监控→诊断→溯源→预警→评价一体化；TRS方案将消保审查+投诉管理+监测预警一体化封装；领雁科技用"管理驾驶舱"命名管理层入口，已成为行业共识。我们的驾驶舱功能类似但尚未建设，当前均为线下Excel和人工操作。Phase 1先复用数字社区+问数产品做报表过渡，Phase 2起逐步建设驾驶舱各模块。驾驶舱内部按「事前防线→事中管控→事后治理」组织，与同业「事前/事中/事后」逻辑一致，但入口统一不拆分。

**消费者之家**：招联已建立"自服务体系"，客户可自主解决部分问题，有效减少进线量；马上消费的"消费者之家"线上专区整合了投诉受理+纠纷调解+征信异议一站式入口。我们IVR自助办理仅固定模板、不调用知识库，客户端自助能力是明显短板。Phase 2-3需重点补足IVR智能自助和消费者之家一站式入口。

### 能力层详解——五个通用引擎

#### 工单流转处理引擎

投诉从受理到结案的核心链路。对应监管要求的"受理→分办→处理→答复→归档"全流程。**同时支撑客服和催收两个业务线**，引擎对前端无感。


| 能力      | 说明                         | 行业实践              |
| ------- | -------------------------- | ----------------- |
| 工单创建/分配 | 统一建单+恢复分单规则（渠道×类型×紧急度）     | 监管要求"及时受理各项投诉并登记" |
| 节点流转/审批 | 工单在客服/征信/贷后间流转；OA审批联动      | "受、转、办"处理机制       |
| 状态更新/关单 | 处理完成→与客户达成一致→关单            | 监管要求"15个工作日内处理完毕" |
| 协办/转办   | 跨部门协办；客服转诉+催收转诉统一入口        | 投诉联席会议机制（复杂投诉）    |
| 批量作业    | 批量建单/批量开票/批量开证明（半自动）       | 消金独有：监管台账批量导入     |
| 业务执行    | 票据开具/合同出具/证明开具/试算计算/纾困方案匹配 | 对接下游业务系统完成具体操作    |


**说明**：业务执行（原「业务开具引擎」）是工单流转的下游动作——工单流转到「处理」节点后，需要执行具体的业务操作（开票、开证明、出合同、试算、纾困方案匹配）。这些操作和工单流转强耦合，作为工单流转引擎的子模块更合理。

**同业对标**：TRS浦发项目已实现6大客服分析因子覆盖3000+标签，智能标签识别准确率达90%，消保数据处理效率提升20倍；招联采用"四精体系"（精确分类+精准施策+精细度量+精锐组织），问题一次性解决率90%。我们Phase 1从5大类15小类起步是务实选择，但需规划向TRS级别的标签体系演进路径。

#### 预警引擎

投诉异常信号的捕获和处理。预警是「防投诉」的核心能力，独立于工单流转——工单流转管的是「来了怎么办」，预警管的是「怎么不再来」。


| 能力       | 说明                | 现状          |
| -------- | ----------------- | ----------- |
| 投诉量异常监测  | 单日/单周投诉量超阈值自动告警   | 无           |
| 监管件升级预警  | 监管转办件超时未处理/重复投诉升级 | 无           |
| 催收频次超限预警 | 催收触达频次超监管要求       | 无           |
| 重复投诉预警   | 同一客户短期内重复投诉       | 无           |
| 规则引擎     | 规则引擎打底→AI辅助增强     | 无，Phase 2建设 |


**同业对标**：招联"天罡客户洞察系统"实现监控→诊断→溯源→预警→评价一体化，60+业务场景实时洞察；TRS方案将监测预警与投诉管理一体化封装。我们预警能力为零，Phase 2从规则引擎起步，Phase 3向AI辅助增强演进。

#### 溯源引擎

投诉根因分析与整改闭环。溯源归因是结案之后的独立动作——找根因、推整改、追效果，不是工单流转的附属品。


| 能力     | 说明                      | 现状                  |
| ------ | ----------------------- | ------------------- |
| 三级标签体系 | 投诉标签→根因标签→整改标签（三级下钻）    | 无，Phase 2从5大类15小类起步 |
| 整改任务派发 | 整改任务→部门认领→完成确认→效果验证     | 无                   |
| 考核评价   | 投诉处理时效/重复投诉率/整改完成率与绩效挂钩 | 无                   |
| 知识库更新  | 整改结论回流到坐席知识库            | 无                   |


**同业对标**：TRS浦发项目6大客服分析因子覆盖3000+标签，智能标签识别准确率90%；某银行处理100万+条历史工单后建出9大类45小类标签体系+三级下钻。我们Phase 2从5大类15小类轻量版起步，Phase 3向9大类45小类完整版演进，与TRS从标签到模型的路径一致。

#### 识别引擎

黑灰产识别与名单管理。识别和管理是两件事——识别是「发现谁在搞事」，管理是「记住谁搞过事」，但两者强关联，统一在一个引擎内。


| 能力     | 说明                   | 现状              |
| ------ | -------------------- | --------------- |
| 黑灰产识别  | 规则引擎初版→AI模型进阶版       | 无，Phase 2规则引擎起步 |

| 营销黑名单  | 客户要求屏蔽营销，推送至触达平台做频控  | 有，手动维护          |
| 异常代理库  | 代理维权/反催收联盟信息         | 无，待建设           |
| 敏感词库   | 客户敏感词+催收备注，统一推送到客户中心 | 分散，定义不统一        |


**会议特别指出**：客服和催收都会给客户打标签，当前标签分散、定义不统一，需统一整合后推送到客户中心。包含催收备注、敏感词等多类标签。客服进线时客户使用的非预留号码信息也需补充，方便催收后续联系客户。

**同业对标**：TRS浦发项目的"疑似黑产识别模型"已产品化，浦发信用卡场景与我们高度相似（代理投诉占比25%-30%），采用模型+规则双驱动；招联累计识别灰黑产号码6000+，定位疑似代理投诉近7万件；奇富科技的"反欺诈专家策略系统"集成欺诈识别→策略制定→情报分析→案件处理四大模块，年干预黑产用户12万+，黑产投诉占比下降54%，协同警方立案12起抓获253人。我们Phase 2从规则引擎起步，Phase 3向识别→处置闭环演进，与TRS从模型到产品的路径一致。

#### 质控引擎

覆盖语音和文本两类内容的质检能力。**依赖总行AI能力**，当前总行质检能力不足（存储量少/出结果慢/准确率低），需以"质检中台"名义向总行提需求。

| 关键词识别 | 敏感词/违规话术识别    | 总行能力准确率低         |
| 情绪识别  | 客户/坐席情绪识别     | 无                |


**同业对标**：平安信用卡的"质检中台"已覆盖催收/营销/客服三场景，统一能力输出——我们已采纳此思路，以"质检中台"名义向总行提需求；TRS方案应用大模型Agent实现智能审查和热词实时监测；招联智鹿大模型实现语音分析+意图识别+情绪识别+实时话术推荐+违规预警。我们Phase 2从催收合规起步，Phase 3扩展至营销+客服+情绪识别，与平安"质检中台"从单场景到多场景的演进路径一致。

## 二、业务流程图

### 2.1 消保投诉处理标准流程（行业最佳实践）

根据《银行业保险业消费投诉处理管理办法》和行业实践，消保投诉处理的标准闭环为六个阶段：

**受理**：统一渠道受理，及时登记告知客户。畅通投诉渠道，在各渠道公布投诉电话、通讯地址。

**分办**：按类型/紧急度/属地分配给对应处理人。建立"受、转、办"处理机制，明确各部门管理职责。

**处理**：调查核实→定方案→审批→执行。处理时限原则上不超过15个工作日，复杂的不超过60个工作日。

**答复**：处理结果告知客户。发现产品或服务确有问题的，应立即采取措施予以补救或纠正。

**归档**：结案数据归档，供后续分析。投诉处理过程需记录并保存。

**溯源整改**：找到根因→推给业务→追踪整改→考核闭环。对每起投诉追溯至业务源头、制度流程或管理环节，力求从根本上解决问题。

仪征农商银行实践（投诉量下降73.15%）：前端预警——苗头性投诉上报机制，力争矛盾化解在萌芽状态；中台调度——转办、督办与协调，复杂投诉启动联席会议；后端根治——"处理一个投诉，解决一类问题"，整改措施固化。

**同业对标**：招联消保智能体采用"三层防线"模式（未病先防→欲病早治→已病综治），覆盖60+业务场景实时洞察，问题一次性解决率达90%。仪征农商银行的73.15%投诉量下降是流程治理的成果，招联的90%一次性解决率则是AI赋能的结果。我们的三阶段建设路径（填断点→建闭环→追效能）与这两个案例的演进逻辑一致。

---

### 2.2 客服进线主流程

客户通过三个渠道进入：400热线进线、APP/小程序在线客服、IVR自助服务。

**在线客服路径**：APP/小程序在线客服（徐州2名专职人员）接待。简单咨询直接回复；投诉/协商还款则创建工单，进入主流程。

**IVR路径**：客户按键自助操作——输入身份证号可自主办理（官授信客户自主发起停催/停扣/关授信，开证明引导至小程序操作）；坚持转人工则询问咨询还是投诉，转接对应接线客服。

**400热线路径**：坐席接听电话，展示客户画像（当前仅零散标签）。根据诉求分流：简单咨询（查信息/回答业务知识）在老系统建咨询单留档；投诉处理在新工单系统创建交易工单；协商还款/纾困方案在新工单系统创建交易工单。

工单创建后进入标准六阶段：

**受理**：工单创建（新工单系统），自动打标（渠道来源/紧急程度/是否监管件），恢复分单规则（渠道×类型×紧急度）。

**分办**：工单按类型分配——客诉人员、征信人员、贷后协助人员。工单仅在客服、征信、贷后部门间流转。

**处理**：联系客户（电话/短信/邮件）→查询关联数据（客户/借据/催收记录）→定方案（息费减免/协商还款/纾困方案）→审批联动（息费减免→OA审批→结果回写）→执行方案。分为单笔作业（审批联动/协商还款/方案执行）和批量作业（批量建单/批量开票/批量开证明，半自动：系统匹配→人工确认→批量生成）。

**答复**：与客户达成一致，处理结果告知客户。

**归档**：关单，工单结案时统计风险点/升级投诉/有责判定，满意度回访后归档。

**溯源整改**：投诉标签→根因标签→整改标签（三级下钻），整改任务派发→部门认领→完成确认→效果验证，考核评价→部门绩效，知识库更新（整改结论回流到坐席知识库）。

**同业对标**：招联通过智鹿智能体实现自动分类+话术推荐，客服操作效率提升80%；TRS浦发项目智能标签识别准确率达90%，6大客服分析因子覆盖3000+标签。我们当前无AI能力，依赖人工分类和判断，Phase 2的溯源归因和Phase 3的三级标签完整版可参考TRS的标签体系演进路径。

### 2.3 监管转诉流程

监管/信访/12378/12345/黑猫平台将投诉名单通过邮件或Excel发送。

**现状**：手动下载Excel，手动在新工单系统逐条建单。痛点：单次13000条逐户手工操作；身份匹配困难（监管台账明文身份证 vs 老客服系统掩码身份证）。

**理想状态**：监管台账上传→自动解析→批量建单；身份匹配管道（明文↔掩码自动转换）；外部数据管道（12378/12345/黑猫自动同步）。依赖外网云桌面启用进度。

建单后进入主流程（分办→处理→答复→归档→溯源整改）。

**同业对标**：TRS浦发项目已将监管转办案件材料收集从1周缩短至最快1天，说明自动化建单在银行端已是成熟方案。我们的批量建单半自动化（系统匹配→人工确认→批量生成）是务实过渡，但需尽快推进。

### 2.4 转诉流程（客服与催收统一）

**现状——割裂**：客服转诉走客服工单系统→OA审批（客服流程）；催收转诉走催收工单系统→OA审批（催收流程）。两套流程、两套审批、数据不互通。

**理想状态——统一**：客服转诉和催收转诉统一归到消保工单系统，统一流转、统一OA审批。一个引擎、一套流程、数据互通。工单流转处理引擎同时支撑客服和催收。

**同业对标**：转诉流程统一是消金独有需求，银行方案中无直接对标（银行催收外包为主，内部不设催收转诉通道）。招联通过消保智能体实现全渠道统一入口，客服和催收共用智鹿大模型能力。我们的"一个底层、两个上层"设计思路与招联的统一入口逻辑一致，但实现路径不同——招联靠AI统一，我们靠引擎统一。

### 2.5 IVR分流流程

客户拨打400热线后进入IVR语音菜单。按键1：业务咨询→播放固定话术。按键2：业务办理→输入身份证号自主操作（官授信客户可自主发起停催/停扣/关授信；开证明引导至小程序操作；其他引导至对应渠道）。按键3：投诉/协商→转接对应接线客服。坚持转人工→询问咨询还是投诉→转接对应接线客服。IVR使用固定模板，不调用知识库。

**同业对标**：招联IVR已接入智鹿大模型，客户可通过自然语言描述诉求，系统自动识别并引导至对应服务；马上消费"消费者之家"整合投诉受理+纠纷调解+征信异议一站式入口，大幅减少人工进线量。我们IVR仍为固定模板、不调用知识库，客户端自助能力是明显短板，Phase 2-3需重点补足。

---

### 2.6 纾困方案处理流程

客户来电或在线客服提出纾困需求后，坐席登记需求。

**现状**：坐席登记需求到线下WPS→支撑组每天查看WPS登记记录→支撑组人工评估方案→人工回复客户（不及时）。

**理想状态**：工单系统内直接发起纾困工单→工单流转到支撑组→支撑组在工单系统内评估→审批联动（OA审批→结果回写）→结果自动通知客户。按复杂度分流：简单停催由客服直接操作；较长停催流转指定人员提交审批；重组/分期方案由支撑组评估→OA审批→执行；司法调解走案件管理系统→调解系统。

**同业对标**：马上消费的"小马调解室"采用线上调解平台+线下调解工作站双轨机制，比我们单一的内部调解系统更完善。2024年12月马上消费与成渝消保中心共建调解工作站，这种"机构+消保中心"共建模式值得我们在Phase 3调解工作站建设中参考。

## 三、三阶段建设路径

### Phase 1：跑通主干道（6-9个月）

**目标**：投诉从受理到归档全流程可追踪，核心断点填上

**前置条件**：无强依赖，Phase 0先恢复原有分单规则（属修复非建设）

**同业对标**：银行（TRS）处于"数据整合"阶段，建设全口径投诉管理大数据平台；招联处于"大模型基座"阶段，发布智鹿大模型。我们此阶段以填断点为主，AI渗透深度最低。


| 建设内容     | 现状         | 目标             | 归属        |
| -------- | ---------- | -------------- | --------- |
| 电话工作台迁移  | 🟡 老客服系统   | 迁移到新工单系统       | 总行底座+自研封装 |

### Phase 2：挂上辅助引擎（6-12个月）

**目标**：质检、预警、归因三大能力上线

**前置条件**：Phase 1核心断点填完，工单主干道跑通；质检引擎依赖总行AI能力初步就绪

**同业对标**：银行（TRS）处于"智能模型"阶段，部署审查风险识别+黑产识别+标签识别等模型；招联处于"智能体转型"阶段，从模型微调转向模型能力+工程能力的智能体应用。我们此阶段开始建闭环，规则引擎打底、AI辅助增强。


| 建设内容    | 现状      | 目标                    | 归属          |

| 催收转诉统一  | 割裂      | 统一归到消保工单系统            | 自研新工单系统     |


### Phase 3：叠智能增强（12-18个月）

**目标**：AI驱动效能提升

**前置条件**：Phase 2质检+预警+归因闭环建成；总行AI能力（实时质检、情绪识别）可调用

**同业对标**：银行（TRS）处于"全流程闭环"阶段，事前审查+事中管控+事后监督一体化封装；招联处于"消保智能体"阶段，三层防线全流程覆盖60+业务场景实时洞察。我们此阶段追效能，AI渗透深度和标签体系向同业靠拢。

| ---------------- | -------- | ------------------------ | ------------------------------ |

### 外部对接事项（需协调外部方）


| 事项        | 阶段       | 当前卡点                   | 建议动作                      |
| --------- | -------- | ---------------------- | ------------------------- |
| 供应商投诉自动同步 | Phase 3  | 邮件手动接收                 | 自研+供应商对接，Phase 3          |

**投入优先级判断**：Phase 1的8项自建事项中，批量操作半自动化和监管转诉自动建单是业务方感知最强的两个痛点，建议优先投入；知识库系统化是后续所有AI增强的基础，同步推进。总行依赖事项中，**外网云桌面启用**和**质检中台需求提交**是两个需要管理层推动的关键卡点，建议在汇报时重点沟通。
