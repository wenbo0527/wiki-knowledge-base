## 1️⃣ 案例 1：Tony 格式/术语不统一（强证据 ⭐⭐⭐⭐）

### 1.1 现象

Tony 6-14 日报 vs 6-15 日报里，**同一个任务**（C3C89082 + 5A4D5B9A）跨日期用了 **2-3 种命名风格**：

| 日期 | 任务 ID | 标题（不同日期的写法）|
|:---|:---|:---|
| 6-14 | C3C89082 | `客户360 v3.1 催收短信提醒（凌晨回写）` |
| 6-15 | C3C89082 | `客户360 v3.1 - 催收记录·还款短信提醒记录` |
| 6-14 | 5A4D5B9A | `客户360 用信列表产品ID 增量 v1.1（凌晨回写）` |
| 6-15 | 5A4D5B9A | `客户360·业务核心明细 TAB·用信列表产品ID 增量 v1.1` |

### 1.2 问题分析

| 维度 | 表现 | 影响 |
|:---|:---|:---|
| **产品命名** | "客户360 v3.1" vs "客户360·业务核心明细 TAB" | 没统一产品大名前缀 |
| **字段命名** | "催收短信提醒" vs "催收记录·还款短信提醒记录" | 没统一字段范围描述 |
| **分隔符** | `-` vs `·` vs `()` | 跨日期分隔符漂移 |
| **后缀标记** | `(凌晨回写)` vs 无后缀 | 同一动作标记漂移 |

### 1.3 实证来源

- **Tony 6-14 日报**：`/Users/wenbo/.openclaw/workspace-agents/tony_stark/memory/daily/2026-06-14.md`
- **Tony 6-15 日报**：`/Users/wenbo/.openclaw/workspace-agents/tony_stark/memory/daily/2026-06-15.md`
- **字段"暗号"错位**（memory/dreaming/light/2026-05-29.md）：
  > "`currentAmount` 站在桥头等，等的是 `creditOverview.totalCreditLimit` 手里那张贴了别名的纸条。**两边都委屈，都觉得自己没做错**"
  > "调额记录那栏：`previousAmount` 以为自己叫 `before`，`newAmount` 以为自己叫 `after`"
- **Tony 6-15 日报"路径修复"段**自我承认：
  > "✅ 已处理 | `/api/v1/ai/health` 404 问题已改用 `/health`，**调用方文档待文博同步**"

### 1.4 派蒙判断

- **这是"AI 忽悠"的典型场景**：AI 输出"看起来合理"的命名，但**没定义命名规范** = 跨时间/跨任务漂移
- **根源**：AI 推理时用的是"上下文最可能的命名"，不是"团队约定的命名"
- **真实损失**：下游 QA/开发要用这些任务 ID 找代码时**找错文件**（dispatching 错位）

### 1.5 建议修复（写给 Tony）

1. **PRD 评审任务 ID 命名规范**（3 段式）：
   - 格式：`<产品大名>·<功能模块>·<具体改动>`
   - 例：`客户360·催收记录·v3.1`
2. **同任务跨日不改名**（C3C89082 永远是 `客户360·催收记录·v3.1`）
3. **回写动作不挂在标题里**（用 status + 日志，不在标题加 `(凌晨回写)`）
4. **AI 分身 P1 System Prompt 加命名约束**（钟离 5-13 已写"P1 = 文博语气风格"，建议加"团队命名约定"）

## 3️⃣ 案例 3："Prompt 能解决却上了更重的方案"（强证据 ⭐⭐⭐⭐）

### 3.1 实证 1：Nick v1 评估"过度乐观"

**完整证据**（6-9 钟离 v2 修订回执）：

> "**v1 漏算 4 项**：
> 1. cdy 是 monorepo 6 workspace
> 2. `@platform/*` 私有包数字社区没有
> 3. LLM 输出 import 不到
> 4. cdy TS `^6.0.3` 写错"
> "**评级变化**：v1 🟢 低（过度乐观）→ v2 🟡 中（**带 1 个 0 min patch**）"
> "**颗粒度 A/B/C**：A ✅ / B 🟡（带 1 工程任务）/ C ❌"

**派蒙解读**：
- v1 评估 = **"上重方案"**（建议装 Skill + 改 monorepo + 升级 TS）
- v2 修正后 = **"0 min patch"** = **改 1 个 Prompt 文件就行**
- **这是最典型的"Prompt 解决却上了更重的方案"** — 团队差点因为 v1 评估去改 monorepo/升级 TS，结果**改 1 个 Prompt 就好**

### 3.2 实证 2：Agent 编排框架选型判断

**派蒙 6-10 sessions 选型分析**：

| 方案 | 风险 | 建议 |
|:---|:---|:---|
| **过度工程化** | 引入 Temporal 后，调试一个 7 Agent 流程要查 5 层日志 | **先 PoC 验证 ROI，别一上来就上重栈** |
| **状态机复杂度爆炸** | 5 Agent + 条件分支 = 状态空间指数增长 | 强制要求：每个 Agent 有显式 State Schema |
| **Agent 本身不稳定** | LLM 输出不可靠会让工作流频繁异常 | 必须设计 Retry + Fallback 路径，**不能裸跑** |
| **跨天状态过期** | 任务跨天后，上下文/外部依赖可能失效 | Checkpoint 必须含"上下文" |

**派蒙解读**：团队评估**4 种重方案风险**，结论都是"**先 PoC 验证，别一上来就上重栈**"= **Prompt 路径优先**。
