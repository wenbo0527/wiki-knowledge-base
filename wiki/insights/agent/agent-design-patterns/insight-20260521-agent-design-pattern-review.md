## 一、执行摘要

### 核心观点

1. **Agent = LLM（大脑） + Harness（框架）**：Harness是差异化的核心，而非模型本身
2. **Harness决定了Agent的上限**：同等模型下，Harness的好坏决定了Agent系统的稳定性和可靠性
3. **多Agent协作是必然趋势**：单一Agent无法完成复杂任务，协作模式设计是关键
4. **治理是Agent系统的安全保障**：爆炸半径控制、生命周期钩子、护栏三明治

### 主要建议

| 建议 | 说明 | 优先级 |
|:---|:---|:---:|
| **先建Harness，再选模型** | Harness是差异化核心 | 🔴 |
| **记忆分层设计** | 短期-任务-长期三层 | 🔴 |
| **工具数量控制** | ≤10个，40-50个召回率骤降 | 🟠 |
| **治理先行** | 先设计失败边界 | 🟠 |
| **Supervisor优先Tool Calling** | 90%场景适用 | 🟡 |
| **爆炸半径控制** | 限制Agent故障扩散 | 🟡 |

## 三、设计权衡（新增章节）

> **来源**: Agent Harness工程 + 多智能体架构设计指南

### 3.1 核心权衡维度

| 决策维度 | 选项A | 选项B | 适用场景 |
|:---|:---|:---|:---|
| **Agent架构** | 单Agent | 多Agent | 先做通单Agent，再拆分超载职责 |
| **执行模式** | ReAct（边想边做） | Plan-and-Execute（先规划再执行） | 长任务/高代价/难回滚场景优先后者 |
| **上下文管理** | 大窗口策略 | 信号密度优化 | 关注常驻信息/检索策略/折叠机制 |
| **验证机制** | 生成器自验证 | 外部独立验证 | 代码/部署/数据写入等场景需外部验证 |
| **系统厚度** | 厚Harness（强结构） | 薄Harness（轻量） | 随模型能力升级动态减薄非承重结构 |

### 3.2 长会话上下文污染问题

> **来源**: Claude Code Subagents深度解析

**问题本质**：
| 现象 | 数据 |
|:---|:---:|
| 长会话探索过程产生大量一次性中间信息 | 半小时积累80k token噪音 |
| 关键决策依据被低密度内容淹没 | 压缩摘要时易丢失重要信息 |
| **核心风险** | "决策变薄"——模型在噪音中找不到重点 |

**解决方案：Subagents上下文卫生管理**

| 策略 | 说明 |
|:---|:---|
| **探索过程隔离** | Subagent处理临时查询，结果只返回结论和证据 |
| **主上下文保持干净** | 隔离探索过程，不污染主上下文 |
| **只读优先** | 子Agent优先设计为只读模式 |

**判断是否需要Subagent**：
- 这段任务是不是独立调查？
- 会不会污染主上下文？
- 子Agent是只读还是写共享状态？

### 3.3 单Agent vs 多Agent决策

> **核心原则**：只要单个Agent能干完，且体感不差，就别折腾多Agent。

**多Agent的隐藏成本**：
- 编排逻辑要写、要维护、要监控
- Agent之间的契约要定义、要版本化
- 调试链路变长，问题定位成本上升
- 上下文要在多个Agent间一致地流转

**新增核心原则**：
> **Design around context boundaries, not roles**
> 不要按角色设计，要按上下文边界设计。

**上下文边界设计三问**：
- 这两件事，需不需要看到对方的中间过程？
- 这两件事，会不会因为对方做完了某一步就影响自己下一步？
- 如果交给同一个Agent一次性做完，会不会更省心？

**判断是否需要多Agent**：

| 检查项 | 问题 | 如果是 → |
|:---|:---|:---|
| **1. 独立调查** | 这段任务是不是独立调查？ | → 适合Subagent |
| **2. 上下文污染** | 会不会污染主上下文？ | → 适合Subagent |
| **3. 只读vs写** | 子Agent是只读还是写共享状态？ | → 只读更适合 |
| **4. 依赖关系** | 子任务之间有没有强依赖？ | → 强依赖慎拆 |
| **5. 结果合并** | 最终结果由谁合并、谁负责写入？ | → 边界清楚有价值 |

**决策流程**：
```
单Agent能干完吗？
     │
     ├── 是，体感不差 → 单Agent（结束）
     │
     └── 否 → 检查5项
              │
              ├── ≥3项符合 → 多Agent
              │
              └── ≤2项符合 → 优化单Agent
```

### 3.4 ReAct vs Plan-and-Execute选择

| 模式 | 特点 | 适用场景 |
|:---|:---|:---|
| **ReAct** | 边想边做，快速响应 | 简单任务、实时交互 |
| **Plan-and-Execute** | 先规划再执行，长周期 | 复杂任务、高代价操作、难回滚场景 |

### 3.6 上下文压缩四要素

> **来源**: Agent Harness上下文管理研究

| 要素 | 必须保留 | 说明 |
|:---|:---|:---|
| **目标** | ✅ | 用户原始目标 |
| **已排除方案** | ✅ | 尝试过但失败的方案 |
| **错误** | ✅ | 已发现的错误和修复方式 |
| **下一步** | ✅ | 下一步要做什么 |

**压缩边界**：
- 避免切断tool-call/result配对
- 压缩时需守住完整性
- 子智能体默认使用独立会话

### 3.7 架构建设顺序

> **来源**: LLM Agent架构演进

| 顺序 | 组件 | 职责 |
|:---:|:---|:---|
| **1** | **Harness** | 系统"脊梁"，故障可观测/可阻断/可回滚 |
| **2** | **Skill** | 降低执行方差，提升可预测性 |
| **3** | **Memory** | 避免过早记忆噪声 |
| **4** | **Multi-agent Protocol** | 协作规范，显式权限控制 |

**原则**：先Harness后Memory，因为Memory需要Harness支撑。


| 经验值 | 说明 |
|:---|:---|
| **≤10个工具** | 单Agent最佳工具数量 |
| **40-50个Skill** | 召回率从95%骤降至30%的临界点 |

## 四、七维模式详解

### 4.1 感知模式（Perception）

| 子模式 | 技术 | 说明 |
|:---|:---|:---|
| **注意力聚焦** | RAG检索、上下文压缩 | 优先处理高价值信息 |
| **多模态融合** | 文本/图像/音频转换 | 统一格式处理 |
| **主动感知** | 实时监控、异常触发 | 主动发现而非被动响应 |

**我们的实践**：RSS监控（234源）、Wiki健康检查、多源输入

### 4.2 推理模式（Reasoning）

| 子模式 | 技术 | 说明 |
|:---|:---|:---|
| **思维链（CoT）** | 逐步推理 | 数学、逻辑问题 |
| **思维树（ToT）** | 多路径探索 | 复杂规划、创意任务 |
| **思维图** | 关联推理 | 图结构表示 |
| **类比推理** | 案例匹配 | 基于历史经验 |
| **元认知推理** | 结构化自省 | DOLORES框架 |

**我们的实践**：教练式对话（追问→确认→框架→研究）

### 4.3 行动模式（Action）

| 子模式 | 技术 | 说明 |
|:---|:---|:---|
| **ReAct** | 推理→行动→观察 | 循环执行 |
| **规划执行** | Plan→Execute→Verify | 结构化执行 |
| **工具编排** | 工具组合、串/并行 | 复杂任务分解 |
| **自适应策略** | 动态调整 | 根据反馈调整 |
| **Checkpoint/回滚** | 断点续跑 | 长任务状态保存 |

#### 长任务治理机制

> **来源**: Claude Code长任务治理 + LangGraph Checkpoint

**目标状态管理**：
| 状态 | 说明 |
|:---|:---|
| **active** | 任务进行中 |
| **paused** | 已暂停，可恢复 |
| **complete** | 已完成 |
| **budget_limited** | 预算耗尽 |

**Checkpoint机制**：
- 开发阶段：MemorySaver
- 生产环境：持久化存储 + thread_id隔离
- 用途：暂停后恢复现场

**LangGraph持久化记忆**：
```
Checkpoint保存 → thread_id隔离会话 → 恢复执行
```

**我们的实践**：HEARTBEAT定时任务、tool_call、飞书推送

### 4.4 反思模式（Reflection）

| 子模式 | 技术 | 说明 |
|:---|:---|:---|
| **自我修正** | Reflexion | 重新生成直到通过 |
| **反思记忆** | 经验库更新 | Buffer of Thoughts |
| **元学习** | 学会学习 | 反馈闭环 |

**我们的实践**：memory归档（✅）、错误案例记录（🟡待加强）

### 4.5 记忆模式（Memory）

| 子模式 | 技术 | 说明 |
|:---|:---|:---|
| **分层记忆** | 短期/中期/长期分层 | 上下文管理 |
| **RAG** | 向量检索 | 外部知识库 |
| **情节记忆** | 事件序列存储 | MemGPT |
| **Graph记忆** | 关系图谱 | 实体关系和时间演化 |

#### 记忆架构路线对比

> **来源**: Agent Memory深度解析

| 路线 | 强项 | 容易踩的坑 |
|:---|:---|:---|
| **Core Memory** | 稳定、低延迟、每轮可见 | 太大就污染上下文 |
| **Vector Store** | 容量大、接入快、适合语义召回 | 旧事实误召回、来源不清 |
| **Temporal Graph** | 擅长关系、时间和演化 | 成本高、图维护复杂 |
| **File-based** | 可读、可审计、可版本化 | 关系查询能力弱 |
| **Self-managed** | 能随模型能力进步 | 弱模型会把记忆搞乱 |

**收敛方向**：
- 只靠向量不够，需要混合关键词、语义、图关系、文件路径
- 需要一小层 always-loaded context，让Agent知道自己知道什么
- 记忆最好是人能读的，别只存在embedding里
- Read-Write Loop要能闭上

#### Claude Code七层记忆（两条链路）

| 链路 | 内容 | 说明 |
|:---|:---|:---|
| **当前任务** | tool-results/microcompact/SessionMemory | 负责当前长任务不断线 |
| **跨会话** | full context/working memory | 负责跨会话长期记忆 |

**我们的三层架构**：
```
Session层（短期）→ 当前会话上下文
Episodic层（任务级）→ SQLite任务板 + memory文件
Long-term层（永久）→ MEMORY.md + USER.md + RAG知识库
```

### 4.6 协作模式（Collaboration）

| 模式 | 说明 | 适用场景 |
|:---|:---|:---|
| **Supervisor-Worker** | 监督者分解任务，分发给工作者 | 复杂工作流 |
| **Tool Calling** | Supervisor控制权始终在手 | 任务明确、流程可预期 |
| **Handoff** | 主动权转移给Worker | 需灵活对话、Worker直接交互用户 |
| **Debate** | 多Agent辩论，裁判评判 | 决策验证、分析 |
| **Graph-Based** | 图结构编排 | 复杂依赖任务 |

#### 常见坑与解决方案

| 问题类型 | 症状 | 修复方案 |
|:---|:---|:---|
| **无限循环** | Supervisor反复调用同一Worker | 设置recursionLimit |
| **上下文污染** | Worker完整历史淹没关键指令 | Worker节点仅返回最后一条结果 |
| **Worker死锁** | A调用B，B调用A导致系统挂死 | 明确Worker prompt：不调用其他Agent |

### 4.7 治理模式（Governance）

| 子模式 | 说明 |
|:---|:---|
| **权限控制** | RBAC、OAuth风格令牌 |
| **爆炸半径** | 沙箱隔离、故障隔离 |
| **审计日志** | 操作可追溯 |
| **护栏三明治** | 输入处理层→执行层→输出验证层 |

**生命周期钩子**：
- H1：输入GR防注入
- H2：Action GR防越权
- H3：Post-exec IFC信息流控制
- H4：人机交互审批
