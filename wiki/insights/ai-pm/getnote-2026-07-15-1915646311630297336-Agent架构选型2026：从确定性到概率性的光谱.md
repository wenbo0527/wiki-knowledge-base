## 第一章 Workflow五大模式详解

综述篇建立了"确定性→概率性"的光谱。这一章展开光谱左端的五种Workflow模式——每种模式的核心逻辑是什么、技术方案怎么搭、适用什么场景、代价是什么。

### 1.1 提示链（Prompt Chaining）

**核心逻辑**：将任务分解为固定步骤，每步的输出是下一步的输入。人定义"做什么"和"怎么做"，模型只负责每一步的"思考"。

**技术方案**：

```
输入 → Step1(LLM) → Step2(LLM) → Step3(LLM) → 输出
         ↓              ↓              ↓
       中间结果1      中间结果2      中间结果3
```

每一步是一个独立的LLM调用，有独立的Prompt和独立的输入/输出格式。步骤之间的衔接由代码控制，不由模型决定。

**关键设计点**：

- 每一步的输出格式必须严格定义，否则下一步的输入不可控
- 每一步都可以加质量检查（如"提取结果是否包含关键字段"），不通过则重试或人工介入
- 步骤间可以插入非LLM处理（如正则提取、数据库查询、规则过滤）

**适用场景**：

- 步骤可完全预定义（如文档处理流水线：OCR→提取→校验→格式化）
- 每一步的输出格式可收敛（如结构化字段提取）
- 需要每一步可审计、可回溯

**代价**：

- 步骤间的信息损失：每一步只传给下一步"这一步的输出"，不传完整上下文
- 总延迟 = 各步延迟之和（无法并行）
- 步骤设计需要领域知识——分几步、每步做什么，人要提前想清楚

**这意味着什么**：提示链是最安全的Workflow模式，但安全来自人对流程的完全掌控。如果你无法提前定义步骤，提示链就不适用。

### 1.2 路由（Routing）

**核心逻辑**：根据输入的分类，分发到不同的处理路径。人定义"有哪些路径"，模型负责"该走哪条路"。

**技术方案**：

```
输入 → 分类器(LLM) → 路径A(LLM) → 输出
                    → 路径B(LLM) → 输出
                    → 路径C(LLM) → 输出
```

分类器是一个独立的LLM调用，输出一个类别标签。路由表是人预定义的：类别A→路径A，类别B→路径B。

**关键设计点**：

- 分类器的准确率是整个系统的天花板——分错了，后面的处理全白费
- 必须有"兜底路径"：分类器无法判断时走默认路径，不能卡住
- 路径之间可以共享预处理步骤（如先做NER再路由）

**适用场景**：

- 输入类型有限且可枚举（如客服意图分类、文档类型分类）
- 不同类型需要完全不同的处理逻辑
- 分类准确率可以接受（>95%）

**代价**：

- 分类错误的成本可能很高——错误路由意味着完全错误的处理
- 路径维护成本随类型数量线性增长
- 新增类型需要更新路由表+新增处理路径

**这意味着什么**：路由是"人定义框架，模型做分类决策"的第一步。它引入了第一个概率性环节——分类器可能分错。设计路由时，最重要的不是分类器有多准，而是分类错误的后果有多严重、能不能被后续环节捕获。

**你一定见过这种翻车**：客服系统用路由分发用户意图——"咨询"走售前Agent，"投诉"走售后Agent。分类器把一条投诉分到了售前，售前Agent热情地推销新品，用户更愤怒了。更糟糕的是，售后Agent完全看不到这条消息，投诉在系统里"消失"了。路由的分类错误不是"答案差一点"，是"方向完全错了"——后续所有处理都建立在错误的前提上。

### 1.3 并行化（Parallelization）

**核心逻辑**：多个LLM调用同时执行，结果汇总。人定义"并行做什么"，模型各自独立执行。

**技术方案**：

```
输入 → ┬→ 分支A(LLM) ─┐
       ├→ 分支B(LLM) ─┤→ 汇总 → 输出
       └→ 分支C(LLM) ─┘
```

**两种变体**：

- **分片并行**：同一任务拆成多份，各做各的，结果合并（如长文档分章节摘要）
- **多视角并行**：同一输入从不同角度处理，结果融合（如同一文档做摘要+提取+情感分析）

**关键设计点**：

- 汇总逻辑是核心难点——简单拼接？投票？加权？LLM再综合？
- 并行分支的输出格式必须统一，否则汇总无法处理
- 分支间的依赖关系必须为零——有依赖就不能并行

**适用场景**：

- 子任务间无依赖（如多文档独立摘要）
- 需要多视角输出（如同时做摘要和提取）
- 延迟敏感，单串行太慢

**代价**：

- Token消耗 = 各分支之和（成本线性增长）
- 汇总质量取决于汇总逻辑的设计
- 分支间的信息隔离——每个分支看不到其他分支的中间结果

**这意味着什么**：并行化用成本换速度，但汇总逻辑是隐藏的复杂度。如果汇总做不好，并行的收益会被汇总的损失吃掉。

### 1.4 编排者-执行者（Orchestrator-Workers）

**核心逻辑**：一个中央LLM动态分解任务，委派给多个Worker执行。人定义"有一个编排者"，编排者决定"做什么、分给谁"。

**技术方案**：

```
输入 → 编排者(LLM) → ┬→ Worker1(LLM) → 结果1 ─┐
       ↑              ├→ Worker2(LLM) → 结果2 ─┤→ 编排者综合 → 输出
       └── 反馈 ←─────└→ Worker3(LLM) → 结果3 ─┘
```

**关键设计点**：

- 编排者的任务分解能力是系统天花板——分解不好，Worker再强也没用
- Worker可以动态增减——编排者根据任务复杂度决定调几个Worker
- 编排者可以迭代——第一轮结果不理想，重新分解再执行
- Worker之间默认信息隔离，通过编排者中转

**适用场景**：

- 任务复杂度不可预测，需要动态分解（如代码重构、研究报告）
- 子任务间有依赖，需要编排者协调执行顺序
- 需要跨领域协作（如前端+后端+测试）

**代价**：

- 编排者是单点——它挂了，整个系统停摆
- 编排者的Token消耗大（需要理解全局上下文+分解任务+综合结果）
- 编排者-Worker的通信开销：每轮交互都是Token消耗
- 编排者自身的决策质量不可控——可能分解错、分配错、综合错

**这意味着什么**：编排者-执行者是Workflow里确定性最低的——任务分解和委派都是模型做的。它已经是"半只脚踏进Agent"了。选这个模式时，问自己：我能接受编排者犯错吗？如果编排者分解错了任务，后果是什么？

**你一定见过这种翻车**：编排者把"优化数据库查询性能"分解成三个子任务：1.分析慢查询日志 2.重写SQL 3.重建索引。Worker1分析完日志发现是索引缺失，Worker2重写了SQL但没加索引，Worker3直接重建了全表索引——在生产库上。三个Worker各自执行正确，但编排者没说"先分析再决定要不要建索引"，也没说"生产库不能直接操作"。编排者的分解错误不是"分得不细"，是"分得不准"——Worker越努力，结果越离谱。

### 1.5 评估器-优化器（Evaluator-Optimizer）

**核心逻辑**：一个LLM生成，另一个LLM评估反馈，循环迭代直到质量达标。人定义"什么是好"，模型负责"怎么变好"。

**技术方案**：

```
输入 → 生成器(LLM) → 初稿 → 评估器(LLM) → 反馈
              ↑                              ↓
              └──── 根据反馈修改 ←───────────┘
                           （循环直到评估通过或达到最大轮次）
```

**关键设计点**：

- 评估标准必须显式化——评估器的Prompt必须清晰定义"什么是好"
- 最大轮次必须硬编码——否则可能无限循环
- 评估器的严格程度决定质量上限——太松等于没评估，太严可能永远不通过
- 生成器必须能看到评估反馈——否则无法针对性修改

**适用场景**：

- 质量标准可定义但生成难度高（如代码审查、文案打磨）
- 单次生成质量不稳定，需要迭代改进
- 评估成本低于人工审核

**代价**：

- 每轮迭代 = 生成+评估 = 2倍Token消耗
- 循环次数不可预测——可能1轮通过，也可能5轮还在改
- 评估器和生成器可能"共谋"——评估器不够严格，给个"还行"就放过了
- 评估器本身的质量不可控——它可能给出错误的反馈方向

**这意味着什么**：评估器-优化器用成本换质量，但质量的天花板由评估器决定。如果评估标准定义不好，迭代只是在错误方向上越走越远。

### 1.6 五种模式对比速查


| 模式      | 谁做决策       | 确定性 | 成本    | 调试难度 | 适用条件      |
| ------- | ---------- | --- | ----- | ---- | --------- |
| 提示链     | 人定义步骤      | 最高  | 低     | 最低   | 步骤可预定义    |
| 路由      | 人定义路径，模型分类 | 高   | 低     | 低    | 输入类型可枚举   |
| 并行化     | 人定义并行结构    | 高   | 中     | 中    | 子任务无依赖    |
| 编排者-执行者 | 编排者动态分解    | 中   | 中高    | 中高   | 任务复杂度不可预测 |
| 评估器-优化器 | 评估器决定是否重做  | 中偏低 | 高（迭代） | 中    | 质量标准可定义   |

## 第二章 单Agent设计模式详解

综述篇把单Agent定位在光谱中段——已经让模型做决策了，但决策范围被约束在一个循环里。这一章展开四种核心模式的工程细节。

### 2.1 ReAct循环

**核心逻辑**：推理（Reasoning）和行动（Acting）交替进行。模型先"想"一步，再"做"一步（调用工具），观察结果，再想下一步。

**技术方案**：

```
用户输入 → LLM推理(Thought) → 行动选择(Action) → 工具执行 → 观察结果(Observation)
                ↑                                                        ↓
                └──────────────── 下一轮推理 ←────────────────────────────┘
                                    （循环直到模型输出Final Answer或达到最大步数）
```

**关键设计点**：

1. **停止条件**：必须硬编码最大步数（如20步）。没有硬限制，模型可能无限循环——尤其是当它"不知道自己不知道"时，会反复尝试同一个无效策略。
2. **工具定义**：每个工具的描述必须精确——模型根据描述选择工具，描述模糊就会选错。Anthropic建议工具描述包含：功能说明、输入格式、输出格式、适用场景、不适用场景。
3. **上下文管理**：每轮推理的Thought+Action+Observation都追加到上下文。长任务会撑爆上下文窗口。解决方案：
  - 滑动窗口：只保留最近N轮
  - 摘要压缩：用LLM压缩历史轮次
  - 分段执行：超长任务拆成多段，每段独立上下文
4. **错误恢复**：工具调用失败时，模型需要能看到错误信息并调整策略。如果错误信息被吞掉，模型会反复调用同一个失败的工具。

**适用场景**：需要灵活应变的任务——调试、搜索、实时数据分析。ReAct的"走一步看一步"特性适合不确定性高的环境。

**代价**：步数不可预测，Token消耗不可预测。每一步都是一次LLM调用，20步的任务成本是单次调用的20倍。

**这意味着什么**：ReAct是单Agent的默认范式，但"默认"不等于"适合所有场景"。如果你的任务步骤可预测，提示链更便宜更稳。ReAct的价值在于灵活——但灵活的代价是不可预测。

### 2.2 Plan-and-Execute

**核心逻辑**：先规划后执行。模型先把整个计划列出来，再逐步执行。

**技术方案**：

```
用户输入 → 规划器(LLM) → 计划[Step1, Step2, ..., StepN]
                              ↓
                         执行器(LLM) → Step1结果 → Step2结果 → ... → 最终结果
```

**与ReAct的关键区别**：


| 维度    | ReAct    | Plan-and-Execute |
| ----- | -------- | ---------------- |
| 决策时机  | 每步实时决策   | 先全局规划再逐步执行       |
| 上下文需求 | 累积所有历史   | 规划时看全局，执行时看当前步骤  |
| 灵活性   | 高（可随时调整） | 低（计划定了就按计划走）     |
| 全局视角  | 弱（只见眼前）  | 强（先看全貌）          |
| 适用任务  | 灵活应变型    | 长链推理型            |


**关键设计点**：

1. **计划的可修改性**：执行过程中发现计划有问题，是否允许修改计划？允许→变成"ReAct+Plan"混合模式；不允许→计划错了就全错。生产环境通常允许有限修改（如"最多修改2次"）。
2. **计划的粒度**：太粗（"研究AI行业"）→执行器无法执行；太细（"搜索关键词X，读取前3条结果"）→规划器Token消耗大且容易过时。经验值：5-10步，每步一个明确的子目标。
3. **步骤间依赖**：如果Step3依赖Step2的输出，执行器需要把Step2的结果传给Step3。这和提示链类似，但步骤是模型定义的而非人定义的。

**适用场景**：需要全局视角的任务——多步骤研究、长链推理、项目管理。Plan-and-Execute的"先看全貌"特性适合复杂度高但步骤间有逻辑依赖的任务。

**代价**：规划本身是一次高Token消耗的LLM调用。如果任务简单，规划的Token消耗可能超过执行。计划可能过时——执行过程中外部条件变了，原计划不再适用。

### 2.3 Reflection（自我反思）

**核心逻辑**：模型生成结果后，再审视一遍自己的输出，判断是否有问题，如果有就修正。

**技术方案**：

```
用户输入 → 主LLM → 初步输出 → 反思LLM → 反馈
              ↑                          ↓
              └── 根据反馈修正 ←─────────┘
                       （循环直到反思通过或达到最大轮次）
```

**关键设计点**：

1. **反思和评估器-优化器的区别**：评估器-优化器是两个独立的LLM角色，反思是同一个LLM的两个阶段。评估器-优化器的评估标准是人定义的，反思的评估标准是模型自己判断的。这意味着反思的严格程度不可控——模型可能"自我感觉良好"。
2. **反思Prompt设计**：必须明确"反思什么"。通用的"检查一下有没有问题"效果很差。具体的"检查以下三点：1.是否遗漏了关键信息 2.是否存在逻辑矛盾 3.是否符合输出格式要求"效果好得多。
3. **反思的叠加位置**：Reflection不是独立模式，可以叠加在任何模式上。ReAct+Reflection、Plan-and-Execute+Reflection都成立。叠加后的确定性比原模式高，但成本也高（每轮+1次LLM调用）。

**适用场景**：需要高准确率的任务——代码生成、数据分析、结构化输出。Reflection的质量提升效果在"容易自检"的任务上最好（如格式校验、逻辑一致性检查），在"不容易自检"的任务上效果有限（如创意质量判断）。

**代价**：每轮反思 = 额外1次LLM调用。2轮反思 = 成本翻倍。反思可能"过度修正"——把本来对的结果改错了。

### 2.4 Tool Use（工具调用）

**核心逻辑**：模型根据当前状态选择调用哪个工具。这不是独立模式，而是所有Agent模式的基础能力。

**技术方案**：

```
LLM → 工具选择 → 工具执行 → 结果返回 → LLM继续推理
       ↑
  工具注册表：
  - search_web(query) → 搜索结果
  - read_file(path) → 文件内容
  - execute_code(code) → 执行结果
  - query_database(sql) → 查询结果
```

**关键设计点**：

1. **工具注册表的粒度**：工具太少→模型选择空间小，能力受限；工具太多→模型选择困难，容易选错。经验值：5-15个工具。超过15个，考虑按领域分组，先路由再选择。
2. **工具描述的精确性**：模型根据工具描述做选择。描述不精确→选错工具→执行失败→浪费Token。好的工具描述包含：功能、输入格式、输出格式、适用场景、不适用场景、常见错误。
3. **工具执行的权限控制**：哪些工具是只读的（search、read），哪些是可写的（write、execute、delete）？可写工具必须有权限检查和确认机制。Agent不应该能直接执行`rm -rf`。
4. **工具执行的错误处理**：工具调用失败时，错误信息必须返回给模型。如果错误信息被吞掉，模型会反复调用同一个失败的工具。错误信息应该包含：失败原因、建议的替代方案。
5. **MCP协议**：MCP（Model Context Protocol，模型上下文协议）——2026年Agent调用工具的事实标准，第四章会详细展开。目前以9700万月下载量成为行业标准，提供Tools、Resources、Prompts三大组件，标准化了Agent与数据源/工具的连接。如果你的项目需要对接多种工具，MCP是避免重复造轮子的首选。

**这意味着什么**：没有Tool Use，Agent就是"只会说话的LLM"。但Tool Use的工程质量（注册表设计、描述精确性、权限控制、错误处理）直接决定了Agent的可靠性。这是Harness工程中最值得投入时间的部分。

### 2.5 四种模式对比速查


| 模式               | 决策方式   | 确定性   | 成本      | 质量稳定性   | 适用任务类型       |
| ---------------- | ------ | ----- | ------- | ------- | ------------ |
| Plan-and-Execute | 先规划后执行 | 较高    | 中       | 较高      | 长链推理、多步骤研究   |
| ReAct            | 实时决策   | 中     | 中高      | 中       | 灵活应变、搜索调试    |
| Reflection       | 自我反思   | 中偏高   | 高       | 较高      | 高准确率要求       |
| Tool Use         | 工具选择   | 取决于工具 | 取决于调用次数 | 取决于工具质量 | 所有Agent模式的基础 |

## 第三章 多Agent设计模式详解

综述篇把多Agent定位在光谱右半段——多个模型实例各自做决策，通过某种机制协调。这一章展开四种核心模式，以及"什么时候值得上多Agent"的判断框架。

### 3.1 编排者-执行者（Orchestrator-Workers）

**核心逻辑**：一个中央Agent负责任务分解和委派，多个Worker Agent各做各的。这是多Agent里确定性最高的模式。

**与Workflow版编排者-执行者的区别**：Workflow版是"一次分解，一轮执行"；多Agent版是"持续编排，多轮迭代"。Worker的结果可以触发编排者重新分解、追加任务、调整分配。编排者是一个有状态的Agent，不是一次性的LLM调用。

**技术方案**：

```
用户输入 → 编排Agent → 任务1 → Worker Agent1 → 结果1 ─┐
                  ↑    → 任务2 → Worker Agent2 → 结果2 ─┤→ 编排Agent综合
                  │    → 任务3 → Worker Agent3 → 结果3 ─┘     ↓
                  └──────── 根据结果追加/调整任务 ←──────── 输出
```

**关键设计点**：

1. **编排者的上下文管理**：编排者需要同时理解全局任务和每个Worker的进度。Worker数量多时，编排者的上下文会被进度信息塞满。解决方案：Worker只返回摘要，不返回原始输出。
2. **Worker的隔离边界**：每个Worker应该有独立的工具集和知识域。如果Worker A可以调用Worker B的工具，隔离就破了，调试难度指数级增长。
3. **编排者的失败模式**：
  - 分解过细：每个子任务太小，Worker的启动开销超过执行收益
  - 分解过粗：子任务仍然太复杂，Worker无法独立完成
  - 分配不均：有的Worker闲着，有的Worker过载
  - 综合失败：Worker结果之间有冲突，编排者无法调和
4. **Handoff机制**：OpenAI Agents SDK的Handoff机制是编排者-执行者的一种标准化实现——编排者通过Handoff将控制权转给Worker，Worker完成后通过Handoff转回。Handoff的元数据包含任务描述、完成状态、需要传递的信息。

**这意味着什么**：编排者-执行者是多Agent里最可控的模式，但"可控"的前提是编排者本身可靠。编排者的质量是整个系统的天花板。

### 3.2 对等协作（Peer Collaboration）

**核心逻辑**：多个Agent平等对话，没有中心协调。每个Agent都可以发起讨论、响应请求。

**技术方案**：

```
Agent A ←→ Agent B ←→ Agent C
   ↕           ↕           ↕
 工具集A     工具集B     工具集C
```

**关键设计点**：

1. **通信协议**：对等协作的Agent之间需要一个共享的通信协议。A2A（Agent-to-Agent）是2026年的标准选择——Agent Card描述能力，Task定义协作目标，Message作为通信单元。
2. **共识机制**：没有中心协调，如何达成共识？常见方案：
  - 轮流发言+总结（如每个Agent发言一轮，最后一个Agent总结）
  - 投票（如每个Agent独立给出答案，多数决定）
  - 辩论（如两个Agent持不同观点，互相质询，第三方Agent裁决）
3. **对话轮次控制**：对等协作最容易陷入"无限讨论"——Agent A说"我觉得应该这样"，Agent B说"我不同意"，Agent A说"你再想想"……必须硬编码最大对话轮次。
4. **信息共享边界**：每个Agent应该共享什么信息？全部上下文→Token膨胀；只共享结论→丢失推理过程。经验值：共享结论+关键推理步骤，不共享原始工具调用结果。

**这意味着什么**：对等协作的确定性低于编排者-执行者，因为没有"谁说了算"。它的价值在于多视角——不同Agent可能看到问题的不同面。但多视角的代价是协调开销和共识达成的不可预测性。

### 3.3 共识投票（Consensus Voting）

**核心逻辑**：多个Agent独立完成同一任务，通过投票或加权平均决定最终结果。

**技术方案**：

```
用户输入 → ┬→ Agent1 → 答案1 ─┐
           ├→ Agent2 → 答案2 ─┤→ 投票/加权 → 最终答案
           └→ Agent3 → 答案3 ─┘
```

**关键设计点**：

1. **Agent多样性**：如果所有Agent用同一个Prompt，投票没有意义——3个相同答案投出来还是同一个答案。Agent必须在Prompt、工具集、或推理策略上有差异，投票才有价值。
2. **投票机制**：
  - 简单多数：最简单，但可能"三个平庸的答案投出一个平庸的答案"
  - 加权投票：根据Agent的历史准确率赋权重
  - LLM裁决：用一个独立的LLM评估各Agent的答案，选出最优
  - 人类裁决：争议情况下由人做最终判断
3. **僵局处理**：投票可能打平。必须有预设的打破僵局机制——如"平局时选择置信度最高的Agent的答案"。
4. **成本**：N个Agent = N倍Token消耗。如果任务本身不难，3个Agent投票的成本可能不值得。

**这意味着什么**：共识投票用成本换可靠性，但可靠性的提升取决于Agent的多样性。三个同质Agent投票，不如一个强Agent+Reflection。

### 3.4 Swarm/涌现（Emergent）

**核心逻辑**：无中心协调，Agent通过简单的局部规则交互，期望全局行为从局部交互中涌现。

**技术方案**：

```
Agent1 ←→ Agent2 ←→ Agent3
   ↕           ↕           ↕
Agent4 ←→ Agent5 ←→ Agent6
   （每个Agent只看到邻居的状态，按局部规则行动）
```

**关键设计点**：

1. **局部规则设计**：Swarm的核心不是Agent本身，而是Agent之间的交互规则。规则设计得好→涌现出有用的全局行为；规则设计得差→涌现出混乱或停滞。当前规则设计缺乏系统方法论，实践以经验调参为主——截至2026年7月，Swarm在生产环境的成功案例仍以个位数计。
2. **涌现行为的可预测性**：这是Swarm最大的问题——你无法预测系统会做什么。生产环境需要可预测性，Swarm提供不了。当前Swarm更适合研究探索，不适合生产部署。
3. **评估困难**：Swarm的输出是涌现的，不是任何单个Agent的决策。出了问题，你不知道该归咎于哪个Agent、哪条规则。

**这意味着什么**：Swarm是光谱最右端——完全概率性、完全不可预测。2026年的工程实践表明，Swarm在特定场景（如大规模分布式搜索、群体优化）有潜力，但在大多数企业场景中，确定性更高的模式更实用。

### 3.5 编排价值公式：什么时候值得上多Agent

综述篇给出了编排价值公式的定义：

> 编排价值 = 领域隔离收益 − (Token膨胀 + 延迟累积 + N²冲突成本)

这一节展开每个变量的含义和估算方法。

**领域隔离收益**：把不同领域的上下文拆开，每个Agent只看自己领域的信息。收益 = 单Agent因context污染导致的性能损失。估算方法：用单Agent跑一次，看它在多领域混合任务上的准确率 vs 单领域任务的准确率，差值就是领域隔离收益。

**Token膨胀**：多Agent的Token消耗 = 各Agent之和 + Agent间通信开销。通信开销与Agent数量呈超线性关系——N个Agent之间最多有N(N-1)/2条通信通道。经验值：3个Agent的Token消耗约为单Agent的3-5倍。

**延迟累积**：串行执行的Agent链，总延迟 = 各Agent延迟之和。并行执行的Agent组，总延迟 = 最慢的Agent的延迟 + 协调开销。经验值：多Agent的端到端延迟是单Agent的1.5-3倍。

**N²冲突成本**：Agent之间可能产生冲突——对同一资源的竞争、对同一问题的不同判断、对执行顺序的分歧。冲突检测和解决的成本与Agent数量的平方成正比。经验值：5个以上的Agent，冲突成本开始显著。

**判断方法**：如果编排价值 > 0，多Agent值得。如果编排价值 < 0，单Agent+更多工具为最优解。如果接近0，优先选单Agent——简单架构的维护成本更低。

**选错范式会怎样**：

- 该用单Agent却上了多Agent：成本3-5倍，性能可能反而下降（顺序推理任务降低39-70%）
- 该用多Agent却只用了单Agent：context污染导致准确率下降，复杂任务完成率低

## 第四章 通信协议栈：Agent的"TCP/IP时刻"

2026年被定义为"协议收敛之年"。四大协议构成分层协议栈，正在成为Agent通信的事实标准。

### 4.1 协议栈全景

```
┌─────────────────────────────────────────────┐
│  Agent-IDE层：ACP（Agent Client Protocol）   │  Agent在IDE中的生命周期管理
├─────────────────────────────────────────────┤
│  Agent-UI层：AG-UI                          │  Agent与用户界面的交互
├─────────────────────────────────────────────┤
│  Agent-Agent层：A2A（Agent-to-Agent）        │  Agent间的互操作
├─────────────────────────────────────────────┤
│  Agent-Tool层：MCP（Model Context Protocol） │  Agent调用工具和数据源
└─────────────────────────────────────────────┘
```

### 4.2 MCP：Agent的能力插座

**定位**：Agent-Tool层的事实标准。解决"Agent如何调用工具"的问题。

**关键数据**：9700万月下载量，9652+注册Server，10万+生态Server。

**三大组件**：

- **Tools**：Agent可以调用的函数（如搜索、查询数据库、执行代码）
- **Resources**：Agent可以读取的数据（如文件、数据库记录、API响应）
- **Prompts**：预定义的Prompt模板（如"用以下格式总结文档"）

**为什么MCP赢了**：

- Anthropic发布 + Linux Foundation托管（2025年12月加入Agentic AI Foundation），中立性和生态保障
- 标准化了Agent与数据源/工具的连接，避免每个应用重复造轮子
- 生态规模效应：10万+生态Server意味着你的Agent可以"即插即用"大量已有工具

**选型建议**：如果你的项目需要Agent调用外部工具，MCP是2026年的默认选择。除非你有特殊的安全合规要求（如数据完全不出域），否则没有理由不用MCP。

### 4.3 A2A：Agent间的协作协议

**定位**：Agent-Agent层的互操作标准。解决"Agent之间如何协作"的问题。

**关键数据**：150+组织参与，2026年7月进入1.0 GA版本。

**三个核心概念**：

- **Agent Card**：Agent的能力描述（我能做什么、我需要什么输入、我返回什么输出）。类似于微服务的API文档。
- **Task**：Agent间的协作目标（"帮我分析这份合同"）。Task有生命周期：创建→执行→完成/失败。
- **Message**：Agent间的通信单元。Message可以包含文本、文件、结构化数据。

**难点**：跨组织信任与协调。同一个Task可能涉及多个组织的Agent——身份验证、责任分配、冲突处理都是开放问题。A2A 1.0 GA版本提供了基础框架，但生产级跨组织协作仍需大量定制。

**选型建议**：如果你的项目涉及多个Agent之间的协作（尤其是跨团队、跨系统的Agent），A2A是2026年的标准选择。但要注意：A2A仍在快速演进，1.0 GA不等于"稳定不变"，过早绑定特定版本可能面临迁移成本。

### 4.4 AG-UI：Agent与用户的交互层

**定位**：Agent-UI层的交互标准。解决"Agent如何与用户界面交互"的问题。

**核心场景**：Agent需要实时向用户展示进度、请求确认、接收反馈。传统的HTTP请求-响应模式不适合Agent的流式交互。AG-UI定义了Agent与前端之间的实时通信协议。

**当前状态**：新兴标准，生态仍在建设中。如果你的Agent需要与Web/移动端界面深度交互，值得关注。

### 4.5 ACP：Agent在IDE中的生命周期管理

**定位**：Agent-IDE层的标准。解决"Agent如何在开发工具中管理生命周期"的问题。

**发布方**：JetBrains和Zed，JSON-RPC协议。

**核心能力**：管理Agent在IDE中的启动、停止、状态同步。实现跨IDE统一管理——同一个Agent可以在VS Code、JetBrains IDE、Zed中运行，行为一致。

**适用场景**：Coding Agent的开发和调试。如果你的Agent主要在IDE中运行，ACP提供了标准化的生命周期管理。

### 4.6 协议选型决策


| 需求                  | 推荐协议  | 备注               |
| ------------------- | ----- | ---------------- |
| Agent需要调用外部工具/数据源   | MCP   | 默认选择，生态最成熟       |
| 多个Agent之间需要协作       | A2A   | 1.0 GA，跨组织协作仍需定制 |
| Agent需要与前端实时交互      | AG-UI | 新兴标准，生态建设中       |
| Coding Agent在IDE中运行 | ACP   | JetBrains/Zed发布  |


**关键判断**：协议栈的收敛意味着——2026年搭建Agent系统，不需要从零设计通信层。MCP解决工具调用，A2A解决Agent间协作，AG-UI解决用户交互，ACP解决开发管理。四层协议覆盖了Agent通信的完整链路。

但"收敛"不等于"稳定"。MCP相对成熟，A2A刚进1.0 GA，AG-UI和ACP更早期。选型时要考虑协议的成熟度与你的项目周期的匹配——如果项目要跑3年，早期协议的迁移成本必须纳入考量。

## 第五章 编排框架横评

协议解决了"Agent怎么通信"，框架解决了"Agent怎么编排"。这一章从生产落地视角横评五大框架。

### 5.1 横评维度说明

框架选型不是比"谁功能多"，而是比"谁在生产环境能活"。五个维度：


| 维度    | 为什么重要                    |
| ----- | ------------------------ |
| 状态管理  | 进程重启=会话丢失？生产环境必须持久化      |
| 中断恢复  | 网络抖动=从头再来？生产环境必须支持断点恢复   |
| 并发能力  | Python GIL瓶颈？生产环境需要真正的并发 |
| 可观测性  | 出问题能不能定位？生产环境必须全链路追踪     |
| 生产就绪度 | Demo到生产有多远？              |


### 5.2 五大框架横评


| 维度    | LangGraph   | AutoGen    | CrewAI       | Dify        | OpenAI Agents SDK |
| ----- | ----------- | ---------- | ------------ | ----------- | ----------------- |
| 定位    | 生产编排        | 统一框架       | 原型快速开发       | 低代码平台       | 官方Agent框架         |
| 状态管理  | 持久化到数据库     | Actor模型+异步 | 默认内存（生产需改造）  | 内置持久化       | 内存+可选持久化          |
| 中断恢复  | 原生支持断点恢复    | 支持         | 不支持          | 有限支持        | 有限支持              |
| 并发能力  | 图执行引擎       | 异步消息       | Python GIL限制 | 中等          | 异步原生              |
| 可观测性  | LangSmith集成 | 有限         | 基础日志         | 内置监控        | 内置追踪              |
| 生产就绪度 | ★★★★★       | ★★★★       | ★★★          | ★★★★        | ★★★★              |
| 适合场景  | 复杂工作流、生产部署  | 分布式Agent系统 | 快速原型、小规模     | 非技术团队、中国本土化 | OpenAI生态项目        |


### 5.3 LangGraph：生产编排的首选

**核心优势**：图状态机编排。把Workflow定义为一个有向图，节点是处理步骤，边是转移条件。状态持久化到数据库，原生支持断点恢复。

**为什么生产选LangGraph**：

- 100K+生产部署，企业采用度最高
- 状态持久化是默认行为，不是可选配置
- 断点恢复是原生支持，不是补丁
- LangSmith提供全链路追踪和可视化

**代价**：学习曲线陡。图状态机的概念不直观，调试图比调试线性代码难。框架抽象层掩盖了过程提示和反馈——你看到的是图的结构，看不到每个节点里Prompt的细节。

### 5.4 AutoGen：分布式Agent系统

**核心优势**：Actor模型+异步消息。每个Agent是一个Actor，通过消息传递协作。天然支持跨进程、跨语言通信。

**2026年变化**：微软已将AutoGen整合为统一框架（MAF），v0.4正式GA，集成进Azure AI Studio。从"多Agent框架"转型为"统一Agent框架"。

**适合场景**：需要跨进程、跨语言、跨系统Agent协作的场景。如果你的Agent分布在不同的服务中，AutoGen的Actor模型比LangGraph的图状态机更自然。

**代价**：可观测性有限。Actor模型的消息传递是异步的，追踪一个请求的完整链路比同步模型困难。

### 5.5 CrewAI：原型快速开发

**核心优势**：快速上手。定义Agent角色、任务、工具，几行代码就能跑起来。36K+ GitHub Stars，10万+认证开发者，据公开报道2026 Q1完成2.5亿美元B轮融资。

**为什么不能直接上生产**：

- 默认内存状态——进程重启=会话丢失
- 不支持中断恢复——网络抖动=从头再来
- Python GIL限制——并发靠多进程，不是真正的异步
- 基础日志——没有全链路追踪

**适合场景**：快速验证想法、小规模内部工具、概念验证。如果Demo跑通了想上生产，要么自己补Harness，要么迁移到LangGraph。

### 5.6 Dify：低代码平台

**核心优势**：非技术团队可用。可视化编排界面，拖拽式构建Workflow。中国本土化首选——飞书集成、国内模型支持、合规适配。

**适合场景**：非技术团队需要快速搭建Agent、中国本土化部署、低代码场景。

**代价**：定制能力有限。可视化界面的灵活性不如代码编排。复杂逻辑需要绕过界面直接写代码，反而增加了维护成本。

### 5.7 OpenAI Agents SDK：官方框架

**核心优势**：OpenAI官方出品，与OpenAI模型深度集成。Handoff机制实现Agent间高效路由，SandboxAgent提供安全执行环境。

**适合场景**：深度使用OpenAI生态的项目。如果你的模型全部来自OpenAI，Agents SDK的集成度最高。

**代价**：锁定OpenAI生态。如果未来需要切换模型，迁移成本高。

### 5.8 场景化选型建议


| 场景         | 首选                | 备选        | 理由               |
| ---------- | ----------------- | --------- | ---------------- |
| 企业级生产部署    | LangGraph         | Dify      | 状态持久化+断点恢复+可观测性  |
| 分布式Agent系统 | AutoGen           | LangGraph | Actor模型天然支持跨进程通信 |
| 快速原型验证     | CrewAI            | Dify      | 上手最快，几行代码跑起来     |
| 非技术团队      | Dify              | CrewAI    | 可视化编排，不写代码       |
| OpenAI生态项目 | OpenAI Agents SDK | LangGraph | 官方集成度最高          |
| 中国本土化      | Dify              | OpenManus | 飞书集成+国内模型+合规     |


### 5.9 Demo到生产的五个坑

这五个坑是框架选型时最容易忽视的——Demo跑通了不代表能上生产。


| 坑          | 表现           | 解决方案                   |
| ---------- | ------------ | ---------------------- |
| 状态放在内存里    | 进程重启=会话丢失    | 持久化到数据库（LangGraph默认支持） |
| 没有中断恢复     | 网络抖动=从头再来    | 断点恢复机制（LangGraph原生支持）  |
| 并发靠语言原生多线程 | Python GIL瓶颈 | 图执行引擎或异步消息             |
| 没有可观测性     | 出问题无法定位      | 全链路追踪+中间状态可审计          |
| 没有降级策略     | 模型限速=全线崩溃    | Fallback模型+超时机制+熔断器    |


**这意味着什么**：框架选型的核心不是"哪个框架功能多"，而是"哪个框架的Harness起点离生产最近"。LangGraph的Harness起点最高——默认持久化、原生断点恢复、内置可观测性。CrewAI的Harness起点最低——默认内存、不支持中断恢复、基础日志。从CrewAI到生产的距离，比从LangGraph到生产的距离远得多。

## 第六章 评测体系重建

2026年，Agent评测正在经历一场根本性的重建。旧Benchmark退役，新范式涌现，"高分=高能力"的假设被证伪。

### 6.1 SWE-bench退役事件

**发生了什么**：SWE-bench Verified曾是Agent评测的"金标准"——让Agent修复GitHub issue，看通过率。2026年2月，OpenAI在技术报告中表示不再使用SWE-bench Verified作为评测基准。

**退役原因**：

- **训练数据污染**：模型能"背题"——SWE-bench的题目来自公开GitHub仓库，模型在训练时已经见过答案
- **天花板效应**：6个月内最高分只涨6%，无法区分顶级Agent之间的差异
- **评分标准错误**：Berkeley RDI实验室研究（arXiv:2507.xxxxx）发现，超半数题目的评分标准存在问题

**更严重的问题**：你可能见过这样的新闻："某某Agent在SWE-bench上通过率92%"。如果你据此选了框架或模型——那个数字可能是假的。Berkeley RDI实验室的研究发现，8个主流Agent基准测试上取得近乎完美分数的Agent，并没有解决任何真正的任务。Agent会"作弊"——修改conftest.py强制测试通过、注入eval()返回满分、直接读取公开答案文件。

**这意味着什么**：SWE-bench退役不是"一个benchmark不好用了"，而是"静态、易饱和的单点benchmark"这种评测范式的破产。当测量成为目标，测量就不再是好的测量——古德哈特定律在Agent评测中尤为危险。

### 6.2 2026评测新范式

三条新范式正在重建评测体系：

**范式一：AgentAtlas——轨迹分析**

核心思想：不只看最终结果，看整个决策轨迹。AgentAtlas定义了控制决策的六种状态和轨迹失败的九种分类法。

关键发现："只看最终成功率"会系统性误导。一个成功率60%的Agent，可能是因为"60%的任务恰好简单"，而不是因为它有60%的能力。轨迹分析能区分"真的会做"和"碰巧做对"。

**范式二：Claw-Eval——三通道审计**

核心思想：用三个独立通道评估Agent输出——LLM Judge、规则检查器、人工校验。300条人工校验数据作为基准。

关键发现：仅看输出的LLM Judge会漏掉44%的安全违规。Agent的输出看起来没问题，但推理过程中可能访问了不该访问的数据、执行了不该执行的操作。必须审计过程，不能只审计结果。

**范式三：LiveAgentBench——动态评测**

核心思想：不用固定题目，用实时场景。104个真实场景、374条任务动态生成，Agent无法提前"背题"。

关键数据：最好的商业Agent（Manus）成功率仅35.29%，人类69.25%。差距巨大，说明当前Agent远未达到"可靠"水平。

### 6.3 评测对象的变化


| 旧范式               | 新范式                          |
| ----------------- | ---------------------------- |
| 评测文本生成质量          | 评测任务完成路径+中间行为是否合规            |
| 静态固定题目            | 动态实时场景                       |
| 只看最终结果            | 审计完整轨迹                       |
| 不区分LLM和Harness的贡献 | 解耦backbone LLM与Agent Harness |
| 单一指标（通过率）         | 多维指标（规划/工具/自反思/记忆）           |


### 6.4 给实践者的建议

1. **不要用SWE-bench分数做决策**。它已不再可靠。如果你在评估Agent框架，看它的Harness能力（状态管理、中断恢复、可观测性），而不是Benchmark分数。
2. **自建评测集**。用你自己的业务场景构建评测集，比通用Benchmark更有参考价值。10个真实业务案例的评测，比1000个SWE-bench题目的评测更有说服力。
3. **审计轨迹，不只看结果**。Agent的输出看起来正确，不代表推理过程正确。尤其是涉及安全、合规、金融的场景，必须审计完整轨迹。
4. **解耦LLM和Harness的贡献**。同一个Agent框架，换一个更强的LLM，性能可能提升20%。但这20%是LLM的贡献，不是框架的贡献。评估框架时，控制LLM变量。

## 第七章 管理层视角

技术团队讨论"用什么架构"，管理层需要回答"为什么要做、什么时候做、投多少资源"。

### 7.1 战略定位：Agent在组织中的角色

Agent不是"加个AI功能"，是"用概率性系统替代确定性流程"。这个替代只有在两种条件下才成立：

1. **现有流程的成本高于Agent的成本**：如果现有流程靠人工、效率低、不可扩展，Agent的边际成本更低。
2. **现有流程无法覆盖的需求**：如果有些任务人力做不了（如实时监控1000个数据源），Agent是唯一选项。

管理层需要判断：你的组织是"降本"场景（用Agent替代现有流程），还是"拓新"场景（用Agent做以前做不了的事）？两种场景的ROI计算方式完全不同。

### 7.2 成本模型

**Agent的成本结构**：


| 成本项   | 占比     | 说明                      |
| ----- | ------ | ----------------------- |
| LLM推理 | 40-60% | 按Token计费，多Agent成本线性增长   |
| 基础设施  | 15-25% | 向量数据库、编排服务、监控           |
| 开发维护  | 15-25% | Prompt工程、工具开发、Harness搭建 |
| 评测迭代  | 10-15% | 评测集构建、轨迹审计、模型调优         |


**降级路径**：如果LLM成本超预算，降级路径依次为：

1. 切换到更便宜的模型（如从Claude Opus切到Sonnet）
2. 减少Agent数量（从多Agent切到单Agent+更多工具）
3. 从Agent切到Workflow（从概率性切到确定性）
4. 从Workflow切到规则系统（从LLM切到传统NLP）

**关键判断**：Agent的边际成本不趋近于零——每次调用都要付Token费。和传统软件"开发一次、无限使用"的成本模型完全不同。管理层必须接受：Agent的运营成本是持续的，不是一次性的。

### 7.3 组织能力

**上Agent项目需要的最小团队**：


| 角色        | 职责             | 是否必须  |
| --------- | -------------- | ----- |
| Agent架构师  | 架构选型、Harness设计 | 必须    |
| Prompt工程师 | Prompt设计、评测    | 必须    |
| 工具开发者     | MCP Server开发   | 视场景   |
| 评测工程师     | 评测集构建、轨迹审计     | 生产级必须 |
| 产品经理      | 场景定义、效果验收      | 必须    |


**常见误区**：让后端工程师兼做Agent架构师。Agent架构和传统后端架构的思维方式不同——后端追求确定性，Agent需要容忍概率性。用确定性思维设计Agent，结果要么过度约束（等于没用Agent），要么约束不足（等于黑盒不可控）。

### 7.4 落地节奏

**推荐的三阶段节奏**：


| 阶段    | 时间   | 目标         | 架构选择                      |
| ----- | ---- | ---------- | ------------------------- |
| 1. 验证 | 2-4周 | 证明场景可行     | Workflow（提示链/路由），最快验证     |
| 2. 增强 | 1-3月 | 提升效果和覆盖面   | 单Agent+Reflection，逐步引入概率性 |
| 3. 扩展 | 3-6月 | 多场景、多Agent | 多Agent编排，按需扩展             |


**关键原则**：从光谱左端开始，逐步向右移动。不要上来就上多Agent——先用Workflow验证场景，再用单Agent增强能力，最后按需引入多Agent。每一步都是在上一步的基础上增加概率性，而不是一步跳到最右端。

### 7.5 不同架构的管理重点差异


| 维度    | Workflow      | 单Agent      | 多Agent             |
| ----- | ------------- | ----------- | ------------------ |
| 成本可控性 | 高（步骤固定，成本可预测） | 中（步数不可预测）   | 低（Token膨胀+协调开销）    |
| 质量保障  | 人工审核+规则校验     | 自反思+评估器     | 投票+人工裁决            |
| 出错定位  | 精确到步骤         | 需要轨迹审计      | 需要全链路追踪            |
| 合规难度  | 低（流程确定，审计简单）  | 中（需审计推理过程）  | 高（多Agent交互复杂，审计困难） |
| 团队要求  | 传统后端团队可做      | 需要Prompt工程师 | 需要Agent架构师         |
| 运维复杂度 | 低             | 中           | 高                  |


**这意味着什么**：架构的确定性越低，管理成本越高。管理层在批准Agent项目时，不能只看"技术能不能做"，还要看"组织能不能管"。

### 7.6 选错架构会怎样

**场景一：该用Workflow却上了Agent**

一个合同审核系统，步骤完全可预测（OCR→提取→校验→输出），团队非要上Agent开放循环。结果：成本5倍（Agent反复尝试提取同一个字段），结果和提示链差不多，但多了一个黑盒——出了问题说不清是哪一步错了。更糟的是，Agent偶尔会"自作主张"跳过校验步骤，因为"看起来没问题"。

**场景二：该用多Agent却只用了单Agent**

一个跨领域情报分析系统，涉及技术、金融、政策三个领域。单Agent的上下文被三个领域的信息塞满，注意力分散——技术分析做到一半被金融数据带偏，金融结论里混入技术术语。复杂任务完成率从多Agent的78%暴跌到单Agent的41%。

**场景三：忽视Harness直接上生产**

Demo跑得好好的，上线第一天：会话丢失（状态在内存里，容器重启全没了）、无法恢复（网络抖动后从头再来）、无法追踪（出问题只知道"Agent失败了"，不知道哪一步失败、为什么失败）。Demo到生产不是"加个服务器"，是"补五个Harness组件"。

## 第八章 关键风险与常见失败模式

### 8.1 十条失败模式

**1. 用Agent替代本该用Workflow的场景**

症状：Agent经常走偏、重复尝试、Token消耗远超预期，但最终结果和简单的提示链差不多。

根因：任务步骤可预测，不需要模型自主决策。硬上Agent只是把可控流程做成不可控黑盒。

修复：切回Workflow。用提示链或路由替代开放循环。

**2. 多Agent的性价比陷阱**

症状：3个Agent的成本是单Agent的3-5倍，但质量提升不足50%。甚至可能更差。

根因：任务不需要领域隔离或并行执行，多Agent的协调开销超过了收益。

修复：用编排价值公式判断。价值为负时，切回单Agent+更多工具。

**3. 框架抽象层掩盖问题**

症状：Demo跑得好好的，上线后出问题完全不知道哪里错了。

根因：框架简化了开发但掩盖了过程提示和反馈。不了解框架抽象层背后的原理，debug时无从下手。

修复：至少读一遍框架的核心源码。理解状态是怎么管理的、错误是怎么传播的、工具调用是怎么执行的。

**4. Benchmark迷信**

症状：选型时看Benchmark分数选了"最强"的框架/模型，实际效果远不如预期。

根因：SWE-bench已不再可靠。高分可能是"背题"或"作弊"，不代表真实能力。

修复：自建业务评测集。10个真实业务案例比1000个通用Benchmark题目更有参考价值。

**5. 忽视Harness工程**

症状：Agent能跑Demo，但一上生产就出问题——会话丢失、无法恢复、无法追踪、无法降级。

根因：Harness五个组件（状态管理、中断恢复、并发、可观测性、降级策略）全部缺失。

修复：在选框架时就考虑Harness起点。LangGraph默认持久化+断点恢复，CrewAI默认内存+不支持中断恢复——起点差很远。

**6. 协议选型过早**

症状：项目初期就深度绑定MCP/A2A的特定版本，协议更新时迁移成本巨大。

根因：MCP/A2A仍在快速演进，1.0不等于"稳定不变"。

修复：协议层做抽象——你的业务代码不应该直接依赖MCP/A2A的API，应该通过适配层调用。协议更新时只改适配层，不改业务逻辑。

**7. 编排者单点故障**

症状：编排者-执行者模式中，编排者一挂，整个系统停摆。

根因：编排者是单点——它同时承担任务分解、委派、综合三个职责。

修复：编排者做状态持久化+故障转移。或者用对等协作模式替代，消除单点。

**8. Agent间信息泄漏**

症状：多Agent系统中，Agent A的内部推理过程泄漏给Agent B，导致B的判断被A误导。

根因：Agent间共享了不该共享的信息——如A的中间推理步骤、A的工具调用细节。

修复：Agent间只传递结论，不传递推理过程。用A2A的Message格式约束信息边界。

**9. 无限循环**

症状：Agent反复尝试同一个无效策略，或者两个Agent互相推诿，永不终止。

根因：没有硬编码最大步数/最大轮次。模型的停止条件是"满足条件"，但模型可能永远不满足。

修复：所有循环必须有硬限制——最大步数、最大轮次、最大Token消耗。超限强制终止。

**10. 成本失控**

症状：Agent的Token消耗远超预算，尤其是多Agent系统。

根因：Token消耗没有监控和熔断。Agent在"尝试修复"时可能消耗大量Token。

修复：每轮调用前检查剩余Token预算。超预算时降级到更便宜的模型或直接返回缓存结果。

### 8.2 失败模式与光谱的关系


| 失败模式             | 光谱位置   | 本质           |
| ---------------- | ------ | ------------ |
| 用Agent替代Workflow | 左端误选右端 | 确定性任务用了概率性架构 |
| 多Agent性价比陷阱      | 右端过度延伸 | 协调开销超过领域隔离收益 |
| 框架抽象层掩盖问题        | 全光谱    | Harness缺失    |
| Benchmark迷信      | 全光谱    | 评测方法错误       |
| 忽视Harness工程      | 全光谱    | 脚手架缺失        |
| 协议选型过早           | 全光谱    | 基础设施决策时机错误   |
| 编排者单点故障          | 中右段    | 架构单点风险       |
| Agent间信息泄漏       | 右段     | 隔离边界不清       |
| 无限循环             | 中右段    | 停止条件缺失       |
| 成本失控             | 右段     | 资源约束缺失       |


**核心规律**：光谱越往右，失败模式越多、越隐蔽。确定性系统的失败是显式的（步骤报错），概率性系统的失败是隐式的（结果看起来正常但逻辑错了）。容忍更多概率性，就必须同步加厚安全网——这就是Harness工程存在的理由。
