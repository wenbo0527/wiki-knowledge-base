## 一、框架总览：消保业务全景

消保的核心是**投诉**，但不只是投诉。消保业务线覆盖七类工单性质：


| 工单性质       | 压力等级 | 量级   | 说明                                 |
| ---------- | ---- | ---- | ---------------------------------- |
| **咨询**🟡   | 低    | 🔴最大 | 亿联银行数据：咨询及建议占工单总量88.5%，坐席日常接的主要是咨询 |
| **投诉**🔴   | 最高   | 🟡中等 | 监管件、客户投诉、催收投诉——压力最大，是系统建设的核心驱动力    |
| **外部转办**🟠 | 高    | 🟡中等 | 12378/12345/信访/黑猫——监管转办件有处理时限，逾期升级 |
| **调解**🟡   | 中    | 🟢较少 | 司法调解、消保中心调解——Phase 3建设，当前走案件管理系统   |
| **信息开具**🟢 | 低    | 🟡中等 | 证明、发票、合同——标准化操作，业务执行台处理            |
| **建议**🔵   | 低    | 🟢较少 | 客户改进意见——记录归档即可                     |
| **表扬**⚪    | 无    | 🟢极少 | 服务肯定——记录归档即可                       |


七类工单性质共享同一套工单流转引擎，差异在于流程深度：投诉和外部转办走完整六阶段+溯源整改，咨询到归档即止，信息开具到执行即止，调解需对接外部调解系统，建议和表扬记录即可。

**投诉是核心驱动力，但系统必须装下全部业务**——因为坐席不分「投诉坐席」和「咨询坐席」，工单流转引擎也不分「投诉工单」和「咨询工单」，系统必须统一承载。

**工单性质之外还有两个分类维度**（监管要求+溯源需要）：


| 维度                             | 用途           | 消金版分类                                                                               |
| ------------------------------ | ------------ | ----------------------------------------------------------------------------------- |
| **业务类别**（对齐央行标准JR/T 0169-2018） | 监管报送口径       | 贷款、债务催收、个人金融信息、定价收费、支付结算、其他（6类，从央行14类裁剪）                                            |
| **投诉原因**（对齐央行标准12大类）           | 溯源引擎标签体系的第一级 | 催收方式和手段★★★★★、定价收费★★★★、管理制度与流程★★★★、信息披露★★★、信息安全★★★、服务态度★★、营销方式★★、合同条款★★、自主选择权★、资金安全★ |


三个维度交叉使用：一个工单 = 工单性质（如投诉）× 业务类别（如债务催收）× 投诉原因（如催收方式和手段）。

对应三道防线：

```
第一道防线：接住 —— 来了能接、接了能办（投诉+转办+咨询+开具+调解）
第二道防线：防住 —— 找到根因、不再重来（主要针对投诉和转办）
第三道防线：看住效果 —— 量在降吗、根在拔吗（投诉和转办的治理效果）
```


| 防线       | 回答什么  | 核心动作           | 对应能力层引擎        | 对应交互层               |
| -------- | ----- | -------------- | -------------- | ------------------- |
| **接住**   | 来了怎么办 | 受理→分办→处理→答复→归档 | 工单流转引擎         | 坐席工作台（事中）、业务执行台（事中） |
| **防住**   | 怎么不再来 | 预警→识别→溯源→整改    | 预警引擎、识别引擎、溯源引擎 | 管理驾驶舱·事前防线+事后治理     |
| **看住效果** | 做得好不好 | 指标→看板→考核→改进    | 溯源引擎（考核评价）     | 管理驾驶舱·事后治理          |


**交互层分类逻辑**：顶层按角色分（谁在用），二级按阶段分（事前/事中/事后）。坐席工作台和业务执行台几乎全是「事中」，不需要按阶段拆分；管理驾驶舱横跨三个阶段，按阶段组织更清晰；消费者之家以事中为主、事后补充。管理驾驶舱的「事前防线」还包含规则配置与系统管理（分单规则、预警阈值、标签体系维护、权限管理）——管理者「搭好舞台让坐席唱戏」的事前动作。

## 二、四层架构速查

三道防线是业务逻辑，四层架构是系统落地。每层回答一个不同的问题：


| 层         | 回答什么     | 当前状态                       | 关键卡点          |
| --------- | -------- | -------------------------- | ------------- |
| **交互层**   | 谁在用什么界面  | 🟢 核心已建（坐席+业务执行），⬜ 管理驾驶舱未建 | 电话工作台仍在老系统    |
| **能力层**   | 系统提供什么能力 | 🟢 工单流转引擎已建，⬜ 其余4个引擎未建     | 质控引擎依赖总行AI能力  |
| **数据层**   | 数据怎么管    | 🟢 投诉数据域已有，🟡 业务数据域部分可用    | 外部数据管道卡在外网云桌面 |
| **基础设施层** | 依赖什么外部支撑 | 🟢 总行触达能力可用，🟡 核心接口部分对接    | 外网云桌面受阻2个月    |


**能力层五个引擎与三道防线的对应**：


| 引擎     | 支撑哪道防线          | 当前状态    | 建设节奏                               |
| ------ | --------------- | ------- | ---------------------------------- |
| 工单流转引擎 | 接住投诉            | 🟢 核心已建 | Phase 1填断点（批量操作、分单规则、纾困系统化）        |
| 预警引擎   | 防住投诉·防升级        | ⬜ 未建设   | Phase 2规则打底→Phase 3 AI增强           |
| 识别引擎   | 防住投诉·防黑产        | 🔵 分散手动 | Phase 2规则初版→Phase 3 AI模型≥85%       |
| 溯源引擎   | 防住投诉·防复发 + 看住效果 | ⬜ 未建设   | Phase 2标签5大类15小类→Phase 3完整版9大类45小类 |
| 质控引擎   | 防住投诉·防过程违规      | ⬜ 未建设   | Phase 2催收合规先行→Phase 3扩展营销+客服       |


**数据层四个数据域**：


| 数据域   | 真相源   | 当前状态       | 关键管道                 |
| ----- | ----- | ---------- | -------------------- |
| 投诉数据域 | 工单中心  | 🟢 已有      | —                    |
| 业务数据域 | 数据中心  | 🟡 部分可用    | 批量提取管道🟢已启动，实时管道🔴待建 |
| 标签数据域 | 溯源中心  | ⬜ 未建设      | Phase 2随溯源引擎建设       |
| 外部数据域 | 渠道接入层 | 🔵 手动Excel | 外部管道🔴待建（卡在外网云桌面）    |


**基础设施层三类依赖**：


| 依赖类型     | 包含什么                | 当前状态       | 关键卡点               |
| -------- | ------------------- | ---------- | ------------------ |
| 总行触达能力   | 呼叫中心、IVR、短信、在线客服    | 🟢 可用      | 与新工单系统割裂，Phase 1融合 |
| 核心业务操作接口 | 核心系统、试算、票务、影像、催收、OA | 🟡 部分对接    | 催收/调解/影像接口需统一封装    |
| 合规知识库    | 产品知识、业务规则、话术模板      | 🔵 线下Excel | 无系统检索，Phase 1系统化   |

## 二、同业框架对照


| 机构          | 框架表述               | 核心驱动   | 与我们的关系                             |
| ----------- | ------------------ | ------ | ---------------------------------- |
| **招联**      | 未病先防→欲病早治→已病综治     | AI驱动   | 逻辑一致，招联靠AI实现，我们靠规则引擎+AI渐进          |
| **马上消费**    | 事前审查→事中检查→事后监督     | 制度+科技  | 逻辑一致，马上消费多了「事前审查」，我们投诉压力驱动暂不覆盖     |
| **银行（TRS）** | 事前审查→事中管控→事后监督     | 合规驱动   | 逻辑相似但重心不同——银行重心在「事前审查」，我们重心在「事中管控」 |
| **我们**      | **接住投诉→防住投诉→看住效果** | 投诉压力驱动 | 从投诉工作流倒推，与消金同业逻辑一致，表述更直白           |


**关键差异**：银行方案重心在「事前审查」（别卖错产品给错人），消金方案重心在「事中管控」（别在催收/营销过程中侵害消费者）。我们的框架从投诉压力出发，第一道防线就是「接住」，不绕弯。

## 三、每道防线的系统支撑

### 第一道防线：接住

**目标**：所有消保业务从进来到结案，全流程可追踪、不断裂

**五类业务场景的差异**：


| 场景     | 流程深度           | 关键差异                   | 当前状态                  |
| ------ | -------------- | ---------------------- | --------------------- |
| 投诉     | 完整六阶段+溯源整改     | 压力最大，监管件有处理时限          | 🟢 核心已建，断点待填          |
| 外部转办   | 完整六阶段+溯源整改     | 批量建单是核心痛点，身份匹配困难       | 🔵 手动Excel逐条建单        |
| 咨询     | 受理→答复→归档       | 量大但轻，到归档即止             | 🟢 已建（老系统咨询单+新系统交易工单） |
| 客户信息开具 | 受理→执行→归档       | 标准化操作，业务执行台处理          | 🟢 已迁移                |
| 调解     | 受理→对接外部调解系统→归档 | 需对接消保中心/司法调解，Phase 3建设 | 🔵 走案件管理系统            |


**核心链路**（以投诉为例）：受理→分办→处理→答复→归档

**系统支撑**：


| 环节  | 做什么                | 引擎          | 当前状态              |
| --- | ------------------ | ----------- | ----------------- |
| 受理  | 统一建单、自动打标、分单规则     | 工单流转引擎      | 🟢 核心已建，分单规则需恢复   |
| 分办  | 按渠道×类型×紧急度分配       | 工单流转引擎      | 🟡 规则砍到只剩1条       |
| 处理  | 联系客户→查数据→定方案→审批→执行 | 工单流转引擎+业务执行 | 🟢 大部分已建，纾困方案待系统化 |
| 答复  | 处理结果告知客户           | 工单流转引擎      | 🟢 已建             |
| 归档  | 结案、满意度回访           | 工单流转引擎      | 🟢 已建             |


**第一道防线的断点**（Phase 1要填的）：

- 🔴 批量操作：单次13000条手工逐条
- 🔴 监管转诉建单：手动Excel逐条
- 🔴 纾困方案：线下WPS登记
- 🟡 分单规则：砍到只剩1条
- 🟡 电话工作台：仍在老系统

### 第二道防线：防住

**目标**：找到投诉和转办件的根因，从源头减少重复投诉

**三个防住方向**：


| 方向      | 防什么                | 引擎   | 当前状态    |
| ------- | ------------------ | ---- | ------- |
| **防升级** | 投诉量异常、监管件超时、催收频次超限 | 预警引擎 | ⬜ 未建设   |
| **防黑产** | 代理维权、反催收联盟、伪造投诉    | 识别引擎 | 🔵 分散手动 |
| **防复发** | 同类投诉反复出现，根因未消除     | 溯源引擎 | ⬜ 未建设   |


**第二道防线的建设路径**：

- Phase 2：预警引擎（规则打底）+ 识别引擎（规则初版）+ 溯源引擎（5大类15小类）
- Phase 3：预警引擎（AI增强）+ 识别引擎（AI模型≥85%）+ 溯源引擎（9大类45小类）

### 第三道防线：看住效果

**目标**：用数据验证「接住」和「防住」是否有效

**核心指标**：


| 指标             | 衡量什么        | 目标方向 |
| -------------- | ----------- | ---- |
| **监管件占比**（北极星） | 投诉升级为监管件的比例 | ↓ 下降 |
| 投诉总量           | 整体投诉压力      | ↓ 下降 |
| 重复投诉率          | 同一客户再次投诉的比例 | ↓ 下降 |
| 结案时效           | 从受理到结案的平均时长 | ↓ 缩短 |
| 一次性解决率         | 一次处理即结案的比例  | ↑ 上升 |


**看住效果的建设路径**：

- Phase 1：复用数字社区+问数产品做报表过渡
- Phase 2：管理驾驶舱看板上线
- Phase 3：考核评价与绩效挂钩

## 六、一句话总结

**消金消保 = 接住 + 防住 + 看住效果**

- 接住靠工单流转引擎（已建核心，Phase 1填断点）——统一承载投诉、转办、咨询、开具、调解五类业务
- 防住靠预警+识别+溯源三个引擎（Phase 2建规则，Phase 3上AI）——主要针对投诉和转办
- 看住靠指标+看板+考核（Phase 1报表过渡，Phase 2看板，Phase 3考核闭环）

与招联「未病先防→欲病早治→已病综治」逻辑一致，但表述更直白——消金的痛点不是「未病」，而是「病了先接住」。
