# Agent Skill、MCP、Prompt区别是什么？

> 原始 ID: 1915204165148771184

我在做一个开源项目[历史注脚](https://github.com/nicholasgao/history-footnote-engine)（一个历史文字游戏引擎），里面有个DM Agent，prompt里白纸黑字写着"不要调用Tool"。

LLM调了3次。

我又加了prefetch注入——调用反而更多。我加了tool_calls过滤——状态不一致。我直接在prompt里写"不要调Tool"——还是调。

最后我把Tool从Agent里拆走。调用降到0-1次。

这个经历让我意识到，市面上解释Prompt、Skill、MCP、Agent区别的文章，基本都在回答同一个问题："它们各自干什么？"——Prompt管指令，Skill管流程，MCP管连接，Agent管规划。像四个并列的岗位说明书。

但没人回答一个更关键的问题：**控制AI的力，你加在哪一层？**

回看那四次修补，其实是在不同层上打补丁：

- **v1**：prefetch注入，把不该调的工具信息提前塞进上下文——**语言层**，等于跟AI多说一遍"别碰"，结果调用反而更多
- **v2**：过滤tool_calls，在输出端拦截——**行为层**，但状态不一致，拦截了A处漏了B处
- **v3**：prompt直接写"不要调Tool"——**语言层**，AI看到了，但不听
- **v4**：把Tool从Agent里拆走——**结构层**，AI根本看不到这个工具，自然不调

四次修补，两种结果：在语言层和行为层使劲，越用力越翻车；在结构层动手，一次到位。

这四个概念不是四个并列工具。它们是同一件事——控制AI行为——在不同层上的实现。约束力从弱到强递进，加错了层，越用力越翻车。

## 三个维度，把四者切开

光说"约束力递进"太抽象。我用三个实操维度把Prompt、Skill、MCP、结构拆分切开，每个维度你一看就知道区别在哪。


|              | Prompt         | Skill                        | MCP                  | 结构拆分(Sub-Agent)        |
| ------------ | -------------- | ---------------------------- | -------------------- | ---------------------- |
| **单次 vs 封装** | 单次——每次手写，用完即弃  | 封装——写好反复调，三层渐进加载             | 封装——一次接入，所有Agent复用   | 封装——架构级决策，改了就是另一个系统    |
| **默认消费者**    | 自己——没人分享prompt | 自己——先给自己用，可选择性分享             | 别人——从设计之初就是给别人调的     | 自己——架构决策是内部的事          |
| **靠什么能力**    | 纯模型——全靠LLM推理   | 模型+判断框架——LLM推理，Skill定"什么算做完" | 其他能力——连接外部工具、数据库、API | 混合——每个Agent可配不同模型+不同工具 |


### 维度一：单次 vs 封装——不是"懒不懒"，是"稳不稳"

很多人说Skill是"固化Prompt"，听起来像是省事——把常用prompt存下来，下次不用手写。

但我在历史注脚项目里做web-testing Skill时翻过车：prompt写"完整测试所有页面"，AI测了两个页面就交差了。"完整"是什么意思？它理解了目标，但不知道什么算做完。

这就是Prompt和Skill的核心区别：**Prompt管"说什么"，Skill管"什么算做完"。** 你手写prompt说"完整测试"，AI猜"完整"是什么意思；你封装成Skill，定义好触发条件、执行步骤、约束规则、完成门槛，AI不用猜。

封装不是为了偷懒，是因为单次手写覆盖不了所有边界。Skill把翻车经验压进结构里，让AI在边界内跑。

### 维度二：默认消费者——Skill和MCP最硬的分界线

Skill和MCP到底什么时候用哪个？市面上的回答是"Skill是能力封装，MCP是连接协议"——说了跟没说一样。

真正硬的分界线是：**默认消费者不同。**

Skill是你给自己写的操作手册。你把追问逻辑、打分规则、兜底策略封装成Skill，绑在你的Agent上。Skill可以分享，但它的第一用户永远是你自己。

MCP是给别人用的接口。你写了一个MCP Server连数据库，任何Agent只要支持MCP协议就能调，不用知道你数据库的密码，不用写连接代码。MCP有marketplace、有一键安装、有权限治理。**它的定位从第一天就是"标准化分发的连接件"。**

一个向内沉淀，一个向外开放。这是设计意图的差异，不是使用场景的绝对划分。

### 维度三：靠模型 vs 靠其他——约束力的天花板

Prompt和Skill的核心能力都来自模型本身——LLM理解指令、LLM做推理、LLM生成输出。约束力上限受限于模型"听不听话"。

MCP和结构拆分的核心能力不依赖模型听话。MCP让模型接入了它本来没有的能力（查数据库、调API），结构拆分让模型根本看不到不该用的工具。

回到开头那个DM Agent：prompt写"不要调Tool"，靠模型听话，调了3次；拆走Tool，不依赖模型听话，降到0-1次。

再看MCP这一层：假设Agent通过MCP连了支付API，模型想绕过单笔限额，但API层有硬校验——金额超限直接返回错误，模型说了不算，API说了算。这就是"靠其他能力"的意思：约束力不来自模型听不听话，来自外部系统本身的规则。

**靠模型听话的约束力天花板低且不稳定，不靠模型听话的约束力天花板高且稳定。** 但"高且稳定"不等于无限——MCP协议本身也有安全漏洞的先例。只是跟语言层比，结构层的天花板明显更高。

## Skill vs MCP：最易混淆的边界

三个维度里，"默认消费者"那条线最值得单独拆出来讲——因为Skill和MCP是实践中最容易搞混的一对。

一个比喻：**MCP是修路，Skill是交通规则。**

路修好了，车能开过去——MCP让Agent连上了数据库、接入了API、读到了文件。但车会不会按规矩开，MCP不管。

交通规则告诉车怎么开——Skill定义了连上之后怎么用：追问几轮、什么算追问透、追问完怎么输出结构化结论。

拿我的诊断器举例：知识库的连接是MCP管的事——配好MCP Server，Agent就能读知识库里的内容。但读完之后追问几轮、打分规则是什么、追问不下去怎么兜底——这是Skill管的事。

**MCP解决"能不能连上"（接入权），Skill解决"连上了怎么用"（行政权）。** 两层缺一不可——路没修好，规则再细也没用；路修好了没规则，车乱开。

## 约束力递进：怎么选？

把三个维度收束成一条链：

**Prompt → Skill → MCP → 结构拆分**

约束力从弱到强，修改成本从低到高，适用场景从简单到复杂。

怎么选？不是四选一，是递进判断：

**语言层够不够？** → 够，Prompt就行。不够 → **行为层（Skill）够不够？** → 够，封装成Skill。不够 → **资源层（MCP）够不够？** → 够，接MCP。还不够 → **结构层，拆分。**

每一层都是在上一层兜不住的时候才往上走。加错了层，越用力越翻车——就像我开头那个DM Agent，在语言层打了三次补丁都没用，拆走Tool一次到位。

回到开头那句话：**控制AI的力，你加在哪一层？加错了层，越用力越翻车。**

---

有人会说，这些加在一起不就是Harness吗？对，行业公式是 Agent = Model + Harness。但Harness不是把Prompt、Skill、MCP、结构拆分平铺进一个框架——**约束力层级递进，才是Harness生效的前提。** 平铺的Harness只是组件清单，递进的Harness才是控制系统。
