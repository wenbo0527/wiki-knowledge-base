## 反例（9:15 报告 · 7-15 wiki-project-status-report-20260715.md §5.2）

**报告原文**：
> L2 Get 笔记 | ~1,130 笔记 / 7 KB 路径 | 🟡 30% 同步

**错误**：
- 看了 v1.0 备份脚本（7 个 HIGH_VALUE_KBS）但只列 4 个
- 完全没调 API 实测
- 没分"订阅 vs 自有"两类
- 笔记总数 ~1,130 是错的（实际 ~3,841）
- KB 总数 4 是错的（实际 15）

**根因**：
- 凭 v1.0 备份"印象"瞎写
- 没有 verify 实时数据
- 没有"知识盘点必分类"的方法论

## 正例（9:35 verify 后）

**实测 API**：
```bash
curl -s "https://openapi.biji.com/open/api/v1/resource/knowledge/list" \
  -H "Authorization: $GETNOTE_API_KEY" \
  -H "X-Client-ID: $GETNOTE_CLIENT_ID"
```

**返回**：
```json
{"data": {"topics": [
  {"id": "04p8P2m0", "name": "投资日记", "note_count": 27},
  {"id": "yYvRWqaY", "name": "文博的ai产品经理转型之路", "note_count": 132},
  ...
  {"id": "n3EGyBd0", "name": "印象笔记", "note_count": 2196}
]}}
```

**修正后**：
- KB 总数 4 → **15**（7 订阅 + 8 自有）
- 笔记总数 ~1,130 → **~3,841**
- 同步覆盖率 30% → **20%**（更糟）

## 治本 SOP（报告/盘点类输出 必检）

### ✅ 必做

1. **实时调 API**（不能用历史印象）
2. **完整分类**（订阅 / 自有 / 公开 等）
3. **完整计数**（所有 KB 都列，不挑熟悉的）
4. **覆盖率真实**（同步数 / 总数）
5. **标注 verify 时间**（报告里要写"9:35 实测"）

### ❌ 反例

| 错误 | 后果 |
|:---|:---|
| 凭记忆写"4 个 KB" | 漏 11 个 |
| 用 v1.0 备份当真实数据 | 配置过时（7-1 改造后 v1.0 已被 v2.0 替代）|
| 不调 API | L-32 对账机制未利用 |
| 不分"订阅/自有" | 漏 6 个自有 KB |
