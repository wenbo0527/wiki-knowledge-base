## 🎯 核心价值定位

AI编程工具的终极目标不是单纯提升编码速度，而是实现**从"写得快"到"交付稳"的关键跨越**。通过实践总结出6个可落地的核心抓手，结合Claude Code的机制层能力（Hooks、Skill、Subagent、权限体系等），形成团队级playbook骨架。

---

## 📌 TL;DR 核心要点速览

- **验收先行**：先定义"如何证明对"，再实现功能
- **任务单化**：提示词需包含范围、证据、约束、验收四要素
- **Plan拆解**：复杂任务通过WBS拆分为模块、依赖、顺序、交付物
- **护栏配置**：通过`CLAUDE.md`+`.claude/settings.json`实现自动化约束
- **Skill沉淀**：将成功经验封装为可复用组件
- **规模扩展**：MCP接入外部系统，Subagents隔离高输出/高噪音任务

## 🔍 抓手1：先写"怎么验收"，再写"怎么实现"

返工是AI编程中最高成本的环节，通常源于未明确"什么是对的"及"对到什么边界"。解决思路是将任何任务转化为**可执行的验收标准**，作为团队流程的第零步。

### 关键验收方式

| 类型 | 验收方法 | 示例 |
|------|----------|------|
| **单测** | 测试命令 | `npm test` / `pnpm test` / `go test ./...` |
| **构建** | 构建命令 | `npm run build` / `cargo build` |
| **代码规范** | 格式化工具 | ESLint / Prettier |
| **端到端** | 测试框架 | `npx playwright test` |
| **回归点** | 业务路径 | 3条"最容易出事"的核心流程 |
| **回滚机制** | 降级方案 | 一句话说明"出问题如何退回去" |

### 交付闭环流程

```
需求描述 → 验收标准 → 实现 → 验证 → 合并/上线
                              ↓
                        验证不通过
                              ↓
                        返回验收标准重新迭代
```

## 📋 抓手2：提示词从"聊天"变成"任务单"

避免将提示词写成模糊期待（如"帮我优化这个模块"），而应采用**固定结构的任务单**，明确四要素：

### 任务单核心结构

1. **范围**：允许修改的目录/文件与禁止修改的路径
2. **证据**：原始报错堆栈、日志、截图、复现步骤
3. **约束**：技术栈、既有规范、必须复用的工具、性能与安全底线
4. **验收**：验证命令、测试用例、期望输出

### 任务单模板

```
目标：实现/修复[具体功能]  
范围：只允许修改 @path1 @path2（禁止修改 @path3）  
证据：[复现步骤/报错堆栈/日志片段]  
约束：[复用组件/依赖限制/API兼容性要求]  
验收：[测试命令/新增用例/输出标准]  
交付：[文档更新/迁移说明/配置示例]
```

## 🔨 抓手3：Plan不是形式主义，它是WBS

复杂需求需通过**Plan Mode**进行结构化拆解，避免直接生成完整代码导致的逻辑漏洞。

### Plan Mode工作流

1. **只读探索**：切到Plan Mode（Shift+Tab），AI仅分析代码库，输出计划不修改文件
2. **需求澄清**：通过追问细化方案
3. **计划确认**：满意后切回Normal Mode执行实现

### Plan输出标准格式

```
模块清单：  
- M1：职责、输入输出、依赖、复杂度、验收方式  
- M2：...  

风险与边界：  
- 不做什么（明确排除项）  
- 可能踩坑的地方（列3条关键风险）  

实施顺序：  
1. 优先任务（理由：依赖/风险/收益）  
2. 次要任务  

验收清单：  
- 每个模块对应的测试/命令/检查点
```

### 团队质量门禁命令

- `/plan`：确认方案与验收标准
- `/tdd`：测试先行（RED→GREEN→REFACTOR）
- `/build-fix`：增量修复构建问题
- `/code-review`：按严重度输出审查报告

## 🛡️ 抓手4：把护栏写进配置，而不是写进人脑

通过`CLAUDE.md`、permissions、sandbox、hooks四大配置，实现"必须发生的事情自动发生"，减少人工干预。

### CLAUDE.md：精简护栏而非百科

```markdown
# Workflow  
- 代码改动后必须运行：<测试命令>  
- 优先跑单测/局部测试，确认后再跑全量  

# Constraints  
- 不引入新依赖，除非明确同意  
- 只允许修改：@src/...（禁止触碰：@infra/...）  

# Pointers  
- 项目入口：@README.md  
- 接口规范：@docs/api-guideline.md  
```

### permissions权限控制

```json
{  
  "permissions": {  
    "allow": ["Bash(npm run:*)", "Bash(pnpm run:*)"],  
    "deny": ["Bash(curl:*)", "Read(./.env)", "Read(./secrets/**)"]  
  }  
}
```

### hooks自动化质量闸门

| 场景 | 触发时机 | 作用 |
|------|----------|------|
| 编辑后自动lint | PostToolUse | 确保代码风格一致 |
| git push前提示 | PreToolUse | 防止误推主分支 |
| console.log审计 | Stop | 会话结束扫描调试代码 |
| 禁止main分支编辑 | PreToolUse | 强制使用feature分支 |

## 🔄 抓手5：把一次成功封装成Skill

Skill是可复用的工具箱，将成功经验转化为"约束+模板+检查清单"，避免重复造轮子。

### Skill核心构成

1. **When to Use**：明确适用场景
2. **Patterns**：团队认同的代码模板
3. **Checklist**：完成前必须通过的验证点

### 优先封装的三类Skill

- **复杂工具/框架标准用法**（如"ES接入""Redis缓存更新策略"）
- **常见错误处理模板**（重试、幂等、分布式锁、事务边界）
- **团队统一产物格式**（方案文档、接口说明、变更说明）

## 📈 抓手6：规模化靠两条腿：MCP + Subagents

### MCP（外部系统接入）

控制上下文成本的三条规则：
1. 常用MCP控制在10个以内，按需添加
2. 用项目级`.mcp.json`固化配置，避免口口相传
3. 密钥通过环境变量注入，配置文件只留占位符

### Subagents（上下文隔离）

子代理在独立上下文运行，仅将摘要返回主对话：

| 代理 | 模型 | 工具 | 用途 |
|------|------|------|------|
| Explore | Haiku | 只读 | 文件发现、代码搜索 |
| Plan | 继承主模型 | 只读 | 规划阶段代码库研究 |
| general-purpose | 继承主模型 | 所有 | 复杂研究、代码修改 |

## 💡 关键洞察

- **验收标准是核心**：AI编程最有效的约束不是"怎么写"，而是"怎么证明对"
- **配置优于人脑**：将团队规则编码为配置文件，避免依赖个人经验
- **隔离提升效率**：Subagents通过上下文隔离解决"高输出任务污染主对话"问题
- **渐进式落地**：从个人习惯到团队规范再到系统集成，分阶段推进可降低阻力
