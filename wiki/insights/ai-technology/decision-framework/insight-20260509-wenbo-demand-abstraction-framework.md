## 核心能力

**需求抽象**是从业务描述的表面需求，提炼出通用可拓展的系统能力。

---

## 框架流程

```
架构直觉 → 预演场景 → 小范围验证 → 算账 → 利益相关者确认 → 抽象通用方案
```

| 步骤 | 说明 | 关键问题 |
|------|------|---------|
| **架构直觉** | 先有系统设计方向 | "这系统应该长什么样" |
| **预演场景** | 想象未来需求场景 | "如果不这样做会遇到什么问题" |
| **小范围验证** | 低成本验证核心逻辑 | "我的直觉对吗" |
| **算账** | 计算线性满足的真实成本 | "这样做的真实代价是什么" |
| **利益相关者确认** | 识别所有受影响方 | "谁会用？谁会维护？" |
| **抽象通用方案** | 确定可拓展的解决方案 | "怎样做才能支持未来增长" |

---

## 关键原则

### 1. 不直接满足表面需求

| 表面需求 | 抽象后的本质 |
|---------|------------|
| "运营要自己配规则" | 规则引擎 |
| "策略说简单线性" | 认知不到复杂度 |
| "业务要快速上线" | 图快是最贵的成本 |

### 2. 架构直觉 + 预演算账

```
架构直觉：先想清楚系统长什么样
预演：想象未来3个扩展场景
算账：计算线性满足的成本 vs 抽象方案的成本
```

### 3. 小范围验证

在投入开发前，先用手工或半自动化方式验证核心逻辑。

### 4. 利益相关者清单

| 角色 | 检查点 |
|------|--------|
| 业务方 | 需求真实吗？预算合理吗？ |
| 技术方 | 能实现吗？维护成本高吗？ |
| 运营方 | 会用吗？复杂度超出认知吗？ |
| 数据团队 | 数据能支撑吗？ |
| 客服 | 会遇到什么问题？ |

## 案例：营销画布

**S（情境）**：
- 金字塔客群分层缺少逻辑
- 用策略堆积+优先级强制处理
- 业务提的是当前切片需求，但营销增长需要长期可拓展

**T（任务）**：
设计通用可拓展的营销配置系统

**A（行动）**：
1. 需求抽象：策略堆积 → 节点抽象；优先级 → 分流实验
2. 架构设计：DAG流程图 + 三种节点（分流/状态/动作）
3. 客群分层：金字塔 → 切块式，满足场景内+场景跃升
4. 可拓展：流程编排 + 节点拓展 + 分流实验

**R（结果）**：
- 系统上线且持续演进
- 支持营销增长

## 适用边界

- ✅ **适用**：中大型复杂需求构建、方案设计
- ❌ **不适用**：维护期小修小补、简单需求

## 与其他框架的关系

```
业务需求
    ↓
[需求抽象] → 判断：做还是不做（工程边界）
    ↓ 如果做
[Demo验证] → 判断：方向对不对
    ↓ 如果对
[产品升级] / [技术选型] → 执行
```
