## 框架定位

这是文博在产品管理领域的**核心方法论**，包含从零散到体系的进化过程。

核心逻辑：**阶段分层 → 量化度量 → 外部对标剪裁 → 体系化落地 → 持续复盘**

---

## 一、产品阶段判断框架

| 阶段 | 判断标准 | 核心任务 | 北极星指标 |
|------|---------|---------|-----------|
| **基础建设** | MUST have 部分不完善 | 完善核心能力 | MUST have覆盖率 ≥ 80% |
| **应用推广** | 建设完成但没用起来，目标用户未使用 | 推动落地使用 | 目标用户DAU/MAU > 40%，用户留存率 > 70% |
| **维护** | 目标用户都在使用 | 保持稳定运行 | 系统可用性 > 99.9%，故障响应时间 < 30分钟 |
| **退出/下线** | 业务停止或被替代 | 安全下线，数据归档 | 完成数据归档，无遗留问题 |

**判断信号：**
```
MUST have不完善 → 基础建设
MUST have完善但没用起来 → 应用推广
目标用户都在使用 → 维护
业务停止/被替代 → 退出/下线
```

## 三、产品管理体系架构

```
产品域
  ↓
应用
  ↓
功能
  ↓
功能点
```

**管理层次：**
1. 产品域：顶层分类，按业务领域划分
2. 应用：具体产品/系统
3. 功能：应用下的功能模块
4. 功能点：功能下的具体功能

## 五、外部对标与剪裁方法

### 剪裁判断维度

| 维度 | 问题 | 决策 | 剪裁记录 |
|------|------|------|---------|
| **公司发展情况** | 哪些能力需要引入？ | 决定引入范围 | [记录剪裁理由] |
| **技术能力** | 能落地哪些？ | 决定实现深度 | [记录限制条件] |
| **业务需求** | 优先级是什么？ | 决定执行顺序 | [记录需求来源] |

### 外部对标原则

- **可以模仿**：交互方式、逻辑流程
- **必须调整**：本地化适配（技术能力、公司发展阶段）
- **不照搬**：完全照搬外部框架通常会水土不服

### 对标来源

- 火山引擎
- 阿里
- 之前公司产品框架

### 剪裁决策记录模板

```markdown
# 剪裁决策记录

| 字段 | 内容 |
|------|------|
| **对标来源** | [如：火山引擎数据中台] |
| **对标功能** | [具体哪个功能/模块] |
| **剪裁决策** | 引入/部分引入/不引入/本地化调整 |
| **决策理由** | [为什么这么决定] |
| **限制条件** | [技术限制/业务限制] |
| **预计效果** | [预期收益] |
| **记录人** | |
| **记录日期** | |
```

## 六、需求拆解与评审流程

### 需求拆解流程

```
业务场景 → 需求澄清 → 需求拆解 → 研发评审 → 排期开发 → 上线验证 → 复盘迭代
```

### 工具流程

| 环节 | 说明 | Owner |
|------|------|-------|
| **需求澄清** | 优化需求澄清工具流程，确保需求清晰 | PM |
| **需求拆解** | 将需求拆解为功能点，评估工作量和优先级 | PM + 技术 |
| **研发评审** | 技术可行性评估，识别风险和依赖 | 技术负责人 |
| **排期开发** | 基于优先级和资源进行排期 | PM + 技术负责人 |
| **上线验证** | 验证功能是否达到预期效果 | PM |
| **复盘迭代** | 上线后复盘，优化流程和需求管理方法 | PM + 技术 |

## 七、方法论进化路径（v0.x → v1.0 → v2.0）

### v0.x：散

| 问题 | 表现 |
|------|------|
| 零散 | 能用就行，没有体系化整理 |
| 文档散乱 | 文档分布在各处，难以查阅 |
| 流程缺失 | 缺少标准化的需求拆解流程 |

### v1.0：体系化

| 改进 | 说明 |
|------|------|
| 完整体系 | 建立了产品域→应用→功能→功能点的层级结构 |
| 流程标准化 | 明确了需求拆解流程 |
| 工具化 | 优化了需求澄清和研发评审的工具流程 |

### v2.0：量化与复盘

| 改进 | 说明 |
|------|------|
| 量化度量 | 每个阶段有明确的北极星指标 |
| 剪裁记录 | 外部对标有决策记录，可追溯 |
| 复盘机制 | 建立定期复盘机制，持续优化 |
| 退出机制 | 增加产品退出/下线阶段 |

### 进化路径

```
散（零散、能用就行）
  ↓ 踩坑后提炼
提炼（识别问题，总结教训）
  ↓
重构（建立体系，流程工具化）
  ↓ 最佳实践对比
量化（量化指标、剪裁记录、复盘机制）
```

## 十、核心原则

### 1. 阶段分层原则
不同阶段有不同目标，每个阶段有明确的北极星指标：
- 基础建设：完善MUST have → 覆盖率 ≥ 80%
- 应用推广：推动落地使用 → DAU/MAU > 40%
- 维护：保持稳定运行 → 可用性 > 99.9%
- 退出/下线：安全终止 → 数据归档完成

### 2. 量化度量原则
每个决策、每个阶段都要有量化指标支撑，避免"感觉还行"的模糊判断。

### 3. 对标剪裁原则
外部框架可以参考，但必须基于本地情况调整：
- 交互方式可以模仿
- 落地程度要结合技术能力
- 优先级要结合业务需求
- 所有剪裁决策必须记录

### 4. 体系化原则
从散到体系是进化路径：
- 零散 → 提炼 → 重构 → 量化
- 工具流程固化是体系化的标志
- 量化指标是持续优化的基础

### 5. 持续复盘原则
不复盘的方法论会僵化：
- 定期复盘每个技术选型决策
- 定期复盘产品阶段进展
- 根据复盘结果更新框架
