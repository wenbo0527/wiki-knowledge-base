## 执行摘要

测试工作方式正在发生变化——从"写脚本"到"搭测试智能体系统"。本文详解Agent+MCP+Skills三层架构如何将测试经验封装成可复用工程能力，实现从脚本生成到测试闭环的完整流程。

---

## 核心转变

> "以前自动化测试的核心是写脚本。现在更像是在搭一个能理解任务、能调用工具、能沉淀经验的测试智能体系统。"

### 传统 vs Agent模式

| 传统模式 | Agent模式 |
|----------|-----------|
| 人读Swagger文档 | Agent读取并理解 |
| 人分析测试场景 | Agent规划测试范围 |
| 人写接口脚本 | Agent生成测试资产 |
| 人执行脚本 | Agent执行+校验 |
| 人看报错+改代码 | Agent自动修复 |
| 人再回归 | 沉淀为回归套件 |

## Planner-Generator-Fixer 三组件

### 1. Planner - 生成测试计划

**职责**：先规划测试范围，明确测试边界

**测试计划示例**：
- 正常参数场景
- 必填字段缺失
- 参数类型错误
- 鉴权失败
- 资源不存在
- 重复提交
- 边界值
- 接口依赖关系
- 断言字段
- 清理策略

**关键价值**：
> "测试工程里，最值钱的不是脚本，而是测试设计。"

### 2. Generator - 生成可执行资产

**可输出类型**：
| 类型 | 工具/格式 |
|------|-----------|
| UI自动化 | Playwright脚本 |
| 接口测试 | Postman兼容脚本、Pytest |
| 性能测试 | Artillery YAML、K6/Locust/JMeter |
| 功能测试 | BDD风格用例、测试步骤型用例 |
| 用例管理 | 可入库的结构化测试用例 |

**核心理念**：
> "AI生成的不一定只是代码，它生成的是测试资产。"

**工程价值**：生成一次、校验一次、沉淀下来，后续直接回归复用。

### 3. Fixer - 自动修复错误

**常见脚本问题**：
- 选择器不稳定
- 登录态没处理好
- 接口字段理解错
- 参数依赖缺失
- 环境变量没配置
- 断言过严或过松
- 浏览器提前关闭
- 测试数据没有清理

**Fixer工作流**：
```
读取执行日志 → 判断失败原因 → 回到生成环节修复脚本 → 重新执行
```

---

## 常见踩坑

| 错误做法 | 问题 | 正确做法 |
|----------|------|----------|
| 直接让大模型生成用例 | 效果不稳定 | 先Planner规划 |
| 直接让大模型写代码 | 脚本经常跑不起来 | Generator+Fixer闭环 |
| 只做聊天窗口 | 变成"问答玩具" | Skills封装测试经验 |

---

## 关键金句

> "AI测试不是把需求丢给大模型，而是把测试流程拆成模型能理解、工具能执行、结果能验证的工程链路。"

> "未来测试工程师的分水岭，不是会不会用AI，而是能不能把测试经验封装成可复用的工程能力。"
