第三篇归总出三层问题：确定性边界、输出可靠性、知识供给。前两层在第四篇解决了——确定性逻辑归SKILL编排层+规则引擎，输出可靠性归字段级兜底。第三层还没动。

知识供给的问题不是"LLM不知道"。LLM不知道的事多了，不知道不是问题，编才是问题。

玩家问"今年赋税怎么这么重"，DM不知道一条鞭法的细节，没关系——它可以说"我也不太清楚"。但它不会说"我也不太清楚"，它会编。编一段听起来很像那么回事的赋税制度，有模有样地解释折银、加派、火耗——全是编的。玩家分不出真假，游戏就废了。

这就是第三层问题的核心：**LLM不知道自己不知道**。不知道的就会编，编了就像真的，像真的就有人信——对一个历史叙事引擎来说，这是致命的。

解法看起来简单：给LLM知识库，让它"知道"。但给了知识库之后，问题变成了——怎么给？给多少？什么时候给？

给少了，DM还是编。给多了，DM被知识淹没，上下文爆炸，延迟60秒，成本翻倍。给错了，DM拿到戚继光的条目，在玩家还没遇到戚继光的时候就提前剧透。

这一篇讲知识库：怎么给DM供料，怎么让DM"知道"但不被知识淹没，以及给完之后实测塌房了什么。

## 时代包：引擎与内容分离

先说一个设计决策：知识库不是"项目的一部分"，是"时代包的一部分"。

历史注脚体验引擎的代码在`engine/`目录下，知识库在`eras/`目录下。换时代不改代码——把`eras/wanli_1587/`换成`eras/tang_755/`，同一个引擎跑安史之乱。加时代也不改代码——在`eras/`下加一个子目录就行。

一个时代包就两样东西：`era.json`和`dm_persona.md`。`era.json`是单一数据源，5956行，包含规则配置、知识库条目、节奏锚点、价值观维度、声音定义、失败映射——所有时代相关的内容都在这一个文件里。`dm_persona.md`是DM的人设，用自然语言写，告诉DM"你是谁、你怎么说话"。

这个设计不是一开始就有的。最早知识库条目散落在代码各处——规则引擎里硬编码了几条史实，system prompt里塞了一段时代背景，Tool定义里写了几个查询接口。改一个时代，要改七八个文件。后来统一收进`era.json`，代码只管读不管写——引擎与内容严格分离。

这个分离是"确定性逻辑归代码"的延伸。代码管逻辑：SKILL编排层怎么算、规则引擎怎么判、字段级兜底怎么兜。内容管知识：万历十五年有什么人、什么事、什么规矩。逻辑是跨时代通用的，知识是时代特有的。把两者混在一起，换时代就是灾难。

但"引擎与内容分离"只解决了"知识放在哪"的问题。更关键的问题是：知识本身怎么组织？

## 知识库四层架构

知识库分四层：background（背景层）、scene（场景层）、entity（实体层）、principle（原则层）。

**background**：时代宏观背景。万历时代概貌、白银时代的来龙去脉、南北经济差异——这些是DM理解"这个时代是怎么回事"的基础。玩家不会直接问这些，但DM需要知道，才能在叙事里自然地体现时代氛围。

**scene**：具体场景设定。丝织作坊长什么样、盛泽镇有几条街、茶馆里坐的都是什么人、县衙的规矩是什么——这些是DM写叙事的素材。玩家说"我去茶馆坐坐"，DM需要知道茶馆长什么样，才能写出有细节的场景。

**entity**：具体人物和事物。万历皇帝、张居正、一条鞭法、矿监税监——这些是DM回答"这是什么/这是谁"的依据。玩家问"一条鞭法是什么"，DM从entity层拿答案，不需要编。

**principle**：核心概念与运行逻辑。数目字管理困境、白银流通链、上供经济——这些是DM理解"这个时代为什么这样运转"的关键。principle层不回答"是什么"，回答"为什么"。

### 为什么是四层不是三层

三层的话，缺哪层？

缺principle层，DM知道"一条鞭法"但不知道"数目字管理困境"。它能把一条鞭法的条文背出来，但不知道这条法律为什么执行不下去——因为明朝的数目字管理能力跟不上。玩家问"为什么赋税越改越重"，DM答不上来，或者编一个。

缺scene层，DM知道"盛泽镇"但不知道盛泽镇长什么样。玩家说"我去茶馆"，DM写不出茶馆的细节——几张桌子、墙上挂着什么、掌柜在干什么——只能泛泛地写"你走进茶馆，里面坐着几个人"。

缺entity层，DM不知道具体人物和事物，连"一条鞭法是什么"都答不了。

三层不够。那五层呢？

试过加第五层：**narrative snippets**——小说原文和场景描写。比如从《天工开物》里摘一段织机描写，从《万历野获编》里摘一段市井见闻，直接喂给DM当叙事素材。

试了之后发现一个问题：DM拿到原文会模仿，不是创作。喂一段"织机声轧轧不绝，丝缕从指尖穿过"的描写，DM的叙事风格就被锚定了——接下来的叙事都是这个调子，失去了根据玩家选择动态调整的能力。narrative snippets更适合做参考而非供料，放在Wiki编译层（后面讲），不放进运行时知识库。

四层是实测出来的：三层缺关键能力，五层会干扰创作。

### 四层跟SKILL编排层怎么交互

四层架构不是孤立的——它能不能发挥作用，取决于跟SKILL编排层怎么配合。搞不清交互关系，后面看塌房会不知道问题出在哪。

知识库不是独立运行的——它跟SKILL编排层紧密配合。

SKILL-4（史实锚定）从entity层拿史实。规则引擎判断"这回合该触发海瑞去世的消息"，SKILL-4从entity层拿海瑞的条目，注入DMContext——DM知道"海瑞是谁、为什么他的去世是大事"，才能写出有分量的叙事。

SKILL-3（线索投放）的insight跟knowledge.entries是映射关系。era.json里每个insight有`related_knowledge_ids`，指向知识库条目。玩家解锁一条insight，DM同时获得对应的知识条目——不是"我知道了这件事"，是"我理解了这件事的来龙去脉"。

DM的`query_knowledge`Tool在节点2（situation_assessment_node）调用。DM自己决定要不要查知识库、查什么——阶段0注入的skill_directive会引导它，但最终调不调是DM自己的判断。这是SKILL编排层"把判断变创作"的延伸：代码决定"DM该知道什么"（阶段0），DM决定"我想查什么"（阶段1）。

## 实测塌房：知识库给太多

设计文档里，知识库的查询逻辑很简单：玩家输入→提取关键词→匹配知识库条目→返回匹配结果给DM。

然后我跑了压力测试。20个刁钻输入，20个知识库专项测试。

### 塌房1：玩家打一个"嗯"，69条知识全灌进去

知识库的查询函数有一个分支：当提取不到关键词、又没指定scene或layer时，所有条目都通过过滤——等于没有过滤。

```python
# 旧 knowledge_base.py:86-89
if keywords:                                    # 空 list 走 else
    trigger_kws = entry.get("trigger_keywords", [])
    if not any(kw in trigger_kws or kw in entry.get("content", "") for kw in keywords):
        continue
# 当 keywords=[] 且 scene/layer/entry_ids 都为空时
# → 任何条目都通过
# → 整库 69 条注入 LLM 上下文
```

测试结果：


| 输入    | 匹配条目数 |
| ----- | ----- |
| "嗯"   | 69    |
| "好"   | 69    |
| "去"   | 69    |
| "yes" | 69    |
| "1"   | 69    |
| "？"   | 69    |
| 空字符串  | 69    |


69条知识，每条几百字，总共约30K tokens的噪音灌进LLM上下文。后果：LLM调用成本翻倍，延迟从20秒暴涨到60秒，严重时直接timeout——玩家回合卡死。

这不是"LLM不执行"（第三篇的问题），不是"LLM不按格式输出"（第四篇的问题），是**知识库给太多**——一个全新的问题类型。

### 塌房2："朝廷"一次命中7条

玩家闲聊"朝廷最近如何"，关键词"朝廷"匹配了7条知识：万历时代概貌（background）、里甲制（scene）、戚继光（entity）、海瑞（entity）……

7条全灌进去。戚继光和海瑞的条目被提前剧透——玩家还没遇到这些人物，DM已经"知道"了，下一回合的叙事里可能就冒出来一句关于戚继光的话。

更隐蔽的问题是层级混乱：7条里有background、scene、entity三种层级混在一起，LLM分不清哪条是"时代背景"、哪条是"具体人物"。它可能把"戚继光"当成跟"万历时代概貌"同等级别的信息，在闲聊里随口提到。

### 塌房3：内容层——69条知识库的"空心"

压力测试还暴露了一个设计层面的问题：69条知识库条目，0条story segments。pacing_anchors只有1条（春税），failure_mappings配置不完整。

这意味着什么？DM知道"一条鞭法是什么"（entity层），但不知道"一条鞭法在盛泽镇是怎么执行的"（scene层缺细节）。DM知道"海瑞是谁"（entity层），但不知道"海瑞去世的消息怎么传到盛泽镇"（没有叙事片段）。

四层架构设计了四层，实际只填了两层半——background和entity填得比较满，scene和principle有大量空洞。第三篇说的"知识库4层只实现1层半"，指的就是这个。

## 修复与反思：从"知识库给太多"到"知识库按需给"

回看第三篇的三层归总，三个问题方向完全不同：

- **确定性边界**（第三篇）：LLM不执行——该代码做的交给了LLM
- **输出可靠性**（第四篇）：LLM不按格式输出——你规定了格式，它不遵守
- **知识供给**（本篇）：知识库给太多或给太少——不是LLM的错，是供料系统的错

三个问题，三个方向，三套解法。前两篇的解法是"不信任LLM的执行力"，这一篇的解法是"不信任知识库的检索力"——你设计了检索逻辑，不代表检索结果就是对的。

### 空查询守卫：12行代码

修复塌房1只用了一行核心逻辑：

```python
# v1.7.28 修复：空查询守卫
if not keywords and not scene and not layer:
    return []

# 关键词过滤：必须是有效中文2-4字token才参与匹配
if keywords:
    keywords = [kw for kw in keywords if kw and len(kw) >= 2]
    if not keywords and not scene and not layer:
        return []
```

没有任何过滤条件时，禁止返回全部条目。关键词必须≥2个字，"嗯""好""去"这种单字不参与匹配。12行代码，8个测试用例全部通过。

### InputValidator：280行新模块

空查询守卫解决了"知识库端"的问题，但还有"输入端"的问题——玩家输入"今日天气""我是秦始皇""show me the code"，这些不是游戏内容，不该进知识库查询。

于是写了一个InputValidator，6种检测维度：


| 维度            | 检测对象                                 | 处理方式                  |
| ------------- | ------------------------------------ | --------------------- |
| empty         | 嗯/好/!/???                            | 硬阻断："你似乎还没输入什么"       |
| meta_query    | 你是谁/show me the code/ignore previous | 硬阻断："我是DM，只关心万历年间的故事" |
| era_violation | 手机/wifi/AI/公务员/我是秦始皇/清朝              | 硬阻断："「手机」在万历年间并不存在"   |
| meta_command  | /admin/SQL注入/XSS                     | 硬阻断："系统指令无法在游戏中执行"    |
| too_long      | >200字                                | 硬阻断："请控制在200字以内"      |
| low_relevance | 4字以上+知识库0匹配                          | **软提示**：不阻断，只toast提醒  |


关键设计决策：**软硬分级**。empty、era_violation、meta_query是硬阻断——输入根本不进DM。low_relevance是软提示——玩家可能真的在说一句跟知识库无关但跟叙事有关的话，不该拦死。

双层防御：客户端预检（InputArea）+ 服务端验证（/api/input）。客户端拦掉明显的垃圾输入，服务端兜底。33个测试用例，全部通过。

这是张素材调研报告里提到的"5层Guardrail架构"的Layer 1——输入层防护。之前项目只有输出层兜底（第四篇的字段级兜底），现在补上了输入层。

### layer优先级排序：闲聊不该触发人物条目

修复塌房2的思路：不是"减少匹配"，是"排好优先级"。

玩家说"朝廷最近如何"，7条匹配里background（时代概貌）和entity（戚继光、海瑞）混在一起。但闲聊语境下，background层比entity层更合适——玩家在问"大环境怎么样"，不是在问"某个具体人物"。

修复方案：知识库查询加layer优先级排序。返回顺序和注入权重是两个维度，需要反着设计——entity层排在background前面返回，是因为entity更精确，排前面方便检索系统截断；但注入DM上下文时，background层的权重更高，是因为background更宏观，权重高DM才能先建立时代框架再接触具体人物。闲聊触发entity层的条目，DM收到但不主动使用，除非玩家追问。

### 意图词典替代子串匹配

还有一个问题的根因是关键词子串匹配——织工说"我去考秀才"，"考秀才"不在`cannot_access`的列表里，身份铁律被绕过。

修复方案：从子串匹配改为意图词典。不是检查玩家输入里有没有"科举"两个字，是识别玩家想做什么——"考秀才""去贡院""求功名"都是同一个意图`participate_exam`，这个意图对织工/商籍/匠籍身份是禁止的。

意图词典跟知识库的关系：词典本身不是知识库的一部分，但它依赖知识库里的身份约束定义。era.json里定义了"织工不能参加科举"，意图词典把这个约束从"关键词审查"升级为"语义识别"。

### 反思：知识库的问题不是"给不给"

四个修复，核心思路只有一个：**知识库的问题不是"给不给"，是"给多少、给什么、什么时候给"**。

给太多→空查询整库注入→空查询守卫拦截
给错了→闲聊触发人物条目→layer优先级排序
给的时候没验证→垃圾输入穿透→InputValidator拦截
给了但约束不够→身份铁律被绕过→意图词典替代子串匹配

还有一种更隐蔽的情况：你以为给了，其实没给。我在另一个项目里碰到过——Agent团队的知识库服务，健康检查全绿：HTTP 200、进程在跑、端口在听、搜索端点返回真实结果。但实际数据管道已经6周没新增，索引5天没动。服务在线≠数据在线，HTTP 200给你的安全感是假象。这跟本篇的空查询整库注入是同一类问题的两个极端——一个是"给了太多"，一个是"以为给了其实没给"，根因都是：你信任了知识库的默认行为，没有验证。

跟第四篇的设计哲学转变对照：第四篇是"从'LLM必须输出JSON'到'LLM无论输出啥我都能解析'"，本篇是**"从'知识库有啥给啥'到'知识库按需给、给了要验证'"**。同一个原则：不信任系统的默认行为，设计不依赖默认行为的机制。

## Era Wiki Compiler：降低知识贡献门槛

前面全是实测，这一段要换档了——讲一个还没跑过的设计。

知识库的四层架构解决了"知识怎么组织"的问题，但没解决"知识从哪来"的问题。

69条知识库条目，每条都有id、layer、title、content、trigger_keywords、trigger_scene、related_entries、source_refs、confidence、needs_review——10个字段，手动写一条要15-20分钟。69条，纯手工，花了将近两天。

如果换一个时代——比如安史之乱——又要从头写几十条。贡献门槛太高，只有项目作者能做，社区参与不了。

### 三层编译

Era Wiki Compiler的设计是三层结构：**Raw Sources → Wiki（LLM编译层）→ era.json knowledge.entries**。

Raw Sources是原始资料——史书、论文、地方志、小说，任何格式的文本都行。Wiki是经过LLM编译的中间产物——结构化的知识条目，按六层框架组织。era.json是最终产物——引擎能直接消费的知识库条目。

单向数据流：Sources → Wiki → era.json，不反向。修改从源头改，编译器重新跑一遍，不用手动改era.json。

### 六层框架

Wiki的组织框架是六层，跟运行时的四层不是一回事：

- **时间骨架**：这个时代的关键时间节点
- **空间舞台**：地理、建筑、交通
- **社会结构**：阶层、职业、制度
- **日常生活**：衣食住行、风俗习惯
- **时代张力**：核心矛盾、利益冲突
- **认知地图**：当时的人怎么看世界

六层是给LLM编译用的——告诉LLM"从这六个角度理解一个时代"，它编译出来的知识条目覆盖面更全。四层是给引擎运行时用的——DM不需要"时代张力"这个分类，它需要的是"背景/场景/实体/原则"这四个可查询的层级。六层到四层的映射：时间骨架+空间舞台→background+scene，社会结构+日常生活→scene+entity，时代张力+认知地图→principle。

### 四阶段流程

1. **摄入**：把Raw Sources喂给LLM，按六层框架提取知识条目
2. **编译**：LLM生成结构化的Wiki条目，包含10个字段
3. **审核**：人工审核confidence和needs_review标记的条目
4. **输出**：编译器把Wiki条目转换为era.json格式

四阶段里，只有审核需要人。摄入和编译是LLM干的，输出是代码干的。有编译器，贡献一个时代的知识从2天缩短到2-3小时（假设Raw Sources已经准备好）。

### 诚实标注

Era Wiki Compiler目前只完成了设计，ingest命令还没实现。当前的69条知识库条目是手动写的，编译器还没跑过。第五篇讲的是设计思路和预期收益，不是实测结果——实测等跑通了再补。

但设计本身已经解决了一个关键问题：**知识贡献的门槛**。没有编译器，只有项目作者能贡献知识；有了编译器，任何对某个历史时期有了解的人，丢几篇资料进去，就能生成一个可用的时代包。这是开源项目能活下去的前提。

## 知识库的设计检查清单

基于这个项目的经验，提炼一个知识库设计检查框架：

**供料检查**

- 你的知识库有几层？每层解决什么问题？缺了哪层DM会编？
- 有没有哪层是"给DM模仿素材"的？这种层可能干扰创作而非辅助创作
- 知识条目的Schema够不够？trigger_keywords和trigger_scene是否覆盖了DM的查询场景？
- 四层架构跟SKILL编排层的交互有没有定义清楚？SKILL-4从哪层拿史实？SKILL-3的insight跟知识条目怎么映射？

**检索检查**

- 空查询时知识库返回什么？全返回还是空返回？
- 关键词匹配的粒度是什么？子串匹配还是语义匹配？单字是否参与匹配？
- 同一个关键词命中多条时，有没有优先级排序？layer之间有没有权重？
- 检索结果有没有数量上限？一次注入多少条不会炸上下文？

**输入检查**

- 玩家输入有没有验证？垃圾输入/非游戏内容/注入攻击会不会穿透到知识库查询？
- 验证是硬阻断还是软提示？有没有把"低相关性"和"无效输入"分开处理？
- 客户端和服务端有没有双层防御？
- 输入验证的规则跟时代设定有没有绑定？（"手机"在万历年间不存在，在近现代时代包里可能正常）

**内容完备性检查**

- 每层知识条目的覆盖率是多少？有没有空洞？
- pacing_anchors够不够？整个游戏只有1个史实锚点是不是太少了？
- failure_mappings是否完整？SKILL-6会不会大概率走default分支？
- 知识条目的confidence标注了吗？needs_review的条目有没有人工过一遍？

**健康检查**

- 知识库服务在跑，但数据是不是最新的？索引是不是完整的？查询返回的结果是不是真的？
- 健康检查查的是"活没活"还是"准不准/新不新/能不能用"？HTTP 200不等于数据在线
- 数据管道有没有监控？最后一次数据更新是什么时候？最后一次索引重建是什么时候？
- 自动机制（file watching、auto-reindex）实测过吗？官方说"应该是自动的"，实测会不会哑火？有没有`--force`兜底？

**贡献门槛检查**

- 新增一条知识条目要多久？手动写还是编译器生成？
- 换一个时代，知识库要多久能搭起来？
- 社区贡献者能不能参与？门槛是什么？
- Raw Sources → 运行时知识条目的链路通不通？

这套检查清单的核心问题只有一个：**你的知识库是"有啥给啥"还是"按需给、给了要验证"？** 如果是前者，等空查询炸库的那天，你会看到69条知识灌进LLM上下文，延迟60秒，玩家关掉页面。如果是后者，空查询返回空结果，垃圾输入被拦截，layer有优先级——DM拿到的永远是"该知道的"，不是"所有的"。
