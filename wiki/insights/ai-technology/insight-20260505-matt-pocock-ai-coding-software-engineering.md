# AI Coding时代软件工程本质：为什么基本功是最高杠杆率的武器

### **💡 核心观点：AI时代的软件工程基本功——不是退场，而是升值**

在大模型能快速生成代码的背景下，一种普遍错觉认为软件工程的"条条框框"（接口设计、架构边界、测试覆盖等）已不再重要。Matt Pocock在演讲中明确反对这一观点，提出**"在AI coding时代，软件工程的基本功不仅没有过时，反而比以往任何时候都更加重要"**。核心逻辑在于：**AI是放大器**——在边界清晰、接口稳定的代码库中会成倍提升效率；在依赖模糊、术语混乱的"屎山"代码中则会加速混乱。

### **要点速览**

| 核心洞见 | 具体含义 |
| :--- | :--- |
| **基本功升值** | 接口、边界、测试、反馈回路、统一语言决定AI是放大优势还是混乱 |
| **specs-to-code的危险** | 非模型能力问题，而是诱导过早放弃设计责任，持续注入系统熵 |
| **坏代码成本更高** | AI在好代码库放大优势，在坏代码库放大混乱，长期维护成本剧增 |
| **共享设计概念缺失** | "AI没做对"多因缺乏共同`design concept`，需先对齐"造什么"再讨论"怎么造" |
| **统一语言降低偏航成本** | `ubiquitous language`（领域驱动设计术语）解决AI啰嗦与偏航问题 |
| **反馈速度=速度上限** | 类型系统、自动化测试等反馈回路决定AI编码的实际效率，而非生成速度 |
| **深模块更适合AI** | 接口薄、内部厚的模块结构同时减轻人与AI的认知负担 |
| **人机分工：战略vs战术** | 人类聚焦模块边界/接口设计/质量标准，AI负责具体实现与快速试错 |

### **【1】specs-to-code：诱人的捷径还是软件退化的加速器？**

`specs-to-code`（从规格直接生成代码）表面看是软件开发的"自动编译器时代"，流程为：写规格说明→模型生成代码→不满足则改spec重新生成。但Matt通过实践指出其致命缺陷：**诱导开发者减少代码审查和系统设计思考**，导致代码持续熵增（"代码越来越乱"）。

**关键问题**：不是模型偶尔写错，而是开发者过早放弃设计责任。这一模式并非自动化软件设计，而是**自动化软件退化**——将本该由人承担的结构责任提前转移，最终导致系统失控。

### **【2】坏代码的代价结构：为什么现在比历史上任何时候都更贵？**

"代码生成成本降低"仅指"生成一段代码的动作"，而**坏代码的长期成本（维护、修改、测试、理解）在AI时代显著上升**。原因在于AI改变了代价结构：
- **好代码库**：AI能识别清晰接口、稳定边界和完整反馈，放大效率优势
- **坏代码库**：AI读取到的是噪音、模糊依赖和错误自由度，放大混乱

**结论**：AI将软件工程基本功的回报率拉得更高，"坏代码更贵"是基本功缺失的直接结果。

### **【3】共享设计概念（design concept）：解决AI"做不对"的核心钥匙**

多数"AI没做成想要的东西"并非模型能力不足，而是**人与AI缺乏对"我们到底在造什么"的隐性共识**。`design concept`包含5个核心要素：
1. 目标是什么
2. 哪些约束是硬约束
3. 需求还有哪些分叉
4. 什么算完成
5. 质量标准在哪里

**实践方法**：类似`Grill Me`技能的需求深度拷问——先问透需求分叉、决策依赖和硬约束，再动手实现。本质是**先对齐"造什么"，再讨论"怎么造"**，避免因概念分歧导致返工。

### **【4】统一语言（ubiquitous language）：降低AI偏航成本的地基**

AI啰嗦且越聊越偏的问题，根源在于缺乏领域驱动设计（DDD）中的`ubiquitous language`（统一语言）。对AI而言，这不仅是文档整洁问题，而是**确保规划、讨论和实现围绕同一套术语和概念地图运转**。

**实施步骤**：扫描代码库和规划材料，整理关键术语（如"订单""模块""发布"）成文档，在协作中反复使用。效果包括：减少AI废话、提升实现与计划的对齐度、降低沟通成本。

### **【5】反馈回路：AI编码的速度上限**

类型系统、浏览器环境、自动化测试等反馈回路不是"配料"，而是**决定AI编码速度的核心约束**。Matt引用《The Pragmatic Programmer》中的`outrunning your headlights`（跑得比车灯照得还快）概念，指出：**反馈速度就是速度上限**。

**关键实践**：避免模型"一口气生成大量代码"，而应通过小步反馈（实现→type check→浏览器反馈→测试→修正）确保每步结果可信，降低偏航风险。

### **【6】TDD的价值：强迫AI小步前进的纪律**

测试驱动开发（TDD）在AI时代的核心价值不是教条，而是**强迫LLM遵循"小步前进"的节奏**：
1. 写测试（明确预期）
2. 测试失败（确认初始状态）
3. 最小实现（只满足当前测试）
4. 测试通过（验证正确性）
5. 重构（优化结构）

**深层逻辑**：TDD将"验证"前移为每一步的硬约束，使AI输出更可控，同时构建"天然更容易测试的代码库"。

### **【7】深模块（deep modules）：同时减轻人与AI的认知负担**

深模块（接口简单、内部功能厚）比浅模块（功能薄、接口复杂）更适合AI时代：
- **浅模块问题**：导致模型在细碎节点间穿梭，因结构散、依赖乱浪费上下文
- **深模块优势**：AI只需理解模块边界和接口即可实现；人类可聚焦接口设计而非内部细节

**设计原则**：**"设计接口，把实现委托出去"**——真正值得关注的是边界、模块地图和接口质量。

### **【8】AI时代的人机分工：人类做战略设计，AI做战术执行**

AI更适合作为"战术执行者"（写实现、跑改动、修报错、快速试错），而人类应聚焦"战略设计"，包括：
- 模块边界划分
- 接口设计
- 术语统一
- 质量标准定义
- 风险判断

**核心思想**：不是减少思考，而是**将思考投入更高杠杆的系统设计层面**，持续投资系统架构（Kent Beck"每天都要继续投资系统设计"）。

### **【9】实践案例：mattpocock/skills仓库——将基本功workflow化**

Matt开源的`mattpocock/skills`（58.2k stars）将演讲理念转化为可执行工作流，核心是**把软件工程基本功编码进Agent时代的协作流程**，而非绕开基本功。关键技能与理念对应：

| 技能 | 解决的问题 | 对应理念 |
| :--- | :--- | :--- |
| `/grill-me` | AI没做对需求 | 共享设计概念 |
| `CONTEXT.md`/ADR | AI啰嗦、偏航 | 统一语言 |
| `/tdd`/`/diagnose` | 反馈速度不足 | 小步反馈回路 |
| `/zoom-out`/`/improve-codebase-architecture` | 系统熵增 | 深模块与架构设计 |

**本质**：不是提供Prompt模板，而是将"设计先行、边界清晰、反馈闭环"等原则转化为可复用的工程动作。

### **📝 可落地实践建议**
1. **需求深度拷问**：让AI在动手前追问需求细节、约束和分叉
2. **建立统一语言文档**：确保规划与实现使用同一套术语
3. **构建小步反馈回路**：优先配置类型检查、浏览器反馈和自动化测试
4. **重构为深模块**：将碎片化代码整合为接口薄、内部厚的模块
5. **转移时间投入**：从"盯实现细节"转向"定义接口、边界和质量标准"

### **🔍 关键洞察**
- **工具进化≠能力跃升**：代码生成速度提升可能掩盖系统崩坏风险，基本功是驾驭AI的"缰绳"
- **Harness Engineering**：用软件工程思维指导AI Coding，核心是定义标准、设计系统和反馈回路
- **工程师价值重构**：当代码生成变便宜，稀缺能力转向系统设计与质量把控，而非手动编码
