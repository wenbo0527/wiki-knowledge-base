### 🏗️ Coding Agent 真正的难点是什么？

**写代码只是小问题，保持工作连续性才是核心**。
- **典型场景**：Agent 修好了会员跨月折扣的目标测试 → 第二天发现**跨时区订单**未覆盖 → 任务并未真正结束。
- **核心挑战**：版本起点、事实时效性、动作记录、测试证明、未验证问题，全程都要对齐。

### 🧩 Sebastian Raschka 的六组件框架是什么？

六个组件深度交织，共同构成 Coding Agent 的运行能力。
- **实时仓库上下文**：开工前收集**稳定事实**，避免裸奔。
- **提示词缓存**：稳定前缀复用，只处理每轮增量。
- **工具**：结构化动作 + 校验 + 审批 + 路径约束，少给自由、多换可靠。
- **上下文管理**：裁剪、去重、按新旧差异化压缩。
- **会话记忆**：完整转录（可恢复）+ 工作记忆（蒸馏态）双层分离。
- **子代理**：支持并行，但必须圈好边界。

### ⚙️ 为什么说 Coding Agent 是受控任务状态机？

六组件提供能力，运行时要始终对齐**任务状态、动作边界、完成证据**三条线。
- **任务状态**：目标、基线、当前进度、停止点。
- **动作边界**：本轮可做什么，哪些动作需批准。
- **完成证据**：改了什么、验证过什么、还有什么没证明。
- 任何一条没对齐 → Agent 仍在输出，但已脱离真实现场。

### 🔄 研发任务的循环链路里，各环节靠什么？

六个组件分散在执行链各处，每个环节都有对应风险。

| 任务环节 | 主要依靠 | 最易出现的问题 |
| :--- | :--- | :--- |
| 观察现场 | 仓库上下文、提示词、上下文治理 | 分支看错、规则漏读、旧信息未失效 |
| 判断下一步 | 当前工作集、任务状态 | 把假设当事实，任务范围悄悄扩大 |
| 执行动作 | 工具、参数校验、权限 | 路径越界，外部副作用重复执行 |
| 核对结果 | 测试、Diff、日志、业务确认 | 局部通过被写成全部完成 |
| 中断恢复 | 会话记录、检查点、Git | 能续聊，却接不上真实现场 |
| 并行探索 | 有边界的子 Agent | 摘要互相冲突，多方同时改权威状态 |

说白了，Agent 进工程现场，代码基线、最小权限、测试、交接这些老办法一个也省不掉。

### 📋 开工前怎么把一句话变成任务卡？

**先收窄成小任务卡，只记最易变化的现场**。
- **任务卡示例（修复会员跨月折扣 CI 失败）**：
  - **目标**：跨月订单按现有规则正确计算折扣
  - **非目标**：不调价格表、不改数据库迁移、不处理生产退款
  - **基线**：分支 `release/2026-08`、保留 `payments/README.md` 他人修改
  - **已确认**：失败用例跨 7 月 31 日 / 8 月 1 日，折扣按自然月计算
  - **待确认**：业务时区以账户、门店还是系统配置为准
  - **完成条件**：目标测试通过 + 类型检查通过 + Diff 在约定范围 + 未覆盖风险写入交接
  - **停止点**：业务口径不清时停 / 需改价格表、迁移时停
- **状态更新原则**：每步重记现场，例如"目标测试通过，但跨时区行为仍未确认"，不勉强写"已修复"。

### 🗂️ 长任务的三类记录怎么分？

任务变长、参与者变多后，三类记录分开存，先不引入庞大平台。

| 记录类型 | 保存内容 | 更新方式 |
| :--- | :--- | :--- |
| 任务状态 | 基线、步骤、阻塞点、下一步 | 带版本更新，同一时刻唯一权威 |
| 动作日志 | 工具调用、参数摘要、动作 ID、结果 | 追加为主，不覆盖已发生动作 |
| 证据引用 | Diff、测试报告、日志、截图、审批 | 指向可复核产物，不靠自然语言转述 |
- **最小状态记录示例**：
  ```
  run_id: billing-discount-20260801
  step: verify-timezone-boundary
  step_version: 4
  last_action_id: test-017
  status: blocked
  evidence: target-test.xml, discount.patch
  next: confirm business timezone
  ```
- **边界判断**：单仓库单分支时，Git + CI + 结构化任务卡够用；跨多系统、有并发写入和外部副作用时，独立状态层收益才明显。

### 📚 上下文怎么保存才有效？

**事实要带出处，也要带"保质期"**，不能保存所有文字。
- **两类上下文区分更新**：
  - 稳定约定（测试命令、目录职责、代码规范、禁改区域）→ 进提示词前缀，便于缓存复用
  - 任务现场（当前分支、失败日志、本轮 Diff、待确认口径）→ 随工具执行及时更新
  - 过期观察必须失效，不能因"曾经读过"就保留权威性
- **缓存失效实例（Mini Coding Agent）**：
  - 问题：文件被 `write_file` / `patch_file` 改过，旧的读取去重状态没清 → 模型看到旧内容
  - 修复代码：`if tool_name in {"write_file", "patch_file"}: seen_reads.discard(path)`
- **事实三要素**：事实内容 + 来源或版本 + 最近观察时间
  - 代码事实 → 绑定 commit 和文件路径
  - 业务规则 → 绑定文档版本或确认人
  - 线上现象 → 绑定请求 ID 和日志时间

### 🛠️ 工具为什么是动作边界而不是菜单？

上下文决定看到什么，工具决定能改变什么，**副作用不同的动作不能用同一套权限**。
- **Codex 公开文档的两层控制**：沙箱限定技术访问范围，审批策略决定何时需人工允许。
- **动作分级与控制**：

| 动作等级 | 常见动作 | 更稳的控制 |
| :--- | :--- | :--- |
| 观察 | 读代码、搜日志、看 Diff | 限制可见范围，记录来源与时间 |
| 本地可回滚 | 改工作区、跑测试、生成草稿 | 限制目录和命令，保留 Diff 与结果 |
| 外部可撤销 | 建 issue、发 draft PR、改测试环境 | 明确身份、目标系统和回滚方式 |
| 高成本/不可逆 | 发布、删库、付款、退款 | 单独审批、幂等键、执行后对账 |
- **权责划分**：模型负责提出下一步，运行时负责判断这一步能否发生。

### ⏱️ 外部动作超时后该怎么做？

**超时不等于未执行，重试前先对账**。
- **四个前置环节**：
  1. **执行前**：读当前状态，确认前置条件
  2. **执行时**：携带请求 ID 或幂等键
  3. **超时后**：先查询真实结果，不自动重放
  4. **部分成功**：有补偿、对账或人工接管入口
- **会话恢复 vs 幂等对账**：前者解决"讨论从哪继续"，后者解决"现实里已发生什么"，职责不能混。

### 🧠 记忆、检查点、Git 各管什么？

别把所有东西都塞进"记忆"，**分开保存恢复才省事**。

| 内容 | 回答的问题 | 更合适的保存位置 |
| :--- | :--- | :--- |
| 运行状态 | 任务走到哪一步，下一步是什么 | 任务卡、工作流状态、检查点 |
| 可复用知识 | 业务规则和工程约定是否适用 | 带来源、版本、有效期的知识层 |
| 变更历史 | 哪些文件在什么基线上被修改 | Git、Diff、构建产物 |
| 审计证据 | 谁批准过，执行了什么，结果如何 | 测试记录、日志、审批与审计系统 |
- **Claude Code 检查点边界**：可跟踪直接文件编辑并随会话保存，但 Shell 命令产生的文件变化、部分子 Agent 修改、外部并发改动不一定能回退。
- **分工**：检查点 = 会话内撤销；Git = 可审查的代码历史；外部副作用 = 自身状态查询 + 补偿。

### 👥 子 Agent 怎么用才稳？

**探索可以并行，状态迁移尽量串行**。
- **适合并行的场景**：定位调用链、分析日志、搜索相似实现、审查 Diff（读多写少）。
- **并行写入的问题**：多个子 Agent 同时改代码 / 更状态 → 主任务收到三份自信摘要 → 协调成本高于节省的时间。
- **子任务交接四要素**：结论（发现了什么）+ 证据（文件、行号、日志）+ 边界（没检查什么）+ 建议（下一步动作与风险）。
- **并行修改的底线**：至少按文件所有权、分支或工作树隔离，合并前重跑同一套验证。

### ✅ 测试通过等于任务完成吗？

**完成分三层，声明不能超过证据范围**。
1. **实现完成**：代码落盘，Diff 符合范围
2. **技术验证完成**：目标测试、类型检查、构建通过
3. **业务验收完成**：行为符合真实业务口径和生产约束
- **交付说明示例**：
  - 改动：调整跨月订单日期边界计算，修改 `apps/billing/discount.ts`
  - 依据：已复现原 CI 失败，已核对折扣规则文档
  - 验证：目标测试通过 + 类型检查通过，全量回归未执行
  - 未决：跨时区订单缺业务口径，未改生产配置和历史数据
  - 下一步：业务确认时区规则后补回归用例

### 🚧 失败复盘的护栏该落在哪一层？

**失败发生在哪一层，护栏就尽量落在哪一层**，别全堆进项目说明。

| 反复出现的问题 | 更合适的落点 |
| :--- | :--- |
| 目标和非目标经常理解错 | 当前任务卡或任务模板 |
| 项目命令、目录约定常漏读 | 精简的 `AGENTS.md` / `CLAUDE.md` / Skill |
| 危险路径被修改 | 参数校验、hook、权限规则或沙箱 |
| 没跑验证就宣布完成 | 可执行检查、停止门或独立复核 |
| 外部调用超时后重复执行 | 状态查询、幂等键、对账与补偿 |
| 同一类错误重复出现 | 回归测试、静态规则或评估集 |
- **原则**：项目说明解释意图，底线问题交给确定性代码和运行时检查；偶发问题先写任务，同类问题连续出现再补稳定规则；涉及资金、数据、发布的副作用，更早放到执行层控制。

### 🚀 团队落地该从哪开始？

**从一条高频、低风险、易验证的窄链路开始**，别一上来搭完整平台。
- **四步放开示例（修复单元测试失败并生成 draft PR）**：
  1. **只读试跑**：允许读仓库、搜索、分析，人工决定修改
  2. **本地修改**：开放限定目录和指定测试，不访问外部系统
  3. **草稿交付**：允许生成 draft PR，要求附带 Diff、测试、未决风险
  4. **受控扩展**：根据真实失败，再评估网络、发布等外部动作
- **试跑评估指标（不数代码行数）**：
  - 多少任务动手前记录了基线与范围
  - 完成说明中多少结论可被测试、Diff、日志独立复核
  - 中断后恢复需补问多少现场信息
  - 外部动作超时后，有没有先查状态再重试
  - 人工介入集中在哪些节点（业务歧义 / 权限 / 验证不足）

### 📝 补充细节
- **产品能力引用边界**：Claude Code 和 Codex 的能力仅引用公开文档（项目指令、沙箱与审批、上下文压缩、检查点、会话恢复、子 Agent），公开资料只用于确认产品边界，不作为内部源码证据。
- **核心观点**：可靠的 Coding Agent = 知道行动依据 + 知道做到哪一步 + 知道什么时候该停下来。
