## 教训总结

> **任何"治本"方案必须同时具备"主动生成"和"自检告警"两层能力，缺一不可。**  
> 6-18 文博拍板的 C 方案只补了下半身（C-3 21:00 自检），漏了上半身（morning auto-write）——结果早上 10:24 文博追问时，**系统沉默 11h 无法响应**。

## 问题背景

2026-06-18 文博追问"我好像有几天没有看到我们的日报了"，盘查发现：
- 6-16 → 6-18 中间日报断档 39h25min
- 系统自动任务正常跑（dreaming/rss/tech_briefing/wiki_health 全部 ✅）
- 唯一缺失：**日报生成**环节

文博拍板 **C 方案**（治本）：
1. 补 6-17 daily
2. 上线 C-3 cron（每日 21:00 自检"24h 内日报落盘"）
3. 补 6-18 daily

**C 方案漏洞**：**没有"morning auto-write"脚本**——C-3 cron 只是"自检告警"，不能"主动生成"。

2026-06-19 早上 10:24，文博问"今天的日报呢"——C-3 cron 要到当晚 21:00 才会自检，**早 11h 是真空期**。

## 根因分析

### 技术层面
- 6-18 C 方案设计时，**只把"日报落盘"当成"晚上回看"任务**（21:00 自检）
- **没有把"日报生成"当成"morning 必须"任务**（08:30 主动生成）
- 两个 cron 触发时间应该错开（08:30 生成 + 21:00 自检），不是只做 21:00

### 流程层面
- **C 方案拍板时，缺"完整闭环检查"**——只问"C-3 cron 能不能发现问题"，没问"C-3 cron 之前谁来生成日报"
- **反思≠改变**：6-8 INC 后我们写了 SOUL §8.1 三条硬约束（C-1/C-2/C-3），但 C-3 只覆盖"自检"，没覆盖"生成"

### 组织层面
- **没有"早 11h 真空期"的概念**——任何 cron 间隔 > 12h 的自检都有这个风险
- **日报是 morning 消费品，不是 evening 任务**——这个用户感知没在 HEARTBEAT.md 里显式说明

## 正确做法

### ✅ 应该做的

1. **任何治本方案必须双轨**：
   - 上半身：主动生成（morning auto-write daily）
   - 下半身：自检告警（21:00 c3 cron）
   - 两层必须**独立**，不能只做一层

2. **cron 间隔 ≤ 12h**：用户感知周期 < 12h 的资源（日报/简报）必须有 cron 覆盖

3. **daily 文件结构标准化**：
   - 顶部 frontmatter + `## ✅ 完稿时间` H2 标题
   - c3 + morning-daily 共用 `is_finished(filepath)` 函数（已实现）

4. **dry-run 不落盘**：测试脚本时用临时文件或 `--dry-run` flag，不直接污染现有 daily

5. **INC 闭环三件套**：INC 报告 + 根因分层（进程级/文件级/系统级）+ lessons 沉淀

### ❌ 不应该做的

1. **不要把"自检告警"当成"治本"**——它只能发现问题，不能解决问题
2. **不要让"自检"和"生成"共用同一触发时间**——真空期 13h 太大
3. **不要用 6-19 daily 做 dry-run 测试**——会污染 6-19 daily（已踩坑）
4. **不要在 c3 第一次跑出 0% ALERT 时不深究根因**——可能是"完稿"判断标准问题，不是日报真的没写

## 经验复用

### 可复用的场景

| 场景 | 如何复用 |
|:---|:---|
| **任何 cron 间隔 > 12h 的自检** | 加 09:00 双触发 + 早上 auto-write 双层闭环 |
| **daily 完稿判断** | 共用 `is_finished()` 函数（要 `## ✅ 完稿时间` H2 + size > 2KB）|
| **INC 根因分析** | 按进程级/文件级/系统级分层（6-15 L-5 模板）|
| **dry-run 测试** | 用临时文件 `/tmp/test_daily.md` 而不是直接动 daily/ |

## 关键反思

> **问"How"不问"Why"**

1. 这个问题当时是怎么一步步发生的？
   - 6-18 早上文博追问"日报缺失" → 盘查 39h 断档 → 拍板 C 方案 → 写 C-3 cron（21:00 自检）→ **没有写 morning auto-write 脚本** → 闭环看似完成。
   - 6-19 早上 10:24 文博问"今天的日报呢" → Nick 手动写日报 → 才意识到 **C-3 cron 是"告警警察"不是"生成工人"**。

2. 为什么当时 C 方案只补 C-3 cron 是"合理"的？
   - C-3 cron 在 6-18 21:00 跑了一次（ratio=100%），**给了我们虚假的"治本"感**
   - 我们以为"C-3 跑通 = 治本闭环"，**没问"C-3 跑通之前怎么办"**

3. 真正的失败模式：
   - 不是技术失败（脚本能跑、cron 能触发、c3 能识别）
   - 是**设计失败**——"自检"和"生成"是两个独立能力，不能合并
   - 是**反思失败**——6-8 写了 C-3，但没问"还有没有 C-4/C-5"
