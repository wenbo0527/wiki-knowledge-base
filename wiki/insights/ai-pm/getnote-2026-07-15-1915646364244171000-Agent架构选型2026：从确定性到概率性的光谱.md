## 一、起点：Workflow和Agent不是对立面

想象一个场景：你的团队要做一个"用户上传合同，AI提取关键条款"的功能。

很多团队拿到这个需求，第一反应是上Agent——让AI自己规划提取流程，多酷啊。给它一个开放循环："你是一个合同分析专家，提取所有关键条款"，让它自己决定调用什么工具、按什么顺序、什么时候停。

但如果你换一种做法——写一个提示链：第一步OCR提取文字，第二步LLM提取甲方乙方，第三步LLM提取金额和日期，第四步格式化输出。四步固定，每步的输出是下一步的输入。

两个方案都能完成同一个任务。但成本差3-10倍，调试难度差一个数量级，稳定性差两个数量级。提示链的每一步你都能预判，开放循环你可能连它调了几次工具都说不清。

**这不是"哪个更好"的问题，是"你的任务需要多少确定性"的问题。**

行业里有一种常见的误解：Workflow是"简单的"，Agent是"先进的"，选型就是从简单升级到复杂。但Anthropic在2026年的构建指南里反复强调一句话："We recommend finding the simplest solution possible, and only increasing complexity when needed. This might mean not building agentic systems at all."

这句话的核心不是"别用Agent"，而是——**Workflow和Agent不是对立面，是同一条光谱的两端。**

光谱的左端是完全确定性：人替模型做所有决策，模型只负责执行每一步的"思考"部分。提示链、固定流水线都在这里。

光谱的右端是完全概率性：模型自己做所有决策，包括下一步做什么、用什么工具、什么时候停。开放Agent循环、Swarm涌现在这里。

中间是渐变地带：人定框架，模型在框架内决策。路由、编排者-执行者、评估器-优化器都在这个地带——它们是Workflow，但已经让模型做了一部分决策。

**选型的本质不是"用Workflow还是Agent"，而是"你能容忍多少概率性"。** 这取决于三个变量：任务的确定性程度有多高、失败的成本有多大、你的工程能力能不能兜住概率性带来的风险。

这篇综述要做的事：把这条光谱画出来，把每种模式放到它该在的位置上，然后给你一个从"容忍度"出发的决策路径。

## 二、单Agent设计模式：在光谱上定位

单Agent是光谱的中段——它已经让模型做决策了，但决策的范围被约束在一个循环里。

### 2.1 四种核心模式

**ReAct循环**（2022）：推理和行动交替进行。模型先"想"一步，再"做"一步（调用工具），观察结果，再想下一步。这是单Agent的默认范式——大多数Agent框架的底层都是ReAct。

**Plan-and-Execute**（2023）：先规划后执行。模型先把整个计划列出来，再逐步执行。和ReAct的区别是：ReAct是"走一步看一步"，Plan-and-Execute是"先看全貌再走"。对需要全局视角的任务（如多步骤推理、长链研究），Plan-and-Execute更稳定；对需要灵活应变的任务（如实时调试），ReAct更敏捷。

**Reflection**（2024）：自我反思。模型生成结果后，再审视一遍自己的输出，判断是否有问题，如果有就修正。这不是一个独立的循环，而是叠加在任何模式上的"质量层"——ReAct+Reflection、Plan-and-Execute+Reflection都成立。

**Tool Use**（2024）：工具调用。模型根据当前状态选择调用哪个工具。这不是一个独立的模式，而是所有Agent模式的基础能力——没有Tool Use，Agent就是"只会说话的LLM"。

### 2.2 在光谱上的位置


| 模式               | 谁决定下一步    | 确定性程度    | 典型场景       |
| ---------------- | --------- | -------- | ---------- |
| Plan-and-Execute | 模型规划，人可审批 | 较高       | 多步骤研究、长链推理 |
| ReAct            | 模型实时决策    | 中等       | 调试、搜索、灵活应变 |
| ReAct+Reflection | 模型决策+自检   | 中等（质量更高） | 需要高准确率的任务  |
| 开放循环（无停止条件约束）    | 模型完全自主    | 较低       | 探索性任务（风险高） |


### 2.3 关键数据：单Agent够不够用？

2026年的实证研究给出了一个让多Agent拥护者不舒服的结论：

- 单Agent在64%的benchmark上与多Agent持平（arXiv:2512.16698）
- 多Agent平均只增加2.1个百分点准确率，但成本翻倍（同上）
- 顺序推理任务上，多Agent反而降低39-70%性能（2026天池论坛Agent框架报告）

这意味着什么？**如果你的任务不需要领域隔离或并行执行，单Agent+更多工具可能是更优解。** 编排价值公式可以量化这个判断：

> 编排价值 = 领域隔离收益 − (Token膨胀 + 延迟累积 + N²冲突成本)

价值为正时，多Agent值得；价值为负时，单Agent+更多工具为最优解。

但有一个重要的边界条件：开源模型（如Qwen-2.5-VL，能力偏弱）多Agent收益显著（+3.3到+6.8分），闭源模型（如Gemini-2.0-Flash，能力较强）在经典benchmark上单Agent反而更好。**模型能力越强，单Agent的竞争力越大——因为强模型不容易被context污染。**

## 三、多Agent设计模式：从半确定性到涌现

多Agent是光谱的右半段——多个模型实例各自做决策，通过某种机制协调。

### 3.1 四种核心模式

**Orchestrator-Workers（编排者-执行者）**：一个中央Agent负责任务分解和委派，多个Worker Agent各做各的。这是多Agent里确定性最高的——编排者定义了"谁做什么"，Worker只在分配到的领域内自主决策。

**对等协作（Peer Collaboration）**：多个Agent平等对话，没有中心协调。每个Agent都可以发起讨论、响应请求。确定性中等——没有"谁说了算"的机制，依赖Agent间的自然协商。

**共识投票（Consensus Voting）**：多个Agent独立完成同一任务，通过投票或加权平均决定最终结果。确定性中等偏低——投票机制本身是确定的，但每个Agent的输出是概率性的，且投票可能陷入僵局。

**Swarm/涌现（Emergent）**：无中心协调，Agent通过简单的局部规则交互，期望全局行为从局部交互中涌现。确定性最低——你无法预测系统会做什么，只能观察。

### 3.2 在光谱上的位置


| 模式                   | 谁决定谁做什么  | 确定性程度 | 协调开销 | 典型场景       |
| -------------------- | -------- | ----- | ---- | ---------- |
| Orchestrator-Workers | 编排者分配    | 较高    | 中等   | 动态任务分解     |
| 对等协作                 | Agent间协商 | 中等    | 较高   | 跨领域讨论      |
| 共识投票                 | 投票机制     | 中等偏低  | 高    | 需要多视角决策    |
| Swarm/涌现             | 无中心      | 很低    | 很高   | 探索性研究（实验性） |


### 3.3 多Agent什么时候值得？

实证研究给出了三种多Agent能稳定胜过单Agent的场景：

1. **Context污染拖累性能**：单Agent上下文被多领域信息塞满，注意力分散。拆成多个专业Agent，每个只看自己领域的信息。
2. **任务可并行执行**：子任务间无依赖，可同时推进。并行化带来的速度收益超过协调开销。
3. **专业化能改善工具选择或任务专注度**：每个Agent只做一件事，工具选择更精准，不容易"手忙脚乱"。

三种场景之外，多Agent的协调开销通常超过收益。多Agent框架成本是单Agent的3-5倍，但质量提升不足50%。Anthropic 2026年6月的报告显示，SWE-bench上5个专业Agent协作团队完成率78.4%，同参数量单体Agent仅41.2%——但这是在**复杂工程任务**上的结果，不适用于所有场景。

**核心判断：多Agent不是默认更先进，而是一种有严格适用条件的架构选择。** 当编排价值公式为正时值得，为负时是浪费。

## 四、Workflow和Agent的关系：光谱的完整图景

### 4.1 五大Workflow模式在光谱上的位置

Workflow不是Agent的对立面，而是光谱左端的起点。Anthropic提出的五大工作流模式，本身就是确定性程度递减的序列：


| Workflow模式                    | 谁做决策        | 确定性程度 | 关键特征                     |
| ----------------------------- | ----------- | ----- | ------------------------ |
| 提示链（Prompt Chaining）          | 人预定义每一步     | 最高    | 步骤完全固定，模型只负责"思考"         |
| 路由（Routing）                   | 人定义路径，模型做分类 | 高     | 分类决策交给模型，但路径是预设的         |
| 并行化（Parallelization）          | 人定义并行结构     | 高     | 多路同时执行，结构是预设的            |
| 编排者-执行者（Orchestrator-Workers） | 编排者动态分解     | 中     | **半只脚踏进Agent**——任务分解是动态的 |
| 评估器-优化器（Evaluator-Optimizer）  | 评估器决定是否重做   | 中偏低   | 循环次数不确定，但循环结构是预设的        |


**编排者-执行者是光谱的转折点。** 左边的四种模式，人定义了"做什么"和"怎么做"；编排者-执行者让人定义了"做什么"，但"怎么做"（怎么分解任务、分给谁）交给了模型。这已经是半概率性系统了。

### 4.2 双维度框架：流程确定性 × 内容确定性

单看"流程确定性"不够。同一个Workflow模式，处理不同确定性程度的内容，风险完全不同。需要一个双维度框架：


|            | 内容确定性高（规则明确、答案收敛）   | 内容确定性低（开放性、答案发散）    |
| ---------- | ------------------- | ------------------- |
| **流程确定性高** | **第一象限：安全区**        | **第二象限：流程可控、内容不可控** |
|            | 提示链 + 结构化提取         | 路由 + 开放生成           |
|            | 风险：低                | 风险：中（输出不可预测，但流程可控）  |
| **流程确定性低** | **第三象限：流程不可控、内容可控** | **第四象限：危险区**        |
|            | Agent + 强约束工具       | 开放Agent循环 / Swarm   |
|            | 风险：中（流程不可预测，但输出可校验） | 风险：高（流程和输出都不可预测）    |


**使用方法**：先判断你的任务落在哪个象限，再选架构。

- **第一象限**：用Workflow，最简单的那种。提示链就够了。
- **第二象限**：用Workflow，但加评估器-优化器做质量兜底。
- **第三象限**：用Agent，但约束工具范围和停止条件。ReAct+Reflection适合这里。
- **第四象限**：要么不上Agent（用Workflow+人工兜底），要么上Agent但必须配强可观测性和人工审批节点。

这个框架的核心洞察：**两个维度交叉才能定位场景，而不是一个维度一刀切。** 流程确定性高但内容确定性低的任务（如创意生成），和流程确定性低但内容确定性高的任务（如代码调试），需要的架构完全不同。

## 五、Harness工程：被忽视的隐藏变量

容忍更多概率性，意味着你需要更强的兜底能力——Harness工程就是你为概率性买的保险。容忍度越高，保费越贵。

讨论Agent架构时，大多数注意力放在"用什么模式"上。但决定一个架构在生产环境能不能活的，往往不是模式本身，而是模式底下的脚手架——Harness工程。

同样一个ReAct循环，配了状态持久化、断点恢复、全链路追踪的，是生产级Agent；什么都没配的，是Demo。你的Agent算Demo还是生产级？答案就在下面五个组件里。

### 5.1 Harness的五个组件


| 组件   | 解决的问题           | 不做的后果            |
| ---- | --------------- | ---------------- |
| 工具调用 | Agent如何与外部世界交互  | Agent是"只会说话的LLM" |
| 状态管理 | 执行到哪了、中间结果是什么   | 进程重启=会话丢失        |
| 权限控制 | Agent能做什么、不能做什么 | Agent可能越权操作      |
| 错误处理 | 工具调用失败怎么办       | 一次失败=全线崩溃        |
| 可观测性 | 出了问题能不能定位       | 黑盒调试，只能"再跑一次看看"  |


### 5.2 Demo到生产的五个坑

这五个坑来自亿级请求量架构白皮书的总结，每一个都对应一个Harness组件的缺失：

1. **状态放在内存里**：进程重启=会话丢失。生产环境必须持久化到数据库。
2. **没有中断恢复**：网络抖动=从头再来。LangGraph原生支持断点恢复，CrewAI不支持。
3. **并发靠语言原生多线程**：Python GIL瓶颈。生产环境需要图执行引擎或异步消息。
4. **没有可观测性**：出问题无法定位。必须全链路追踪、中间状态可审计。
5. **没有降级策略**：模型限速=全线崩溃。必须有fallback模型和超时机制。

### 5.3 核心判断

**Agent能力不只来自大模型，更来自Harness工程。** 同样一个ReAct循环，配齐了五个组件的是生产级系统，什么都没配的是Demo。这也是为什么框架选型很重要——不是框架本身决定了架构模式，而是框架决定了你的Harness起点。LangGraph默认持久化状态和断点恢复，CrewAI默认内存状态且不支持中断恢复。选错了框架，你会在Harness上花比业务逻辑更多的时间。

## 六、架构模式全景与选型决策

### 6.1 完整光谱图

```
确定性 ←————————————————————————————————————————————→ 概率性

提示链    路由    并行化    评估器-优化器    编排者-执行者    ReAct    Plan&Exec    Reflection    多Agent编排    共识投票    Swarm
  │        │       │           │                │            │        │           │            │            │         │
  └── Workflow ────────┘       └── 半只脚踏进Agent ──┘    └── 单Agent ──────────────┘    └── 多Agent ───────────────┘
```

**光谱上的关键转折点**：

- 编排者-执行者：从"人做决策"到"模型做决策"的过渡
- ReAct：从"预设流程"到"自主循环"的过渡
- 多Agent编排：从"一个决策中心"到"多个决策中心"的过渡

### 6.2 选型决策树

从"你能容忍多少概率性"出发：

```
你的任务步骤是否可预测？
├── 是 → 流程确定性高
│   ├── 内容是否收敛（答案是否唯一）？
│   │   ├── 是 → 第一象限 → 提示链（最简单）
│   │   └── 否 → 第二象限 → 路由+评估器-优化器
│   └── 是否需要动态分解？
│       ├── 是 → 编排者-执行者（半概率性）
│       └── 否 → 提示链或并行化
└── 否 → 流程确定性低
    ├── 失败成本有多高？
    │   ├── 高 → 第三象限 → Agent+强约束+人工审批
    │   └── 低 → 第四象限 → 可以尝试开放循环
    └── 是否需要领域隔离或并行？
        ├── 是 → 多Agent（编排价值公式为正时）
        └── 否 → 单Agent+更多工具
```

### 6.3 行业场景速查表


| 行业场景    | 流程确定性 | 内容确定性 | 推荐架构   | 典型模式             |
| ------- | ----- | ----- | ------ | ---------------- |
| 合同条款提取  | 高     | 高     | 第一象限   | 提示链              |
| 客服意图路由  | 高     | 中     | 第二象限   | 路由+评估器           |
| 代码调试    | 低     | 高     | 第三象限   | ReAct+Reflection |
| 创意文案生成  | 高     | 低     | 第二象限   | 评估器-优化器          |
| 复杂工程任务  | 低     | 中     | 第三/四象限 | 多Agent编排         |
| 开放性研究   | 低     | 低     | 第四象限   | 需强可观测性兜底         |
| 金融风控审核  | 高     | 高     | 第一象限   | 提示链+人工审批         |
| 多领域情报分析 | 低     | 中     | 第三象限   | 编排者-执行者          |


### 6.4 2026年的三个关键判断

**判断一：架构-任务对齐取代Agent数量成为成败关键。** 多Agent不是默认更先进，单Agent不是默认更简单。选型的标准是：架构的确定性程度是否匹配任务的确定性程度。

**判断二：Harness工程是隐藏变量。** 同样的架构模式，Harness配不配决定了它是生产级还是Demo级。先确保Harness到位，再追求架构模式的先进性。

**判断三：评测体系正在重建，别被旧Benchmark骗了。** SWE-bench已不再被业界视为可靠评测（训练数据污染+天花板效应+评分标准错误），高分不等于真实能力。LiveAgentBench显示最好的商业Agent成功率仅35.29%（人类69.25%）。评测对象从"最终结果"变为"任务完成路径+中间行为是否合规"。
