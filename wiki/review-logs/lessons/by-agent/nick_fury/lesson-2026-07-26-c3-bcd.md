## L-50.1：监控告警必须真信号 + 降噪双轨设计

**陷阱**：单告警重复推送（5 天 9 次）= 噪音掩盖真信号。

**治本**：
1. **完稿语义明确** —— `## ✅ 完稿时间` 标记是 Nick 主动信号，不是 size 阈值
2. **去重机制** —— `data/c3_alert_dedup.json` 记录 24h 内推送状态
3. **时间窗口分段** —— 09:00 骨架检查 / 21:00 完稿率检查，分工明确

**验证**：
- INC 之前：7-22 单天 4 次推送 → 真信号被噪音掩盖
- INC 之后：每天最多 1 次告警（21:00）+ 09:00 骨架生成静默

## L-50.2：正则匹配要严格（结构化前缀）

**陷阱**：骨架模板里有 `*待 Nick 确认/补充后修改"完稿时间"为 ✅*` —— 被首版正则 `完稿时间.*[✅完]` 误判为完稿（因为字符串里有"完稿时间"+"✅"）。

**治本**：完稿标记必须是**结构化前缀**：
```python
FINISHED_MARKER_RE = re.compile(r"^##\s*✅\s*完稿时间", re.MULTILINE)
```

**测试矩阵**：
| 内容 | 期望 | 旧正则 | 新正则 |
|:---|:---:|:---:|:---:|
| `> 完稿时间: ⏳ 待 Nick 确认` | ❌ | ❌ | ❌ |
| `*待 Nick 确认/补充后修改"完稿时间"为 ✅*` | ❌ | ✅（误判）| ❌ |
| `## ⏳ 完稿时间（morning auto-write 追加）` | ❌ | ❌ | ❌ |
| `## ✅ 完稿时间` | ✅ | ✅ | ✅ |
| `## ✅ 完稿时间 2026-07-26 18:30` | ✅ | ✅ | ✅ |

**复用场景**：所有"标记判定"正则必须要求**结构化前缀**（如 `## ✅ ` 二级标题、`# TODO` 注释标记），避免自然语言误判。

---

## L-50.3：时段判定必须 if/elif 显式分支

**陷阱**："cron 只在 9:00 和 21:00 跑"的假设不可靠 —— 手动跑 / 调试跑会触发非预期路径。

**反例**（修复前）：
```python
if current_hour == MORNING_HOUR:
    ...return 0

# 21:00 路径：检查完稿率  ← 顶层 if，12:30 跑也会进
if ratio < RATIO_THRESHOLD:
    ...
```

**治本**：
```python
if current_hour == MORNING_HOUR:    # 9:00 路径
    ...
    return 0

elif current_hour == EVENING_HOUR:  # 21:00 路径（含 dedup + 100% 清理）
    ...
    return 0

# 其他时段（12:30, 14:00, ...）→ 落到 sync + KB 独立检查，无 daily 告警
```

**复用场景**：所有"按时段执行不同逻辑"的脚本必须 `if/elif` 显式分支 + else 静默，不能依赖"cron 配置不跑该时段"的隐式假设。

## L-50.4：调试入口（mock env var）测完必删

**陷阱**：写 `C3_MOCK_HOUR` 环境变量调试 21:00 路径 → 测试通过后**忘了删** → 真实环境被环境变量污染。

**治本**：C-1 铁律 + L-15 治本要求：
1. 调试代码必加注释 "L-15 调试入口（仅测试用）"
2. 测试完**立即删**，不留 commit
3. bak 文件保留备查（含调试入口）

**验证**：
- 修复前：`C3_MOCK_HOUR` 留在 main 里 → 真实环境如果被 env var 污染会误判
- 修复后：mock hour 已删，bak 文件保留可回滚
