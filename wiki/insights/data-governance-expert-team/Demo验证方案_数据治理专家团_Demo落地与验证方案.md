# 数据治理专家团：Demo落地与验证方案

> 本文档为《数据治理专家团：完整架构方案（v1）》的落地补充，覆盖MVP范围、技术选型、Prompt配置、元数据灌入、准确率验证五部分。

---

## 一、MVP范围：3个鲸跑通最小闭环

Phase1先上探路鲸+问数鲸+调度鲸，解决"找数→问数→回答"的最短链路。

Demo阶段调度鲸可用硬编码路由代替意图判断，省掉分支逻辑的复杂度。核心验证命题：**多Agent协作比单Agent问数强在哪**。

需要跑出两个关键场景：
1. **单Agent搞不定的**：用户问"上个月逾期率为什么涨了"——单Agent要么只查数要么只归因，专家团能从问数→溯源→核规→归因一路串下来
2. **人工审核门控的价值**：问数鲸生成SQL后拦截执行，展示给用户确认——这是安全底线，也是和原诊断器最大的差异点

---

## 二、技术选型

优先OpenClaw（已跑过产品管理工作流，熟悉度最高），分支和回环用子流程嵌套实现。跑通后再考虑是否迁移到Dify/Coze等原生支持多Agent协作的框架。

## 三、Prompt配置

### 3.1 探路鲸

```
## 角色
你是数据治理专家团的探路鲸。你的唯一职责是：把用户的自然语言问题翻译成元数据定位结果。

## 输入
- 用户问题（自然语言）
- 元数据目录（表名、字段名、业务含义、所属模块）
- 要素字典（指标定义、口径说明）

## 输出格式（严格JSON）
{
  "matched_tables": [{"table_name": "", "confidence": "", "reason": ""}],
  "matched_fields": [{"field_name": "", "table": "", "confidence": "", "reason": ""}],
  "unmatched_keywords": [],
  "clarification_needed": true/false
}

## 硬约束
- 只做定位，不回答业务问题
- confidence分三档：high/medium/low，low必须标注reason
- 匹配不到的字段必须放入unmatched_keywords，不许编造
- 同一字段名在多张表出现时，全部列出并标注所属模块
- 关键词歧义时（如"逾期"可能指M1也可能指M1+），clarification_needed=true
```

### 3.2 问数鲸

```
## 角色
你是数据治理专家团的问数鲸。你的职责是：把业务问题+探路鲸的定位结果，翻译成可执行的SQL并返回答案。

## 输入
- 用户原始问题
- 探路鲸输出的元数据定位结果
- 口径定义（来自核规鲸快速模式，Demo阶段可先硬编码）
- 已验证SQL模板库（如有）

## 输出格式（严格JSON）
{
  "original_question": "",
  "sql": "",
  "sql_explanation": "",
  "caliber_basis": "",
  "review_status": "已验证|待确认|请小心",
  "answer": "",
  "confidence": ""
}

## 硬约束
- SQL必须展示给人类审核，review_status=待确认时禁止自动执行
- 口径不确定时必须列出所有可能口径，让用户选择
- 禁止DELETE/UPDATE/DROP，只允许SELECT
- 敏感字段（手机号、身份证）必须脱敏
- 单表预估行数>10万时，提示"建议用脚本取数"
- SQL必须带注释说明每段逻辑
```

## 四、元数据灌入格式

探路鲸依赖元数据做定位，灌入格式如下。现有数据发现模块和数据管理模块的元数据按此结构导出即可使用。

```json
{
  "catalog_version": "1.0",
  "last_updated": "2026-05-29",
  "tables": [
    {
      "table_name": "dm_loan_overdue_daily",
      "table_comment": "贷款逾期日汇总表",
      "module": "数字授信",
      "schema": "dm",
      "update_freq": "T+1",
      "fields": [
        {
          "field_name": "overdue_m1_cnt",
          "field_comment": "M1逾期笔数",
          "data_type": "int",
          "business_alias": ["逾期1-30天笔数", "M1笔数"],
          "caliber": "贷款到期日后1-30天内未还款的借据笔数，含宽限期",
          "caliber_source": "数据标准v2.1",
          "sample_values": ["0", "15", "230"],
          "related_fields": ["overdue_m1_amt", "loan_cnt"]
        }
      ],
      "common_queries": ["本月M1逾期率", "M1逾期金额趋势"]
    }
  ],
  "glossary": [
    {
      "term": "M1逾期率",
      "definition": "M1逾期金额/在贷余额",
      "formula": "overdue_m1_amt / loan_balance_amt",
      "source_tables": ["dm_loan_overdue_daily"],
      "note": "分母用期末在贷余额，不含已结清"
    }
  ]
}
```

### 关键字段说明

| 字段 | 为什么必须有 |
|------|------------|
| business_alias | 业务人员说"M1笔数"和字段名overdue_m1_cnt对不上，alias是桥梁，探路鲸命中率的第一决定因素 |
| caliber | 口径定义直接传给问数鲸，带着口径依据减少SQL语义错误 |
| sample_values | 帮模型判断数据类型和取值范围，避免生成离谱条件 |
| common_queries | 预埋高频问法，探路鲸匹配到表后能推荐关联问题 |
| glossary | 指标字典独立于表结构，一个指标可能跨多张表计算 |

### 灌入策略

1. 先灌5张核心表（逾期、放款、获客、在贷余额、还款），约50-80个字段
2. 先灌10个核心指标（M1逾期率、FPD30、获客成本、通过率、在贷余额、件均、复借率、资金成本、风险定价、不良率）
3. 跑通5个验证问题后再逐步扩展

### 从现有系统导出的快捷路径

- 数据发现模块 → 导出表名+字段名+注释 → 补上business_alias和caliber
- 数据管理模块 → 导出口径定义 → 对应到glossary和字段的caliber字段
- business_alias是唯一需要手工补的，系统里存的是技术名，业务别名只有人知道

## 五、准确率验证方案

分三层验证，从单Agent到端到端逐步推进。

### 5.1 第一层：探路鲸——元数据命中率

准备20个真实业务问题（从日常问数场景抽取），人工标注每个问题对应的正确表和字段。

| 指标 | 计算方式 | 及格线 |
|------|---------|--------|
| 表命中率 | 命中正确表的次数/总题数 | ≥85% |
| 字段命中率 | 命中正确字段的次数/总题数 | ≥70% |
| 歧义识别率 | 该提示歧义时正确标注clarification_needed的比例 | ≥60% |

命中率低通常两个原因：元数据描述不够（业务叫法和字段名对不上）、问题本身有歧义。前者补business_alias，后者靠探路鲸主动追问。

### 5.2 第二层：问数鲸——SQL正确率

同样20个问题，探路鲸定位完后喂给问数鲸，人工判断生成的SQL。

| 指标 | 计算方式 | 及格线 |
|------|---------|--------|
| SQL可执行率 | 语法正确且能跑通的/总题数 | ≥90% |
| 语义正确率 | 结果和人工写的SQL一致的/总题数 | ≥70% |
| 口径标注准确率 | caliber_basis和实际口径定义一致的/总题数 | ≥80% |

语义正确率70%在Demo阶段够用——有人工审核门控兜底，SQL不对时用户会拦住。口径标注准确率更重要，口径错了比SQL错了更危险。

### 5.3 第三层：端到端——用户满意度

找3-5个同事实际用一轮，不教怎么问，看自然提问下的体验。

| 指标 | 说明 |
|------|------|
| 完成率 | 问题最终得到正确答案的比例 |
| 返工率 | 需要追问或改写问题才能得到答案的比例 |
| 审核拦截率 | 人工审核时发现SQL有问题的比例（越高说明门控越有价值） |

### 5.4 快速启动路径

先从自己的日常问数场景挑5个最常见的问题，手动构造元数据（Excel导出成JSON即可），跑通探路鲸+问数鲸的链路。5个问题全对再扩到20个。

## 六、验证方案漏洞补丁（拷问后追加）

### 漏洞1：验证了单Agent能力，没验证协作增益

现有三层验证测的都是单个Agent能不能答对——探路鲸命中率、问数鲸SQL正确率、端到端完成率。但方案的核心卖点是"多Agent协作比单Agent强"，验证的东西和要证明的东西不是一回事。

协作可能有损耗：探路鲸命中率85%，但问数鲸拿到它的输出后SQL正确率反而可能下降（比如探路鲸返回了多张表的候选，问数鲸选错了）。

**补丁：增加协作增益测试**

同样20个问题，对比三种模式：

| 模式 | 说明 |
|------|------|
| 纯问数鲸 | 不给元数据定位，直接从问题生成SQL |
| 问数鲸+手工喂表名 | 人手工告诉问数鲸查哪张表 |
| 探路鲸→问数鲸自动传参 | 完整协作链路，探路鲸输出自动传给问数鲸 |

核心看第三种模式比第一种强多少（增益），以及比第二种差多少（协作损耗）。如果协作增益<10%，说明探路鲸的价值没发挥出来，要回去改Prompt或补business_alias。

### 漏洞2：所有问题等权看待，但错误后果天差地别

"逾期率"算错和"件均"算错，严重程度完全不一样——前者可能影响风控决策和监管报送，后者只是汇报偏差。现有方案把20个题的正确率一视同仁，一个核心指标算错和一个边缘指标算错对通过率的影响一样。

**补丁：按后果严重性分级**

| 级别 | 判定标准 | 及格线 | 典型题目 |
|------|---------|--------|---------|
| P0核心题 | 涉及金额/风险/监管的指标 | 正确率≥90% | 逾期率、不良率、FPD30、在贷余额 |
| P1业务题 | 日常经营分析指标 | 正确率≥70% | 件均、渠道占比、获客成本、复借率 |
| P2辅助题 | 描述性/统计类问题 | 正确率≥60% | 字段含义、表更新频率、数据来源 |

P0核心题挂一个比P2辅助题挂三个都严重。验证不通过时优先修P0的case。

### 漏洞3：端到端验证的"友好用户偏差"

让3-5个同事用一轮，但同事会迁就Demo——他们会下意识把问题改成系统能答的格式，跳过系统不擅长的问法。测到的不是"自然提问下的体验"，是"友好用户帮你调优"。

**补丁：增加对抗性问题集**

在正常测试题之外，故意放5个系统能力边界外的问题：

| 对抗类型 | 示例问题 | 期望行为 |
|---------|---------|---------|
| 需要归因的 | "上个月逾期率为什么涨了" | 诚实说"我目前只能查数，不能做归因分析" |
| 需要核规的 | "这个口径跟监管要求一致吗" | 诚实说"我无法判断合规性，建议咨询合规团队" |
| 跨系统关联的 | "这批客户在信用卡那边的表现怎么样" | 诚实说"我无法跨系统查询" |
| 模糊意图的 | "帮我看看最近的数据" | 追问具体要看哪个指标、什么时间范围 |
| 不存在的指标 | "我们的NPS是多少" | 诚实说"元数据中未找到NPS相关字段" |

关键看系统是诚实说"做不了"，还是硬编一个答案出来。硬编答案比答错更危险——答错用户会拦住，硬编用户可能直接用。
