### **🔍 AI Agent开发的核心痛点（背景）**

**典型问题场景**
- **架构约束缺失**：AI Agent因不了解团队架构规则（如`internal/types/`不能import `internal/config/`），生成代码违反分层约束，导致lint失败。
- **上下文窗口限制**：修复错误时，错误日志和diff迅速填满上下文，Agent"忘记"初始任务目标，形成"修复-新错误"循环。
- **隐式规则依赖**：团队规范文档（钉钉/Notion）无法被AI读取，依赖LLM"常识"导致不可靠，code review时发现大量规范问题。
- **缺乏验证机制**：Agent直接生成代码而不预先验证，类似"新入职工程师不提问直接动手"，导致引入新bug。

### **🏗️ Harness工程的核心理念（解决方案）**

**核心类比**：仓库是Agent的"操作系统"，LLM是"CPU"，Harness则是赋予Agent方向的"系统软件"。

#### **(一) 四大关键原则**
1. **仓库作为唯一事实来源**
   - 架构决策、层级约束、命名规范必须编码为**版本化文件**提交到Git，而非依赖Wiki或口头约定。
   - 知识与代码同步演进，新人或Agent克隆仓库即可获得完整上下文。

2. **AGENTS.md：地图而非手册**
   - 控制在**~100行**，仅做索引和指路，详细内容放在`docs/`目录按需加载。
   - 避免500行巨型指令文件挤占上下文窗口，同时降低文档腐烂风险。

3. **层级化架构约束**
   - 按依赖方向划分层级（Layer 0至Layer 4+），规则：**高层可import低层，反之不可**。
   - 示例分层：
     - Layer 0：类型定义（无内部依赖）
     - Layer 1-2：工具函数和配置（仅依赖更低层）
     - Layer 3：业务逻辑
     - Layer 4+：HTTP handler和CLI命令

4. **人类角色转变**
   - 从"写出正确代码"→"设计让Agent可靠产出正确代码的环境"。
   - 类比：从"拧螺丝"到"设计流水线"。

### **🛠️ Harness工程的落地架构（执行系统）**

#### **(一) 双引擎协作**
- **harness-creator**：分析代码库，生成基础设施（文档、lint脚本、目录结构），按文档/规则覆盖率评分（0-100分）。
- **harness-executor**：执行开发任务，工作流为"检测环境→加载上下文→制定计划→人类批准→执行→验证→完成"。

#### **(二) 项目目录结构**
```
my-project/
├── AGENTS.md                    ← 导航地图（~100行）
├── docs/                        ← 详细文档
│   ├── ARCHITECTURE.md          ← 架构、层级、依赖规则
│   ├── DEVELOPMENT.md           ← 构建/测试/lint命令
│   └── design-docs/             ← 组件设计文档
├── scripts/                     ← 验证脚本（核心）
│   ├── lint-deps.*              ← 层级依赖检查
│   ├── lint-quality.*           ← 代码质量规则
│   └── validate.py              ← 统一验证管道
└── harness/                     ← 状态管理与学习
    ├── tasks/                   ← 任务状态和检查点
    ├── trace/                   ← 执行轨迹和失败记录
    └── memory/                  ← 经验教训存储
```
### **✅ 四层验证管道（质量保障）**

| 验证层级 | 工具/脚本 | 核心目标 | 示例检查项 |
| :------- | :-------- | :------- | :--------- |
| **编译** | `build` | 代码能跑吗？ | 语法错误、依赖缺失 |
| **架构合规** | `lint-arch` | 结构对吗？ | 跨层import检查、目录规范 |
| **单元测试** | `test` | 逻辑对吗？ | 函数返回值、边界条件 |
| **端到端验证** | `verify` | 功能对吗？ | CLI命令输出、API响应 |

**关键实践**：
- **事前预防**：创建文件/跨包import前运行`verify_action.py`预验证，如：
  ```python
  # 合法操作示例
  python3 scripts/verify_action.py --action "create file internal/types/user.go"
  # 非法操作示例（返回具体修复建议）
  python3 scripts/verify_action.py --action "import internal/core from internal/handler"
  ```
- **错误信息质量**：需包含"规则违反+原因+修复方案"，如：
  ```
  internal/handler (L4) cannot import internal/core (L3). Fix: handler should depend on core through interfaces
  ```
### **🧠 上下文管理策略（效率提升）**

#### **(一) 协调者-执行者分离模式**
- **协调者（Coordinator）**：仅负责规划、委派、汇总，**不写代码**，保留摘要级上下文。
- **执行者（子代理）**：从干净上下文启动，完成特定任务后释放，避免上下文污染。

#### **(二) 模型分级调度**

| 任务类型 | 推荐模型 | 特点 | 示例场景 |
| :------- | :------- | :--- | :------- |
| 快速执行 | Claude Haiku | 响应快、成本低 | 改typo、简单重命名 |
| 深度推理 | GPT-5.3 Codex/Claude Opus | 质量优先 | 复杂重构、架构设计 |
| 代码检索 | Gemini 3 Flash | 速度优先 | 大型代码库定位文件 |

#### **(三) 交叉Review机制**
- 使用**不同模型**进行Review，检查逻辑正确性、边界条件、命名清晰度、性能隐患。
- 示例流程：编码子代理→机械验证→Review子代理（不同模型）→协调者→合并。

### **🔄 Harness的自我进化（持续优化）**

#### **(一) 失败学习循环**
1. **Agent执行** → 2. **验证抓问题** → 3. **Critic分析模式** → 4. **Refiner更新规则**
- 失败记录保存于`harness/trace/failures/`，Critic定期分析根因（如某包未加入层级映射），Refiner更新规则。

#### **(二) 三种记忆系统**
- **情景记忆**：具体事件教训（如路径符号链接问题）。
- **程序记忆**：成功操作步骤（如添加API端点的标准流程）。
- **失败记忆**：供Critic分析的结构化失败数据。

#### **(三) 轨迹编译**
- 同一任务成功执行3次以上且步骤一致时，自动编译为确定性脚本（如`make add-endpoint`），降低LLM依赖。

### **🚀 实践起步指南**

#### **(一) 最小可行AGENTS.md**
```markdown
# [项目名] Agent Guide
## 快速链接
- [架构总览](docs/ARCHITECTURE.md) — 分层规则、数据流
## 分层规则
Layer 0: types/         → 纯类型定义，无内部依赖
Layer 1: utils/         → 工具函数，仅依赖Layer 0
Layer 4: api/ cli/ ui/  → 接口层，依赖Layer 0-3，彼此不互相引用
## 质量标准
- 禁止console.log/print()，使用结构化日志
- 单文件不超过500行
```
#### **(二) 实施节奏**
1. **当日**：创建AGENTS.md  
2. **当周**：添加lint-deps脚本  
3. **当月**：搭建完整验证管道  
4. **长期**：开启Critic→Refiner循环，实现自我进化

### **📝 关键洞察**
- **环境设计＞Prompt调优**：好的Harness可让普通模型产出可靠代码，反之顶级模型也会反复出错。
- **棘轮效应**：Harness的记忆和规则持续累积，形成"只进不退"的系统能力，换模型无法复制。
- **成本效益**：初期投入（1个下午搭建基础）随时间复利增长，半年后形成高度适配团队的Agent运行环境。
