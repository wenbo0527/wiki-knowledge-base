## 二、传统Agent架构的局限性

### 静态工具列表的瓶颈

| 问题 | 影响 |
|:---|:---|
| **硬编码依赖** | 工具需在Agent启动时定义，无法动态扩展 |
| **连接复杂性** | n个工具需n(n-1)/2个点对点集成 |
| **状态不可知** | 无法实时感知工具在线状态、版本变化 |

### 跨系统协作的挑战

- **技术栈碎片化**：浏览器、沙箱、Python/Rust服务难以统一管理
- **可观测性缺失**：跨进程调用链日志分散
- **触发方式单一**：主要依赖Agent主动调用

---

## 三、新后端架构的核心设计

### 三大核心概念

| 原文术语 | 工程化翻译 | 具体含义 |
|:---|:---|:---|
| **Worker** | 参与者 | 可连接运行时的进程（Agent/浏览器/沙箱/微服务） |
| **Function** | 能力 | 具有稳定ID的工作单元（工具/API/脚本） |
| **Trigger** | 入口 | 触发能力执行的事件源（HTTP/队列/cron/状态变化） |

### 运行时能力目录的关键特性

- **动态注册机制**：Worker连接时自动注册，断开后实时注销
- **双模式访问**：查询当前可用能力（同步）+ 订阅能力变化（异步）
- **统一元数据**：ID、描述、输入输出Schema、版本、权限

## 四、架构演进对比

| 维度 | 传统Agent架构 | 新后端架构 |
|:---|:---|:---|
| **工具形态** | 静态函数数组 | 动态能力目录 |
| **连接方式** | 点对点集成 | 共享运行时引擎 |
| **触发机制** | Agent主动调用 | 多源事件触发 |
| **可观测性** | 分散日志 | 端到端Trace传播 |
| **扩展能力** | 代码级修改 | 动态Worker上下线 |

## 五、与MCP的区别

| 维度 | MCP | 运行时能力目录 |
|:---|:---|:---|
| **解决的问题** | 工具复用 | 工具可用性和连接性 |
| **核心差异** | 协议标准化 | 动态发现与状态感知 |

## 六、工程落地的边界问题

| 问题 | 说明 |
|:---|:---|
| **中心引擎可用性** | 运行时引擎成为关键依赖 |
| **触发语义差异** | HTTP/队列/cron本质差异无法掩盖 |
| **能力目录治理** | 命名规范、版本策略、权限控制 |
| **动态安全风险** | 临时Worker的RBAC、沙箱隔离 |
| **许可证限制** | Elastic License 2.0 商业化合规 |

## 七、认知更新

### 旧认知
- 工具需要预先定义
- Agent是独立进程

### 新认知
- 工具应动态注册和发现
- Agent是后端系统中的普通Worker，可被业务事件触发
