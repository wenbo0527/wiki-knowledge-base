## 一、核心问题

### 研究背景

在代码Agent中，使用Claude Opus、GPT-5.3-Codex等昂贵Token的大模型执行终端命令、跑测试、读报错等基础任务是否存在资源浪费？

### Microsoft研究结论

《Terminus-4B: Can a Smaller Model Replace Frontier LLMs at Agentic Execution Tasks?》提出**Execution Subagent**架构，基于Qwen3-4B训练的**Terminus-4B小模型**可在不降低解题成功率的前提下，使主Agent的token使用量下降约**30%**。

---

## 二、核心痛点：终端输出淹没上下文窗口

编程智能体执行终端操作会导致：

| 问题 | 影响 |
|:---|:---|
| **Token消耗巨大** | 单次测试运行可产生数万token |
| **核心信息被挤占** | 冗长日志取代代码上下文 |
| **滚雪球效应** | 上下文窗口拥挤，实际解决步骤减少 |

**关键洞察**：主智能体仅需终端输出的**简明摘要**（如错误原因、测试结果统计），而非完整原始输出。

---

## 三、核心设计：执行子代理（Execution Subagent）架构

### 核心思想

将终端执行任务外包给专门的子Agent，主Agent仅接收压缩后的有效信息。

### Execution Subagent定义

| 属性 | 说明 |
|:---|:---|
| **定位** | 极窄任务Agent，仅负责运行终端命令并生成结构化摘要 |
| **输入** | Query（任务描述）+ Description（执行说明） |
| **输出** | 必须包含`<final_answer>`标签的结构化摘要 |

### 关键约束设计

| 约束项 | 具体限制 |
|:---|:---|
| **工具权限** | 仅能使用Terminal工具，无法读文件、改代码或搜索仓库 |
| **调用频率** | 每轮只能调用一次Terminal |
| **轮次限制** | 默认最多10轮，超时强制输出结果 |
| **输出要求** | 必须返回约200 token结构化总结 |

**设计逻辑**：终端执行是边界清晰、格式稳定的可训练任务，无需大模型的通用能力，适合小模型专精处理。

## 四、模型训练：Terminus-4B的两阶段后训练

### 阶段1：监督微调（SFT）

| 项目 | 内容 |
|:---|:---|
| **数据基础** | 3200个真实执行任务（5种语言，730个仓库） |
| **训练目标** | Terminal工具调用、日志阅读、结构化输出格式 |
| **训练量** | 2个Epoch轻量级训练 |

### 阶段2：基于GRPO的强化学习

**创新点1：主副代理解耦Rollout框架**
- 使用"阉割版"Qwen3-4B作为虚假主智能体
- 执行轨迹完全由Terminus-4B展开，摆脱对昂贵大模型的依赖

**创新点2：基于执行计划的多维奖励机制**
```
Reward = α × s_pos + (1-α) × s_fa - s_pit
其中：
- s_pos: 执行质量（7个维度）
- s_fa: 最终答案质量（3个维度）
- s_pit: 失败模式惩罚（4个维度）
- α = 0.5
```

## 五、评估结果与关键发现

### 动机案例：Serilog仓库任务对比

| 指标 | 基线智能体（无子代理） | Terminus-4B |
|:---|:---:|:---:|
| **终端调用次数** | 18次 | 9次 |
| **交互轮次** | 40轮 | 32轮 |
| **主Agent Token消耗** | 246万 | 74万 |
| **返回内容** | 原始终端输出 | 约200 token结构化摘要 |

### 跨语言泛化能力（SWE-Bench Pro）

以Claude Opus 4.6为主智能体：

| 指标 | 结果 |
|:---|:---|
| **解决率** | 31.5%（vs基线30.0%） |
| **Token节省** | 主Agent减少13% |
| **终端调用减少** | 73.7%（从3.8次降至1.0次） |
| **信任度提升** | 不信任信号从27%降至14% |

### 极限剥夺测试

| 模型 | 表现 |
|:---|:---|
| **Vanilla-4B** | Token使用量增加9.5%，重复调用率1.51 |
| **Terminus-4B** | 重复调用率0.89，与Claude Opus持平 |

## 六、与DOLORES/EVOCHAMBER的关系

| 框架 | 层级 | 核心机制 |
|:---|:---|:---|
| **DOLORES** | Agent内部推理 | 结构化元认知 |
| **EVOCHAMBER** | 多Agent协作 | CODREAM协作反思 |
| **Terminus-4B** | 任务执行 | Execution Subagent |

**三者构成完整链路**：
```
DOLORES (推理结构)
      ↓
Terminus-4B (执行优化)
      ↓
EVOCHAMBER (协作进化)
```

## 七、实践启示

### 什么时候用Execution Subagent？

| 场景 | 建议 |
|:---|:---|
| **代码Agent终端任务** | ✅ 强烈推荐 |
| **长上下文任务** | ✅ 推荐 |
| **Token成本敏感** | ✅ 推荐（节省30%+） |

### 核心原则

```
□ 终端执行是边界清晰的可训练任务
□ 小模型可以专精处理
□ 主Agent需要摘要，不需要完整日志
□ 执行轨迹可以结构化
```

## 八、认知更新

### 旧认知
- 大模型执行所有任务更可靠
- 终端输出必须完整保留

### 新认知
- 小模型可以专精执行任务
- 摘要比完整日志更有价值
- 执行与推理分离是效率关键
