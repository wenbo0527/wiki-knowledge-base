## 🧩 1. 背景:为什么"模型分级"不是可选项

派蒙作为大总管,管理 **17 个 Agent 节点**(管理层 9 + 执行层 7 + 老六挂起 + 风险问数),每个节点任务复杂度差异巨大:
- **派蒙大总管**:cron 巡查 + sessions_send 中转 + HEARTBEAT 落档(高频低复杂)
- **钟离架构师**:跨团队架构设计 + LangGraph 状态机设计(低频高复杂)
- **PM 产品**:任务派发 + 收口报告(中频中复杂)
- **dev/qa/doc 执行层**:具体实施 + 测试 + 文档(高频中复杂)

如果所有节点用同一个模型、同一个 timeout、同一个派单节奏,**会出现 3 个致命问题**:
1. 简单任务用大模型 = **Token 浪费**(能力过剩)
2. 复杂任务给小模型 = **质量崩塌**(能力不足)
3. 派单无节奏 = **5h 滑动窗口击穿**(`FailoverError usage limit`)

**核心方法论**:**任务复杂度 → 模型分级 → 成本-体验平衡**

## 🛠 3. 方案:四级分级体系(任务 → 模型 → 配置 → 节奏)

### 3.1 模型分级(2026-06-17 文博拍板"全部默认 M3")

### 3.2 配置分级(cron timeout 按 payload 大小)

| Cron | payload 大小 | timeoutSeconds | 撞墙风险 | 实证 |
|:--|:--|--:|:--|:--|
| **dev-ack-watchdog** | 中 (~300 tokens) | **300 (5 min)** 🔴 | **最高** | 6/30 INC-1450 |
| **T3' 团队2** | 大 (1500+ tokens) | **600 (10 min)** 🟡 | 中 | 6/30 INC-1450 |
| **派蒙自查 cron** | 小 (命令) | 默认(短) 🟢 | 低 | 6/30 INC-1450 |

**核心逻辑**:**payload 越大 = fallback chain 切换时间越长 = timeout 越长**

### 3.3 节奏分级(派单节奏控制 SOP v1.0,2026-06-04 派蒙签)

**5 条硬规矩**:

1. **单次派单 ≤ 3 张任务卡**(超 3 张分批派,间隔 30min+)
2. **派单消息精简模板 ≤ 1500 字**(详细描述放 task board,不放派单消息)
3. **批量读 → 批量写**(避免"小步快跑"累积 token)
4. **减少 sessions_send 频次**(15min 巡查,不连续)
5. **大消息拆分 2-3 次发**(核心 + SOP + 截止分开发)

**派单时机分级**:

| 优先级 | 时机 | 节奏 |
|:--|:--|:--|
| **P0** | 立刻 | 单次派单(1-2 张),不等 |
| **P1** | 30min 后 | 累积到 2-3 张一起派 |
| **P2** | 1h 后 | 累积到 3-5 张一起派 |
| **巡查** | 15min / 30min / 60min | **不连续巡查** |

### 3.4 Fallback 分级(M3 → M2.5 → GLM-4.7-Flash 待注册)

```
Primary:   minimax/MiniMax-M3  (主模型,质量优先)
  ↓ (60s timeout / overloaded)
Fallback:  minimax/MiniMax-M2.5 (同 provider,降级保活)
  ↓ (60s timeout / rate_limit)
[未注册]  bigmodel/GLM-4.7-Flash (跨 provider,成本 -90%)
```

**待文博拍板**:注册 bigmodel = 治本(0 外部 fallback → 1 外部 fallback)
