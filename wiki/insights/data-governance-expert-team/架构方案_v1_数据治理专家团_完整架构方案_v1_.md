# 数据治理专家团：完整架构方案（v1）

> 从诊断器专家团的方法论出发，按上下文边界拆分，覆盖数据治理全链路。

---

## 一、全局架构

### 1.1 八个鲸

| 角色 | 上下文 | 做什么 | 不做什么 |
|------|--------|--------|----------|
| 调度鲸 | 用户意图+任务状态+会话上下文 | 判断入口、处理分支回环、跨Agent传参、汇总输出 | 不做专业分析 |
| 探路鲸 | 自然语言→元数据定位 | 把"那个算逾期的表"翻译成具体的表/字段/指标 | 不回答业务问题 |
| 问数鲸 | 业务问题→数据答案 | 理解问题→生成SQL→人类审核→执行→翻译答案 | 不改数据、不导出数据、不替人类审核 |
| 取数鲸 | 数据需求→可交付数据集 | 生成取数SQL→人类审核→执行→脱敏→交付 | 不做分析、不回答业务问题 |
| 溯源鲸 | 表/字段/指标→上下游血缘 | 追踪数据来源和影响范围 | 不改口径、不判断对错 |
| 核规鲸 | 指标/字段→口径定义+标准对比 | 核实口径是否一致、是否偏离标准 | 不修复口径、不给终态结论（只给证据链） |
| 归因鲸 | 异常现象→根因定位 | 从数据异常反推哪个环节出了问题 | 不做修复方案 |
| 执笔鲸 | 分析结论→结构化报告 | 组装前几个鲸的输出成可交付报告 | 不做新增分析 |

### 1.2 调用关系

```
用户输入
  ↓
调度鲸（判断意图，派发任务，维护会话上下文）
  ↓
  ├─ "XX表在哪/XX字段什么意思" → 探路鲸
  ├─ "上个月逾期率多少" → 问数鲸
  │     ├─ 调探路鲸定位数据源
  │     ├─ 调核规鲸（快速模式）获取口径依据
  │     ├─ 生成SQL → 展示给人类审核
  │     └─ 人类审核通过后执行 → 翻译答案
  ├─ "把这批数据导出来" → 取数鲸
  │     ├─ 可复用问数鲸已定位的数据源和口径
  │     ├─ 生成取数SQL → 展示给人类审核
  │     └─ 人类审核通过后执行 → 脱敏 → 交付
  ├─ "这个数据从哪来/改了影响谁" → 溯源鲸
  ├─ "口径对不对" → 核规鲸（深度模式）
  ├─ "数据为什么不对" → 归因鲸
  │     ├─ 调溯源鲸查数据流向
  │     └─ 调核规鲸（深度模式）查口径变更
  └─ "帮我出个报告" → 执笔鲸（汇总前面所有输出）
```

### 1.3 跟诊断器的关键差异

| 维度 | 诊断器（7只虾） | 数据治理专家团（8头鲸） |
|------|-----------------|------------------------|
| 流转模式 | 严格线性 | 有分支和回环 |
| 人类介入 | 结构化虾输出后暂停等确认 | 问数/取数必须人类审核SQL |
| 跨Agent调用 | 萃取虾直通火匠 | 高频调用（问数↔探路/核规）走直通，低频调用走调度鲸 |
| 信任模型 | 结论由业务方自取 | 人类审核SQL给置信度盖章，Agent不替人做事实判断 |

## 二、核心设计

### 2.1 问数鲸——人类审核门控

问数鲸是整个专家团的发动机，也是唯一必须人类介入的环节。

**流程：**

```
业务方提问
  ↓
问数鲸：理解问题 → 调探路鲸定位 → 调核规鲸（快速模式）获取口径依据
  ↓
问数鲸：生成SQL + 口径依据 → 一起展示给人类
  ↓
人类审核SQL：已验证 / 待确认 / 请小心
  ↓
已验证 → 执行SQL，答案置信度=高
待确认 → 执行SQL，答案标注"口径待确认"
请小心 → 不执行，列出风险点
  ↓
问数鲸：翻译答案 → 附带置信度+审核状态
```

**人类审核三档的含义：**

| 审核结果 | 问数鲸行为 | 答案置信度 | 责任归属 |
|----------|-----------|-----------|----------|
| 已验证 | 直接执行 | 高 | 人类审核者对SQL逻辑负责 |
| 待确认 | 执行但标注 | 中 | 业务方对使用未确认数据负责 |
| 请小心 | 不执行，列风险 | — | 问数鲸若执行则问数鲸负责 |

**已验证SQL模板库：**

- 同一指标首次问数 → 人类审核 → 审核结果存入模板库
- 再次问相同指标 → 匹配模板库 → 已验证的直接执行，待确认/请小心的按原状态处理
- 口径变更后 → 模板库中相关SQL标记"需重新审核"
- 模板库 = 数据管理中"通用数据逻辑维护"的Agent化升级

**问数鲸输出格式：**

```json
{
  "question": "原始问题",
  "interpreted_intent": "理解后的查询意图",
  "caliber_used": "使用的口径定义",
  "caliber_source": "口径来源（数据标准/业务口径/开发口径）",
  "caliber_evidence": "核规鲸提供的口径依据原文",
  "sql": "生成的SQL（人类可见）",
  "sql_explanation": "SQL逻辑的自然语言解释",
  "human_review": {
    "status": "pending/verified/uncertain/caution",
    "reviewer": "审核人",
    "review_time": "审核时间",
    "notes": "审核备注"
  },
  "result": {"value": "", "unit": "", "time_range": ""},
  "answer": "业务语言回答",
  "confidence": "高/中/低",
  "caveats": ["需要注意的事项"]
}
```

**问数鲸硬约束：**
- 人类未审核前，禁止执行SQL
- "请小心"状态下禁止执行，必须列出风险点
- 审核记录必须保留，不可删除
- 同一SQL已验证过可跳过审核（口径变更后需重新审核）
- 口径不确定时，把口径选项和SQL一起展示给人类，审核SQL和确认口径合并一步完成

### 2.2 核规鲸——双模式

核规鲸服务两类调用方，节奏和深度完全不同，但知识来源相同，不拆成两个Agent。

**快速模式（问数鲸/取数鲸调用）：**

- 只对比当前口径定义，不追溯历史
- 输出是证据链，不是终态结论
- 不独立盖章，作为问数鲸SQL审核材料的一部分

**深度模式（归因鲸调用）：**

- 追溯口径变更历史
- 多来源交叉比对（业务口径+开发口径+数据标准）
- 输出包含口径变更时间线和偏差分析

**核规鲸输出格式：**

```json
{
  "indicator": "指标名",
  "mode": "quick/deep",
  "definitions": [
    {"source": "业务口径", "definition": "", "owner": ""},
    {"source": "开发口径", "definition": "", "owner": ""},
    {"source": "数据标准", "definition": "", "owner": ""}
  ],
  "consistent": true,
  "deviations": ["口径偏差描述"],
  "standard_reference": "数据标准中的定义（如有）",
  "severity": "高/中/低",
  "change_history": [
    {"date": "", "change": "", "trigger": ""}
  ],
  "evidence": "口径依据原文（供人类审核时参考）"
}
```

**核规鲸硬约束：**
- 不给终态结论"口径一致/不一致"，只给证据链让人类判断
- 口径来源可信度必须标注（数据标准>业务口径>开发口径>人工填报）
- 快速模式不追溯变更历史，深度模式必须追溯

### 2.3 取数鲸——问数鲸的交付版

跟问数鲸共享人类审核门控，但输出形态不同。

**取数鲸硬约束：**
- 含敏感字段（手机号、身份证号）必须脱敏，不允许导出明文
- 行数超过10万行必须提示"数据量较大，建议用脚本方式取数"
- 必须附带口径说明，不允许只交付裸数据
- 人类审核门控规则同问数鲸

### 2.4 归因鲸——分析引擎

**四类根因框架：**

| 根因类型 | 典型表现 | 归因鲸动作 |
|----------|---------|-----------|
| 数据源问题 | 上游数据缺失/延迟/变更 | 调溯源鲸追踪上游 |
| 口径问题 | 定义不一致/标准偏离 | 调核规鲸（深度模式）追溯口径变更 |
| 加工问题 | ETL逻辑错误/任务失败 | 调溯源鲸查加工链路+任务日志 |
| 业务问题 | 业务本身变化，数据没出错 | 排除前三类后归因 |

**归因鲸硬约束：**
- 必须给出具体证据，不能只说"可能是XX问题"
- 四类根因必须逐一排查，不能跳过
- 口径问题必须调核规鲸（深度模式），不允许自己判断口径

### 2.5 调度鲸——会话上下文管理

调度鲸比诊断器的调度虾更复杂，因为数据治理有分支和回环。

**核心能力：**

1. 意图判断：问数/取数/找数据/查血缘/核口径/归因/出报告
2. 跨Agent传参：问数鲸定位的表和口径，取数鲸可以直接复用
3. 分支处理：归因鲸需要溯源+核规时，调度鲸并行派发，汇总结果再传回
4. 回环控制：核规鲸发现口径问题→调度鲸判断是否需要触发溯源鲸→结果传回核规鲸

**调度鲸硬约束：**
- 高频调用（问数↔探路/核规）允许直通，不走调度鲸中转
- 低频调用（归因↔溯源/核规）走调度鲸，保证链路可追踪
- 会话上下文30分钟过期，过期后问数鲸需要重新定位数据

## 三、模型分配

| 角色 | 模型 | 理由 |
|------|------|------|
| 调度鲸 | Claude Sonnet | 分支判断+回环+会话上下文管理需强推理 |
| 探路鲸 | Claude Sonnet | 语义匹配需强推理 |
| 问数鲸 | Claude Sonnet | Text-to-SQL+口径理解+结果验证，最重的推理任务 |
| 取数鲸 | 千问Max | SQL生成后主要是格式化输出和脱敏检查 |
| 溯源鲸 | 千问Max | 结构化检索+格式化输出 |
| 核规鲸 | Claude Sonnet | 口径对比需理解语义差异，快速模式要快但深度模式要准 |
| 归因鲸 | Claude Sonnet | 根因分析推理最重 |
| 执笔鲸 | 千问Max | 报告组装是框架化输出 |

## 四、知识库对应关系

| 角色 | 依赖的知识库 | 位置 |
|------|-------------|------|
| 探路鲸 | 元数据目录+要素字典 | 数据发现+数据管理（已有部分） |
| 问数鲸 | 元数据+口径定义+已验证SQL模板库 | 数据管理+新建模板库 |
| 取数鲸 | 同问数鲸 | 同上 |
| 溯源鲸 | 血缘关系+加工逻辑 | 数据管理（Q3扩展全链路） |
| 核规鲸 | 数据标准+口径定义+血缘 | 数据管理（标准Q3制定） |
| 归因鲸 | 溯源鲸+核规鲸的输出+任务日志 | 数据管理+调度系统日志 |
| 执笔鲸 | 前几个鲸的结构化输出 | 无独立知识库 |

## 五、上线节奏

**Phase 1（最快出价值，Q3前）**：探路鲸+问数鲸+取数鲸
直接解决"找数、问数、取数"三个最高频痛点。不依赖数据标准，现有元数据就能喂。问数鲸的人类审核门控从第一天就有，建立信任基础。

**Phase 2（Q3标准到位后）**：溯源鲸+核规鲸
血缘全链路+口径标准到位后才能做深度核实。核规鲸快速模式随问数鲸一起用，深度模式在这个阶段才真正跑起来。

**Phase 3**：归因鲸+执笔鲸
需要前两层都跑稳，血缘+口径+问数的历史数据都积累够了，归因才有足够的素材做根因分析。

调度鲸最后配——编排逻辑依赖所有角色就位。

## 六、与现有数据底座的现实约束

| 约束 | 影响 | 应对 |
|------|------|------|
| 元数据部分实现 | 探路鲸搜索覆盖不全 | 初期标注"元数据未覆盖领域"，逐步补全 |
| 血缘只有表-指标关联 | 溯源鲸只能做浅层追踪 | Q3前标注"链路不完整"，Q3后扩展 |
| 数据标准Q3才制定 | 核规鲸无标准口径参照 | Q3前只对比业务口径和开发口径，标注可信度 |
| 口径靠人工维护 | 核规鲸的口径来源可信度有限 | 人工填报的口径标注"可信度：低"，已验证SQL模板库逐步替代 |
| 权限体系Q2线上化 | 问数鲸/取数鲸可能访问无权限数据 | 权限不足时提示申请，不硬查 |
