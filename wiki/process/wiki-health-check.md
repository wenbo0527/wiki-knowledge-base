# Wiki健康走查方案

> 保障Wiki结构满足MECE原则且合理归类

---

## 一、方案概述

### 1.1 目标

确保Wiki知识库满足：
- **MECE原则**：相互独立（Mutually Exclusive）、完全穷尽（Collectively Exhaustive）
- **合理归类**：内容放在正确的专题层级
- **结构清晰**：层级分明、导航顺畅
- **链接健康**：无失效链接

### 1.2 走查频率

| 频率 | 时间 | 内容 |
|------|------|------|
| **每日** | 08:00 | 链接健康检查（自动化） |
| **每周** | 周一09:00 | 结构完整性检查 |
| **每月** | 每月1日 | MECE原则深度审查 |
| **引入后** | 实时 | 新内容归类验证 |

### 1.3 走查角色

| 角色 | 职责 |
|------|------|
| **尼克·弗瑞** | 执行日常走查、记录问题 |
| **派蒙** | 协调复杂归类决策、审核方案 |
| **钟离** | 技术专题归类把关 |

## 二、检查清单

### 2.1 结构完整性检查（Weekly）

#### 专题层级检查

```
□ 专题数量是否合理（5-12个一级专题）
□ 子专题是否完整覆盖父专题范围
□ 是否有孤岛专题（无内容或无入口）
□ 专题命名是否符合规范
```

#### 内容完整性检查

```
□ 每个专题是否有README.md
□ 每个专题是否有至少1个Insight
□ 专题内容是否达到最小填充标准（500字）
□ 是否有待填充的placeholder
```

#### 目录结构检查

```
□ README.md是否放在正确位置
□ 内容文件是否在正确目录层级
□ 相关文件是否就近放置
```

### 2.2 MECE原则检查（Monthly）

#### 相互独立检查（Mutually Exclusive）

```
□ 检查项：同一内容是否只出现在一个专题
□ 检查项：专题之间是否有明显重叠
□ 检查项：子专题之间是否互不包含
□ 检查项：是否有内容被多个专题引用
```

**常见问题模式**：

| 问题 | 描述 | 解决方案 |
|------|------|----------|
| **重复归类** | Agent内容同时出现在"AI编程"和"Agent工程" | 明确边界，选主要专题 |
| **父子重叠** | 父专题和子专题包含相似内容 | 子专题只放差异内容 |
| **交叉引用过多** | 同一内容被5+个专题引用 | 考虑是否需要拆分或上移 |

#### 完全穷尽检查（Collectively Exhaustive）

```
□ 检查项：是否有内容无法归入任何专题
□ 检查项：新引入内容是否有对应专题
□ 检查项：是否有"其他"或"杂项"专题（应避免）
□ 检查项：专题是否覆盖领域主要方面
```

**边界模糊内容处理**：

| 场景 | 处理方式 |
|------|----------|
| 跨多个专题 | 放入主要专题，其他专题引用 |
| 新兴领域 | 创建新专题或放入"前沿探索" |
| 通用方法论 | 放入通用专题（如"分析框架"） |

### 2.3 归类合理性检查（On-demand）

#### 归类决策树

```
新内容到达
    │
    ▼
属于金融科技领域？
    │
    ├─ 是 → 属于哪个子领域？
    │         │
    │         ├─ 消费金融/信贷 → fintech/consumer-finance
    │         ├─ 风控/数据 → fintech/risk-management
    │         ├─ 合规/监管 → fintech/compliance
    │         ├─ 数据平台 → fintech/data-platform
    │         └─ 其他 → fintech/intelligent-systems
    │
    └─ 否 → 属于AI领域？
              │
              ├─ 是 → 属于哪个子领域？
              │         │
              │         ├─ 编程/开发 → ai-programming
              │         ├─ Agent/智能体 → ai-native/agent-engineering
              │         ├─ 基础设施 → ai-native/ai-infrastructure
              │         └─ 应用案例 → ai-native/ai-application
              │
              └─ 否 → 属于产品管理？
                        │
                        ├─ 是 → product-management
                        │
                        └─ 否 → 分析框架/知识管理/其他
```

#### 归类质量评分

| 维度 | 评分标准 | 权重 |
|------|----------|------|
| **相关性** | 内容与专题主题的相关程度 | 30% |
| **唯一性** | 是否主要归属该专题 | 25% |
| **可发现性** | 用户能否快速找到 | 20% |
| **扩展性** | 未来内容是否适合加入 | 15% |
| **导航清晰度** | 层级是否合理 | 10% |

### 2.4 链接健康检查（Daily）

#### 链接类型检查

| 链接类型 | 检查频率 | 检查方法 |
|----------|----------|----------|
| **内部Wiki链接** | 每日 | wiki_lint.py自动检查 |
| **外部URL** | 每周 | 抽样验证 |
| **图片引用** | 每周 | 检查是否可访问 |
| **相对路径** | 引入时 | 验证路径正确性 |

#### 常见链接问题

```
□ 死链：目标文件不存在
□ 悬空链：目标文件被移动或删除
□ 循环链：A→B→C→A
□ 过长链：嵌套超过3层
□ 歧义链：链接文本与目标不匹配
```

## 三、自动化工具

### 3.1 Wiki Lint脚本

```python
# scripts/wiki_lint.py 检查项
CHECKS = {
    "link_integrity": "检查所有Wiki内部链接",
    "orphan_pages": "检查孤岛页面（无入口）",
    "empty_dirs": "检查空目录",
    "readme_missing": "检查缺失README的目录",
    "depth_check": "检查目录层级深度（≤4层）",
    "name_normalization": "检查命名规范",
}
```

### 3.2 MECE验证脚本

```python
# scripts/mece_validator.py 检查项
CHECKS = {
    "overlap_detection": "检测专题间内容重叠",
    "coverage_check": "检测是否有内容遗漏",
    "assignment_score": "计算归类质量评分",
}
```

### 3.3 执行命令

```bash
# 每日链接检查
python3 scripts/wiki_lint.py --check link_integrity

# 每周结构检查
python3 scripts/wiki_lint.py --check all

# 每月MECE检查
python3 scripts/mece_validator.py --full-report
```

## 四、问题处理流程

### 4.1 问题分级

| 级别 | 标准 | 处理时限 |
|------|------|----------|
| **P0 严重** | 死链导致页面无法访问 | 立即修复 |
| **P1 重要** | 归类明显错误 | 24小时内 |
| **P2 一般** | 结构不够优化 | 本周内 |
| **P3 建议** | 优化建议 | 排期处理 |

### 4.2 归类争议处理

```
争议场景：内容X应归入专题A还是B
    │
    ▼
尼克·弗瑞提出归类建议 + 理由
    │
    ▼
派蒙审核（如涉及多个Agent领域）
    │
    ▼
做出决策，记录归类原则到本文档
    │
    ▼
更新归类决策树（如有必要）
```

## 五、MECE归类原则库

### 5.1 金融科技专题（Fintech）

| 子专题 | 包含内容 | 不包含内容 |
|--------|----------|------------|
| **consumer-finance** | 消费金融、现金贷、信用卡、分期 | 企业贷款（→risk-management） |
| **risk-management** | 风控模型、特征工程、信用评估 | 消费金融业务（→consumer-finance） |
| **compliance** | 监管政策、合规要求 | 业务策略（→对应业务专题） |
| **data-platform** | 数据架构、数据治理、数据中台 | 数据分析应用（→intelligent-systems） |
| **intelligent-systems** | 智能风控、智能营销、智能客服 | 纯数据平台（→data-platform） |

### 5.2 AI专题（AI Native/AI Programming）

| 子专题 | 包含内容 | 不包含内容 |
|--------|----------|------------|
| **ai-programming** | Vibe Coding、代码生成、代码审查 | Agent开发（→agent-engineering） |
| **agent-engineering** | Agent框架、Harness、多Agent协作 | 具体编程实践（→ai-programming） |
| **ai-application** | 行业AI落地案例 | 技术实现细节（→对应技术专题） |
| **ai-infrastructure** | 模型部署、推理优化、算力 | 应用场景（→ai-application） |

### 5.3 边界模糊内容处理

| 内容类型 | 处理原则 | 示例 |
|----------|----------|------|
| **Harness Engineering** | 放入agent-engineering | 工具调用、上下文管理 |
| **代码理解工具** | 放入ai-programming | Linear Walkthroughs、UModel |
| **测试自动化** | 放入ai-programming或对应业务专题 | Agent+MCP+Skills |
| **合规与业务交叉** | 放入compliance，在业务专题引用 | 网络营销管理办法 |

## 六、专题边界定义（参考今日引入内容）

### 6.1 Agent工程专题（agent-engineering）

**核心边界**：Agent系统的架构、设计、工程实践

**应包含**：
- Agent框架选型（LangChain、AutoGen等）
- 多Agent协作模式（Subagents、Hierarchical等）
- Harness Engineering（工具调用、上下文管理）
- Agent评估与安全
-SequentialThinkingTool等思考框架

**不包含**（应归入其他专题）：
- 具体编程实践 → ai-programming
- 行业应用案例 → ai-application
- 模型训练优化 → ai-infrastructure

### 6.2 AI编程专题（ai-programming）

**核心边界**：用AI辅助编程的实践方法

**应包含**：
- Vibe Coding工作流
- 代码生成与优化
- AI代码审查
- 测试自动化（Agent+MCP+Skills）
- 代码理解工具（Linear Walkthroughs、UModel）

**不包含**（应归入其他专题）：
- Agent系统开发 → agent-engineering
- 模型训练 → ai-infrastructure

### 6.3 产品管理专题（product-management）

**核心边界**：产品经理的工作方法论和实践

**应包含**：
- PM能力模型
- 需求分析方法
- 项目管理实践
- GitHub PM作品集
- AI时代PM转型

**不包含**（应归入其他专题）：
- 纯技术内容 → 对应技术专题
- 业务分析 → fintech对应专题
