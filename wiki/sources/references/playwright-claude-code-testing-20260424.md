## 原文正文

**标题**：Playwright CLI × Claude Code 自动化测试实战

### 背景

本项目源于团队在日常 Web 业务测试中遇到的痛点：随着核心业务流程（如项目立项、OA 审批提交等）日益复杂，人工回归测试成本急剧上升，覆盖率难以保证。

团队引入 playwright-cli 工具，结合 AI Agent 能力，将自然语言测试意图自动转化为可执行的浏览器自动化脚本，从而沉淀测试资产、降低回归成本、提升整体测试效率。

典型场景：
- **项目立项流程**：手动填写立项信息、逐步点击提交，涉及多个页面跳转，人工回归一次耗时 5～10 分钟
- **OA 审批提交**：登录 OA 页面，完成流程干预、提交通过等多个步骤，每次版本迭代后都需要重复执行
- **权限验证测试**：不同角色用户登录后页面访问控制差异化验证，需要来回切换账号执行

### 什么是 Playwright-CLI？

Playwright-CLI 是 Microsoft 基于 Playwright 推出的命令行浏览器自动化工具，专为 AI 编程助手（如 Claude Code、GitHub Copilot）设计。

核心特点：**token 高效**——每条命令返回精简的 YAML 页面快照（含元素 ref 引用），而非将整个页面 DOM 塞入模型上下文，大幅降低 AI Agent 的推理成本。

### 演进六阶段

#### 第一阶段：初识 playwright-cli，手动跑第一个用例

Claude Code 里手写了第一条指令：导航到 DPMS 首页，登录，关闭指引反馈弹框。

不到 30 秒登录成功。再获取一份 snapshot，找到反馈关闭按钮的 ref，点击，成功关闭了反馈窗口。

问题：**测试资产无法沉淀**——没有任何步骤被保存，下次复现要全部重来。

#### 第二阶段：把执行过程整理成文件——第一个 .md 用例诞生

手动将第一个用例整理成 `tests/01-login-feedback.md`，包含：
- 当前用例说明
- 前置配置（平台地址、账号、密码）
- 每步用什么命令
- 期望验证什么

问题：Agent 开始自由发挥，把 .md 里写的步骤当做"参考"而不是"指令"，导致每次执行路径不一致、Tool 调用次数暴增。

> 文档只是"建议"，不是"契约"——Agent 自由发挥导致执行路径不可控、成本不可预测、结果不可信。

#### 第三阶段：加入强制约束，用例开始可靠重复执行

在 .md 用例文件中加入 **CRITICAL RULES** 约束，明确一系列严格禁止行为：

```markdown
CRITICAL RULES:
- 不要对 .yml 快照文件使用 Read 工具（用 Grep 更快）
- close 后立刻停止，不要再拓展任何操作
- 不要使用 waitForTimeout，用 waitForURL 或 waitForSelector
- .md 里已写的命令一字不改直接执行，不要重写或内联
- 不要自起名目进行 ls / find / glob 文件系统探索
```

效果：**Tool 调用次数从 20+ 降到 9 次**。

#### 第四阶段：用例变复杂，Batch 分组与前置依赖

将长流程按语义分组（Batch 1: 导航/填写基本信息，Batch 2: 项目计划/新增任务，Batch 3: 提交验证），失败范围明确。

跨系统传参方案：`localStorage.TESTPROJECTNAME` 传递项目名称。

前置依赖抽离：把公共流程（登录、OA审批）抽成独立 .md 模块（`00-oa-approve-prerequisite.md`），后续用例只需声明依赖。

复杂 JS 外置：`scripts/` 目录存放前端操作脚本，用例里只保留 `run-code cat scripts/04-step2-basic-info.js`。

#### 第五阶段：创建用例经验沉淀——Skill 1 诞生

把前四个阶段踩过的坑和最佳实践，固化为 **Skill 1（adding-playwright-cli-tests）**：

当测试人员输入"添加测试场景：xxx"时，Skill 1 自动激活，引导 AI Agent 完成标准化流程。

效果：新增一个测试场景的时间从**半天手动摸索**缩短到**十几分钟自动生成+验证**。

#### 第六阶段：用例多了，执行需标准化——Skill 2 诞生

用 **haiku 模型**而非主 Agent 直接执行，为每个用例启动一个独立的子 agent 并行运行。

理由：
- haiku 成本远低于 sonnet/opus
- 适合大量重复执行
- 复杂用例不适合在一个 agent 里串行塞太多流程

#### 第七阶段：指标暴露问题——自动优化循环应运而生——Skill 3 诞生

Skill 2 的副产品是每次执行结束都有准确指标。发现 04-pre-project-initiation.md 首次跑通 Tool、Token、耗时全部超标。

Skill 3 核心设计：
1. `parse-agent-log.py` 脚本分析 Claude Code jsonl 日志文件
2. 提取 Tool 调用次数、Token 消耗、各步耗时
3. Agent 对比阈值、定位问题、生成优化方案

### 最终优化效果

| 轮次 | Tool调用 | Token消耗 | 耗时 | 关键措施 |
|------|---------|---------|------|---------|
| 初始版 | 28次 | 35,240 | 103s | — |
| 第1轮 | 22次 | 28,000 | 83s | 删除冗余snapshot |
| 第2轮 | 16次 | 20,500 | 47s | Bash命令批量化 |
| 第3轮 | 12次 | 16,200 | 40s | waitForURL替代waitForTimeout |
| 第4轮 | 10次 | 14,850 | 36s | 合并同页面步骤+已知ref硬编码 |

**最终效果：Tool -64%, Token -58%, 耗时 -65%**

### 与传统方案的对比

| 维度 | 传统 Playwright (.spec.ts) | Playwright MCP | 本方案（playwright-cli + Skill） |
|------|---------------------------|----------------|--------------------------------|
| 本质 | 开发者手写自动化测试代码 | AI通过MCP协议实时操控浏览器 | AI按预定义的.md脚本批量执行 |
| 编写门槛 | 需要 JS/TS 编程能力 | 无需编码，自然语言即可 | 无需编码，自然语言即可 |
| 用例格式 | .spec.ts 代码文件 | 无持久化用例，每次对话即用即走 | .md Markdown 文档，人机双可读 |
| 执行一致性 | 高（代码固定） | 低（AI自由推理，路径可能不同） | 高（CRITICAL RULES约束） |
| 执行成本 | 固定（CI资源） | 高（每步都是LLM推理） | 低（haiku批量执行） |
| 资产沉淀 | 代码即资产，可版本管理 | 无沉淀，对话结束即丢失 | .md + .js 文件沉淀，可版本管理 |
| 自优化能力 | 无，需人工review | 无 | 有，Skill 3自动分析日志 |
| 跨系统能力 | 需手动编排多个spec | 支持，但需每次重新描述 | 天然支持多Tab、多系统、localStorage传参 |
| 适用场景 | 有专职自动化测试工程师的团队 | 一次性探索、临时验证 | 需要长期回归的核心业务流程 |
