## 三、⭐ 需求 1：样本统计（继承 v0.4）

> 详见 `2026-07-10-需求理解-CDP事件测试v0.2.md` § 二
> v0.5 不重写，**关键回归**：

- **核心业务诉求**：为运营同学和事件管理员提供"事件测试台"，观察接入事件 + 虚拟事件的运行情况
- **7 个业务诉求**（T-01 ~ T-07）：分时点 / 粒度切换 / 时间范围 / 点查 / 字段详情 / 异常检测 / 字段筛选

- **2 类角色**：运营 + 事件管理员
- **v0.5 增量**：增加"圈选命中状态"只读筛选维度（详见 §5.3）
- **v0.6 增量**：增加"事件Schema合规性检测"能力（详见 §3.1）+ "字段值格式校验"能力（详见 §3.2）

### 3.1 🆕 v0.6 增量：事件Schema合规性检测

> **竞品对标**：Segment Protocols 的 Tracking Plan 定义预期事件/属性，实时校验入站事件，违规标记 Violation；神策的强校验模式（normal_token 只接收已注册事件，super_token 可自动创建），事件命名白名单管理。

#### 3.1.1 业务背景

当前PRD从"事件已从Kafka接入"开始，假设上游事件已经"干净"。但在消费金融实际场景中：

- 前端组件重构导致属性缺失（如：还款事件缺少 `loan_id`）
- 事件命名混乱（如：`repay_success` vs `repayment_done` 同义不同名）
- 上报口径不一致（如：同一事件在不同渠道的属性类型不同——A渠道 `amount` 是字符串，B渠道是数值）

这些脏数据会直接灌进样本统计和ID-mapping，导致"测试台"本身测不准。

#### 3.1.2 业务诉求

- **运营同学**：接入新事件后，想快速确认"这个事件的数据结构是否符合预期？有没有缺字段、类型不对？"
- **事件管理员**：想全局看"哪些事件存在Schema违规？违规类型分布如何？"以便推动上游修复

#### 3.1.3 业务范围（仅测试 PRD 视角）


| 项            | 内容                                                     |
| ------------ | ------------------------------------------------------ |
| **检测维度**     | ① 事件名是否在注册列表中（未知事件检测）② 必填属性是否齐全（缺失检测）③ 属性类型是否匹配（类型检测）  |
| **检测来源**     | 以事件管理中心已注册的事件Schema为基准（引用 FEAT-MKT-CRD-EVENT）          |
| **展示位置**     | 样本统计模块的"字段筛选"维度新增一项：「Schema合规状态」                       |
| **合规状态枚举**   | 合规 / 属性缺失 / 类型不匹配 / 未知事件                               |
| **业务规则**     | 仅作**只读检测+展示**，不拦截事件、不修改Schema、不阻断下游流程                  |
| **与异常检测的关系** | 异常检测（T-06）关注数据值的异常（如空值率突增），Schema合规性关注数据结构的合规——两者互补不重叠 |


#### 3.1.4 业务验收标准


| 验收项         | 标准                                  |
| ----------- | ----------------------------------- |
| **合规状态可见**  | 样本统计模块能用"Schema合规状态"维度筛选事件          |
| **违规明细可查**  | 点查事件详情页能看到具体违规项（缺了哪个属性 / 哪个属性类型不匹配） |
| **未知事件可识别** | 事件名不在注册列表中的事件，Schema合规状态标记为"未知事件"   |
| **不影响主流程**  | 检测结果仅展示，不拦截事件进入下游                   |


#### 3.1.5 不在本 PRD 范围

- ❌ 事件Schema的创建 / 编辑 / 删除（由 FEAT-MKT-CRD-EVENT 负责）
- ❌ 事件拦截 / 阻断（本PRD只做"看见"，不做"拦截"——拦截是事件管理中心的治理能力）
- ❌ Schema合规性的实时告警推送（本期不做，后续可扩展）
- ❌ 自动修复 / 自动补全属性（本期不做）

### 3.2 🆕 v0.6 增量：字段值格式校验（基于样本抽样数据）

> **竞品对标**：Segment Protocols 的 Tracking Plan 支持为属性定义 allowed values 和 regex pattern，入站事件实时校验字段值是否符合预设格式规则；Adobe Experience Platform 的 XDM Schema 支持字段级别的 format 约束（如 email / uri / date-time）。
>
> **与 §3.1 Schema合规性检测的关系**：Schema合规性检测关注"结构层"（字段有没有、类型对不对），字段值格式校验关注"内容层"（字段的值符不符合业务规则）。两者互补，不重叠。

#### 3.2.1 业务背景

Schema合规性检测解决了"字段有没有"的问题，但在消费金融场景中，更常见的数据质量问题是**关键字段的值不符合业务格式规则**：

- 客户唯一标识：身份证号应为18位，手机号应为11位——格式不对直接导致ID-mapping失败
- 事件触发时间：应为 ISO 8601 格式（如 `2026-07-14T10:22:00+08:00`），但上游可能传入时间戳或自定义格式——格式不对导致时序分析失真

**v0.6 明确**：事件的强制字段只有两个——**客户唯一标识**和**事件触发时间**。格式校验优先聚焦这两个强制字段，其他字段为可选校验。

这些问题在Schema层面是"合规"的（字段存在、类型是String），但业务上不可用。**样本统计模块需要能"看见"这些内容层的违规**。

#### 3.2.2 业务诉求

- **运营同学**：接入新事件后，想确认"关键字段的值格式是否合规？身份证号是不是18位？手机号是不是11位？"
- **事件管理员**：想全局看"哪些事件的字段值存在格式违规？违规类型和占比如何？"以便推动上游修复

#### 3.2.3 业务范围（仅测试 PRD 视角）


| 项          | 内容                                                                                                                   |
| ---------- | -------------------------------------------------------------------------------------------------------------------- |
| **校验优先级**  | 强制字段（客户唯一标识 + 事件触发时间）必须校验；其他字段按已配置的格式规则可选校验                                                                          |
| **校验方式**   | 基于样本统计模块的抽样数据，对已配置格式规则的字段执行校验（强制字段必校验，可选字段按配置校验）                                                                     |
| **格式规则来源** | 强制字段：硬编码规则（客户唯一标识格式 + 事件触发时间格式）；可选字段：事件管理中心已注册的字段格式约束（引用 FEAT-MKT-CRD-EVENT）                                         |
| **校验维度**   | ① 长度校验（如：身份证号=18位，手机号=11位）② 正则校验（如：手机号匹配 `^1[3-9]\d{9}$`）③ 格式校验（如：时间字段必须为 ISO 8601）④ 枚举校验（如：事件类型白名单）⑤ 范围校验（如：金额 ≥ 0） |
| **校验时机**   | 样本统计模块查询时实时校验（非全量扫描，基于当前抽样窗口的数据）                                                                                     |
| **展示位置**   | 样本统计模块的"点查事件详情"页，在字段详情中展示格式校验结果                                                                                      |
| **校验状态**   | 合规 / 格式违规（附具体违规原因，如"身份证号长度不足18位"）                                                                                    |
| **筛选支持**   | 样本统计模块的"字段筛选"维度新增一项：「字段格式合规状态」                                                                                       |
| **业务规则**   | 仅作**只读校验+展示**，不拦截事件、不修改数据、不阻断下游流程；强制字段校验不可关闭，可选字段校验可按配置开关                                                            |


#### 3.2.4 消费金融场景典型格式规则示例

**强制字段（必须校验）**：


| 字段          | 格式规则        | 校验方式                | 违规示例                          |

**可选字段（按需配置校验）**：

| ---- | ------ | ---- | ------------- |

## 四、 需求 2：ID-mapping 事件触发（继承 v0.4）

### 4.1 业务背景

#### 4.1.1 现状问题（业务视角）

- 事件中心处理 Kafka 接入事件（Kafka 为事件唯一入口），每个事件都涉及"哪个用户做了这件事"
- **现状**：ID-mapping 使用数仓离线数据，存在 T+1 延迟——**当日进件的新客户在离线表中查不到身份**，事件变成"孤儿"
- 孤儿事件的后果：圈选不准确、人群计算偏差、营销触达错位
- **核心痛点**：离线数据导致当日新客户的事件无法关联身份，实时业务场景（如当日进件→当日营销触达）断裂

#### 4.1.2 业务诉求

**对每一个事件，都执行一次 ID-mapping 动作**——

- 命中（客群中心能查到）→ 用客群中心的统一身份做关联
- 未命中（客群中心查不到）→ 触发兜底（核心接口补全身份信息），沉淀为待回填数据

**核心变化（v0.6 明确）**：ID-mapping 数据源从"数仓离线表"改为"客群中心"，解决当日进件新客户身份缺失问题。客群中心数据为准实时（当日可查），兜底路径补齐客群中心仍查不到的剩余缺口。

**本质**：让"事件 → 身份"的映射从离线 T+1 升级为准实时，当日进件当日可关联，覆盖率从 ~95% 提升到 ≥ 99%。

### 4.2 业务范围

#### 4.2.1 触发对象

- ✅ **所有事件**（Kafka 是事件唯一入口，所有事件均经 Kafka 接入，无其他入口）
- ❌ 虚拟事件（虚拟事件是派生的，依赖基础事件的 ID-mapping 结果）
- ❌ 测试/mock 事件

#### 4.2.2 业务路径（双路径）


| 路径          | 触发条件        | 业务动作             | 结果               |
| ----------- | ----------- | ---------------- | ---------------- |
| **路径 A：命中** | 客群中心能查到用户身份 | 用客群中心的统一身份做关联    | 事件携带统一身份 ID 进入下游 |
| **路径 B：兜底** | 客群中心查不到     | 触发外部能力（核心接口）补全身份 | 补全结果沉淀为待回填数据     |


> 两条路径都做"ID-mapping 动作"，只是来源不同（客群中心 vs 外部能力）。
>
> **v0.6 明确**：路径 A 的数据源从"数仓离线表"改为"客群中心"。客群中心为准实时数据源，当日进件可查；兜底路径补齐客群中心仍查不到的剩余缺口。

#### 4.2.3 不在本次范围

- ❌ 核心接口的内部实现（黑盒视角）
- ❌ 临时表的数据结构 / 库 / 保留时长
- ❌ 回填 ID-mapping 底表的执行机制
- ❌ 虚拟事件触发的 ID-mapping

### 4.3 业务场景

#### 场景 1：运营同学视角——"今天事件身份覆盖率怎么样？"

- 角色：运营同学
- 诉求：看每天事件身份的命中/兜底比例，发现数据质量问题
- 现状：无可观测界面，只能问数据开发
- 期望：样本统计模块能看到 ID-mapping 命中/兜底状态

#### 场景 2：事件管理员视角——"兜底失败的事件有多少？怎么排查？"

- 角色：事件管理员
- 诉求：定位兜底失败的具体事件，看原始 ID + 失败原因
- 现状：无系统化排查工具
- 期望：样本统计能筛"未命中"事件 + 看兜底状态

### 4.4 业务规则

#### BR-IDM-001 触发规则


| 字段       | 内容                         |
| -------- | -------------------------- |
| **规则**   | 每个事件必须执行一次 ID-mapping 动作   |
| **范围**   | 全量事件（Kafka 为唯一入口，无白名单/黑名单） |
| **执行点**  | 事件进入事件中心后、下游处理前            |
| **失败处理** | 兜底失败的事件进入"待补全"状态，可在样本统计中查询 |


#### BR-IDM-002 命中路径规则


| 字段      | 内容                     |
| ------- | ---------------------- |
| **规则**  | 客群中心能查到 → 直接用客群中心的统一身份 |
| **优先级** | 高（快路径）                 |
| **后续**  | 事件携带统一身份 ID 进入下游       |


#### BR-IDM-003 兜底路径规则


| 字段       | 内容                        |
| -------- | ------------------------- |
| **规则**   | 客群中心查不到 → 触发外部能力补全        |
| **外部能力** | 核心接口（李宵友团队提供）——**不写技术细节** |
| **沉淀**   | 补全结果沉淀为待回填数据              |
| **下游事件** | 事件携带补全后的统一身份 ID 进入下游      |


#### BR-IDM-004 业务可观测性


| 字段      | 内容                              |
| ------- | ------------------------------- |
| **要求**  | 样本统计模块必须能区分"命中事件"和"兜底事件"        |
| **可视化** | 样本统计能按"ID-mapping 状态"筛选         |
| **明细**  | 点查事件时能看到 ID-mapping 来源（客群中心/外部） |


### 4.5 业务验收标准


| 验收项        | 标准                                     |
| ---------- | -------------------------------------- |
| **触发完整性**  | 100% 事件都执行了 ID-mapping 动作（Kafka 为唯一入口） |
| **覆盖率提升**  | ID-mapping 覆盖率从现状（假设 ~95%）提升到 ≥ 99%    |
| **业务可观测**  | 样本统计能看到命中/兜底/失败 3 种状态                  |
| **运营自助排查** | 运营同学能筛"兜底失败"事件，自助定位问题                  |
| **不影响主流程** | 兜底失败不应阻塞事件进入下游（标记"待补全"即可）              |


### 4.6 异常场景（业务视角）


| 异常                  | 业务期望                                 |
| ------------------- | ------------------------------------ |
| ID-mapping 客群中心查询失败 | 业务上等同于"未命中"，走兜底路径                    |
| 核心接口调用失败            | 事件标记"待补全"进入下游，**不阻塞**                |
| 核心接口超时              | 业务上等同于"未命中+失败"，事件标记"待补全+兜底失败"        |
| 全部路径都失败             | 业务上**接受数据丢失**（业务侧有容错），但要求**可观测+可追溯** |


> 业务对"丢少量数据"是**有容忍的**（95% → 99% 的提升已经够用），但**对"看不见丢了什么"是不能容忍的**——这是可观测性的关键。

### 4.7 业务边界（明确不做）

| --------------------- | ----------------------------- |

| 临时表数据如何回填底表           | 后续单独 PRD（不在本次）                |
| ID-mapping 客群中心接口本身维护 | 引用 FEAT-MKT-CRD-IDMAPPING，不重写 |
| 实时计算 vs 离线计算          | 不在 PRD 范围（技术方案定）              |
| 多语言/国际化               | 业务暂无诉求                        |

### 5.4 🆕 v0.6 增量：圈选溯源链路升级

> **竞品对标**：市面CDP（Segment / Tealium / 神策）均未提供"事件→圈选规则"的反向溯源能力。当前 `is_targeted_by_audience_rule` 只回答"有没有被命中"（是/否），但运营和事件管理员更需要知道"被哪几条规则命中了"——这是从"观测"到"诊断"的跨越，是差异化机会。

#### 5.4.1 业务背景

当前 `is_targeted_by_audience_rule` 是布尔值，只回答"这个事件有没有被圈选规则命中"。但实际业务中：

- 运营接入新事件后，不仅想知道"有没有被命中"，更想知道"被哪几条规则消费了"——以便确认事件是否按预期进入目标人群
- 事件管理员排查问题时，需要从事件维度追踪到具体的圈选规则，判断是规则配置问题还是事件数据问题
- 圈选规则变更后，需要验证"哪些事件受影响"——反向溯源是前提

#### 5.4.2 业务诉求

- **运营同学**：点查事件时，能看到"该事件被哪些圈选规则命中"的列表（规则名+规则ID）
- **事件管理员**：能从事件维度跳转到圈选规则详情页，完成"事件→规则"的诊断闭环

#### 5.4.3 业务范围（仅测试 PRD 视角）


| 项         | 内容                                                                 |
| --------- | ------------------------------------------------------------------ |
| **升级字段**  | `is_targeted_by_audience_rule` 从布尔值升级为结构化字段                        |
| **新字段定义** | `targeted_by_rules`：数组类型，包含命中的圈选规则列表 `[{rule_id, rule_name}]`      |
| **兼容性**   | 保留原 `is_targeted_by_audience_rule` 布尔值字段（数组长度>0 即为"是"），不破坏已有逻辑     |
| **展示位置**  | 样本统计模块（需求1）的"点查事件详情"页，在 `is_targeted_by_audience_rule` 下方展示命中的规则列表 |
| **筛选支持**  | 样本统计模块的"字段筛选"维度保留「圈选命中状态」（是/否），新增「命中规则数」数值筛选                       |
| **跳转支持**  | 规则列表中的 rule_id 可点击跳转至圈选规则详情页（引用圈选 PRD v2.0 的规则管理界面）                |
| **业务规则**  | 仅作**只读展示**，不创建/编辑/删除圈选规则                                           |


#### 5.4.4 业务验收标准


| 验收项          | 标准                                                       |
| ------------ | -------------------------------------------------------- |
