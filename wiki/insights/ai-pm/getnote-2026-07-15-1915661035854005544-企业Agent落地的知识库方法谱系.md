## 一、为什么需要方法谱系

同一个需求——"给公司建一个知识库"——技术方案可能完全不同。

一家消费金融公司要做合规知识库，答案必须溯源到监管文件的具体条款，不能有一丝偏差。一家SaaS公司要做技术知识库，工程师需要跨文档的综合推理——这个API和那个API能不能一起用，文档里没写，得自己推断。一个独立开发者要做个人知识库，只想把读过的论文和笔记变成可查询的体系，维护成本越低越好。

三个场景，三种完全不同的技术路线。但过去两年，行业的默认答案是同一个：RAG。

把文档切片存进向量库，查询时检索相关片段，让LLM基于检索结果生成答案。NotebookLM这么干，ChatGPT文件上传这么干，市面上绝大多数企业知识库产品也这么干。

RAG没有错。但RAG有一个被长期忽视的根本问题：**没有复利**。

你问了100个问题，LLM做了100次检索、100次拼接、100次推理。但第101个问题来的时候，知识库并没有因此变得更聪明。上次好不容易得出的概念关系、矛盾点、判断依据，死在了聊天记录里。

2026年4月，Andrej Karpathy在X上抛出一句话："Compile, don't retrieve"——先编译，不检索。三个月内，这条推文浏览量超过1600万，GitHub Gist收获5000+星标。它不是在优化RAG，而是在说：**RAG的底层逻辑可能从方向上就错了。**

这引出了一个更根本的问题：知识库应该怎么建？

答案取决于三个变量：

- **谁来读**——是人查原文做业务决策，还是LLM做推理分析？
- **知识怎么变**——是高频变更的政策文档，还是稳定积累的技术知识？
- **合规要求多高**——答案必须溯源到原文条款，还是综合结论即可？

当前行业的问题不是RAG不好，而是**RAG成了唯一答案**。LLM Wiki被热炒，但企业落地水土不服。裸LLM被忽视，但很多场景其实不需要知识库。

这篇文章要做的事：把知识库的方法谱系画清楚——有哪些范式、各自定位、什么场景用什么、怎么选。

## 二、三种范式：按"知识组装时机"划分

理解知识库范式的关键维度是**知识组装时机**——知识在什么时刻被组织成可用的形态。按这个维度，当前存在三种截然不同的范式：


| 维度         | 裸LLM                        | RAG                     | LLM Wiki                            |
| ---------- | --------------------------- | ----------------------- | ----------------------------------- |
| **知识组装时机** | 训练时                         | 查询时                     | 摄入时                                 |
| **核心逻辑**   | LLM本身就是"模糊的维基百科"，有损压缩的互联网知识 | 每次从原始文档检索片段，现场拼答案       | LLM将原始资料"编译"成结构化Wiki，查询时检索编译后的高质量知识 |
| **知识形态**   | 固化在模型参数中                    | 原始文档切片+向量索引             | LLM生成并维护的结构化Markdown                |
| **典型产品**   | ChatGPT（无RAG模式）             | NotebookLM、ChatGPT文件上传  | ClaudeCode + llm-wiki插件             |
| **基础设施成本** | 零                           | 中（向量库+Embedding模型+检索管线） | 中低（Markdown文件+LLM调用）                |
| **核心优势**   | 即问即答，无需准备                   | 实时性强，文档变了立刻生效           | 知识有复利，越用越聪明                         |
| **核心缺陷**   | 私有知识全靠幻觉                    | 没有积累，每次从零开始             | 编译成本高，LLM可能引入偏差                     |


用一个比喻说清楚：

- **裸LLM**像是一个博学但没有记忆的教授——什么都知道一点，但从来不记笔记，也不认识你
- **RAG**像是一个每次考试都翻课本的学生——答案基于原文，但考完就忘，下次还得从头翻
- **LLM Wiki**像是一个认真做笔记并持续整理的研究员——每次学完都把知识编译进笔记本，交叉引用、标注矛盾，下次直接查笔记

还有一个更精确的类比来自编程语言：裸LLM是固件（出厂写死），RAG是解释器（每次运行从源码重新翻译），LLM Wiki是编译器（提前把源码编译成机器码，执行快但需要编译过程）。

### 关键洞察：LLM Wiki是"机器的知识库"，RAG是"人的知识库"

先看两个真实场景：

**场景A**：一家消费金融公司用LLM Wiki做合规知识库。审计时，监管要求每个AI生成的答案必须能溯源到原始监管文件的具体条款。但LLM Wiki的答案是编译后的"二手知识"——中间经过LLM的理解和概括，溯源链路断裂。审计员问："这个结论来自哪份文件的哪一条？"知识库答不上来。合规审查不通过。

**场景B**：一个研发团队用RAG做技术知识库。工程师问"API-A和API-B能不能一起用"，RAG检索到两份独立的API文档，各说各的，没有交叉引用。LLM基于两份片段拼接出一个答案，但遗漏了一个关键的版本兼容问题。每次有人问同样的问题，系统都要从头检索、从头推理，上一次好不容易发现的兼容性问题，死在了聊天记录里。

两个场景，同一个根源：**没有区分知识库的"读者"是谁。** 场景A错在让"人"去依赖"机器编译的知识"做合规决策；场景B错在让"机器"每次都从零检索，而不是用编译好的知识加速推理。

这引出了整个谱系最重要的判断：

LLM Wiki和RAG不是同一种东西的两种实现，而是服务不同"读者"的两种知识系统。


| 维度       | LLM Wiki                      | RAG                 |
| -------- | ----------------------------- | ------------------- |
| **主要读者** | LLM自己                         | 人（以及被人监管的LLM）       |
| **知识形态** | 编译后的结构化Markdown——LLM生成的"二手知识" | 原始文档切片——保留原文的"一手知识" |
| **核心价值** | 让LLM"懂"得更快、更准、更有上下文           | 让人"查"得到、信得过、可审计     |
| **所有权**  | LLM独占——LLM写、LLM维护、LLM更新       | 人主导——人上传、人审核、人确权    |


为什么LLM Wiki更适合作为"LLM查询分析的知识库"？因为Wiki层本质上是LLM为自己准备的"速查手册"——上下文完整、关系显式化、查询效率高、有复利。知识库维护的痛点不是读和想，而是"记账"——更新交叉引用、保持摘要最新、标注矛盾、维护几十个页面的一致性。人类会因为维护成本随规模暴涨而放弃。把Wiki层的所有权交给LLM，维护成本就被压到接近零。

为什么RAG更贴合实际的业务层面——人查看的知识库？因为企业业务场景中，知识库的核心用户是人。溯源是硬性要求（金融合规场景下答案必须能溯源到原始文档的具体条款），权限管控需要文档级粒度，审计需要可追溯，人要读原文而不是摘要，实时性要求政策变了立刻生效。LLM Wiki的编译产物是"二手知识"，中间经过LLM的理解和概括，溯源链路断裂。一篇直接讨论LLM Wiki企业落地的文章指出："网红项目的'个人最佳实践'，到了企业场景里，全是水土不服的坑——权限兜不住敏感数据，溯源找不到具体条款，上万份文档跑起来成本直接炸锅。"

## 三、范式选择决策树

从三个维度判断该用什么范式：

```
你的知识是否涉及私有数据？
├── 否 → 裸LLM是否够用？
│   └── 是 → 裸LLM
│   └── 否 → RAG（补充私有知识）
└── 是 → 知识变更频率如何？
    ├── 高频（每天/每周变更）→ 答案是否需要溯源到原文？
    │   ├── 是（合规场景）→ RAG
    │   └── 否 → RAG（仍推荐，实时性优势明显）
    └── 低频（月度/季度变更）→ 是否需要跨文档综合推理？
        ├── 是 → 知识是否属于"探索型/研究性/持续更新"领域？
        │   ├── 是 → LLM Wiki
        │   └── 否 → RAG（普通知识归档，不需要编译）
        └── 否 → 文档规模如何？
            ├── 大（万级以上）→ RAG
            └── 中小（千级以内）→ RAG（维护成本更低）
```

### 行业场景速查


| 行业/场景             | 推荐范式             | 关键考量                                    |
| ----------------- | ---------------- | --------------------------------------- |
| 金融合规（政策解读、合同审查）   | RAG为主            | 溯源到原文条款是硬性合规要求，编译后的"二手知识"不可接受           |
| 研发技术知识库           | LLM Wiki为主       | 技术概念间的交叉引用、版本演进、矛盾标注是核心需求               |
| 客服中心              | RAG为主            | FAQ高频变更，实时性优先                           |
| 学术研究              | LLM Wiki为主       | 文献综述、概念关系、研究脉络需要深度综合                    |
| 企业内部培训            | LLM Wiki + RAG融合 | 培训内容（稳定）用Wiki沉淀，最新政策（变更）用RAG实时检索        |
| 个人知识管理（探索型/研究性领域） | LLM Wiki         | 知识持续更新、需要深度综合的领域（如AI进展追踪）；普通笔记归档用RAG更合适 |

## 四、融合架构：终局不是二选一

RAG和LLM Wiki不是替代关系，而是分工关系。企业级知识库最可能的长局形态是"人机分离"的融合架构：

```
┌──────────────────────────────────────────────────┐
│                  查询路由层                        │
│          判断查询者是人还是LLM Agent                │
├────────────────────┬─────────────────────────────┤
│                    │                             │
│   LLM Wiki         │         RAG                 │
│   （机器的知识库）   │     （人的知识库）            │
│                    │                             │
│  · LLM独占维护     │  · 人主导管理                 │
│  · 编译后的结构化知识│  · 原始文档+切片索引          │
│  · 概念关系、综合结论│  · 可溯源、可审计、可权限控制   │
│  · LLM快速理解用   │  · 人查看和合规用              │
│                    │                             │
├────────────────────┴─────────────────────────────┤
│              原始文档层（Raw Sources）              │
│         RAG直接检索；LLM Wiki从中编译              │
└──────────────────────────────────────────────────┘
```

### 核心设计原则

- **Raw层是source of truth**：原始文档不可变，LLM永远不修改原始资料，只从中抽取信息写进Wiki
- **Wiki层LLM独占**：人类不直接编辑Wiki页面，只做审阅和修正。避免人机混写导致的一致性问题
- **RAG层人主导**：文档上传、权限设置、版本管理由人控制，LLM只读不写
- **两层共享Raw层**：RAG和LLM Wiki都从同一份原始文档出发，但加工方式不同——RAG做切片+向量化（保留原文），LLM Wiki做编译+结构化（生成新知识）

### 融合查询流程

1. **查询路由**：LLM判断问题类型——需要综合知识还是实时数据？
2. **沉淀层查询**：概念性问题、跨文档综合、历史脉络 → 查LLM Wiki
3. **实时层查询**：最新政策、实时数据、精确条款 → 查RAG
4. **双层融合**：复杂问题同时查两层，Wiki提供背景知识和概念框架，RAG补充最新事实
5. **溯源保障**：最终答案中的事实性声明，必须能溯源到原始文档（RAG层保障）

### 不同场景下的层间协作


| 场景            | LLM Wiki层做什么          | RAG层做什么              |
| ------------- | --------------------- | -------------------- |
| LLM Agent自主分析 | Agent查Wiki获取概念框架和综合结论 | 补充最新事实和精确数据          |
| 人查知识库         | 不直接参与（人看Wiki页面作为辅助参考） | 人检索原始文档，查看原文，溯源条款    |
| 合规审计          | 不参与（编译产物不可作为合规依据）     | 提供原始文档+审计日志+权限记录     |
| Agent反馈回写     | 新经验编译进Wiki页面          | 原始文档经审批后更新，触发RAG增量索引 |
| 知识矛盾处理        | Wiki中显式标注矛盾，供LLM推理时参考 | 人审阅后更新原始文档，消除矛盾源头    |


### 融合架构的适用条件


| 条件           | 说明                  |
| ------------ | ------------------- |
| 文档规模中等（千级以内） | LLM Wiki的编译成本可承受    |
| 知识有稳定层和实时层之分 | 不是所有知识都在频繁变更        |
| 有溯源合规要求      | RAG层保障事实性声明的可溯源性    |
| 有质量审阅能力      | LLM Wiki的编译产物需要人工抽检 |

## 五、企业Agent落地现状

### 当前主流方案：RAG为主

截至2026年7月，企业Agent+知识库的主流方案仍然是RAG。原因很简单：RAG的工程化成熟度最高，增量更新机制成熟，溯源能力天然支持合规要求，向量数据库生态完善。

LLM Wiki在个人和小团队的**探索型、研究性、持续更新**的知识领域已经验证可行（Karpathy本人的AI研究工作流就是证明），但**不适合普通的个人笔记归档**——那种"把笔记存起来方便查"的场景，RAG更简单更实用。LLM Wiki的企业级落地尚在早期——编译质量管控、多人协作、权限管理、合规溯源等企业刚需，目前缺乏成熟方案。

### 三个关键判断

**判断一：Agent从知识库取知识，也得往知识库存知识。** 没有反馈回写的知识库永远是静态的——Agent的纠错经验不沉淀，下次犯同样的错。但回写必须受控：写入不可审计，检索越强污染传播越快。

**判断二：单Agent优先，多Agent是最后手段。** Google Research在180种Agent配置横评中发现：单Agent在64%的benchmark上与多Agent持平，多Agent平均只增加2.1个百分点准确率，但成本翻倍。多Agent能稳定胜出只有三种场景：context污染拖累性能、任务可并行执行、专业化能改善工具选择或任务专注度。

**判断三：80%的优化信号在隐式反馈里。** 快速跳过、重复提问、修改后重新提交——这些行为信号比显式的点踩和评分量大得多，但大多数团队只做了显式反馈，错过了大部分优化机会。

### 两个关键风险

1. **Agent只取不存**：没有反馈回写的知识库永远是静态的，Agent的纠错经验不沉淀，下次犯同样的错
2. **Agent随意写知识库**：写入不可审计，检索越强污染传播越快，必须经过证据约束和权限校验
