## 框架定位

这是文博在产品升级领域的**核心方法论**，来源于营销画布从周期配置到灵活拖拉拽的重大升级实践。

核心逻辑：**需求抽象 → 关键解决点 → Demo验证**

## 二、干系人对齐（新增）

> 每个升级项目开始前，必须明确干系人角色

### 干系人矩阵

| 角色 | 责任 | 参与方式 |
|------|------|---------|
| **决策者** | 最终拍板资源投入和方向 | 关键节点汇报 |
| **支持者** | 提供资源、协调推动 | 定期沟通 |
| **执行者** | 具体落地实现 | 日常协作 |
| **受影响者** | 升级后会影响其工作流程的用户 | 提前沟通、变更通知 |

### 检查项

```
□ 决策者是否确认升级目标和价值？
□ 支持者是否愿意提供资源？
□ 执行者是否理解需求和技术方案？
□ 受影响者是否提前沟通了变更影响？
```

## 四、核心流程详解

### Step 1：需求收集

**动作：**
- 明确业务有那些场景
- 了解经营方案和后续的策略准备

**输出：**
- 业务场景清单
- 经营目标描述

### Step 2：现状分析

**动作：**
- 评估现有系统能力
- 评估团队技术能力

**输出：**
- 现状能力矩阵

### Step 3：能力差距分析

**动作：**
- 对比目标场景和现状能力
- 识别能力缺口

**输出：**
- 能力差距清单
- 优先级排序

### Step 4：调研收集

**动作：**
- 调研行业最佳实践
- 分析同类产品的解决方案

**对标来源：**
- 火山引擎MA
- 平安、众安MA产品
- COZE、阿里PAI（可视化工作流）
- 数巅等内部产品

### Step 5：剪裁

**判断维度：**
| 维度 | 问题 | 决策 |
|------|------|------|
| **公司发展情况** | 哪些能力需要引入？ | 决定引入范围 |
| **技术能力** | 能落地哪些？ | 决定实现深度 |
| **业务需求** | 优先级是什么？ | 决定执行顺序 |

**剪裁原则：**
- 交互方式可以模仿
- 落地程度要结合技术能力
- 优先级要结合业务需求
- **不能大而全，"如无必要，勿增实体"**

**剪裁记录：**

```markdown
| 对标来源 | 对标功能 | 剪裁决策 | 理由 | 限制条件 |
|---------|---------|---------|------|---------|
| 火山引擎 | XXX功能 | 引入/不引入 | ... | ... |
```

### Step 6：技术方案预演

**动作：**
- 技术同学预演技术方案
- 评估可行性和复杂度

**输出：**
- 技术方案可行性评估
- 复杂度评估

### Step 7：Demo验证

**这是核心动作。**

**动作：**
- 用AI快速做出前端Demo
- 验证可行性

**解决的问题：**
- 交互方案说明
- 产品快速验证
- 提高业务接受度
- 完成策略预演
- 让前端同学有参考基础

### Step 8：风险清单（新增）

```markdown
| 风险类型 | 风险描述 | 影响 | 概率 | 应对策略 |
|---------|---------|------|------|---------|
| 技术风险 | | | | |
| 业务风险 | | | | |
| 资源风险 | | | | |
| 时间风险 | | | | |
```

### Step 9：实现

**分阶段交付：**
- 第一期：交付MVP，验证核心假设
- 迭代期：基于用户反馈持续优化

**执行要点：**
- 保持简洁，不追求大而全
- 持续验证，边做边调整

## 五、停止标准（新增）

> 什么情况下不做这个升级

### 停止条件检查

```
□ 业务需求不明确，无法定义MVP
□ 技术方案无法Demo验证可行性
□ 团队能力无法支撑实现
□ 成本超出预期且无法优化
□ 业务优先级发生变化，资源无法保障
□ 风险无法接受且无应对策略
```

### 决策逻辑

```
如果以上任一条件为"是" → 暂停或终止升级
如果所有条件为"否" → 可以继续推进
```

## 六、3个成功关键词

| # | 关键词 | 含义 |
|---|--------|------|
| **1** | 需求抽象 | 了解业务策略需求，抽象系统能力 |
| **2** | 关键解决点 | 找到核心问题，不追求大而全 |
| **3** | Demo验证 | 用AI快速验证可行性，统一认知 |

---

## 七、适用边界

| 适用 | 不适用 |
|------|--------|
| 业务需求明确、目标清晰的产品升级 | 探索性产品（如数据门户） |
| 需要重大架构升级的场景 | 迭代优化类的小功能升级 |
| 团队有新能力需要验证的场景 | 原有体系可以渐进改良的场景 |

---

## 八、核心原则

### 1. 如无必要，勿增实体
基于业务实际需求出发，不能大而全。每增加一个功能，都必须问：这个功能对业务目标贡献多少？

### 2. Demo验证前置
用AI快速验证可行性，统一业务、技术、设计的认知，避免开发完成后返工。

### 3. 关键解决点原则
找到核心问题，优先解决。不是所有问题都要现在解决。

### 4. 分阶段交付原则
不要试图一次性交付所有功能。第一期验证核心假设，后续基于反馈迭代。

## 九、案例对应

**案例：营销画布升级**

| 框架环节 | 案例对应 |
|---------|---------|
| 干系人对齐 | 业务团队、CDP、MA、权益、触达、电销团队 |
| MVP定义 | 第一期：周期配置升级 + 核心功能 |
| 需求收集 | 明确经营场景：T0短信、T3电话 |
| 现状分析 | 原有系统：周期配置，不支持实时热场景 |
| 能力差距 | 数据时效、策略灵活度、策略可分析性 |
| 调研收集 | 火山引擎、平安、众安、COZE、阿里PAI |
| 剪裁 | 基于公司情况选择引入哪些能力 |
| Demo验证 | 自己用AI做前端Demo验证可行性 |
| 风险清单 | 前端复杂度、团队学习成本 |
| 实现 | 分阶段交付，50万/小时吞吐量达成 |

**关键成功动作：**
用AI做前端Demo，解决了交互方案说明和可行性确认的问题，让业务提高接受度，完成策略预演。

## 十、对托尼的建议

做升级前必须明确知道：
1. 升级的目标是什么？
2. 要解决什么问题？
3. 第一期交付什么、不做什么？

**最大坑：** 大而全、追求完美功能、忽视团队实际能力。
