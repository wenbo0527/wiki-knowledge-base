## 六、范式一：裸LLM

### 6.1 核心逻辑

LLM的参数中编码了训练数据的统计规律。从知识管理的角度看，LLM本质上是"互联网文本的有损压缩"——它记住了训练语料中的模式，但不存储原文，也无法保证事实准确性。

这个"有损压缩"的比喻很精确：LLM知道光合作用需要阳光和水，但如果你问它某个冷门公司的2024年Q3营收，它可能自信地编一个数字出来。通用知识压缩得好，长尾知识压缩失真。

裸LLM的知识边界由三个因素决定：

- **训练数据的覆盖范围**：互联网上的公开知识覆盖充分，私有领域知识几乎为零
- **训练截止日期**：模型不知道训练完成之后发生的事
- **压缩失真**：训练数据中的统计模式被保留，但具体事实可能被"平均化"或"混淆"

### 6.2 技术方案

裸LLM无需额外基础设施，但有两个可用的增强手段：

**System Prompt注入（上下文学习）**

在System Prompt中注入领域知识，让LLM在当前会话中"知道"这些信息：

```
你是一个消费金融领域的知识助手。以下是公司基本信息：
- 公司全称：XX消费金融有限公司
- 成立日期：2015年3月
- 注册资本：15亿元
- 主要产品：现金贷、分期商城
...
```

局限：上下文窗口有限（当前主流模型8K-128K tokens），注入知识量受约束。超过窗口容量后，早期注入的知识会被"遗忘"。

**多轮对话中的知识累积**

通过多轮对话逐步补充背景信息，让LLM在当前会话中积累上下文。但会话结束后，这些知识不会保留——下次对话从零开始。

### 6.3 评估方案


| 评估维度    | 方法               | 说明                 |
| ------- | ---------------- | ------------------ |
| 通用知识准确率 | MMLU、C-Eval等基准测试 | 衡量模型在通用知识上的表现      |
| 领域准确率   | 构建领域问答集，人工标注标准答案 | 用100-500个领域问题测试准确率 |
| 幻觉率     | 将模型输出与已知事实对比     | 统计"自信但错误"的回答比例     |
| 知识截止影响  | 测试训练截止日期后的事实性问题  | 量化时效性损失            |


### 6.4 存在问题


| 问题       | 表现               | 严重程度      |
| -------- | ---------------- | --------- |
| 私有知识全靠幻觉 | 问公司内部制度，模型自信编造   | 致命        |
| 知识截止日期   | 不知道训练完成后的新信息     | 高         |
| 无法溯源     | 答案无法追溯到具体来源文档    | 高（合规场景致命） |
| 无法更新     | 知识过时只能重新训练或微调    | 高         |
| 一致性差     | 同一问题不同次提问，答案可能不同 | 中         |


**结论**：裸LLM适用于通用知识问答、创意生成、代码辅助等不涉及私有数据和合规要求的场景。任何需要事实准确性和可溯源性的企业场景，裸LLM都不应作为唯一知识来源。

## 七、范式二：RAG（检索增强生成）

### 7.1 核心逻辑

RAG的核心逻辑是"查询时检索"——每次用户提问，系统从外部知识库检索相关文档片段，LLM基于检索结果生成答案。

**核心价值**：

- **事实准确性**：答案基于检索到的具体文档，可溯源到原文
- **实时性**：文档更新后立刻生效，无需重新训练模型
- **数据安全**：数据不出本地库，私有化部署可满足合规要求

**核心缺陷**：

- **没有复利**：100次问答后，知识库和第1次一模一样。上次好不容易得出的概念关系、矛盾点、判断依据，死在了聊天记录里
- **碎片化**：文档被切成chunk，上下文断裂，跨文档的综合推理困难
- **矛盾不可见**：两份文档说法矛盾，RAG可能同时召回两个chunk，LLM随机采信

### 7.2 技术方案

#### 检索管线全景：改写→召回→重排

在展开技术细节之前，先看清RAG检索管线的全貌。用户的一个问题，从输入到输出，要经过三道关卡：

**第一道：Query改写**——把用户"说人话"的模糊问题，翻译成知识库"听得懂"的精确查询。口语化问题、多轮对话的指代、日常用语与专业术语的鸿沟，都在这一步解决。

**第二道：多路召回**——同时用语义向量、关键词、知识图谱三种方式检索，各有所长，融合后取长补短。这一步追求"不漏"，宁可多召回一些，也不能漏掉关键文档。

**第三道：重排序**——从召回的20-100条候选中，用深度匹配模型精排出最相关的3-5条。这一步追求"不噪"，把无关的干扰项过滤掉。

三步缺一不可：没有改写，好问题进不去；没有多路召回，好文档出不来；没有重排序，好文档被淹没在噪音里。实测数据：混合检索+重排序可将准确率从62%提升至87%。

下面逐项展开。

#### 7.2.1 四层架构模型


| 层级        | 职责                 | 核心组件                                 |
| --------- | ------------------ | ------------------------------------ |
| **知识来源层** | 汇聚企业各类知识资产         | 内部Wiki、Git代码仓、工单系统、邮件系统、IM、数据库、本地共享盘 |
| **知识处理层** | 文档解析、语义切分、向量化和索引构建 | 文档解析器、Chunking引擎、Embedding模型         |
| **知识存储层** | 混合存储               | 向量数据库 + 结构化数据库 + 知识图谱                |
| **应用服务层** | 面向员工和AI应用提供服务      | 问答、检索、推荐、引用溯源                        |


#### 7.2.2 多模态文档入库

企业知识库的内容类型分布：纯文本约40%，含图像的PDF/PPT约35%，数据表格约15%，音视频及其他约10%。传统纯文本RAG对35%+的内容视而不见。

**文档格式识别与路由**——入库的第一步是"分诊"：


| 文档格式                   | 路由方向     | 处理方式                   |
| ---------------------- | -------- | ---------------------- |
| 纯文本（TXT/MD/DOCX）       | 直接文本解析   | 文本清洗→分块→向量化            |
| 富媒体PDF（含扫描图/矢量图/OCR文本） | PDF多模态解析 | 版面识别→图文分离→分别处理         |
| 表格（Excel/CSV）          | 表格解析     | 表格结构识别→转自然语言/结构化存储     |
| 图片（JPG/PNG）            | 图像处理     | OCR文字提取 + 视觉模型生成描述     |
| 音频（MP3/WAV）            | 语音处理     | ASR转文字→文本分块→向量化        |
| 视频（MP4）                | 视频处理     | 关键帧提取→图像处理 + 字幕提取→文本处理 |


**图片入库处理**：

1. OCR文字提取：识别图片中的文字内容（如扫描合同、截图）
2. 视觉模型描述生成：对非文字内容（流程图、架构图、产品图），使用Vision LLM生成文字描述
3. CLIP嵌入：将图像和文字描述映射到同一向量空间，支持"以图搜文"和"以文搜图"
4. 元数据标注：添加来源页码、文档标题、图片类型等元数据，辅助后续过滤检索

**表格入库处理**：

1. 表格结构识别（TSR）：识别行列关系、合并单元格、表头层级
2. 转自然语言描述：将表格内容转为可检索的文本描述（如"2024年Q1营收为1.2亿元，同比增长15%"）
3. 结构化存储：关键数据同时存入关系数据库，支持精确查询

**音频入库处理**：

1. ASR转文字：使用Whisper等模型将语音转为文本
2. 说话人分离：识别不同发言人，标注对话角色
3. 时间戳对齐：保留时间信息，支持"定位到第X分钟"的引用
4. 文本分块→向量化：与纯文本走相同的后续流程

**视频入库处理**：

1. 关键帧提取：按时间间隔（如每5秒）或场景变化提取关键帧
2. 字幕提取：有字幕→直接提取；无字幕→ASR生成字幕
3. 双通道处理：图像帧走CLIP嵌入，字幕文本走Text嵌入
4. 统一向量存储（带模态标签）：所有模态的向量存在同一向量库中，但标注模态类型

**多模态统一入库架构**：

```
原始文档 → 模态识别与拆分 → 文本块/图像块/表格块/音频块
                                    ↓              ↓            ↓            ↓
                              Text Emb      CLIP Emb    表格解析     ASR+Text Emb
                                    ↓              ↓            ↓            ↓
                              统一向量存储（带模态标签 + 元数据）
                                    ↓
                              混合检索引擎 → 多模态生成（Vision LLM）
```

核心原则：模态统一化（所有模态最终都映射到可检索的向量空间）、语义结构化（保留文档逻辑结构）、元数据增强（来源、页码、模态类型、信源等级）。

#### 7.2.3 Query改写

用户原始查询通常存在三大缺陷：表达模糊（口语化、省略关键实体）、指代不清（多轮对话中的代词）、词汇鸿沟（日常语言 vs 专业术语）。

**三条核心技术路径**：


| 路径     | 核心思路               | 适用场景                 | 典型算法                                        |
| ------ | ------------------ | -------------------- | ------------------------------------------- |
| 语义增强型  | 生成假设性答案，用答案搜答案     | 跨风格检索（口语化问题 vs 专业文档） | HyDE                                        |
| 任务分解型  | 将复杂问题拆解为子问题并行检索    | 多维度对比、复合问题           | Sub-Query Decomposition、Step-Back Prompting |
| 上下文补全型 | 提取对话历史，补全当前请求的省略信息 | 多轮对话                 | 指代消解、对话历史压缩                                 |


**五种具体方法**：

**① 查询重写（Rewriting）**——通过Prompt让小参数量大模型将模糊问题改写为清晰、结构化的问题。

- 改写前："手机发热怎么办？"
- 改写后："智能手机在运行过程中出现异常发热现象，可能由哪些硬件或软件因素导致？请提供针对不同操作系统的故障排查步骤和降温方案。"

**② 多查询扩展（Multi-Query Expansion）**——为用户问题生成3-5个不同角度/同义词的子问题，并行检索后去重合并，扩大召回覆盖面。

- 原始查询："绿色能源有哪些？"
- 扩展查询1："可再生能源的种类"、扩展查询2："清洁能源技术的例子"、扩展查询3："对环境友好的发电方式"

**③ HyDE（假设文档嵌入）**——不直接改写问题，而是让大模型先生成一段"假设性理想答案"，再用这段答案去向量库检索。假设答案与真实文档在语义风格上更接近，能有效弥合"问题-文档"的语义鸿沟。

**④ 后退提示（Step-Back Prompting）**——当知识库中没有用户所需的具体信息时，先"退一步"询问更高层的抽象问题，获取上下文后再推理。

- 原问题："2024年Q3某产品销量是多少？" → 后退问题："该产品的销售趋势和季度变化规律是什么？"

**⑤ 子查询分解（Sub-Query Decomposition）**——将包含多个维度的复杂问题拆解为独立子问题，分别检索后逻辑整合。

- 原问题："A公司和B公司的财报对比如何？" → 子查询1："A公司2024年营收和利润" + 子查询2："B公司2024年营收和利润"

**工程落地难点**：


| 难点        | 具体表现                | 应对思路                              |
| --------- | ------------------- | --------------------------------- |
| 系统延迟      | 额外调用大模型改写，增加2秒+等待时间 | 小参数量模型做改写；异步改写+缓存热门query          |
| 改写质量不稳定   | 过度改写偏离原意，或改写后仍无法匹配  | A/B测试改写效果；设置改写置信度阈值，低置信度时保留原query |
| 多轮对话上下文丢失 | 长对话中指代消解失败          | 滑动窗口保留最近N轮对话；关键实体显式提取             |


**这意味着什么**：Query改写是RAG系统里"投入产出比最高"的优化手段——不改写，后面的检索再精细也是用错误的问题找答案。但改写本身也是一把双刃剑：过度改写会偏离原意，改写延迟会增加用户等待时间。工程上的折中方案是：用小参数量模型做改写，设置置信度阈值，低置信度时保留原query。

#### 7.2.4 匹配逻辑：混合检索

**第一轮：多路召回**

企业级RAG不依赖单一检索方式，而是多路并行召回后融合：


| 检索方式        | 原理                      | 优势               | 局限                     |
| ----------- | ----------------------- | ---------------- | ---------------------- |
| 语义向量检索      | 将query和文档都映射为向量，计算余弦相似度 | 理解同义词和语义关联       | 对关键词精确匹配弱；高维空间稀疏时区分度下降 |
| 关键词检索（BM25） | 基于词频-逆文档频率的精确匹配         | 对专有名词、法条编号等精确匹配强 | 无法理解语义相似性              |
| 知识图谱检索      | 沿图谱路径查询实体关系             | 支持多跳推理和确定性规则查询   | 需预先构建图谱，覆盖范围有限         |


**融合策略**：

- **倒数排名融合（RRF）**：将各路检索结果的排名倒数求和，按总分重排。计算简单、效率高，适合延迟敏感场景
- **加权得分融合**：为不同检索方式分配权重（如语义0.6 + 关键词0.3 + 图谱0.1），按加权分排序。权重可根据场景调优

**元数据过滤**——在向量检索前/后，利用元数据缩小检索范围：

- 按信源等级过滤（优先T1/T2级信源）
- 按时间范围过滤（仅检索最新版本）
- 按部门/业务线过滤（权限隔离）
- 按模态类型过滤（仅检索文本/仅检索图像）

这是企业级RAG区别于通用RAG的关键能力——业务边界控制召回范围。

**这意味着什么**：多路召回解决的是"不漏"的问题，元数据过滤解决的是"不噪"的问题。但两者之间有一个张力——过滤太严会漏掉相关文档，过滤太松会召回太多噪音。工程上的做法是：召回阶段宽松（宁可多召回），过滤阶段逐步收紧，最后靠重排序做精排。

#### 7.2.5 重排序（Rerank）

向量检索（Bi-Encoder）将query和文档分别编码为向量再计算相似度，速度快但精度有限——它只能做"浅层匹配"。重排序模型（Cross-Encoder）将query和每个候选文档拼接后联合编码，能做"深度匹配"，精度显著提升。


| 维度   | Bi-Encoder（向量检索）       | Cross-Encoder（重排序） |
| ---- | ---------------------- | ------------------ |
| 编码方式 | query和文档分别编码           | query和文档拼接后联合编码    |
| 计算速度 | 快（向量预计算，检索时只需算query向量） | 慢（每个候选文档都要重新编码）    |
| 精度   | 中等（浅层语义匹配）             | 高（深度交互匹配）          |
| 适用阶段 | 初筛召回（Top-K，K通常20-100）  | 精排筛选（Top-N，N通常3-5） |


**完整流程**：

```
用户Query → Query改写 → 多路召回（语义+关键词+图谱）→ 元数据过滤
                                                          ↓
                                                    Top-K候选（20-100条）
                                                          ↓
                                                    Cross-Encoder重排序
                                                          ↓
                                                    Top-N精排（3-5条）
                                                          ↓
                                                    拼接Context → LLM生成
```

**效果数据**：混合检索+重排序可将检索准确率从62%提升至87%，提升幅度约40%。

**模型选型**：


| 模型                 | 特点           | 适用场景        |
| ------------------ | ------------ | ----------- |
| bge-reranker-v2-m3 | 轻量级，多语言支持    | 通用企业场景      |
| bge-reranker-large | 精度更高，计算开销更大  | 对精度要求极高的场景  |
| Cohere Rerank      | API调用，无需本地部署 | 快速验证、不想自建模型 |
| Jina Reranker      | 开源，支持长文档     | 长文档检索场景     |


**这意味着什么**：重排序是RAG效果提升最显著的单项优化——从62%到87%，提升40%。但它的代价是延迟：每个候选文档都要重新编码，计算开销是向量检索的10-50倍。工程上的折中：召回Top-20（而非Top-100）再做重排，控制延迟在可接受范围内。

#### 7.2.6 知识分层存储

企业知识不是铁板一块，不同类型的知识需要不同的存储方式：


| 层级  | 知识类型     | 存储方式                    | 典型内容                  |
| --- | -------- | ----------------------- | --------------------- |
| 第一层 | 主数据与实体   | 图数据库（Neo4j/NebulaGraph） | 产品、套餐、客户群、区域——业务的骨架   |
| 第二层 | 业务关系与规则  | 图数据库                    | 互斥规则、适用条件、生效时间——确定性关系 |
| 第三层 | 结构化属性    | 关系数据库                   | 产品编码、标准名称、别名、权益明细     |
| 第四层 | 非结构化文档   | 向量数据库（Milvus/FAISS）     | 政策说明、活动口径、客服话术——语义检索  |
| 第五层 | 临时/过程性知识 | 缓存+日志                   | 用户交互记录、临时查询结果         |


核心原则：Neo4j处理确定性关系，Milvus负责语义检索。不能把所有文档塞进向量库，也不能把所有知识塞进图数据库——否则系统要么召回乱，要么查询慢，要么答案不可信。

**三种存储技术选型对比**：


| 维度   | 向量数据库                        | 知识图谱              | 关系数据库               |
| ---- | ---------------------------- | ----------------- | ------------------- |
| 核心能力 | 语义相似性搜索                      | 实体-关系网络，复杂推理      | 结构化数据管理，事务一致性       |
| 优势   | 高效召回相关文档片段；支持动态更新            | 精准关系推理；上下文完整性     | 数据可靠性强（ACID）；复杂查询能力 |
| 局限   | 上下文丢失风险；关系推理能力弱              | 构建成本高；大规模查询延迟     | 不适合非结构化数据；语义理解能力弱   |
| 代表产品 | Milvus、FAISS、Chroma、Pinecone | Neo4j、NebulaGraph | PostgreSQL、MySQL    |
| 适用场景 | 客服FAQ匹配、文档语义检索               | 供应链追溯、医疗多跳推理      | 金融交易记录、合规审计         |


#### 7.2.7 语义访问中台

大厂落地的核心经验：**不要让业务部门迁移数据**。采用"语义访问中台"思路：

- 原系统不动，只构建统一语义索引层
- 通过Wiki API拉取、Git定时同步、工单系统对接、文件服务器扫描、邮件解析等方式连接分散数据
- 核心原则：只读、不改、不影响原系统——阻力最小

#### 7.2.8 数据治理

企业数据普遍存在"脏数据"问题：同一文档多个版本、过期方案未标记、同名不同项目、复制粘贴文档泛滥。数据治理是知识库落地中工程量最大的环节，需要在技术层面建立自动化检测机制（版本去重、过期标记、相似度去重）。

#### 7.2.9 技术选型参考


| 组件    | 选型                     | 选型理由           |
| ----- | ---------------------- | -------------- |
| 向量化模型 | BAAI/bge-large-zh-v1.5 | 中文语义理解强，开源     |
| 多模态嵌入 | CLIP / BridgeTower     | 图文统一向量空间       |
| 语音转文字 | Whisper                | 多语言ASR，开源      |
| 视觉模型  | Qwen-VL / GPT-4V       | 图像内容理解和描述生成    |
| 向量数据库 | Milvus                 | 开源、高性能、支持混合检索  |
| 大模型   | Qwen2.5-72B-Instruct   | 部署于企业内网，保障数据安全 |
| 图数据库  | Neo4j / NebulaGraph    | 处理确定性业务关系      |
| 重排序模型 | bge-reranker-v2-m3     | 轻量级，提升检索精度     |


### 7.3 评估方案

RAG的好坏80%由检索决定。如果检索阶段没找到正确的文档，后面的生成再好也是在错误的基础上编故事。

#### 7.3.1 检索质量指标


| 指标              | 定义                 | 理想标准 | 评估方法                   |
| --------------- | ------------------ | ---- | ---------------------- |
| 召回率 Recall@K    | 前K个结果中包含了多少比例的相关文档 | ≥90% | 构建测试集，每条问题绑定标准答案来源文档片段 |
| 精确率 Precision@K | 前K个结果中有多少是真正相关的    | ≥70% | 同上                     |
| F1分数            | 召回+精确的调和平均值        | ≥0.8 | 综合评估                   |
| MRR             | 第一个相关文档排名的倒数均值     | 越高越好 | 衡量"用户需要翻几页才能找到答案"      |
| NDCG            | 考虑排序位置的加权评分        | 越高越好 | 排序质量的黄金标准              |


常见问题判定：

- Recall低 → chunk切割不合理、Embedding能力弱、缺少关键词检索
- Precision低 → 大量无关片段被召回，干扰大模型，必须加Rerank过滤

#### 7.3.2 生成质量指标


| 指标                        | 定义               | 核心价值                           |
| ------------------------- | ---------------- | ------------------------------ |
| 答案忠实度（Faithfulness）       | 生成答案与检索上下文的事实一致性 | 防幻觉核心指标——答案是否基于检索到的文档，而非模型自行编造 |
| 答案相关度（Answer Relevance）   | 生成答案与用户查询的语义匹配程度 | 确保回答不偏离原始问题                    |
| 上下文相关度（Context Relevance） | 检索到的上下文与用户问题的关联性 | 直接影响生成答案的准确性                   |


**忠实度是最危险的指标**：模型忠实复述了检索到的错误信息，这是最危险也最难被发现的失败模式——答案看起来有理有据，但引用的来源本身就是错的。

#### 7.3.3 系统性能指标


| 指标            | 说明               | 参考标准             |
| ------------- | ---------------- | ---------------- |
| 响应时间（Latency） | 从用户提问到生成答案的全流程耗时 | 问答场景≤3秒，复杂分析≤10秒 |
| 资源利用率         | GPU/CPU占用率、存储消耗  | 决定系统扩展性和成本       |
| 并发处理能力        | 同时支持的用户查询数       | 根据企业规模设定         |


#### 7.3.4 业务效果指标

技术指标达标≠业务有价值。最终要看知识库是否真正改变了业务结果：


| 指标       | 评估方式            | 参考目标          |
| -------- | --------------- | ------------- |
| 新人上手周期缩短 | 入职到独立工作的天数      | 缩短20-30%      |
| 重复提问下降率  | 同一问题被不同人反复询问的频率 | 下降50%+        |
| 知识检索效率   | 员工平均每天搜索信息的时间   | 从2.5小时降至0.5小时 |
| 答案采纳率    | 用户对AI回答的正面反馈比例  | ≥80%          |
| 知识库月活    | 每月使用知识库的员工占比    | ≥60%          |


#### 7.3.5 评估工具


| 工具       | 核心能力                                      | 适用场景        |
| -------- | ----------------------------------------- | ----------- |
| RAGAS    | 4项核心指标（上下文相关性、上下文召回率、答案忠实度、答案相关度），支持自动化评估 | 最主流的RAG评估框架 |
| DeepEval | CI友好的测试框架，支持集成到开发流水线                      | 持续评估和回归测试   |


#### 7.3.6 评估实施建议

1. **构建标准测试集**：整理100-500个典型问答对，每条绑定标准答案来源文档片段
2. **分层评估**：先评估检索（Recall/Precision），再评估生成（Faithfulness/Relevance），最后评估业务效果
3. **对比实验**：不同chunk尺寸、不同Embedding模型、是否开启BM25混合检索、是否开启Rerank——逐一对比
4. **负面样本测试**：模糊提问、专业专有名词提问、多条件复合问题——测试边界场景
5. **定期回归**：每次知识库更新后跑一次评估，防止效果退化

### 7.4 存在问题


| 问题       | 表现                        | 影响                |
| -------- | ------------------------- | ----------------- |
| 没有复利     | 100次问答后知识库和第1次一模一样        | 知识不积累，重复推理浪费算力    |
| 碎片化      | chunk切割导致上下文断裂            | 跨文档综合推理困难         |
| 矛盾不可见    | 两份文档说法矛盾，RAG可能同时召回两个chunk | LLM随机采信，答案不可控     |
| 幻觉放大     | 模型忠实复述检索到的错误信息            | 最危险的失败模式——有理有据地犯错 |
| 数据治理工程量大 | 脏数据问题普遍                   | 上线前最大工作量          |

## 八、范式三：LLM Wiki（编译式知识库）

### 8.1 核心逻辑

"Compile, don't retrieve"——先编译，不检索。这是Karpathy 2026年4月提出的核心洞察。

LLM Wiki的核心逻辑是"摄入时编译"——LLM将原始资料编译成结构化Wiki，查询时检索编译后的高质量知识，而非从原始文档重新检索。

**核心价值**：

- **知识有复利**：编译一次长期复用，每次摄入新资料后Wiki自动更新，知识持续积累
- **跨文档综合能力强**：编译时已做综合和交叉引用，不存在chunk切割导致的上下文断裂
- **矛盾显式化**：编译时标注矛盾，不隐藏冲突，让人类审阅决策

**核心缺陷**：

- **编译成本高**：每次摄入新资料都需要LLM深度阅读+编译更新，Token消耗远超RAG的检索
- **编译偏差**：LLM在编译过程中可能遗漏关键细节、过度概括、引入自己的理解偏差
- **不适合高频变更**：文档频繁变动时，每次变更都要重新编译受影响的Wiki页面
- **不适合普通归档**：如果知识只是"存起来方便查"，不需要跨文档综合和交叉引用，LLM Wiki的编译成本是浪费——RAG更简单更实用
- **溯源困难**：编译后的Wiki是LLM的"二手知识"，追溯到原始文档需要额外的引用机制

### 8.2 技术方案

#### 8.2.1 三层架构

Karpathy在llm-wiki.md中定义了三层架构：

```
┌─────────────────────────────────┐
│         Schema（规则层）          │  告诉LLM如何组织Wiki的配置文档
├─────────────────────────────────┤
│         Wiki（知识层）            │  LLM生成和维护的Markdown文件集合
├─────────────────────────────────┤
│     Raw Sources（原始资料层）     │  不可变的源文档集合
└─────────────────────────────────┘
```

**Raw Sources（原始资料层）**：所有原始文档存放于此，不可变。PDF、论文、会议纪要、网页剪藏——原样保存，只读不改。这是source of truth。

**Wiki（知识层）**：这是LLM的"编译产物"。每篇原始资料被LLM阅读后，编译成结构化的Markdown页面：自动生成摘要、建立反向链接、做概念分类、标注矛盾和冲突、关联相关文章。传统知识管理是"人写机器读"，LLM Wiki是"机器写人审阅"。

**Schema（规则层）**：配置文档，告诉LLM应该怎么组织Wiki——页面模板、分类体系、命名规则、质量标准。Schema是人给LLM的"编辑手册"。

#### 8.2.2 三个核心操作


| 操作             | 作用                                     | 触发时机    |
| -------------- | -------------------------------------- | ------- |
| **Ingest（摄入）** | 导入新文档，LLM阅读后更新Wiki——可能新建页面、更新已有页面、标注矛盾 | 有新资料加入时 |
| **Query（查询）**  | 基于Wiki内容回答问题，而非原始文档                    | 用户提问时   |
| **Lint（检查）**   | 定期健康检查——发现孤立页面、过时信息、矛盾标注未解决、交叉引用断裂     | 定期执行    |


#### 8.2.3 摄入管线：两步思维链

Ingest是LLM Wiki最核心的操作，工程落地时通常拆为两步思维链：

**第一步：理解与定位**

LLM阅读新文档，判断：

- 这篇文档的核心主题是什么？
- Wiki中是否已有相关页面？如果有，应该更新哪些？
- 是否与已有知识存在矛盾或冲突？

**第二步：编译与更新**

LLM执行具体操作：

- **新建页面**：为全新主题创建Markdown文件，包含摘要、关键概念、来源引用
- **更新页面**：将新信息整合进已有页面，标注新增内容
- **矛盾标注**：如果新文档与已有知识冲突，在页面中显式标注矛盾点和两方来源
- **交叉引用**：在相关页面之间建立双向链接

**关键设计原则**：

- **知识只编译一次**——同一份资料不会反复处理
- **增量更新**——新资料进来只更新受影响的部分，不重建整个Wiki
- **矛盾显式化**——不隐藏冲突，而是标注出来让人类审阅决策

#### 8.2.4 查询机制

Karpathy发现了一个反直觉的结论：**基于LLM Wiki的查询，不需要复杂的RAG系统。**

原因：

- Wiki已经是"编译后"的高质量知识——摘要、分类、交叉引用都做好了
- LLM通过自己维护的索引文件和交叉引用，能快速定位相关页面
- 查询时LLM面对的不是零散的文档切片，而是结构化的知识页面——上下文完整、逻辑清晰

这就像查百科全书和翻原始论文的区别：百科词条已经有人帮你总结好了，你不需要再从头读一遍原始文献。

#### 8.2.5 扩展架构：四层分治

在Karpathy原始三层架构基础上，工程落地时可扩展为四层：

```
┌─────────────────────────────────┐
│      Outputs（输出层）            │  高价值答案持久化，可被后续查询直接引用
├─────────────────────────────────┤
│      Wiki（知识层）               │  LLM生成和维护的Markdown文件集合
├─────────────────────────────────┤
│      Raw Sources（原始资料层）    │  不可变的源文档集合
├─────────────────────────────────┤
│      Log（日志层）               │  操作日志，记录每次Ingest/Query/Lint的详细过程
└─────────────────────────────────┘
```

Outputs层存放经过验证的高价值答案（如复杂技术问题的综合解答），可被后续查询直接引用，避免重复推理。Log层记录所有操作过程，支持审计和回溯。

### 8.3 评估方案

LLM Wiki的评估维度与RAG有本质差异——RAG重检索质量，LLM Wiki重编译质量。


| 评估维度  | 方法                              | 说明              |
| ----- | ------------------------------- | --------------- |
| 知识完整性 | Wiki覆盖了Raw Sources中多少核心概念       | 衡量编译的覆盖度        |
| 编译质量  | 人工抽检Wiki页面的准确性和遗漏率              | 核心指标——编译偏差的直接度量 |
| 矛盾检出率 | Wiki中标注的矛盾是否覆盖了实际存在的矛盾          | 衡量LLM发现矛盾的能力    |
| 查询效果  | 基于Wiki的查询准确率 vs 基于原始文档的RAG查询准确率 | 对比两种范式的端到端效果    |
| 维护成本  | 每次Ingest的Token消耗、Lint的检出率       | 衡量运维经济性         |


**编译质量是核心**：建议定期（每月）随机抽取5-10个Wiki页面，人工与原始文档对比，检查遗漏、偏差、过度概括。

### 8.4 存在问题


| 问题       | 表现                          | 严重程度        |
| -------- | --------------------------- | ----------- |
| 编译偏差     | LLM可能遗漏关键细节、过度概括            | 高           |
| 编译成本     | 每次摄入新资料Token消耗远超RAG检索       | 中高          |
| 不适合高频变更  | 文档频繁变动需反复编译                 | 高（特定场景致命）   |
| 不适合普通归档  | 知识只是"存起来方便查"时，编译成本是浪费       | 中（普通笔记归档场景） |
| 溯源困难     | 编译产物是"二手知识"，溯源到原文需额外引用机制    | 高（合规场景致命）   |
| 企业合规挑战   | 金融等行业要求答案可溯源到原文条款           | 致命（金融场景）    |
| 权限管控     | Wiki层LLM全权维护，权限粒度难以做到文档级    | 高           |
| 规模天花板    | 千级文档以上编译成本和一致性维护压力陡增        | 中高          |
| 企业落地尚在早期 | 编译质量管控、多人协作、权限管理等企业刚需缺乏成熟方案 | 中           |


**结论**：LLM Wiki适用于**探索型、研究性、持续更新**的知识领域（研究文献库、技术知识体系、AI进展追踪等个人/小团队场景），这些领域知识需要深度综合、交叉引用、矛盾标注，维护成本是核心痛点。但普通的个人笔记归档——"把笔记存起来方便查"——RAG更简单更实用。金融合规等要求答案可溯源到原文的场景，LLM Wiki不应作为主知识库。

## 九、跨范式公共议题

无论选择哪种范式，企业落地都会遇到四个公共议题：安全合规、知识更新、Agent集成、效果评估。但不同范式的适配差异很大。

### 9.1 安全与合规

**选错范式会怎样**：一家消费金融公司用LLM Wiki做合规知识库。银保监审计时，要求每个AI生成的答案必须能溯源到原始监管文件的具体条款。但LLM Wiki的答案是编译后的"二手知识"——LLM在编译过程中可能对原文做了概括、重组甚至理解偏差。审计员问："这个结论来自哪份文件的哪一条？"知识库答不上来，因为编译产物和原始文档之间没有逐条对应关系。合规审查不通过，项目被叫停。

**数据分级分类**——企业知识库涉及的数据必须按敏感程度分级管理：


| 级别  | 数据类型           | 存储要求      | 访问要求       |
| --- | -------------- | --------- | ---------- |
| 公开  | 已公开的行业报告、产品介绍  | 无特殊要求     | 全员可访问      |
| 内部  | 内部流程文档、培训资料    | 加密存储      | 按部门/角色授权   |
| 机密  | 客户信息、风控模型、经营数据 | 加密存储+审计日志 | 严格授权+审批    |
| 绝密  | 核心算法、战略规划      | 加密存储+隔离网络 | 极少数人+双因素认证 |


**不同范式的合规适配**：


| 合规要求    | RAG              | LLM Wiki            | 裸LLM       |
| ------- | ---------------- | ------------------- | ---------- |
| 答案溯源到原文 | ✅ 天然支持           | ❌ 编译产物是"二手知识"       | ❌ 无法溯源     |
| 权限管控    | ✅ 文档级粒度          | ⚠️ Wiki层LLM全权维护，粒度粗 | ❌ 无权限概念    |
| 审计追溯    | ✅ 原始文档+审计日志      | ⚠️ 需额外机制            | ❌ 无审计能力    |
| 私有化部署   | ✅ 成熟方案           | ⚠️ 可行但工具链不成熟        | ✅ 本地模型即可   |
| 敏感信息脱敏  | ✅ 入库前/生成时/日志三层脱敏 | ⚠️ 编译过程可能泄露         | ❌ 数据进入模型参数 |


**消费金融行业特殊合规要点**：

- **个人信息保护**：《个人信息保护法》要求对客户数据的采集、存储、使用全流程合规，知识库中的客户画像、风控数据必须脱敏
- **数据跨境**：涉及外资股东或海外业务时，数据跨境传输需通过安全评估
- **监管报送**：银保监/金管局要求的数据留存和可追溯性，知识库需支持审计追溯
- **模型可解释性**：AI生成的答案在合规场景下必须可溯源到具体文档和条款

**等保三级要求**：身份鉴别需双因素认证；访问控制策略细化到用户+功能+数据级别；审计日志保留不少于180天且不可篡改；敏感数据须加密存储与传输；系统具备防勒索、防横向渗透能力。

### 9.2 知识更新与版本管理

**选错范式会怎样**：一个研发团队用LLM Wiki管理API文档。API每周迭代一个版本，每次变更都需要LLM重新编译受影响的Wiki页面。编译一次耗时15分钟、消耗数千Token，而API文档每周变更3-5处。一个月下来，编译成本远超RAG的增量索引，且编译延迟导致Wiki内容经常滞后于最新API——工程师查到的还是上周的接口参数。

**增量更新的核心矛盾**：


| 矛盾         | 说明                      | 后果            |
| ---------- | ----------------------- | ------------- |
| 实时性 vs 成本  | 每次变更都重建索引太贵，但延迟更新又怕信息过时 | 要么浪费算力，要么信息滞后 |
| 一致性 vs 可用性 | 更新期间旧数据还在被检索，新旧数据可能矛盾   | 用户可能拿到互相矛盾的答案 |
| 粒度 vs 复杂度  | 文档级更新简单但浪费，切片级更新精准但复杂   | 粒度太粗浪费，太细难维护  |


**不同范式的更新适配**：


| 更新需求  | RAG           | LLM Wiki            |
| ----- | ------------- | ------------------- |
| 文档新增  | 切片+向量化，即时生效   | LLM阅读+编译更新Wiki，延迟较高 |
| 文档修改  | 增量更新（文档级/切片级） | 重新编译受影响的Wiki页面      |
| 文档删除  | 删除向量+索引，即时生效  | 删除相关Wiki内容+更新交叉引用   |
| 大规模变更 | 全量重建或批量增量     | 编译成本高，可能需要重建Wiki    |


**RAG增量更新的技术实现**：

1. **指纹机制**：基于正文、标题、权限、元数据一起计算哈希。只看文件更新时间不可靠——权限变化也可能影响检索结果
2. **先删旧块再插新块**：每个向量块必须带上来源文档ID（doc_id），更新某份文档时，先按doc_id把旧向量全删掉，再灌入新内容。漏删旧块是最常见的坑——会导致旧政策和新政策同时被召回
3. **双缓冲索引切换**：维护两套索引（活跃索引和构建索引），增量更新写入构建索引，完成后原子切换，保证查询一致性
4. **删除文档的同步清理**：文件被下架后，对应向量也必须清掉
5. **定时自动同步**：挂一个每天凌晨跑一次的同步任务，全自动

### 9.3 Agent集成

**选错范式会怎样**：一个客服中心用裸LLM（无知识库）做智能客服。产品政策每天变更，但LLM的训练数据是半年前的。客户问"当前分期手续费率是多少"，LLM自信地报出已过期的费率。客户投诉，监管介入。没有知识库的Agent，等于没有刹车的高速列车——跑得越快，出事越严重。

**知识库作为Agent工具层（MCP协议）**

MCP（Model Context Protocol）已赢得Agent-Tool层的事实标准地位。在Agent架构中，知识库封装为MCP工具，Agent根据任务需求选择调用。

**Agent反馈回写知识库**

Agent从知识库取知识，也得往知识库存知识。反馈闭环分三层：


| 层级          | 时间尺度    | 机制                             |
| ----------- | ------- | ------------------------------ |
| 即时修正层       | 当前对话内   | 用户纠错后，Agent在当前会话中立即修正输出        |
| Few-shot示例库 | 跨会话（中期） | 将纠错信息结构化存入示例库，相似场景自动引用         |
| Prompt模板优化  | 系统级（长期） | 统计高频纠错，转化为规则，定期更新System Prompt |


**受控回写流程**：

```
Agent执行任务 → 发现新经验/纠错记录
        ↓
  证据约束校验（是否有事实依据？）
        ↓
  权限校验（Agent是否有写入权限？）
        ↓
  结构化沉淀（转为标准格式的Learning文档）
        ↓
  人工审批（T3级以下信源需审批）
        ↓
  写入知识库（带作者、证据、版本、审计记录）
```

**反馈信号分类**：


| 信号类型 | 来源                | 质量  | 采集率        |
| ---- | ----------------- | --- | ---------- |
| 显式反馈 | 用户点踩、评分、纠错文本      | 高   | 低（大多数用户沉默） |
| 隐式反馈 | 快速跳过、重复提问、修改后重新提交 | 中   | 高（需从日志挖掘）  |


80%的优化信号在隐式反馈里。只做显式反馈的团队，错过了大部分优化机会。

**知识沉淀的最小单位：Learning**

每次值得保留的经验收敛为一个Learning（结构化Markdown文档），包含：问题描述、解决方案、证据来源、适用条件、创建者、版本号。拒绝长篇叙事，只围绕一个明确解决的工程问题展开。

**单Agent vs 多Agent判断框架**

编排价值公式：

```
编排价值 = 领域隔离收益 − (Token膨胀 + 延迟累积 + N²冲突成本)
```

当编排价值为负时，单Agent + 更多工具就是最优解。

单Agent的三大硬性瓶颈（只有遇到这些瓶颈时才考虑多Agent）：


| 瓶颈        | 表现              | 典型场景         |
| --------- | --------------- | ------------ |
| 上下文窗口容量瓶颈 | 工具描述+任务信息塞不进上下文 | 工具超过10个      |
| Context污染 | 不同职责的信息互相干扰     | 同时处理销售+投诉+库存 |
| 任务可并行     | 子任务之间无依赖        | 同时查3个独立数据源   |



| 任务特征                | 推荐架构                | 理由                 |
| ------------------- | ------------------- | ------------------ |
| 步骤清晰、工具交互简单         | 单Agent + 多工具        | 协调成本为零             |
| 需要多视角审查             | 多Agent Team         | 各Agent独立视角         |
| 子任务可并行              | Subagent模式          | 父子Agent独立context   |
| 任务链长（8步+），每步成功率<95% | 多Agent + Checkpoint | 需分步校验              |
| 顺序推理、单线决策           | 单Agent              | 多Agent反而降低39-70%性能 |


关键数据：Google Research在180种Agent配置横评中发现，单Agent在64%的benchmark上与多Agent持平，多Agent平均只增加2.1个百分点准确率但成本翻倍。Anthropic数据进一步揭示了成本结构：Token膨胀从单Agent的4×到多Agent的15×——多Agent系统中，Agent间通信、上下文传递、协调开销带来的Token消耗远超单Agent。

### 9.4 效果评估体系

**选错范式会怎样**：一个企业用RAG的评估体系（Recall/Precision/Faithfulness）来评估LLM Wiki。结果发现"Faithfulness"指标始终很低——因为LLM Wiki的答案是编译产物，不存在"基于检索上下文生成"的链路，Faithfulness的定义本身就不适用。用错误的尺子量正确的东西，得出的结论是"LLM Wiki效果差"，但真正差的是评估方法。

**不同范式的评估侧重**：


| 评估维度  | RAG侧重                           | LLM Wiki侧重            | 裸LLM侧重 |
| ----- | ------------------------------- | --------------------- | ------ |
| 检索质量  | 核心指标（Recall/Precision/MRR/NDCG） | 不适用（查询基于编译后页面）        | 不适用    |
| 生成质量  | 忠实度（Faithfulness）为核心            | 编译质量为核心               | 幻觉率为核心 |
| 知识完整性 | 覆盖率（文档是否都被索引）                   | 覆盖率（Wiki是否覆盖Raw中核心概念） | 不适用    |
| 系统性能  | 响应时间、并发能力                       | 编译速度、Ingest吞吐         | 响应时间   |
| 业务效果  | 新人上手周期、重复提问下降率                  | 知识复用率、矛盾检出率           | 通用准确率  |

## 十、管理层视角：知识库落地不是技术问题

### 10.1 战略定位

企业知识库的核心定位不是"把文档电子化、分类存好"，而是构建一条让知识高速流向业务现场的高速公路。这条高速公路需要同时满足三个维度：

- **知识获取的即时性**：一线员工遇到问题时，能否在秒级获得精准答案
- **知识更新的敏捷性**：新产生的经验与教训，能否在最短时间内转化为组织可共享的资产
- **知识应用的场景性**：知识支持是否嵌入在业务操作的自然流程中

AI时代知识库的定位升级：传统知识库是"资料馆"，核心能力是分类、搜索和浏览；AI时代的知识库是"企业第二大脑"，核心能力是理解问题、检索依据、生成答案、给出引用，并能接入业务流程。

**市场规模参考**：IDC报告显示，2025年全球企业级知识库市场规模突破420亿美元，中国市场规模达120亿人民币，年复合增长率37%。这不是一个"要不要做"的问题，而是一个"怎么做才对"的问题。

### 10.2 治理机制

**知识管理委员会**：负责知识管理的总体规划和流程运行，以及专家库的管理。

**知识地图与分类体系**：识别行业和战略所需的知识和能力，将知识系统化和结构化；识别哪些是外部知识，哪些是组织内部需要拥有的自有知识；识别哪些知识是空白的。

**四级信源分级体系**：


| 级别  | 类型    | 说明                 | 示例              |
| --- | ----- | ------------------ | --------------- |
| T1  | 权威事实型 | 可独立核验的客观资质，LLM优先采信 | 专利、软著、政府备案、认证证书 |
| T2  | 量化经营型 | 可交叉验证的企业运营数据       | 交付准时率、设备综合效率    |
| T3  | 流程制度型 | 企业内部标准化文件，具备完整溯源链路 | 业务流程、管理制度       |
| T4  | 宣传观点型 | 软性素材，仅作辅助补充，需人工核验  | 品牌文案、行业观点       |


**权限与版本治理**：一份知识只有一个最新有效版本，明确责任人——谁负责更新、谁审核、谁发布。数据归属权、权限边界、标签体系、版本混乱、历史垃圾数据——这些是信息孤岛的核心问题，必须在治理层面先解决。

### 10.3 组织文化

**三阶段推进模型**：


| 阶段  | 目标           | 核心动作                | 关键策略                        |
| --- | ------------ | ------------------- | --------------------------- |
| 启动期 | 全员知晓并初步参与    | AB角机制；各部门搭建基础知识框架   | 一把手工程，自上而下推动；选定1-2个重点部门先行试点 |
| 推进期 | 各部门实际填充内容    | 员工提报内容经审批入库；内容评级+奖励 | 激励+低门槛；优先支持重点部门             |
| 成熟期 | 知识管理成为日常工作习惯 | 停止激励，转为常态化维护        | 用标杆部门带动全员；出台制度文件规范化管理       |


**隐性知识显性化**：企业70%的知识存在于员工个人头脑和电脑中。隐性知识（经验、诀窍、最佳实践）的显性化是知识库建设的核心难点。

### 10.4 不同范式的管理重点差异

选了不同的范式，管理层要管的事情完全不同。这是很多团队忽略的——以为"建知识库"的管理工作是一样的，其实RAG和LLM Wiki的管理挑战根本不在同一个维度上。


| 管理维度     | RAG的管理重点                                   | LLM Wiki的管理重点                          | 融合架构的管理重点                           |
| -------- | ------------------------------------------ | -------------------------------------- | ----------------------------------- |
| **数据质量** | 数据治理是最大工程量——版本去重、过期标记、相似度去重，脏数据直接导致召回噪音    | 编译质量抽检——定期人工对比Wiki页面与原始文档，检查遗漏、偏差、过度概括 | 两层一致性协调——Wiki层的编译结论和RAG层的原始文档之间不能矛盾 |
| **权限管控** | 文档级权限粒度——谁上传、谁审核、谁可见，必须严格                  | Schema维护——人给LLM的"编辑手册"必须准确，否则LLM编译方向跑偏 | 权限隔离——RAG层人主导，Wiki层LLM独占，人机混写是一致性灾难 |
| **知识更新** | 增量更新机制——指纹检测、双缓冲切换、版本回溯                    | 编译节奏控制——多久做一次Ingest、Lint检查频率           | 更新同步——原始文档变更后，RAG层即时生效，Wiki层需触发重新编译 |
| **效果评估** | 检索质量（Recall/Precision）+ 生成质量（Faithfulness） | 编译质量（完整性、准确性）+ 矛盾检出率                   | 双层评估——RAG层查检索质量，Wiki层查编译质量，端到端查融合效果 |
| **组织机制** | 数据治理责任制——谁负责更新、谁审核、谁发布                     | 编译审阅机制——谁抽检Wiki页面、谁修正编译偏差              | 跨层协调机制——谁负责发现和解决两层之间的矛盾             |


**核心差异一句话**：RAG管的是"数据干净不干净"，LLM Wiki管的是"编译靠谱不靠谱"，融合架构管的是"两层一致不一致"。如果管理层用RAG的思路去管LLM Wiki——只关注数据治理，不关注编译质量——知识库一定出问题。

### 10.5 落地节奏

选一个高价值场景打穿，不碰其他部门。正确做法是选择明确ROI的窄场景：研发技术问答、运维故障排查、客服知识辅助、法务合同检索。目标明确：减少重复提问、缩短新人熟悉周期、提升跨团队协作效率。

### 10.6 管理层与技术层交汇检查清单


| 环节      | 管理层必须做的                               | 技术层必须做的                            |
| ------- | ------------------------------------- | ---------------------------------- |
| 启动前     | 高管牵头组建专项小组；明确战略定位和SMART目标；选定1-2个高价值场景 | 评估现有系统现状；确定技术路线；规划架构               |
| 框架搭建    | 建立AB角机制；搭建知识分类体系；定义信源分级标准             | 搭建语义访问中台；建立Connector连接层；设计知识分层存储方案 |
| 内容填充    | 推动隐性知识显性化；设立内容评级和激励机制                 | 实现多模态文档入库管道；建立数据治理自动化机制            |
| 检索优化    | 定义业务场景的检索质量标准；收集用户反馈迭代                | 部署Query改写；实现混合检索+元数据过滤+重排序         |
| 安全合规    | 定义数据分级标准；建立访问审计制度                     | 实现敏感信息脱敏管道；部署私有化方案；配置RBAC+审计日志     |
| 效果评估    | 设定业务效果指标；定期价值评估                       | 构建标准测试集；部署自动化评估；监控检索质量和幻觉率         |
| 知识更新    | 建立知识更新责任制；定义文档生命周期                    | 实现增量更新管道；版本快照与回溯机制                 |
| Agent集成 | 评估业务场景是否需要多步推理；定义Agent行为边界            | 知识库封装为MCP工具；设计工具描述；多Agent并发查询的权限传递 |
| 反馈闭环    | 建立Agent经验沉淀的审批流程                      | 实现三层反馈闭环；Learning结构化沉淀+受控回写        |
| 架构选型    | 评估团队规模和维护能力；避免盲目追求多Agent              | 用编排价值公式判断单Agent vs 多Agent          |
| 持续优化    | 建立评估-反馈-优化闭环；跟踪AI技术演进                 | 迭代Embedding和Rerank模型；扩展知识图谱覆盖范围    |

## 十二、关键风险与常见失败模式

1. **一上来做全公司知识库**：范围过大难以落地，应选一个高价值场景打穿
2. **只关注技术选型，忽视治理机制**：信息孤岛70%是组织问题
3. **强行集中迁移数据**：项目必死，应采用语义访问中台思路
4. **把所有文档塞进向量库**：导致召回乱、查询慢、答案不可信，应分层存储
5. **知识库建成即废弃**：缺乏持续运营机制，需要评估-反馈-优化闭环
6. **忽视隐性知识**：70%知识在员工头脑中，不显性化就无法沉淀
7. **忽视多模态内容**：35%+的企业知识以图像/表格形式存在，纯文本RAG对近半内容视而不见
8. **跳过Query改写直接检索**：口语化问题与专业文档的语义鸿沟导致召回失败
9. **只做向量检索不做重排序**：Bi-Encoder精度有限，Cross-Encoder重排可将准确率从62%提升至87%
10. **没有效果评估体系**：建完了不知道好不好，用起来不敢放心
11. **忽视安全合规**：金融行业知识库涉及客户数据，不满足合规要求可能导致罚款甚至业务关停
12. **只做全量重建不做增量更新**：知识库越用越脏，旧答案和新答案同时被召回
13. **Agent数量越多越好**：顺序推理任务上多Agent反而降低39-70%性能，架构-任务对齐才是关键
14. **Agent只取不存**：没有反馈回写的知识库永远是静态的，Agent的纠错经验不沉淀
15. **Agent随意写知识库**：写入不可审计，检索越强污染传播越快
16. **用LLM Wiki替代RAG做合规场景**：编译后的"二手知识"无法满足溯源到原文的合规要求
17. **人机混写Wiki页面**：人类直接编辑Wiki页面会导致与LLM编译产物的一致性冲突，Wiki层应LLM独占
