### **🧠 什么是递归自我改进（RSI），和 Harness 有什么关系？**

RSI 是 AI 用自身智能**改进自身智能机制**的反馈循环，harness 是近期最现实的落地路径。
- **RSI 起源**：I. J. Good 1965 年提出「超智能机器」概念，Yudkowsky 2008 年正式命名 **recursive self-improvement**。
- **现代 RSI 两种形式**：
  - 直接改写模型自身权重
  - 改进**训练流水线 + 部署系统** → 产出更强的下一代模型
- **Harness 定义**：包裹基础模型的系统，负责编排执行、规划思考、调用工具、感知上下文、存储产物、评估结果。
  说白了，harness 就是 AI 的「操作系统 + 工具箱 + 工作流管理器」，不是模型本身，但直接决定模型能发挥多大能力。
- **本文范围**：只讲 harness 工程如何贡献于 RSI，不涉及自博弈、合成数据、测试时训练等其他 RSI 方向。

### **🏗️ Harness 工程和早期 Agent 框架有什么不一样？**

Harness 工程**更接近软件系统设计**，不止是提示词模板。
- **早期 Agent 框架**：Agent = LLM + 记忆 + 工具 + 规划 + 行动
- **Harness 新增内容**：工作流设计（循环工程）、评估、权限控制、持久化状态管理
- **设计原则**：刻意保持简单通用 → 利用模型预训练中的软件工程知识 → 未来配置、工具接口等协议可能**行业标准化**
- **类比**：Harness 之于模型 = 操作系统之于硬件 → 封装复杂逻辑，对外保持简洁接口

### **🔄 Harness 有哪两个核心设计模式？**

两个基础模式分别解决**自动化流程**和**长期记忆**问题。

#### 模式 1：工作流自动化

**核心 = 目标导向的闭环迭代**，直到目标达成。
- **经典循环**：计划 → 执行 → 观察/测试 → 改进 → 再执行
- **代表案例**：Karpathy 的 autoresearch 仓库
- **关键特征**：模型分析自身轨迹和失败案例 → 通过「Agent 运行时」迭代，而非静态提示词
- **主动交互**：过程中可主动向用户询问任务规格或执行偏好

#### 模式 2：文件系统作为持久记忆

**核心 = 状态不放在上下文里，存在文件里**。
- **为什么需要**：长周期任务产生的实验日志、代码 diff、论文摘要、错误轨迹等，远超模型训练时的上下文窗口
- **基础能力**：LLM 通过 bash 命令读写编辑文件系统 → 能力随基础模型提升自然增强
- **并行子 Agent**：
  - 主 Agent 可生成多个子 Agent 并行执行（搜索多假设、并发跑实验、委派子任务）
  - 父 Agent 需进程管理器：启动任务、查看日志、取消失败运行、合并结果
- **设计关键**：并行性要**显式、可检查** → 子 Agent 输出存为文件/日志/状态记录 → 中断后可恢复，可回溯推理

### **💻 主流编码 Agent 的 Harness 长什么样？**

主流编码 Agent 接口已**趋于稳定**，核心是「工具集 + 循环」。
- **代表产品**：Claude Code、Codex、OpenCode、Cursor 类 Agent
- **工具分类**：

| 工具组 | 核心能力 |
| :--- | :--- |
| 文件系统 | glob、grep、read、write、edit、apply_patch 等 |
| Shell 执行 | bash、PowerShell |
| IO | lsp、git_status、git_diff、git_commit |
| 外部上下文 | MCP 工具、Skills |
| 网络搜索 | web_search、web_fetch、浏览器工具 |
| 产物 | 读文档/图片、生成 HTML/图片 |
| 后台进程 | CronCreate、CronDelete、CronList |
| Agent 委派 | spawn_agent、resume_agent、wait_agent 等 |

### **⚖️ Harness 层和核心智能，哪个更重要？**

近期 RSI **不会从模型直接改权重开始**，harness 是切入口，最终两者互相促进。
- **近期路径预测**：
  1. Harness 工程向**元方法论**演进 → 优化「获得更好答案的机制」，而非只优化答案本身 → 启发式规则减少，通用机制增多
  2. 成熟的 harness 支撑自动研究 → 推动模型自我改进 → 更强的模型防止 harness 过度工程化，保持系统可持续
- **长期趋势**：很多 harness 改进会**内化**到核心模型行为中，但外部上下文和工具接口仍会保留
  - 类比提示工程：指令微调 + 模型推理能力提升后，手动提示技巧重要性下降，但「指定目标、约束、上下文、评估」的需求从未消失

### **📝 Harness 优化的对象是怎么一步步升级的？**

优化对象从简单到复杂，大致经历 **5 个层级**。
- **演进路径**：指令提示词 → 结构化上下文 → 工作流 → harness 代码 → 优化器代码
- **规律**：模型越智能，越能优化更复杂的目标，方法也越通用

### **🔧 上下文工程方向有哪些代表性研究？**

上下文工程解决**长周期任务中信息爆炸**的问题，从手工规则走向元优化。

#### ACE（Agentic Context Engineering，2025）

把上下文当作**可演化的手册**，而非越来越长的提示词。
- **三大组件**：
  - Generator：参考要点生成任务轨迹
  - Reflector：从成败轨迹中提炼洞察
  - Curator：用增量条目更新结构化上下文
- **关键设计**：Curator 不重写整段提示词 → 输出带标识符的结构化要点 → 确定性逻辑合并到上下文日志 → 定期去重精炼
- **局限**：更新规则和整体工作流仍是手工设计

#### MCE（Meta Context Engineering，2026）

把「管理上下文的机制」和「上下文内容」**分离**，机制层面也做进化。
- **双层优化**：
  - 内层：给定技能 s，在训练集上找最优上下文
  - 外层：在验证集上找最优技能
- **技能组成**：静态组件（提示词、知识库、代码库）+ 动态算子（搜索、选择、过滤、格式化）
- **进化方式**：元级 Agent 对历史技能做**交叉（crossover）**生成新技能 → 基础级上下文工程师执行技能、从反馈中学习
- **实现**：上下文函数实例化为目录下的文件集合，元级和基础级优化都在编码 Agent 环境中用标准工具集执行

#### Meta-Harness（2026）

优化对象再深一层：**优化 harness 本身的代码**，即「harness 的 harness」。
- **核心机制**：提议者本身是编码 Agent → 生成多个 harness 候选 → 只保留帕累托前沿上的合格方案
- **设计特点**：
  - 全部执行历史通过文件系统访问 → 用 grep/cat 读取，不塞进单个提示词
  - 每个候选 harness 是文件系统中的字典，含源码、得分、运行轨迹、状态更新
  - 循环迭代生成新 harness，只保留合格的
- **结论**：一旦 harness 设计成为可执行搜索空间，强编码 Agent 就能探索人类工程师的同款设计空间

### **📋 工作流设计方向有哪些研究？**

工作流从**专家手工设计**走向**自动搜索优化**。

#### 手工设计的代表
- **AI Scientist（2026，Nature）**：完整流水线 = 提出研究想法 → 写代码 → 跑实验 → 分析结果 → 写论文 → 同行评审
- **ScientistOne（2026）**：核心约束是**可验证性** → 每个声明（引用、数值、方法、结论）必须有证据来源，经证据链检查审计
- **Autodata（2026）**：Agentic 数据科学家 → 生成难度「刚刚好」的合成数据（强求解器能做、弱求解器做不了）
  - 角色：挑战者（出题）+ 弱求解器 + 强求解器 + 验证者/裁判
  - 局限：只微调弱求解器，不迭代改进强模型 → RSI 味道较弱，更像间接蒸馏

#### 自动搜索的代表
- **ADAS（Automated Design of Agentic Systems，2025）**：
  - 把 Agent 设计本身定义为优化问题 → 元 Agent 搜索新的工作流设计
  - 流程：初始化简单 Agent 存档 → 元 Agent 受存档启发编写新 Agent（代码形式）→ 两次自精炼检查新颖性 → 评估后成功者加入存档 → 循环
- **AFlow（2025）**：
  - 把 Agent 工作流表示为**图**（节点=LLM 动作，边=代码逻辑）
  - 用 **MCTS（蒙特卡洛树搜索）** 优化工作流
  - 实验：在 QA、代码、数学任务上，效果优于手工设计工作流和 ADAS

### **🔄 自我改进的 Harness 有哪些进展？**

从优化单个组件走向**优化整个 harness 代码库**，代码是通用优化语言。

#### STOP（Self-Taught Optimizer，2023）

早期递归脚手架改进的代表，目标是**改进「改进器」本身**。
- **机制**：种子改进器 I₀ 接收问题+效用函数+黑盒模型 → 返回改进的解
- **递归更新**：用元效用（下游任务平均效用）衡量改进器性能 → Iₜ = Iₜ₋₁(元效用, Iₜ₋₁; M)
- **发现的策略**：遗传算法、分部分改进、多臂老虎机提示、模拟退火、温度调节、束搜索/树搜索
- **关键警示**：
  - 用 GPT-4 时，迭代中平均下游性能持续提升
  - 用 GPT-3.5、Mixtral 等弱模型时，性能下降
  - 结论：**递归结构本身不够，基础模型必须足够强才能改进机制**

#### Lin et al. (2026) 的能力拆解

把 harness 进化能力拆成**两个独立维度**，结论反常识。
- **两个维度**：
  - Harness-updating：产出有用 harness 编辑的能力
  - Harness-benefit：利用更新后的 harness 提升任务表现的能力
- **实验发现**：
  - 从 Qwen3.5-9B 到 Claude Opus 4.6，不同大小模型的 **harness 更新能力相近**
  - Harness 收益能力**非单调**，中等模型受益最多
- **解读**：要用好 harness，模型需要正确及时调用技能/工具、擅长长程指令跟随

#### Self-Harness（2026）

通过「**弱点挖掘 → 提议 → 验证**」循环自我改进 harness。
- **三阶段循环**：
  1. 弱点挖掘：把失败聚类为**基于验证器的失败模式** → 记录丰富信息（终端原因、Agent 行为因果状态、抽象机制）→ 找根因
  2. Harness 提议：基于失败模式提出**有界的** harness 编辑 → 优先解决可复现、非任务特定、可通过小改动修复的错误 → 候选要多样
  3. 提议验证：在 held-in（测弱点是否解决）和 held-out（测是否引入新问题）上做回归测试 → 两边都无回归才接受 → 合并成新 harness
- **实验**：在 Terminal-Bench-2 上，MiniMax M2.5、Qwen3.5-35B-A3B、GLM-5 都能学到模型特定的 harness 指令，提升 held-out 通过率
- **安全担忧**：如果程序能编辑操作系统 → 抽象边界被打破 → 可编辑表面、权限控制、安全层必须在循环之外

#### AHE（Agentic Harness Engineering，2026）

核心瓶颈是**可观测性**，三大支柱支撑闭环进化。
- **组件可观测性**：每个可编辑 harness 组件都在文件系统中有表示 → 动作空间明确可追踪
  - Harness 含 7 组件：系统提示、工具描述、工具实现、中间件、技能、子 Agent 配置、长期记忆
  - 每个失败模式映射到一个组件 → 编辑更精准
- **经验可观测性**：把大量原始轨迹分析总结为**分层的证据和失败模式**
  - Agent debugger 分析每个轨迹文件 → 生成单任务根因报告
  - 聚合为基准概览 → 需要时可查原始轨迹 → 更省 token
- **决策可观测性**：每个编辑都附带下一轮预测 → 可验证
  - 编辑只作用于 harness 工作区 → runs 目录、追踪器、验证器、LLM 配置只读 → 防止奖励黑客（如禁用验证器、换模型、加推理预算）
  - 编辑是证据驱动的，含清单条目：失败证据名、推断根因、目标修复、预期影响（修复+回归风险）
- **实验**：Terminal-Bench-2 上优于人工设计 harness（OpenCode、Terminus-2、Codex），Hard 级别除外；冻结后可迁移到 SWE-bench-verified → 进化出的是通用工程经验，不是基准过拟合

### **🧬 进化搜索方向有哪些工作？**

进化搜索适合**搜索空间大、梯度难算但易评估**的问题，harness 搜索很匹配。

#### 提示词层面
- **Promptbreeder（2023）**：通过丰富的变异操作优化任务提示词 → 连「变异提示词」本身也一起进化
- **GEPA（2025）**：反思式提示 + 进化搜索 → 用自然语言反思试错轨迹来提议提示词更新

#### 程序/代码层面
- **AlphaEvolve（2025）**：编码 Agent 进化搜索系统 → 冻结 LLM 生成 diff 改进候选程序 → 评估后保留成功者
  - 关键设计：代码改进区域用 `# EVOLVE-BLOCK-START/END` 显式标记；元提示词也共同进化
- **后续变体**：
  - ThetaEvolve（2025）：进化搜索 + RL + 上下文学习
  - DemoEvolve（2026）：加入人类专家演示作为参考经验
  - ShinkaEvolve（2025）：三个新组件提升采样效率 → 父采样平衡性能排名和后代数量 + 代码新颖性拒绝采样 + 元草稿本识别成功模式

#### Harness 层面
- **Darwin Gödel Machine（DGM，2025）**：明确目标是进化**可编辑的 harness 代码仓库** → Agent 可修改自身 harness
  - 流程：初始一个编码 Agent → 按性能正比、后代数反比选父代 → 父代检查自身评估日志 → 改进自身 harness 代码 → 评估后高性能者加入种群 → 循环
  - 实验：Claude 3.5 Sonnet 为底座，SWE-bench Verified 从 20% → 50%，Polyglot 从 14.2% → 30.7%
- **Hyperagents（2026）**：引入元 Agent 控制如何修改现有任务 Agent 以创建新 Agent
- **适用场景**：候选可自动评估、适应度易量化的领域（矩阵乘法、GPU 核优化、算法竞赛、数据中心调度）
- **不适用场景**：评估慢、模糊、主要靠启发式的领域

### **⚖️ 有没有同时优化 Harness 和模型权重的尝试？**

有早期探索，但**证据还不充分**。
- **SIA（2026）**：同一优化循环中同时更新 harness 和模型参数
  - 三组件：元 Agent（提议初始 harness）+ 任务特定 Agent（执行任务）+ 反馈 Agent（决定更新 harness 还是模型权重）
  - 局限：任务特定 Agent 远弱于元/反馈 Agent（gpt-oss-120b vs Claude Sonnet 4.6），基线太弱 → 结果难解读
- **Continual Harness（2026）**：长周期游戏场景 → harness 更新 + 蒸馏强教师模型标签来学习策略模型
- **开放挑战**：训练稳定性、古德哈特定律（优化指标偏离真实目标）

### **🚧 迈向完全 RSI 还有哪些核心挑战？**

共 **7 大瓶颈**，很多和评估、安全、长期价值相关。
1. **弱且模糊的评估器**
   - 很多研究主张和现实任务没有快速精确的验证器
   - 研究品味、新颖性、长期科学价值很难衡量
   - 当前自改进循环只在**评估指标可测、客观**的任务上效果好

2. **上下文和记忆生命周期**
   - Agent 越自主，记忆增长越快
   - Harness 需要管理上下文和记忆，弥补长上下文生成的局限
   - 类比人类终身记忆 → 上下文工程应成为智能的核心部分，而非停留在软件系统层

3. **负面结果**
   - 人类研究偏向发表成功结果 → 文献有成功偏差
   - LLM 可能不擅长决定何时放弃假设、报告负面结果、承认失败
   - 研究 harness 应该让失败尝试易于保存 → 从失败中学习是缩小搜索空间的最好方式

4. **多样性崩溃**
   - 进化和 RL 循环倾向于利用已知高回报模式
   - 需要机制防止种群坍缩为同一方案的变体
   - 开放式研究中尤其关键 → 最好的路径初期可能在当前评估器下表现更差

5. **奖励黑客**
   - 自改进循环会优化给定的任何信号
   - 单元测试奖励 → 过拟合测试；裁判模型奖励 → 学奖励黑客技巧；基准分数奖励 → 利用基准伪影
   - 对策：评估器和权限控制放在进化循环之外 + 留出测试 + 轨迹审计 + 关键决策点人工审核

6. **长期成功**
   - 当前优化目标太短视 → 能完成手头任务，但不一定保护代码库长期健康
   - 沙盒式训练很少捕捉可维护性、所有权边界、迁移成本、向后兼容性、未来调试负担

7. **人类的角色**
   - 人类应该向上移动到技术栈更高层，而非被移出循环
   - 在正确的时间、正确的抽象层级提供监督
   - 系统设计要考虑何时、如何设置人工接触点

### **📊 附录：有哪些相关基准测试？**
- **PaperBench（2025）**：复现 20 篇 ICML 2024 Spotlight/Oral 论文 → 8316 个评分项 → Claude 3.5 Sonnet ~21%，未超过 ML 博士
- **CORE-Bench（2024）**：90 篇论文的 270 个复现任务 → 跨 CS、社科、医学 → GPT-4o 最难任务仅 21% 准确率
- **ScienceAgentBench（2025）**：44 篇论文的 102 个任务 → 数学、化学、生物、地理四学科
- **RE-Bench（2025）**：7 个开放式 ML 研究工程环境 → 人类专家 8 小时尝试 82% 非零分、24% 达参考方案 → AI 2 小时预算得分是人类 4 倍，但 8/32 小时人类反超
- **MLE-bench（2024）**：75 个 Kaggle ML 工程竞赛 → o1-preview + AIDE 16.9% 竞赛达铜牌水平
- **KernelBench（2025）**：250 个 PyTorch GPU 核任务 → 指标 fast_p = 正确且快于基线的比例
