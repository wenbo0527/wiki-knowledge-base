### 🏢 供应商付款卡壳，问题出在哪？

**流程全绿但事实错误**，Agent 走完了流程，却把品牌和主体混为一谈。
- **表面现象**：准入面板全绿，材料、合规、信安、合同审批全部通过，付款时才发现品牌、签约主体、收款主体不一致。
- **根本原因**：系统把**品牌名和法定主体合成了同一个实体**，后续 Agent 直接复用了这条错误关系。
- **核心矛盾**：Agent Loop 只能证明任务走完了，Graph Engineering 还要保证多 Agent 交接的**事实可信**。

### 📊 为什么要分「执行图」和「事实图」两张图？

两张图管的是**完全不同的两件事**，边的含义和出错后果都不一样。

| 维度 | 执行图 | 事实图（知识图谱） |
| :--- | :--- | :--- |
| 节点内容 | 工作任务（材料收集、合规检查等） | 实体（品牌、公司、账户、合同） |
| 边的含义 | 依赖、分支、重试、状态变化 | 关系语义、来源、有效时间、版本 |
| 核心问题 | 任务谁先做、谁后做、失败回哪 | 关系由什么证据支持、有效期多久 |
| 出错后果 | 流程卡住或重复执行 | 流程一路绿灯，最后得到错误报告 |
- **执行图本质**：Agent Loop 就是一张**有向循环图**，生产环境天然有重试、审批、外部事件，不必硬凑 DAG（有向无环图）。
- **事实图本质**：记录实体间的关系及证据，例如「品牌 A 的法定主体是公司 B」「公司 B 使用账户 C 收款」。
- **两者关系**：执行结果可以引用事实版本，但**执行状态和事实关系不能混存**。

### 🧠 「共享记忆」里其实装了哪三类东西？

共享记忆是个笼统说法，实际要拆成**运行、事实、证据**三类状态，保存方式和负责人都不同。

| 状态类型 | 回答的问题 | 典型内容 | 管理方 |
| :--- | :--- | :--- | :--- |
| 运行状态 | 这次任务到哪了 | run_id、node_id、attempt、checkpoint、节点产物 | 编排器、运行状态库 |
| 事实状态 | 当前能相信什么 | 实体、关系、来源、有效时间、置信度 | 事实服务 |
| 环境与证据状态 | 当时凭什么判断 | commit、沙箱快照、测试结果、审批记录 | 运行环境、审计系统 |
- **常见误区**：
  - 拿 checkpoint 当长期知识 → 中间结论过期后仍被复用。
  - 拿知识图谱代替运行状态 → 回答不了工具是否执行成功、恢复时是否重复写入。
- **上下文边界**：即使有十万条事实的图谱，模型每轮也只能读一小部分，仍需围绕当前任务选「最小充分工作集」。

### 🌰 出行、排障、依赖升级，错法都一样？

不同场景的**状态混淆问题本质相同**，只是表现形式不同。
- **家庭出行场景**：
  - 日期确认、票价判断、支付重试 = 执行路径。
  - 证件有效期 = 事实状态。
  - 证件过期仍订票 = 事实未更新；两人同时重试订两间房 = 流程未做幂等。
- **线上故障排障**：
  - 并行查指标、日志、发布，决定限流/回滚 = 执行路径。
  - 服务归属团队、依赖的数据库/队列 = 服务事实。
  - 当前版本、查询时间窗、当时配置 = 环境快照。
- **研发依赖升级**：
  - GitHub Actions 的 `jobs..needs` 声明前置依赖 = 管任务顺序。
  - 包依赖图、函数调用图 = 管代码关系。
  - 交接时不带文件位置和 commit → 换分支结论就不成立。

### 📝 Agent 抽出来的信息为什么不能直接当事实？

Agent 输出的只是**候选主张**，必须经过校验才能成为可复用的规范事实。
- **核心原则**：离事实越近，失败代价越高，越不能只靠 Prompt 兜底。
- **信息转化链路**：
  `证据（原文、快照、哈希） → 候选主张 → 实体消解与校验 → 规范事实 → 按版本查询`
- **候选主张关键字段**：
  - `observed_at`：系统看到材料的时间 ≠ `valid_from`：关系开始成立的时间。
  - `source_span`：保留原文片段，避免争议时找不到依据。
  - `subject_mention` / `object_mention`：保留材料原始名称，实体合并后仍可核对。
  - `status`：标记为候选，等待核验。
  - `producer_run_id`：指向产生主张的执行现场。
  - `schema_version` / `predicate`：用受控词表统一关系语义，避免歧义。
- **校验不通过**：转人工复核，补证据或纠正实体后修订重提。
- **事实失效/错误**：走撤回流程，标记旧报告、重算、复核，通知使用方。

### 🏗️ 最小 Graph Engineering 架构怎么搭？

先分开**执行域和事实域**，用四个接口连接，不用一开始就上图数据库。
- **执行域**：编排器调度 Agent 工作节点，运行状态库保存 run、attempt、checkpoint，负责恢复与重放。
- **事实域**：事实服务管理候选主张、规范实体，PostgreSQL 存 claims/entities/relations，证据存储存原文/快照/哈希。
- **四个核心接口**：
  - `submit_claim()`：工作节点提交发现。
  - `query_facts(entity_id, as_of, evidence_required)`：执行图查询事实。
  - `publish_fact()`：规则/人工复核后发布。
  - `retract_fact()`：撤回失效事实。
- **起步四件要事**：
  - **时间和版本**：已发布事实不能静默覆盖，修订生成新版本，旧版本保留有效区间。
  - **幂等**：同一来源重放时，用幂等键挡住重复主张。
  - **权限**：遍历时就校验租户、关系类型、字段权限，不能先取全图再过滤。
  - **撤回**：事实失效发 `fact.retracted` 事件，执行系统标记旧报告/重算/转人工。

### ⚠️ 图数据库有什么坑？

图不会帮你忘掉错误，**存下来不等于可靠**。
- **实体消解问题**：
  - 未匹配名称可能直接从图里消失 → 需为未匹配实体保留单元素分组。
  - 合并过头（如具体任务并入宽泛项目）→ 图变整齐但具体事实丢失。
- **评测误区**：只比较实体端点、不核对谓词语义 → 关系召回率只是上界，不能代表关系抽得准。
- **生产差距**：Anthropic Knowledge Graph Cookbook 用 `client.messages.parse()` + Pydantic 抽取、Claude 消解、NetworkX `MultiDiGraph` 存储，适合验证想法，离生产还差分块消解、增量更新、持久化、权限、冲突处理。

### 🔍 有了图谱，RAG 还要留着吗？

**两者是搭档**，适用场景不同，搭配使用效果最好。
- **RAG 擅长**：单文档内找具体条款（如「这份合同的退款期限是多少」），路径短、原文完整，成本更低。
- **图谱擅长**：跨多份材料的多跳关系查询（如「哪些供应商与最近三次事故有关，母公司是否相同」）。
- **组合方式**：向量检索找原文，图遍历找关系，模型结合两边证据生成回答。
- **值得上图谱的四个信号**：
  1. 同一实体在不同文档有多个名称。
  2. 回答经常需要跨两跳以上关系。
  3. 关系要长期积累，保留来源和有效时间。
  4. 多个 Agent 重复生产、校验、消费同一批事实。

### 🚀 从零开始怎么试？

先拿一个**故意会出错的小流程**跑通边界，再考虑扩大规模。
- **试跑范围（以供应商准入为例）**：
  1. 执行图只覆盖一个工作流。
  2. 事实层先支持候选主张、规范实体、来源、状态，不做自动覆盖。
  3. 从脱敏历史记录选 **20–50 个真实问题** 做小型评测集。
  4. 每次回答带回引用的事实版本与原文片段。
  5. 人为制造 4 种故障：节点中断、重复写入、实体误合并、事实撤回，验证报告能否重放、标记过期、进入复核。
- **验收三件事**：**版本可查，证据可审，失败可退**。
- **先做哪张图的判断**：
  - 流程稳定，麻烦在并行/审批/重试/恢复 → 先做执行图。
  - 流程简单，麻烦在跨文档对齐/多跳查询/来源追踪 → 先做知识图谱。
  - 开放研究任务难固定路径 → 未必适合硬编码成图，Agent Harness 可能更自然。

### 💡 关键洞察

Graph Engineering 的核心不是用不用图数据库，而是**把藏在提示词、对话历史、临时脚本里的关系拿出来，给它明确的语义、写权限和生命周期**。任务走到哪能检查，事实从哪来能追溯，事实错了能沿着版本和引用找到受影响的报告——这些跑通了，存储结构反倒是后面的选择。
