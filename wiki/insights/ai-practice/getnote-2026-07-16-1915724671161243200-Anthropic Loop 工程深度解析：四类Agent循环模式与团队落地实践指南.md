### 🏆 核心背景与核心理念

2026年6月30日，Claude Code团队在《Getting started with loops》中给出了Agent Loop的朴素定义：**Agent重复执行一轮轮工作，直到满足停止条件**。
本文的核心洞察并非“多跑几轮不难”，而是**难的是留下足够证据，让接手的人能快速复核，也清楚出问题怎么退**。这一理念打破了将Loop视为“从低到高的自动化成熟度阶梯”的常见误区，强调四类Loop是可按需组合的不同工作方式，选择的核心依据是团队愿意交出多少控制权、错误能扩散多远。

### 📊 四类Loop模式全维度对比

四类Loop的核心差异由“谁推动下一轮执行”决定，对应Claude Code的不同能力，具体参数如下：

| Loop 类型 | 触发方式 | 停止条件 | Claude Code对应能力 | 核心控制权特征 |
| :--- | :--- | :--- | :--- | :--- |
| **回合式 Turn-based** | 用户主动输入提示启动一轮 | Claude认为任务完成、或需要更多上下文时自动停下 | 普通提示 + Skills 自检 | 完全由人主导下一轮的启动 |
| **目标式 Goal-based** | 用户手动输入目标启动 | 目标达成、或到达预设最大轮次时停下 | `/goal` 指令 | 人定义最终目标，Agent自主推进轮次直到满足条件 |
| **定时式 Time-based** | 按用户约定的固定间隔自动运行 | 人手动取消、或PR合并/队列清空等外部工作完成时停下 | `/loop`、`/schedule` 指令 | 按时间节奏自动触发，不受单次任务完成限制 |
| **主动式 Proactive** | 由事件或时间自动触发，无需人实时在场 | 单个任务达成目标后退出，持续运行的Routine直到人主动关闭 | `/schedule` + `/goal` + Skills + Dynamic Workflows + Auto mode | 全链路无人值守，是多能力组合的复杂模式 |

#### 关键细节区分
- `/loop` 运行在本地设备，电脑关机后循环直接终止；需要云端持续运行时，可使用处于research preview阶段的`/schedule`创建Routine。
- 主动式Loop并非单一指令，而是多组件协同的结果：定时/事件模块发现工作、`/goal`定义单次任务验收标准、Skills固化验证方法、Dynamic Workflows组织多Agent协作、Auto mode跳过无人值守时的权限确认弹窗。

### 📝 长任务Loop的可追溯设计方案

当Loop运行数小时甚至跨多次定时唤醒后，聊天记录不再是可靠的工作账本，作者提出了一套标准化的现场信息短链：
`目标 → 当前状态 → 已做动作 → 证据 → 权限边界 → 待人决策`

这套信息链可以无缝融入现有团队流程，无需搭建额外平台：
1.  **会话内Agent工作回路**：读取当前状态 → 改代码/跑检查 → 整理证据 → 判断继续条件是否成立
2.  **会话外团队工作现场**：状态同步到Issue/状态文件、改动落盘到Git/Worktree、验证结果写入CI/测试日志、交接物输出为PR/Runbook
3.  **人工接手环节**：工程师按“状态→证据→Diff→未决项”的顺序复核，最终做出继续/合并/停止的决策

以依赖升级任务为例，标准化的任务卡可直接复用以下字段，大幅降低复核成本：
```
SPEC：只升级依赖X；公共API、认证和数据库行为不变；最多5轮
STATE：当前版本、候选版本、已尝试路径、失败原因和下一步
EVIDENCE：测试命令与退出码、依赖树Diff、发布说明中的风险项
IMPACT：可能受影响的服务、用户路径和运行环境
PERMISSION：可写独立分支和草稿PR；不自动合并，不改生产配置
HANDOFF：为什么停止，哪些风险未覆盖，需要谁做什么决定
```
### ⚠️ 常见认知误区澄清
1.  **CI全绿 ≠ 任务完成**：CI绿色状态仅代表已配置的检查通过，Claude Routine的绿色运行标识仅说明会话启动退出时无基础设施错误，不代表业务任务执行成功。`/goal`的内置评估器存在边界：它不会自行运行命令、读取文件，仅能识别Claude已写入对话记录的证据。
2.  **合格的复核证据包必须覆盖4个维度**：
    - 所有单元测试、集成测试、构建和静态检查的执行记录与退出码
    - 服务启动、认证/数据库/关键调用链路的最小烟雾测试结果
    - 公共API、依赖树、默认配置、发布说明中的重点Diff清单
    - 未覆盖的环境/路径、以及明确的上线回退方案

### 🛡️ 权限放权的风险控制原则

Loop自动化程度越高，人需要保留的核心控制权越多，放权决策的核心标尺是**错误能扩散多远、出问题后能否快速恢复**：
- 分层隔离防护：Worktree隔离文件改动、Sandbox限制进程访问范围、权限Hook管控可执行动作、Checkpoint支持本地编辑撤回，数据库/外部系统/远端写入需单独配置回滚机制。
- 风险路径规避：不可信外部输入、敏感数据读取、对外写操作三类能力，禁止在同一会话中同时开放，可通过拆分到隔离环境、增加人工闸门切断风险链路。
- 渐进式放权节奏：先开放只读运行观察判断稳定性，稳定后再开放独立分支与草稿PR权限，自动合并、生产写入、客户外发这类高风险动作建议长期保留在人工环节。

### 🚀 第一条Loop的落地试跑流程

新手落地Loop工程无需从复杂场景切入，优先选择文档漂移、CI失败分类、依赖升级预检查、发版前核验这类低风险任务，遵循5步稳妥推进：
1.  **复盘真实任务**：抽取近期同类型人工PR，提取Reviewer反复执行的稳定检查动作
2.  **写入Skill/脚本**：将确定性检查转化为具体命令、退出码、阻塞记录规则，避免“仔细检查兼容性”这类模糊描述
3.  **影子运行**：Agent同步执行任务但不产出正式结果，人工流程保持不变，重点观察有效发现率、误报率、漏报率和人工接手耗时
4.  **独立Worktree验证**：确认结果稳定后，允许Agent在隔离工作区生成Diff和草稿PR，明确所有失败场景和回滚路径
5.  **有限自动化**：确认风险可控后，逐步开放`/goal`、定时触发、有界写入能力，合并、外发、生产写入环节保留人工闸门

### 💡 关键洞察

成熟的Loop本质是**一份可运行的交接协议**：Agent在可自主推进时自动执行，一旦证据不足、超出预设权限边界，立刻将清晰的上下文交还给人。最终的验收标准非常朴素：第二天接手的工程师能在几分钟内判断任务走向，这条Loop才算真正融入团队流程，而非把人工复核工作从夜里的Agent转移到早上的工程师身上。
