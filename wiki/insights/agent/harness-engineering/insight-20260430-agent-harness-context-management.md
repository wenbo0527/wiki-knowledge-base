## 核心背景

**行业趋势**：2026年多智能体（Multi-Agent）系统竞争已从**模型能力**转向**系统可靠性**，关键矛盾在于如何将有限的上下文窗口转化为**可持续运行的工作集**。

**核心洞察**：上下文管理已成为Agent Harness的核心竞争力。

---

## 核心概念转变

### 传统模式（Transcript Mode）

- 按时间顺序堆砌消息
- 旧工具输出反复占用token
- 文件读取缺乏分页
- 压缩后难以恢复原始事件
- **长任务后期易失真**

### 现代模式（Managed Working Set）

- 每轮生成最小可用视图
- 大文件检索/分页/切片
- 大输出留preview（完整对象放窗口外）
- 会话落成可恢复事件日志
- **长任务后期仍可恢复**

## 上下文管理分层模型

```
┌─────────────────────────────────────────────────────────────┐
│                     输入源：事件/文件/工具                    │
├─────────────────────────────────────────────────────────────┤
│                    预算策略：限流/分页                        │
│                  （如Pi限制文件读取2000行或50KB）             │
├─────────────────────────────────────────────────────────────┤
│                   窗口视图：摘要/切片                         │
│              （Claude Code对>256KB文件先stat再拒绝）          │
├─────────────────────────────────────────────────────────────┤
│                窗口外存储：日志/记忆/完整对象                  │
│                     （Letta Code超大输出写入overflow文件）    │
└─────────────────────────────────────────────────────────────┘
```

## 关键技术模块对比

| 管理对象 | 核心问题 | 主流解决方案 | 代表系统 |
|----------|----------|-------------|----------|
| **文件读取** | 大文件超限 | hard cap+offset/limit+grep | Claude Code（256KB阈值）、Letta Code（10MB拒绝） |
| **工具输出** | 窗口撑爆风险 | 字符上限+preview+磁盘存储 | OpenClaw（工具输出占窗口30%）、Alyx（JSON压缩预览） |
| **会话压缩** | 状态丢失 | LLM分维度总结+checkpoint | Claude Code（按primary request/errors等6维度总结）、Letta Code（reflection subagent迁移记忆） |
| **子智能体** | 上下文污染 | 隔离会话+结果仅返回 | Pi（子任务新进程）、OpenClaw（isolated session） |

## 上下文窗口运行链路

```
┌─────────────────────────────────────────────────────────────┐
│  Session Log（事件流/可回放）                                │
│  ↓ Budget Gate（限流/截断/分页）                            │
│  ↓ Context View（切片/摘要/预览）                           │
│  ↓ 状态分层                                                 │
│    ├── 事件层（user turn/tool call）                        │
│    ├── 数据层（文件切片/检索索引）                           │
│    └── 记忆层（任务状态/用户偏好）                          │
└─────────────────────────────────────────────────────────────┘
```

## 会话压缩的工程挑战

**核心难点**：压缩后需保持任务可续性

**必须保留的关键状态**：
- 用户目标
- 已排除方案
- 错误修复
- 下一步动作

**边界处理**：
- 避免切断tool-call/result配对
- 压缩自身撑爆窗口时需兜底（如中间截断留头留尾）

## Agent Harness自查清单

| # | 检查项 |
|---|--------|
| 1 | 工具预算：大内容工具是否设硬上限？ |
| 2 | 访问路径：截断内容是否提供继续访问方式？ |
| 3 | 分页参数：工具描述是否包含offset/limit等指令？ |
| 4 | 压缩维度：是否分层保留任务状态（目标/文件/错误/计划）？ |
| 5 | 工具边界：压缩时是否守住tool call/result完整性？ |
| 6 | 子体隔离：子智能体是否默认使用独立会话？ |
| 7 | 状态持久化：关键状态是否迁移至文件/数据库/记忆仓库？ |
| 8 | 可观测性：是否监控token用量/截断/压缩等指标？ |
| 9 | 模块解耦：session/harness/sandbox是否分离？ |
