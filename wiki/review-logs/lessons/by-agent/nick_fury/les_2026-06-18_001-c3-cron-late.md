## 教训总结

> **"待办"无 Owner = 永远待办。治本机制的设计 + 上线必须由同一人闭环。**

---

## 问题背景

C-3 cron（每日 21:00 扫描日报完稿率）设计于 6-15 INC-2026-06-15-001 闭环后，写入 SOUL §8.1 硬规矩。但 6-16 daily 把 C-3 标"待做"后**3 天无人实施**——直到 6-18 08:46 文博发现日报缺失，治本机制（C-3）**自己也是漏洞受害者**。

| 时间 | 状态 | 备注 |
|:---|:---|:---|
| 6-15 19:35 | C-3 设计完成 | SOUL §8.1 写入 |
| 6-16 08:46 | daily 标 P1 #7 "🔴 待做" | 6-16 daily.md:81 |
| 6-16 17:25 | 仍待做 | 6-16 daily 落盘 |
| 6-17 24h | 仍待做 | daily 缺失 |
| 6-18 08:46 | 文博发现 | 触发本 INC |
| 6-18 10:56 | C-3 上线 | 本日闭环 |
| 6-18 11:00 | INC + Lesson 闭环 | 本文件 |

**总延期：3 天**

## 根因分析

### 技术层面

| 问题 | 说明 |
|:---|:---|
| **C-3 设计完无 owner** | SOUL §8.1 写进硬规矩，但没指定"谁上线" |
| **P1 #7 无人跟踪** | daily 标"待做"后无后续 checklist 跟进 |
| **治本机制本身是漏洞** | C-3 是检测"日报缺失"的机制，但它自己"缺失"了 3 天——**自指悖论** |

### 流程层面

```
预期流程：
  SOUL §8.1 写 C-3 → Nick 写 daily 标"待做" → Nick 当天实施 → 闭环

实际流程：
  SOUL §8.1 写 C-3 ✅ → Nick 写 daily 标"待做" ✅ → 闭环 ❌
                                        ↓
                                  无人实施（owner 缺失）
```

**核心问题**：
- "待办" 是一种**状态描述**，不是**行动触发**
- 没有 "owner + 截止时间" 的"待办" = 永远待办
- daily 标"待做"后，**没有自动提醒机制**——只能靠人脑记忆

### 组织层面

- **C-3 cron 设计者（派蒙）** = **C-3 cron 实施者** = **同一组织内不同人/角色**（设计归 SOUL，实施归 Nick）
- 6-15 派蒙起草 Standing Orders v2.0 → 6-15 Nick 认领 → 但 6-16 daily 标"待做"后**无派单动作**
- 派蒙/Nick 之间无"派单→接单→闭环"的标准动作

## 正确做法

### ✅ 应该做的

1. **"待办" 必须有 owner + 截止时间 + 验证机制**
   ```markdown
   - [ ] **P1 #7 C-3 cron 上线** 
     - owner: nick_fury
     - 截止: 6-16 21:00
     - 验证: launchctl list 看到 com.nickfury.daily-report-c3
   ```

2. **治本机制必须有"上线日"而非"待做"**
   ```
   ❌ "P1 #7 C-3 cron 🔴 待做"
   ✅ "P1 #7 C-3 cron owner=nick_fury 截止=6-16 21:00"
   ```

3. **同一人闭环设计+上线**
   - 派蒙起草 C-3 → Nick 认领 → Nick **当天**实施 → 闭环
   - 设计归 SOUL（持久化），实施归 daily（短期）

4. **依赖关系明确化**
   - 任何"待办"必须在 daily 显式标"下一天验证节点"
   - "今天 21:00 验证 C-3 是否还在跑"

### ❌ 不应该做的

1. ❌ "待办" 无 owner
2. ❌ "待办" 无截止时间
3. ❌ "待办" 跨日仍未实施不标"🔴 延期"
4. ❌ "待办" 期望设计者自己会来实施（**不实施 = 漏洞**）

## 经验复用

### 可复用的场景

| 场景 | 如何复用 |
|:---|:---|
| **任何"治本机制"** | 实施完才标"✅ 完成"，不标"待做" |
| **任何"待办"事项** | 必须有 owner + 截止时间 |
| **任何"待办"延期** | 自动升级为 🔴 P0 + 飞书告警 |
| **任何"流程改进"** | owner = 设计者本人（同一人闭环）|

### 预防措施

```
1. C-3 cron 上线后，明日 21:00 首次自动跑
2. C-3 cron 跑出告警 → Nick 下次唤醒时主动推飞书
3. HEARTBEAT.md 加"无任务"日报模板 → 闭环后无静默
4. daily 模板强制要求 "待办" 必须有 owner + 截止时间
5. 派蒙每 24h 派单检查 Nick daily "待办"项延期情况
```

## 关键反思

> **问"How"不问"Why"**
>
> **这个问题当时是怎么一步步发生的？**
> 1. 6-15 派蒙起草 C-3 cron 设计 → 写入 SOUL §8.1
> 2. 6-15 19:35 Nick 闭环 INC-2026-06-15-001 → 庆祝 → 忘记 C-3
> 3. 6-16 08:46 Nick 写 daily → 标 P1 #7 "🔴 待做" → 无 owner
> 4. 6-16 17:25 Nick 落盘 daily → 18 个 plist 修复 + 6 KB 同步 + 148 篇 → **C-3 被淹没**
> 5. 6-17 Nick 进入"无任务"模式 → 无新驱动 → 静默
> 6. 6-18 08:46 文博被动发现
>
> **为什么当时"待办"无 owner 是合理的？**
> - Nick 默认假设"待办"会自实施（**错误假设**）
> - SOUL §8.1 没强制要求"待办"必须有 owner
> - 派蒙起草时没强调"实施闭环"
> - 流程没要求"待办延期自动升级"
>
> **而不是：为什么你不实施 C-3？**
> - "不实施"是结果，不是原因
> - 根因 = 流程漏洞（owner 缺失 + 延期无升级）
