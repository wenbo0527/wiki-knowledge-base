## 三、评估维度

### 3.1 六大评估维度

| 维度 | 核心问题 | 指标 | 说明 |
|:---|:---|:---|:---|
| **正确性** | 能否做对？ | Task成功率 | 最终能完成任务 |
| **可靠性** | 一次就能做对？ | First-Trial Rate | 第一次尝试成功率 |
| **效率** | 做得快不快？ | 平均耗时、响应时间 | - |
| **成本** | 花多少资源？ | Token消耗、API调用次数 | - |
| **稳定性** | 是否一致？ | 一致性分数、方差 | - |
| **安全性** | 是否可控？ | 安全边界符合率 | - |

#### 正确性 vs 可靠性（核心区分）

| 指标 | 问题 | 允许重试 | 应用场景 |
|:---|:---|:---:|:---|
| **Task Success Rate** | 最终能做成吗？ | ✅ 允许重试 | 目标导向任务 |
| **First-Trial Rate** | 一次能做成吗？ | ❌ 不允许 | 高成本场景 |

**组合分析矩阵**：

| 组合 | Success高+First高 | Success高+First低 | Success低+First高 | Success低+First低 |
|:---|:---:|:---:|:---:|:---:|
| **评价** | 🌟 优秀 | 👍 需优化重试 | 😐 不稳定 | 🔴 整体差 |
| **行动** | 保持 | 减少重试次数 | 提高稳定性 | 全面改进 |

**新增指标定义**：

```
First-Trial Rate = 第一次尝试就成功的次数 / 总尝试次数
Retrial Rate = 1 - First-Trial Rate
Avg Trials per Success = 总尝试次数 / 成功次数
```

### 3.2 能力Eval vs 回归Eval

| 类型 | 问题 | 起步通过率 | 目标 |
|:---|:---|:---:|:---:|
| **能力Eval** | Agent目前能做到什么程度？ | 20%（低才有爬坡空间） | 逐步提升 |
| **回归Eval** | 之前能做的还做得好吗？ | - | 接近100% |

**生命周期耦合**：当一个能力Eval被做到接近满分，它就可以"毕业"成回归集。

> **判据绑定原则**：判据绑在产出和状态上才经得起模型升级。

### 3.3 Transcript vs Outcome

| 概念 | 说明 | 判据 |
|:---|:---|:---|
| **Transcript** | Agent做了什么的完整轨迹 | 辅助判断 |
| **Outcome** | 做完之后环境的状态 | 核心判据 |

**例子**：客服Agent回复得再漂亮，工单是否真的被关闭才是真正的判据。

## 四、评估方法

### 4.1 Benchmark

| Benchmark | 场景 | 特点 |
|:---|:---|:---|
| **WebArena** | 网页导航 | 真实网站环境 |
| **SWE-bench** | 软件工程 | GitHub真实Issue |
| **τ-bench** | 零售支持 | 模拟客服场景 |
| **τ2-bench** | 航空预订 | 多轮对话 |
| **AgentBench** | 多场景综合 | 8个环境 |

### 4.2 Grader三层架构

| 类型 | 典型手段 | 强项 | 短板 |
|:---|:---|:---|:---|
| **Code-based** | 字符串匹配、单元测试 | 快、便宜、可复现 | 对合法变体过敏 |
| **Model-based** | Rubric评分、自然语言断言 | 灵活、能扩展 | 有随机性、需校准 |
| **Human** | 专家审阅、A/B测试 | 标准权威 | 慢、贵 |

#### 部分计分（多组件任务）

| 场景 | 计分方式 |
|:---|:---|
| **客服Agent** | 识别问题(✅) + 验证客户(✅) + 退款失败(❌) > 完全没解决问题 |
| **复合任务** | 加权/二元/混合（取决于是否允许"部分达成"）|

#### Evaluation harness vs Agent harness

| 概念 | 说明 |
|:---|:---|
| **Evaluation harness** | 跑测试的脚手架（测试代码） |
| **Agent harness** | Agent本身运行的框架 |

> **核心洞察**：评估一个Agent实际是在评估harness和模型的组合。

### 4.3 Grader三角色

| 角色 | 职责 | 核心设计 |
|:---|:---|:---|
| **Grader Agent** | 评估断言是否通过 | 8步流程 + 自我批评 |
| **Comparator Agent** | 双盲判断输出质量 | 不知道来源，双维度评分 |
| **Analyzer Agent** | 事后分析与基准分析 | 角色A/B双重角色 |

> **自我批评机制**："A passing grade on a weak assertion is worse than useless."

## 五、评估流程

### 5.1 五阶段闭环

```
任务与基准 → 执行前验证 → 受控执行 → 多级判断 → 持续回归
```

| 阶段 | 内容 | 产出 |
|:---|:---|:---|
| **任务与基准** | 明确环境和成功标准 | Task定义 |
| **执行前验证** | 沙盒、依赖、权限检查 | 环境就绪 |
| **受控执行** | 记录完整轨迹 | Transcript |
| **多级判断** | 结果级+轨迹级+评估者级 | Score |
| **持续回归** | 失败→回归测试用例 | 回归集 |

### 8.2 差距分析

| 框架维度 | 我们现状 | 差距 | 优先级 |
|:---|:---|:---|:---:|
| **Benchmark** | 无标准化Benchmark | 缺少行业基准对比 | 🟠 |
| **能力Eval** | 无能力Eval/回归Eval区分 | 未建立能力基线 | 🟠 |
| **Comparator** | 无双盲比较 | 无法客观对比Skill | 🟡 |
| **Analyzer** | 无模式分析 | 缺乏深层洞察 | 🟡 |
| **五阶段闭环** | 部分实施 | 流程不完整 | 🟡 |
| **CI集成** | 无 | 未接入CI/CD | 🟠 |
| **七维评估** | 有框架 | 尚未系统执行 | 🟡 |

### 8.3 差距原因分析

#### 差距1：Benchmark缺失

| 项目 | 说明 |
|:---|:---|
| **原因** | 我们的Skill偏向业务定制，非通用能力 |
| **影响** | 无法与行业对比进步速度 |
| **根本** | 业务型Skill不需要通用Benchmark |

#### 差距2：能力Eval/回归Eval未区分

| 项目 | 说明 |
|:---|:---|
| **原因** | skillbench关注综合表现，未拆分 |
| **影响** | 不知道"能做什么"和"是否回归" |
| **根本** | 测评目的不清晰 |

#### 差距3：Comparator未实施

| 项目 | 说明 |
|:---|:---|
| **原因** | Skill数量少（10个），两两对比成本低 |
| **影响** | 难以客观判断Skill改进效果 |
| **根本** | 规模未达到需要自动化的程度 |

#### 差距4：五阶段闭环不完整

| 项目 | 说明 |
|:---|:---|
| **原因** | 偏重执行，验证和回归环节薄弱 |
| **影响** | 可能引入回归问题 |
| **根本** | 缺乏自动化验证机制 |

#### 差距5：七维评估未系统执行

| 项目 | 说明 |
|:---|:---|
| **原因** | 评估主观性强，缺乏客观指标 |
| **影响** | Agent能力提升无量化反馈 |
| **根本** | 七维是能力框架，不是评估流程 |

### 8.4 改进建议

| 优先级 | 任务 | 说明 |
|:---:|:---|:---|
| 🔴 | 建立能力Eval基线 | 明确每个Skill的"能做什么" |
| 🟠 | 接入CI/CD | 每次提交跑自动化Eval |
| 🟠 | 区分能力Eval/回归Eval | 拆解skillbench指标 |
| 🟡 | 实施Comparator | Skill超过15个后启动 |
| 🟡 | 系统执行七维评估 | 每月一次自评 |
