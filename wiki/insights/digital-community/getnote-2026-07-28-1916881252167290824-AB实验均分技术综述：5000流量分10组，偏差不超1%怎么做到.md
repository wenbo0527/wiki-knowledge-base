7月23日，策略上线。AB分流配置50:50，实验组和对照组各占一半流量。

跑了10天，数据回来了——实验组累计4700人，对照组4300人，偏移5%。单日数据更夸张，某天直接跑出29:71的极端偏离。

50:50的配置，跑出了5%的偏差。问题出在哪？

这不是个例。5000量级的流量做AB实验，分流偏差是高频踩坑点。看似简单的"随机分两组"，在大样本下勉强够用，一旦样本量收紧，随机波动就会把偏差推到不可控的范围。要把它压到1%以内，需要跨四道坎：第一道，怎么分才均匀？直接取模分配，哈希碰撞会让组间人数飘忽不定；第二道，分完怎么保证偏差可控？5000的样本量不大，光靠哈希兜不住；第三道，分完就算人数均匀了，怎么确认分流本身没有系统性偏差？第四道，人数匀了、分流也验证了，但样本量够不够检测出真实效果？

这四道坎，对应的是AB实验分流技术的四个核心环节：分桶、校准、验证、检测能力。下面逐个拆开讲。

## 一、分桶：用哈希把用户打散

先看现有系统的问题。当前分流逻辑是：节点ID拼接客户ID做哈希，落到0-99共100个桶，再按配置比例直接抽取——50:50就是0-49号桶给A组，50-99号桶给B组。问题出在"区间直接切分"：100个桶里，每个桶的实际人数不均，0-49号桶的总人数和50-99号桶的总人数直接传导为组间偏差。某几个桶偏重，整组就偏重，没有校准机制。

哈希分桶的思路没问题，但现有实现有两个短板：桶数太少、缺少校准。改进方向是两个：换哈希算法、加桶数。核心逻辑如下：

```
bucket_id = hash(user_id + salt) % num_buckets
group_id = bucket_id % num_groups
```

用用户的唯一标识（user_id）加上一个盐值（salt，通常是实验ID），做一次哈希运算，对桶数取模，得到桶号；再把桶号对组数取模，得到实验组号。

这里有两个关键选择：哈希算法用什么，桶数设多少。

**哈希算法选MurmurHash3。** 不是MD5，不是SHA，是MurmurHash3。原因很实际：它快，均匀性接近密码学哈希但运算量小一个量级。AB实验场景下，每次用户请求都要实时算一次分组，性能敏感。业界主流的AB平台——字节跳动的实验系统——底层都用的它。

**桶数设1000，不是10。** 这是最容易踩的坑。直觉上分10组就开10个桶，每组1个桶，简单直接。问题是：10个桶里，哈希碰撞导致的桶间人数差异可能很大。某个桶分到540人，另一个桶只有460人，偏差直接8%。

把桶数开到1000就不一样了。1000个桶，每桶期望5人，再按 `bucket_id % 10` 归组——每组拿到100个桶的聚合结果。桶与桶之间的随机波动，在100个桶的聚合中被均摊稀释。这就像掷骰子：掷10次，出现两次6的概率不低；掷1000次，6的出现频率会非常接近1/6。

**桶数远大于组数**，是分流均匀性的第一层保障。

## 二、校准：1000桶也兜不住1%偏差

第一层保障够不够？算一下。

5000用户分到1000个桶，每桶期望5人。泊松分布下，桶间标准差约 √5 ≈ 2.24人。每组聚合100个桶，标准差放大到 2.24 × √100 = 22.4人。取3倍标准差（99.7%置信区间），波动范围在 ±67人。每组期望500人，67/500 = **13.4%**。

结论很直接：**光靠哈希分桶，偏差大概率超过1%。** 1000桶把10桶的8%压缩到了13%的3σ范围——但离1%还差一个量级。

需要第二层保障：分桶后校准。

### 蛇形分配：确定性的偏差控制

蛇形分配（S-shape allocation）的思路不复杂：分完桶之后，不急着按 `bucket_id % 10` 归组，而是先统计每个桶的实际人数，按人数从大到小排序，然后用蛇形策略把桶分配给各组。

具体做法：

1. MurmurHash3把5000用户分到1000个桶
2. 统计每个桶的实际人数
3. 按桶人数降序排列
4. 第1大桶给组1，第2大桶给组2……第10大桶给组10；第11大桶给组10，第12大桶给组9……交替反向
5. 每组100桶，总人数偏差可控制在5人以内（<1%）

蛇形分配的本质是一个贪心均衡算法。最大的桶给当前最"穷"的组，次大的桶给次"穷"的组，往复交替。它不依赖运气、不需要重试，是确定性保证。

对比另一种思路——重哈希（换salt值重新分桶，直到偏差达标），蛇形分配有两个优势：一是**确定性**，不靠随机重试，一次到位；二是**可复现性**，同一批用户、同一个salt，分桶结果永远一致，用户不会因为重哈希而在不同请求中被分到不同组。这在AB实验中是硬性要求——同一个用户在整个实验周期内必须始终在同一个组。

### 代码实现

```python
import mmh3
import statistics

def assign_groups(user_ids, num_buckets=1000, num_groups=10, salt="exp_001"):
    # Step 1: 哈希分桶
    buckets = {i: [] for i in range(num_buckets)}
    for uid in user_ids:
        hash_input = f"{uid}_{salt}"
        bucket_id = mmh3.hash(hash_input, signed=False) % num_buckets
        buckets[bucket_id].append(uid)
    
    # Step 2: 按桶人数降序排列
    sorted_buckets = sorted(buckets.items(), key=lambda x: len(x[1]), reverse=True)
    
    # Step 3: 蛇形分配
    groups = {i: [] for i in range(num_groups)}
    for idx, (bucket_id, users) in enumerate(sorted_buckets):
        cycle = idx // num_groups
        pos = idx % num_groups
        group_id = pos if cycle % 2 == 0 else (num_groups - 1 - pos)
        groups[group_id].extend(users)
    
    # Step 4: 验证偏差
    group_sizes = [len(g) for g in groups.values()]
    mean_size = statistics.mean(group_sizes)
    std_size = statistics.stdev(group_sizes)
    hash_diff = std_size / mean_size
    print(f"Hash_diff: {hash_diff:.4f} ({'PASS' if hash_diff < 0.01 else 'FAIL'})")
    
    return groups
```

核心就四步：哈希分桶 → 排序 → 蛇形分配 → 偏差校验。

### 固定桶映射：实验期内不变

蛇形分配解决了"怎么分得匀"，但还有一个工程约束必须点明：用户固定归属某个桶（哈希结果不变），实验期内桶到组的映射关系固定不变——同一用户在整个实验周期内始终在同一组。

这不是可选项，是AB实验的硬性要求。如果用户今天在实验组、明天跑到对照组，策略效果和自然波动就搅在一起，实验结论直接作废。

实际项目中，本项目的实验周期约定为60天。这个周期有两个作用：一是保证足够的样本累积，二是控制用户重复进入实验的概率——60天窗口内，同一用户不会因为实验重新启动或配置变更而被分到不同组。

## 三、验证：分完不能假设均匀

人数偏差控制住了，不等于分流没问题。一个容易被忽略的事实：人数均匀只是分流质量的必要条件，不是充分条件。如果哈希函数对某种特征的用户有系统性偏好——比如某种user_id前缀的用户集中落在某几个桶——即使组间人数一模一样，用户的特征分布也可能不均，实验结论照样失真。

所以分完之后必须做三层验证。

**第一层：Hash_diff（组间均匀性检验）**

```
Hash_diff = 组间人数标准差 / 组间人数均值
```

目标值 < 0.01。这个指标在蛇形分配后基本能过，但它是必须检查的——不验证就声称均匀，等于没做。

**第二层：SRM校验（样本比例不匹配检验）**

Hash_diff过了，只说明人数比例看起来匀。但"看起来匀"和"统计上匀"是两回事。SRM（Sample Ratio Mismatch）校验是业界标准前置环节——每次实验分析前必须先通过SRM测试，否则后续所有结论都不可信。

SRM的原理是卡方拟合优度检验：拿各组实际人数和期望人数做比较，看偏差是否在统计上可接受。

```
X² = Σ(Oi - Ei)² / Ei

其中：
Oi = 第i组的实际观测人数
Ei = 第i组的期望人数（= 总人数/组数）
自由度 = 组数 - 1
```

5000人分10组，期望每组500人。假设蛇形分配后实际分布是 [495, 505, 498, 502, 496, 504, 497, 503, 499, 501]，卡方值 = (25+25+4+4+16+16+9+9+1+1)/500 = 0.22，自由度9，P ≈ 0.999——远大于0.05，通过。

判定规则：**P > 0.05 → 分流均匀，可以开始实验；P < 0.001 → 存在SRM问题，实验结论不可信，必须排查原因。**

回到开头那个真实场景：4700 vs 4300，偏差5%。代入卡方检验——X² = (4700-4500)²/4500 + (4300-4500)²/4500 = 40000/4500 + 40000/4500 ≈ 17.78，自由度1，P < 0.0001。SRM必然不通过。也就是说，那10天的实验数据，从统计学的角度看，根本不能用来下结论。

```python
from scipy.stats import chisquare
import numpy as np

observed = np.array([495, 505, 498, 502, 496, 504, 497, 503, 499, 501])
expected = np.array([500] * 10)
chi2, p = chisquare(observed, expected)
print(f"Chi-square: {chi2:.4f}, p-value: {p:.4f}")
# p > 0.05 → 通过SRM
```

SRM失败时的排查方向：分流服务异常、机器人爬虫数据混入、其他实验"窃取"流量、用户属性变化导致分组偏移。

**第三层：AA实验（空跑验证）**

AA实验是让所有组跑相同策略（没有对照组和实验组的差异），观察核心业务指标——点击率、转化率、客单价——在组间是否有统计显著差异。

如果有，说明分流本身引入了系统性偏差。可能是哈希函数和用户特征之间存在耦合，也可能是salt值选取不当。这时需要更换salt重新分桶，或者检查user_id的生成规则是否存在模式。

AA实验通常建议跑3-7天。时间太短，日间波动可能掩盖分流偏差；太长则占用实验排期。

Hash_diff管的是"人数匀不匀"，SRM管的是"统计上匀不匀"，AA实验管的是"人本身匀不匀"。三层都过，分流才算真的稳。

## 四、边界：偏差控制 ≠ 检测能力

前面三步解决了"分得匀"的问题。但有一个容易混淆的点：分流偏差控制在1%以内，不等于这个实验能检测出1%的效果差异。这是两回事。

分流偏差是**分配层面**的问题——各组人数匀不匀。检测能力是**统计层面**的问题——样本量够不够把真实效果从随机噪声中分辨出来。

5000用户分10组，每组500人。假设核心指标是转化率，基线5%。在95%置信度下，500人样本的最小可检测效果（MDE）大约在3-4个百分点。也就是说，如果实验策略把转化率从5%提升到6%，这个差异在500人样本下大概率检测不出来——统计功效不够，p值压不到0.05以下。

回到开头那个真实场景：策略跑了10天，实验组4700人、对照组4300人，合计9000人。如果分10组，每组900人，MDE会略好一些，但量级仍在3个百分点左右。也就是说，效果小于3%的差异可能检测不出来——你看到"没有显著差异"，可能不是策略没用，而是样本量不够分辨。

这不是分流方案的问题，是样本量的问题。要检测更小的效果差异，要么增加流量，要么多周期累积样本。还有一种统计学方法——CUPED方差缩减，能在相同样本量下提升检测灵敏度，后面会展开讲。

一个实操建议：在设计实验时，先算MDE，再定流量。而不是反过来——先拍一个流量数字，再发现检测不出效果。流量分配和统计功效是AB实验设计的一体两面，分流方案解决前者，样本量计算解决后者，缺一不可。

## 五、离线还是实时：算法层的根本差异

前面讲的方案——哈希分桶 + 蛇形分配 + 三层验证——有一个隐含前提：**分流是离线批量完成的**。5000个用户全在手里，先分完、再排序、再蛇形分配，偏差确定性压到1%以内。

如果改成实时事件分流呢？用户是一个一个来的，分第一个用户的时候，不知道后面还有谁。蛇形分配用不了——它需要知道所有桶的人数才能排序。那实时分流靠什么保证均匀？

### √n数学下界：实时分流的物理极限

回到前面的数学推导。5000用户分1000桶，每桶期望5人，桶间标准差 √5 ≈ 2.24，每组聚合100桶后标准差 22.4人，3σ相对偏差 13.4%。

回到前面的推导——3σ相对偏差13.4%，这个数字揭示了一个更深的结论：**单层实时分流的偏差服从 √n 渐近线**。n是用户量，偏差与 √n 成反比——用户量越大，偏差越小，但改善速度越来越慢。

实测验证了这个理论。对5000用户做实时无状态哈希分流（不加任何校准），100次重复采样：


| 用户量    | 平均偏差   | <1%通过率 | 评价      |
| ------ | ------ | ------ | ------- |
| 500    | 24.64% | 0%     | 灾难      |
| 5000   | 7.98%  | 0%     | 当前水平    |
| 50000  | 2.37%  | 0%     | 接近      |
| 100000 | 1.67%  | 10%    | 刚摸到1%边缘 |
| 500000 | 1.34%  | —      | 3σ理论值   |


5000量级下，实时分流平均偏差7.98%，与理论下界13.4%的3σ范围吻合。**0%的通过率意味着：5000用户做实时分流，不可能稳定压到1%以内。** 要纯实时压到1%，需要把流量放大到50万——这不是算法问题，是统计物理下界。

### 五套方案实测对比

为了验证"实时分流能不能通过算法优化突破√n下界"，实际跑了五套方案的对比实验：


| 方案          | 平均偏差      | <1%通过率  | SRM通过率 | 一致性   | 工程成本 |
| ----------- | --------- | ------- | ------ | ----- | ---- |
| **批量蛇形分配**  | **0.51%** | **96%** | 100%   | ✓     | 低    |
| 实时无状态hash   | 7.98%     | 0%      | 90%    | ✓     | 极低   |
| 实时两次hash异或  | 7.82%     | 0%      | 93%    | ✓     | 低    |
| 实时多salt众数投票 | 7.98%     | 0%      | 97%    | ✓     | 中    |
| 实时桶级微调      | 5.99%     | 0%      | 100%   | ✓     | 中    |
| 实时多映射切换     | 0.51%     | 98%     | 100%   | **✗** | 中    |


这张表的信息量很大，但真正需要记住的只有三件事。

**发现一：任何O(1)的局部优化都改不了√n渐近线。** 两次hash异或（7.82%）、多salt众数投票（7.98%）、桶级微调（5.99%）——都比无状态hash（7.98%）好一点点，但量级没变，0%通过率。因为这些优化都是局部操作，无法改变全局分布。

**发现二：批量蛇形分配是5000量级唯一能稳定压到1%的算法。** 它不是O(1)优化，而是全局贪心均衡——先看全量数据再分配。96%通过率，平均偏差0.51%。

**发现三：实时多映射切换"看似达标实则违规"。** 表格里唯一打✗的就是它。偏差0.51%、98%通过率，看起来和蛇形分配一样好。但它通过切换桶到组的映射关系来校准偏差，切换时同一用户可能被分到不同组——**一致性被破坏**。生产中等同于实验数据污染，不可用。

结论很清楚：**5000量级下，实时分流存在√n数学下界，任何O(1)优化都突破不了。唯一稳定方案是批量蛇形分配。**

### 生产推荐：预分桶 + 静态查表

既然批量蛇形分配是唯一解，怎么在运行时用？答案是预分桶 + 静态查表：

1. 实验启动前，用蛇形分配一次性算出所有用户的分组
2. 生成 `user_id → group_id` 映射表，部署到Redis
3. 运行时O(1)查表：`group = redis.get(f"exp:{exp_id}:{user_id}")`
4. 新用户首次进入实验时，落入预分桶表

这样既继承了蛇形分配的偏差控制（<1%），又保证了运行时性能（毫秒级查表）和一致性（映射关系固定不变）。字节、阿里、美团等生产平台的标准做法都是这个模式。

预分桶+静态查表解决了5000量级的分流问题。但如果流量从5000涨到50万、实验从1个变成50个并发，这套方案还够用吗？

## 六、业界标杆：字节的DataTester做了什么

前面讲的是5000流量级别的分流方案——够用，但只是起步。如果要看工业级AB系统长什么样，字节跳动的DataTester是绕不开的参照系。它是字节内部唯一的AB实验平台，据字节跳动数据平台公开技术博客，截至2023年中累计跑了240万次实验，同时运行5万个，服务500+条业务线。

DataTester在前面讲的分桶+校准+验证之上，多做了三件事。

**第一件：正交分层，解决流量不够用的问题。**

前面讲的方案是单层分流——一个实验把流量分完就结束了。但实际业务中，推荐、搜索、广告、UI多个团队同时要做实验，流量根本不够分。DataTester的做法是正交分层：每个实验占一层，层与层之间流量正交——用户穿越每一层时都会通过加盐哈希重新打散。同层实验互斥（流量不重叠），跨层实验正交（流量复用）。数学上，正交性要求第一层的每个分组在第二层中均匀分布：N(A∩C) = N(A) × N(C)。这样100%的流量可以被多个实验同时使用，互不干扰。

**第二件：两次哈希，降低系统性偏差。**

前面讲的是一次哈希分桶。DataTester在分组过程中做两次：第一次把用户分配到桶，第二次在分组时再次哈希。两次哈希相当于对随机序列做了二次独立扰动，降低单次哈希可能产生的系统性偏差。此外，互斥域还会做第三层哈希，形成流量层之间的强制隔离。据火山引擎开发者社区技术博客介绍。

**第三件：CUPED方差缩减，小样本的统计补救。**

前面讲了MDE的限制——500人样本检测不出3%以下的差异。CUPED（Controlled-Experiment Using Pre-Experiment Data）是字节采用的补救方案：利用实验前的历史数据对实验结果做修正，公式是 Y_corrected = Y - θ × (X - X̄)，其中 θ = Cov(Y,X) / Var(X)，使修正后方差最小。修正后结果仍为无偏估计，但方差缩减了。效果是：据《AB实验：科学归因与增长的利器》（刘玉凤著，机械工业出版社，2022年），在1%流量、相对收益0.003的场景下，召回率从35%提升到90%——原来因流量不够检测不出的收益，现在能检测出来了。

这三件事，正交分层解决"流量不够"，两次哈希解决"分得不匀"，CUPED解决"检不出来"。对应的是AB实验从"能跑"到"能规模化跑"的升级路径。

## 总结

回到开头那个场景：50:50的分流跑出5%偏差，问题不在策略，在地基。完整链路是这样的——

MurmurHash3做哈希分桶，1000桶打底保证基本均匀；蛇形分配做分桶后校准，确定性把偏差压到1%以内；Hash_diff + SRM卡方检验 + AA实验做三层验证，确认分流既匀人又匀特征；用MDE评估样本量够不够，确认实验的检测能力；流量不够时，CUPED方差缩减是统计层面的补救方案。

如果考虑实时分流——5000量级下存在√n数学下界，任何O(1)优化都突破不了，平均偏差7.98%，0%通过率。生产级方案是预分桶+静态查表：实验前用蛇形分配一次性算完，运行时O(1)查表，兼顾偏差控制和实时性能。

分流是AB实验的地基。地基稳了，上面跑的实验结论才值得信。
