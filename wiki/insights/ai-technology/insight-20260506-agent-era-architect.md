# Agent时代架构师核心能力框架：从工具追逐到系统沉淀

> 来源: Get笔记
> 导入日期: 2026-05-06
> 原始ID: 1909139523149952696

### **🔍 核心问题提出（背景）**

**行业现状**
- **技术迭代加速**：Agent领域框架（如LangGraph、Mastra）和模型能力每周更新，易导致开发者陷入"新闻流追逐"陷阱。
- **工程化挑战**：当Agent进入真实系统，需解决上下文管理、工具设计、状态保存、权限控制等**系统性问题**，而非仅关注模型性能。
- **核心命题**：架构师需培养**跨框架、跨模型的复用性工程能力**，聚焦半衰期长的底层系统能力建设。

### **📌 太长不看（核心结论）**
* • 优先沉淀跨模型/框架的**底层工程能力**，而非追逐工具清单。
* • 建立**筛选机制**：评估新技术的半衰期、系统兼容性、解决真实问题的价值。
* • 上下文设计为**运行时工作集**，而非聊天记录；工具设计遵循**清晰接口契约**。
* • **评估前置**：用样本和trace替代体感判断Agent效果；**Harness作为运行底座**，整合状态、权限、成本等核心功能。
* • 多Agent设计优先考虑**上下文与读写边界**，而非角色分工；落地起点为**窄目标、可度量、可回滚的小闭环**。

### **⚖️ 筛选比路线图更耐用**

**技术筛选五维评估框架**

| 评估问题 | 判断标准 | 示例（高价值vs低价值） |
|---------|---------|----------------------|
| 半年后是否重要 | 属于包装层还是底层能力 | 协议设计（高） vs 模型封装层（低） |
| 能否接入现有系统 | 是否兼容日志/权限/部署体系 | 接口标准化工具（高） vs 独立SDK（低） |
| 解决什么失败模式 | 生产环境痛点还是Demo新鲜感 | 状态恢复机制（高） vs 特效展示（低） |
| 能否被评估验证 | 可通过trace和样本量化效果 | 准确率提升（高） vs "更智能"体感（低） |
| 延迟采用损失 | 系统能力沉淀优先级 | 沙箱隔离（高） vs CLI参数优化（低） |

**关键洞察**：模型榜单、Agent SDK、Demo产品等半衰期短（通常<6个月），而协议、状态管理、评估体系等底层能力半衰期长，应作为**团队资产重点沉淀**。

### **🧠 上下文：运行时工作集管理**

**上下文分层架构**

| 层级 | 承载内容 | 管理策略 |
|------|---------|---------|
| 模型窗口 | 当前目标、关键约束、决策信息 | 动态筛选，仅保留高密度信息 |
| 会话状态 | 任务计划、已完成动作、错误记录 | 结构化存储，支持回溯与压缩 |
| 文件/数据库 | 代码、文档、可回放事实 | 按需检索，避免全量加载 |
| 项目规范 | AGENTS.md、验收标准、团队约定 | 静态缓存，保持版本稳定 |
| 工具层 | 检索、验证、权限受控动作 | 结果分页，仅返回关键摘要 |

**工程实践**：参考Claude Code 92%缓存命中率的实现，将稳定内容（系统规则、工具定义）与动态内容（任务历史、用户输入）分离，通过**上下文结构优化**提升模型推理效率。

### **🛠️ 工具：业务接口化设计**

**高质量工具的核心特征**
- **数量精简**：5-10个边界清晰的工具优于20个重叠工具，减少模型选择困惑。
- **描述精准**：需明确工具适用场景、参数格式、返回结构及错误处理指引。
- **安全可控**：危险操作需权限分级、二次确认，并记录完整调用trace。

**协议层趋势**：MCP（模型控制协议）通过标准化工具、资源、能力边界定义，降低Agent与外部系统的集成成本，代表**工具接口化的长期方向**。

### **📊 评估：从体感到系统化验证**

**核心评估原则**
- **样本驱动**：从真实业务trace中提取评估样本（建议≥50条），覆盖成功/失败场景。
- **指标量化**：针对不同业务场景定义关键信号（见下表），避免主观判断。
- **持续迭代**：每次模型升级、prompt优化或工具调整后重新评估，防止能力退化。

**场景化评估指标**

| 业务场景 | 关键评估信号 |
|---------|------------|
| 编程Agent | 代码保留率、测试通过率、返工次数、回滚率 |
| 客服Agent | 问题解决率、转人工率、用户追问次数 |
| 数据分析Agent | SQL执行成功率、图表采用率、结论修正率 |
| 运维Agent | 告警恢复率、误操作率、MTTR（平均恢复时间） |

### **🏗️ Harness：模型运行底座**

**核心功能定位**
- **任务调度**：上下文组织、工具调用、子任务分发。
- **系统保障**：状态保存、失败重试、结果验证、权限控制。
- **可观测性**：日志记录、成本监控、性能分析、模型切换适配。

**产品化启示**：Agent质量取决于**模型+ Harness组合**，同一模型在不同上下文策略、工具契约、评估体系下表现差异显著。需定期清理Harness中的"历史补丁"，避免对新模型能力形成限制。

### **💾 状态：超越窗口的持久化管理**

**状态分类与存储策略**

| 状态类型 | 存储位置 | 核心价值 |
|---------|---------|---------|
| 当前推理状态 | 模型窗口 | 支持实时决策 |
| 任务进度 | Session/Checkpoint | 实现断点续跑 |
| 可回放事实 | 文件系统/数据库 | 保障可追溯性 |
| 团队经验 | AGENTS.md/Skill库 | 沉淀复用知识 |
| 用户偏好 | 记忆模块/画像系统 | 优化个性化体验 |

**实践案例**：Coding Agent（如Claude Code、Cursor）通过文件系统实现代码状态的diff、回滚与审查，验证了**传统工程方法在Agent领域的复用价值**。

### **🤝 多Agent：边界优先于角色**

**Subagent适用原则**
- **上下文隔离**：将搜索、验证等探索性任务放入子Agent，避免污染主上下文。
- **读写控制**：子Agent优先设计为只读模式，仅返回结论与证据；写操作需明确权限边界。
- **依赖管理**：强依赖任务建议串行执行，独立任务可并行处理，减少协同复杂度。

**落地建议**：默认从单Agent起步，待上下文压力、工具延迟等问题实际出现后，再引入Orchestrator-Subagent架构。

### **🔒 权限与沙箱：安全前置设计**

**核心安全措施**
- **最小权限原则**：文件读写范围、命令执行白名单、网络出口控制。
- **操作防护**：危险动作二次确认、密钥作用域限制、沙箱环境隔离。
- **审计追溯**：完整操作trace、权限变更日志、故障回滚路径。

**关键认知**：安全风险伴随Agent工具调用产生，需在设计阶段纳入考量，而非等到客户审计时补漏。

### **🚀 落地策略：小闭环启动**

**最小闭环构建步骤**
1. **定义窄目标**：选择业务明确、可量化的任务（如客服工单分流、固定报告生成）。
2. **搭建基础组件**：单Agent循环、3-7个工具、窗口外状态存储、沙箱环境、评估样本集。
3. **驱动迭代**：通过失败模式识别改进方向（如上下文污染→分页/压缩，工具误用→接口优化）。

**核心价值**：早期闭环的主要作用是暴露失败模式，而非实现全面功能；让架构随业务需求自然生长，避免过度设计。

### **⏱️ 可延后关注的技术**
- **包装层框架**：仅提供模型/工具封装，需替换现有系统组件的SDK。
- **复杂记忆系统**：在上下文分层、工具检索、状态管理未完善前，优先级较低。
- **多角色Agent**：在上下文与读写边界未明确时，易导致协同混乱。
- **公开Benchmark**：无法替代真实业务场景下的内部评估。
- **模型追新**：建议按季度评估模型升级，避免发布节奏被工具更新打乱。
