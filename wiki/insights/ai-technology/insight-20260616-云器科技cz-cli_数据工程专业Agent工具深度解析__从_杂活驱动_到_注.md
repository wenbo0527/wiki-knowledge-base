### **🌟 核心概述（背景）**

**产品定位**：cz-cli是云器科技自研的**数据工程专业Agent工具**，旨在通过内置的工程化能力，将数据工程师从cron格式记忆、页面切换、语法试错等重复琐事中解放，专注于建模、数据质量校验等核心工作。

**核心价值**：实现数据开发从"杂活驱动"向"注意力驱动"的转变，同时赋能业务人员自主取数，重构数据团队与业务方的协作模式。

### **🔍 数据工程师的注意力困境（问题提出）**

#### **注意力消耗的主要场景**
- **高频上下文切换**：记cron格式、跨平台配置、语法试错等单次耗时短（几十秒）但高频率的操作。
- **非技术挑战的精力占用**：内部调研显示，数据开发中真正消耗精力的是"平台配置差异、语法方言、页面来回切换"，而非复杂业务逻辑。

#### **效率对比案例**

| 任务类型 | 人工操作 | cz-cli Agent执行 |
| :------- | :------- | :--------------- |
| **日报表搭建** | 需多页面跳转，涉及建表、调度配置、上线验证等多步骤人工介入 | **全程无需人工介入**，从建表、配置凌晨2点调度到上线验证全自动化 |

### **🛠️ 技术路径演进：从通用方案到专业Agent（方案设计）**

项目组在开发cz-cli前尝试了三条技术路线，均暴露通用方案在数据工程领域的局限：

| 技术路线 | 具体做法 | 核心问题 |
| :------- | :------- | :------- |
| **大模型直接调用JDBC/SDK API** | 模型直接操作数据接口 | 上下文窗口易被海量数据撑爆，token消耗不可控，模型处理中间结果时易"失焦" |
| **轻量级skill嵌入主Agent** | 将能力封装为skill集成到通用Agent | skill数量增加后调用稳定性下降，复杂任务中存在调用非预期skill的风险 |
| **MCP（Model Context Protocol）方案** | 采用通用多模型上下文协议 | 冷启动成本高，通用协议对数据工程场景注意力不够集中 |

**最终方案**：构建专注数据开发的**专用子Agent（cz-cli）**，可独立运行或被主Agent调用，拥有聚焦的上下文和内置知识，确保工程级数据操作的稳定性。

### **🔧 核心能力：37个skill构建数仓规范harness（技术架构）**

#### **skill体系设计**

cz-cli的核心是内置的**37个skill**，每个skill标注三个维度：**正确做法、平台限制、常见坑**，形成驾驭LLM搭建规范数仓的完整harness（驾驭系统）。

#### **skill分类与覆盖范围**

| 分类 | 数量 | 核心功能 |
| :--- | :--- | :------- |
| **基础与连接** | 5 | SQL语法指南、元数据查询、连接配置等 |
| **数据导入与管道** | 11 | 文件/OSS/Kafka接入、离线/实时CDC同步、任务调度、管道诊断等 |
| **建模与计算** | 6 | 数仓建模、Dynamic Table、查询优化、索引管理等 |
| **运维与治理** | 8 | 权限管理、集群运维、监控、数据恢复、血缘分析、成本分析等 |
| **SDK与集成** | 7 | Python/Java/Spark/Flink SDK、BI工具连接、外部函数等 |

#### **关键机制**：每层验证
- **实现方式**：完成一层DWD（数据仓库明细层）建设后自动触发数据验证，确认无误后再进入下一层。
- **价值**：避免错误逐层累积，降低后期回滚重算的成本。

### **📈 典型应用场景（实践案例）**

#### **1. 数据血缘分析**
- **能力**：自动加载血缘skill，综合调度任务依赖、DDL语句、job history等多源信息，交叉验证后输出完整血缘关系图。
- **效果**：演示中自动绘制一张表的四层血缘，清晰展示每层上游表及任务节点。

#### **2. 调度任务巡检**
- **自动化流程**：拉取任务列表、状态、调度时间，识别耗时异常任务并生成可读报告。
- **移动端支持**：通过IM（飞书、企微）调用子Agent，工程师可在移动端完成巡检，输入自然语言指令即可获取结构化报告。

#### **3. Pipeline搭建与schema change分析**
- **Pipeline搭建**：自动查询原表结构→规划任务步骤→逐层建表并刷新数据→主动验证；遇平台语法差异时，内置知识库自动检索并修正。
- **schema change影响评估**：分析链路血缘和依赖格式→推理风险表及脆弱依赖项→提供兼容性变更方案和上线次序建议。

### **🚀 业务赋能：从需求方到自主取数者（价值延伸）**

#### **财务团队案例**
- **背景**：财务人员需分析账户成本，但不会SQL和数仓操作。
- **配置**：主Agent + cz-cli子Agent + 费用账单业务说明文档。
- **成果**：财务人员自主生成天猫报表，维度拆分清晰，支持一键导出CSV和IM分享。

#### **角色转变**
- **业务人员**：从"提需求"转向"用工具自主取数"。
- **数据团队**：从"接需求做表"转向"建平台、建能力"。

### **⚙️ 增量计算：AI掌握生产级细节（技术深化）**

#### **AI在增量计算中的痛点**

大模型易遗漏工程化细节，如状态表生命周期、维表join决策、hint添加避免存储膨胀等。

#### **cz-cli增量计算skill能力**
- **核心功能**：SQL→DT自动转换、DT类型决策（静态/动态分区）、增量SQL合规检查、风险识别与替代方案。
- **细节补充**：状态表生命周期默认值设置、一次性开关强制重置、Append-only hint声明、维度表join声明等。

#### **应用案例**
- **需求**：将原有四层pipeline（数据新鲜度1.5小时）改造为10分钟级增量链路。
- **输出**：完整改造方案，包括每层原表与目标表、变更情况、约束条件、架构图、风险与预期效果，接近生产级标准。

### **🎯 核心愿景：让注意力回归工程师（总结）**

cz-cli的目标不是让工程师成为更快的"SQL手写员"，而是**将注意力的支配权还给人**，聚焦于：
- 数据建模策略
- 口径对齐标准
- 数据质量定义

**产品状态**：目前仍在打磨细节，首批试用用户将获赠token，实现"安装即用、无需操心配置"。

### **❓ Q&A关键问题解析**

| 问题 | 核心解答 |
| :--- | :------- |
| **37个skill如何避免调用错误？** | 采用子Agent架构，skill范围聚焦；skill描述精简，详细内容延迟加载；新skill上线前通过测试流程校验。 |
| **AI能否处理2000行SQL、几十张表？** | 采用分步读取（代码库管理）、依赖图谱绘制（coding graph）、长SQL分段（speck工具）、流程强制拆分（先拆plan再执行验证）。 |
| **生产环境AI出错如何兜底？** | 生产环境默认只读权限，需人工确认后开放写操作；改造前搭建临时链路与原链路并行，自动校验数据一致性，支持time travel回滚。 |
| **非治理环境下AI如何找对表？** | 从核心链路开始沉淀血缘图谱，覆盖80%业务查询；为易混淆表添加semantic view（业务含义标注）。 |
