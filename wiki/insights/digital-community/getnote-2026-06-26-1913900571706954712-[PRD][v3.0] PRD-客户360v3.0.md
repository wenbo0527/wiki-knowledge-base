## 三、需求背景

### 3.1 目标

构建客户360全景能力，作为客户信息查询系统，支持客服系统和人工审批系统接入，提供统一的客户信息视图。

### 3.2 痛点

1. 客户数据分散在多个系统，客服和审批人员缺乏统一的查询入口
2. 客户信息不全，无法支撑客服和审批决策
3. 缺乏完整的历史记录展示，影响服务质量
4. **搜索能力受限**：现有模糊搜索仅支持姓名+证件组合，无法按产品和授信时间进行筛选

### 3.3 核心挑战

1. 多渠道数据整合与统一客户ID识别
2. 数据脱敏与安全合规
3. 支持客服系统和审批系统的查询接入
4. **授信时间数据关联**：需要关联产品授信时间到客户维度

#### STORY-DEX-C360-SEARCH-005：产品+授信时间查询

| 字段 | 内容 |
|:---|:---|
| 角色-场景-价值 | 作为客服/审批人员，在需要查找某段时间内授信特定产品的客户时，需要支持产品名称+授信时间的组合查询，以便快速定位目标客户 |
| 优先级 | P0 |
| 状态 | 待开发 |

**验收标准**：

1. 支持按产品名称模糊匹配（输入产品名关键词即返匹配结果）
2. 支持授信时间范围选择（开始日期~结束日期）
3. 支持产品名称+授信时间的AND组合查询
4. 查询结果展示：客户名称、产品名称、授信时间、授信状态
5. 查询结果支持分页（默认20条/页）
6. 查询响应时间 < 2s

**交互说明**：

```
搜索框 → 选择「产品+时间」查询模式
     → 输入产品名称（支持模糊匹配，自动补全）
     → 选择授信开始日期 ~ 结束日期
     → 点击查询
     → 展示匹配结果列表
```

**FP 清单**:

| FP-DEX-C360-SEARCH-005-001 | 产品名称模糊匹配 | 接口 | 支持关键词模糊匹配，支持自动补全 |

## 十一、ID命名规范

### 11.1 ID格式

| 类型 | 格式 | 示例 |
|:---|:---|:---|
| Epic | `EPIC-{DOMAIN}-{模块}` | `EPIC-DEX-CUSTOMER_360` |
| Feature | `FEAT-{DOMAIN}-{Epic简称}-{SEQ}` | `FEAT-DEX-C360-SEARCH` |
| Story | `STORY-{Domain}-{Epic简称}-{Feature简称}-{SEQ}` | `STORY-DEX-C360-SEARCH-005` |
| FP | `FP-{Domain}-{Epic简称}-{Feature简称}-{FPSEQ}` | `FP-DEX-C360-SEARCH-005-001` |

### 11.2 ID命名规范要点

- 前缀必须大写：`EPIC-`、`FEAT-`、`STORY-`、`FP-`
- 产品域缩写：`DEX`（数据探索）
- 不允许使用下划线（`_`），统一用中划线（`-`）
- 序号统一使用3位数字（001, 002...）
