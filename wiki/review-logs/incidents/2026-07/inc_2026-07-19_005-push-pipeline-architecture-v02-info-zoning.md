## 2️⃣ 3 种信息分区模式（对比）

### 模式 A · 按主题分区（推荐）

**核心**：每条推送 = 一个独立主题 · 主题之间互不重叠

```
08:30  📊 投资简报       （rss.daily · ETF · 行情）
08:35  🔬 技术日报       （tech·briefing · AI 资讯 · Get 笔记）
09:00  🏥 系统健康       （daily·report·c3 · cron 状态）
21:00  📝 笔记入库       （daily·note·scan · Get 笔记扫描）
22:00  🌙 投资纪律       （evening_tracker · 晚间复盘）
```

**优点**：
- ✅ 主题边界清晰，文博按主题优先级查看
- ✅ 每条推送只讲一件事，认知负担低
- ✅ 不破坏现有 cron（最小改动）
- ✅ 容易扩展（新主题 = 新推送）

**缺点**：
- 🟡 多条通知（仍然 5 条/天）
- 🟡 需要文博"知道"每条推送是讲什么的（标题清晰化）

**关键技术改造**：
- 推送标题加 emoji + 主题前缀（如 `📊 投资简报 | 2026-07-19`）
- 推送内容加章节（避免 reader 不知道结构）

---

### 模式 B · 按紧急度分区（信息分层）

**核心**：推送按"紧急度"分层 · 文博按场景查看

```
🔴 紧急层（即时 · < 5min 内推）
  - 投资纪律触发（美联储议息 / 重大行情）
  - cron 失败告警
  - 系统异常（API 限流 / 网络故障）

🟠 重要层（早报 · 08:30-09:00）
  - 投资简报
  - 技术日报
  - 笔记入库

🟡 日常层（晚间 · 22:00）
  - 投资纪律晚间复盘
  - C-3 自检
  - Wiki 健康度

🟢 周报层（周日 22:00）
  - cron 健康度周报
  - 知识沉淀周报
```

**优点**：
- ✅ 紧急信息立即见
- ✅ 重要信息集中（早 1 次看完）
- ✅ 日常信息不影响早间注意力
- ✅ 周报用于周末复盘

**缺点**：
- 🟠 推送时间需要按紧急度排序（不能固定）
- 🟠 需要"紧急度判定"逻辑（哪些算 🔴 紧急？）
- 🟠 改造较大（推送时机 + 内容分级）

**关键技术改造**：
- 推送时机自适应（紧急 → 立即 · 重要 → 早间 · 日常 → 晚间）
- 内容分级打标（每篇 RSS / 每个事件打紧急度）
- 推送路由器按紧急度选渠道

---

### 模式 C · 按场景分区（按"何时查看"分）

**核心**：推送按"文博何时查看"分场景

```
🌅 晨间场景（08:00-09:00 · 文博开工前）
  - 投资简报
  - 技术日报
  - 笔记入库
  → 1 条合并推送，3 个章节

🌞 午间场景（12:00-13:00 · 文博午休）
  - 实时行情（如果异常）
  - GitHub 动态（如有新仓库）
  → 静默推送（如无事件不推）

🌙 晚间场景（22:00-22:30 · 文博下班）
  - 投资纪律
  - C-3 自检
  → 1 条合并推送

🗓️ 周末场景（周日 22:00）
  - 健康度周报
  - 知识沉淀周报
  → 1 条合并推送
```

**优点**：
- ✅ 最贴合文博实际工作节奏
- ✅ 每场景 1 条推送（4 场景 = 4 条/天 · 比模式 A 少 1 条）
- ✅ 静默推送避免无关打扰
- ✅ 周末复盘独立场景

**缺点**：
- 🟠 改造最大（推送时机 + 场景判定 + 内容合并）
- 🟠 需要"场景感知"（午间场景 vs 晚间场景）
- 🟠 文博工作节奏变化时需重新校准

**关键技术改造**：
- 场景引擎（detect current scenario based on time + activity）
- 内容合并（每场景内所有内容合并为 1 条）
- 静默机制（无事件不推送）

## 3️⃣ 三模式对比表

| 维度 | 模式 A 主题分区 | 模式 B 紧急度分区 | 模式 C 场景分区 |
|:---|:---:|:---:|:---:|

| **扩展性** | 🟢 高（新主题 = 新推送） | 🟡 中（紧急度需重新定义） | 🟢 高（新场景 = 新时段） |
| **实施时长** | 1-2 周 | 3-4 周 | 5-6 周 |

## 4️⃣ 推荐方案

### 🏆 主推：模式 C（场景分区）· 终极目标

**理由**：
- 最贴合文博"产品经理 / 研究员"工作节奏
- 早间 1 条（最重要），午间静默，晚间 1 条，周末 1 条
- 周末独立复盘场景，避免被推送淹没

**实施路径**：
- 阶段 1（1 周）：模式 A 主题分区落地（最小改造 · 立即缓解）
- 阶段 2（2 周）：升级到模式 C 场景分区（场景引擎 + 静默机制）

### 🥈 备选：模式 A（主题分区）· 务实选择

**理由**：
- 改造最小，立即可见效果
- 推送条数不变，但每条更聚焦
- 不需要复杂的"场景判定"

### ❌ 不推荐：模式 B（紧急度分区）

**理由**：
- 紧急度判定本身需要数据训练（哪些事件算紧急？）
- 推送时机不可预测（紧急=即时 → 文博可能凌晨收到推送）
- 改造复杂度高于模式 A 但效果不如模式 C

## 6️⃣ 模式 C 场景分区（终极目标 · 5-6 周）

### 6.1 场景引擎设计

```python
class ScenarioEngine:
    """场景感知推送引擎"""
    
    def detect_scenario(self, current_time: datetime, recent_activity: List[Dict]) -> str:
        """检测当前场景"""
        hour = current_time.hour
        weekday = current_time.weekday()  # 0=周一, 6=周日
        
        # 周日 22:00 → 周末复盘场景
        if weekday == 6 and 22 <= hour < 23:
            return "weekend_review"
        
        # 晨间 08:00-09:00 → 早报场景
        if 8 <= hour < 9:
            return "morning_brief"
        
        # 午间 12:00-13:00 → 午间静默场景
        if 12 <= hour < 13:
            return "noon_silent"
        
        # 晚间 22:00-22:30 → 晚间复盘场景
        if 22 <= hour < 23:
            return "evening_brief"
        
        # 紧急事件（实时检测）
        if self.has_emergency_event(recent_activity):
            return "emergency"
        
        return "default_no_push"
    
    def compose_for_scenario(self, scenario: str, content: Dict) -> str:
        """按场景组合内容"""
        if scenario == "morning_brief":
            return self.compose_morning(content)  # 投资 + 技术 + 笔记合并
        elif scenario == "evening_brief":
            return self.compose_evening(content)  # 投资纪律 + C-3 自检
        elif scenario == "weekend_review":
            return self.compose_weekend(content)  # 健康度周报 + 知识沉淀
        elif scenario == "emergency":
            return self.compose_emergency(content)  # 紧急事件立即推
```

class PushRouter:

    def route(self, content: Dict, scenario: str) -> PushPlan:
        """按场景决定推送时机"""
        if scenario == "emergency":
            return PushPlan(immediate=True, channel="feishu_user")
        elif scenario in ["morning_brief", "evening_brief"]:
            return PushPlan(scheduled_time="08:30" or "22:00", channel="feishu_user")
