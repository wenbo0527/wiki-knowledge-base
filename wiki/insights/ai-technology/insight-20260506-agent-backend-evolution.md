### **🔄 Agent架构的三层演进路径（背景）**

作者基于前期"30分钟手搓Agent"的最小闭环实践，提出Agent系统架构需经历三个发展阶段：
1. **基础Loop层**：模型→工具→观察的核心循环（已实现）
2. **Harness工程层**：上下文管理、权限控制、错误恢复等系统能力（发展中）
3. **后端融合层**：与业务系统的深度集成，解决工具发现、生命周期管理和可观测性（当前探索重点）

### **⚙️ 传统Agent架构的局限性（问题）**

#### **(一) 静态工具列表的瓶颈**
- **硬编码依赖**：工具需在Agent启动时定义（如`readFile`/`runCommand`），无法动态扩展
- **连接复杂性**：n个工具需n(n-1)/2个点对点集成，4个Agent对接5个系统将产生80条组合路径
- **状态不可知**：无法实时感知工具在线状态、版本变化和权限更新

#### **(二) 跨系统协作的挑战**
- **技术栈碎片化**：浏览器、沙箱、Python/Rust服务等不同环境难以统一管理
- **可观测性缺失**：跨进程/语言调用链的日志分散，排障依赖"日志 grep"
- **触发方式单一**：主要依赖Agent主动调用，缺乏业务事件驱动能力

### **🏗️ 新后端架构的核心设计（方案）**

#### **(一) 三大核心概念重定义**

| 原文术语 | 工程化翻译 | 具体含义 |
|---------|-----------|---------|
| `Worker` | **参与者** | 可连接运行时的进程（Agent/浏览器/沙箱/微服务等） |
| `Function` | **能力** | 具有稳定ID的工作单元（工具/API/脚本等） |
| `Trigger` | **入口** | 触发能力执行的事件源（HTTP/队列/cron/状态变化等） |

#### **(二) 运行时能力目录的关键特性**
- **动态注册机制**：Worker连接时自动注册Functions和Triggers，断开后实时注销
- **双模式访问**：支持查询当前可用能力（同步）和订阅能力变化（异步）
- **统一元数据**：每个能力包含ID、描述、输入输出Schema、版本、权限等治理信息

#### **(三) 架构演进对比**

| 维度 | 传统Agent架构 | 新后端架构 |
|------|-------------|-----------|
| **工具形态** | 静态函数数组 | 动态能力目录 |
| **连接方式** | 点对点集成 | 共享运行时引擎 |
| **触发机制** | Agent主动调用 | 多源事件触发（HTTP/队列/状态等） |
| **可观测性** | 分散日志 | 端到端Trace传播 |
| **扩展能力** | 代码级修改 | 动态Worker上下线 |

### **💻 核心实现与代码解析（实践）**

#### **(一) 运行时注册示例**
```typescript
import { registerWorker } from "iii-sdk";  

// 1. 注册Worker并连接运行时
const runtime = registerWorker("ws://localhost:49134");  

// 2. 暴露能力
runtime.registerFunction("hello::greet", async (input) => {  
  return { message: `hello ${input.name}` };  
});  

// 3. 配置触发入口
runtime.registerTrigger({  
  type: "http",  
  function_id: "hello::greet",  
  config: { api_path: "/greet", http_method: "POST" },  
});  
```
#### **(二) 关键技术点**
- **断线重连**：SDK自动重新注册Functions和Triggers
- **竞态处理**：通过`function_owners`机制解决Worker上下线的状态一致性
- **Trace传播**：所有调用携带`traceparent`和`baggage`字段，实现跨系统追踪

### **⚠️ 工程落地的边界问题（挑战）**
1. **中心引擎可用性**：运行时引擎成为关键依赖，需解决部署、扩展和容灾
2. **触发语义差异**：HTTP关注延迟、队列关注重复消费、cron关注执行窗口，统一抽象无法掩盖本质差异
3. **能力目录治理**：需建立命名规范、版本策略、权限控制和废弃流程
4. **动态安全风险**：临时Worker的RBAC、沙箱隔离和资源配额需严格控制
5. **许可证限制**：核心引擎采用Elastic License 2.0，商业化需注意合规边界

### **📌 补充细节**
- **MCP与运行时目录的区别**：MCP解决工具复用问题，运行时目录解决工具可用性和连接性问题
- **Agent角色转变**：从独立进程进化为后端系统中的普通Worker，可被业务事件触发
- **上下文工程的持续性**：运行时能力目录仅解决"系统能做什么"，无法替代"当前该用什么上下文"的决策逻辑
