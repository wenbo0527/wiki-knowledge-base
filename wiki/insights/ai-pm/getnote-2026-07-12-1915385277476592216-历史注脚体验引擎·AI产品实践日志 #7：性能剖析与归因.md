# 历史注脚体验引擎·AI产品实践日志 #7：性能剖析与归因

> 来源: Get 笔记
> 知识库: ai-pm
> 原始 ID: 1915385277476592216
> 创建时间: 2026-07-12 15:32:28
> 同步时间: 2026-07-15T14:42:55.900130

测试的时候发现，有的时候服务不可用。前端toast报了个错，白底红字。

我第一反应是LLM慢——每次调用3-7秒，前端30秒timeout，超时很正常。改到60秒？还是报错。后端日志显示53.9秒——但加计时器跑3次后发现：冷启动惩罚，稳定态11-30秒。第一次归因就错了。不是代码慢，是外部服务冷启动。

稳定态11-30秒也不快。计时日志给出了真正的瓶颈：**LLM#1反复调Tool**。DM Agent绑了10个Tool——6个查询类+4个决策类。LLM#1先调2-3个查询类Tool，拿到结果再调一次LLM判断"信息够了没"，够了才放行到LLM#2生成叙事。2-3次Tool调用，每次3-7秒，光LLM#1就吃掉5-15秒。

阶段0的SKILL编排层已经把结论注入了DMContext——LLM不需要查，但它看到了这些Tool，就想调。

怎么发现这个瓶颈的？笨办法：在LangGraph每个节点的入口和出口打一行`[DM-PROF]`，记录当前毫秒数和节点名。跑3次input，把日志拉出来对齐看。不需要LangSmith（虽然LangSmith也能做，但配置成本更高），不需要APM工具，10行代码就能定位"哪个节点慢"。关键是**每个节点都要打**——不是只打LLM调用，后处理、序列化、兜底逻辑，全要打。因为隐藏的瓶颈往往不在你以为的地方。

我以为找到了真问题。后面还有更隐蔽的。

```
一次 /api/input 的调用链（v0 基准）

game_loop._run_round()
  ├─ SKILL编排层 [Python, <5ms] → 结论注入DMContext
  ├─ LLM#1 (situation_assessment) [3-7s × 2-3次] ← 瓶颈
  │   ├─ 调get_state → 返回 → 再调LLM#1
  │   ├─ 调check_rules → 返回 → 再调LLM#1
  │   └─ 判断"够了" → 放行到LLM#2
  ├─ LLM#2 (narrative_fusion) [3-4s × 1次] → 生成叙事
  └─ state_apply [Python, <1s]
```

## 修补1：给LLM更多信息

LLM#1反复调Tool，是因为它不知道当前状态，所以得自己查？那就让它不用查。

6个查询类Tool全是本地函数——get_state读内存，check_rules跑规则引擎，query_knowledge查Chroma——每个不到5毫秒。我把它们从LLM的"自主决策"变成game_loop的"预取"：在LLM上场之前，game_loop先把6个Tool全调一遍，结果打包成一条HumanMessage注入messages。LLM看到所有信息了，1轮就决策"够不够"，不用反复查了。

想法很漂亮。实测一跑，傻了。

LLM#1调Tool的次数从2-3次**反增到1-4次**。总HTTP从15-30秒涨到17-50秒。

为什么？因为prefetch给了LLM更多上下文，LLM看到更多上下文，决定"再查更细"。原来它调get_state+check_rules+recall_events，3次；现在它调query_story_segments+get_random_segment，也是3次——但不是重复查询，是**探索**。它看到叙事片段的摘要，想知道完整内容；看到随机段落，想再抽一段。

我犯了一个假设错误：我以为"加上下文让LLM决策更精准"。实际LLM是agentic主体——给它越多，它越想探索。它没有"够了"的概念。

修补没修好，还让情况更糟了。

## 修补2：不让LLM调

既然LLM看到Tool就调，那就让它调不了。

v2的思路：prefetch照做（v1的方法），但加一层过滤——LLM#1输出tool_calls之后，遍历一遍，查询类的移除，决策类的保留。LLM想调get_state？过滤掉。想调save_event？放行。

实测：LLM#1调Tool的次数确实降到了0-1。过滤立竿见影。

然后LangGraph崩了。

filter移除了LLM期望的tool_calls，但messages里没有对应的tool_result跟着。LLM#2 invoke的时候，上下文是"半成品"——LLM说"我要调get_state"，但messages里没有get_state的返回结果。LangGraph的ReAct循环要求tool_call和tool_result成对出现。缺了tool_result，直接BadRequestError——"tool call and result not match"。触发所有provider fallback，HTTP 500。

还有更隐蔽的：prefetch注入了一条1-2KB的HumanMessage到messages里。LLM#2 invoke的时候，messages是累积的——它仍然看到这条prefetch message。上下文长度2-3倍膨胀，推理时间5-10倍慢。原来3-4秒的LLM#2，现在动不动30秒+。

修补一个问题，制造了更大的问题。v1是"没修好"，v2是"越修越烂"——LLM#1的Tool调用确实减少了，但LLM#2直接崩了。

## 修补3：在prompt里说"不要调"

v2的反噬太重了。我需要一个更轻量的方案——不动架构，不改代码逻辑，只改prompt。

在system prompt末尾加一句："信息已预取，不要再调用查询类Tool。"

实测：LLM行为**完全无变化**。照样调2-3次。

为什么？我翻了一遍system_base.md——里面有7处结构化诱导LLM调Tool："Wiki是**按需**注入……**调用**""你**应该**采纳""**每次**必须输出events块"……还有4处类似的。7处"应该调"，1处"不要调"。LLM跟随多数。

我之前以为改prompt是"低风险低成本"方案。实际是"高风险低回报"——可能影响narrative质量（你不知道加了一句话会不会让LLM在其他地方也变保守），但几乎不改变LLM的Tool调用行为。

三次修补，三次失败，每次的失败方式都不一样：v1是LLM好奇心，v2是状态不一致+上下文暴增，v3是文字对抗失败。我需要退一步想想了。

## 用户一句话

三次修补失败，我写了一份失败报告，把v1-v3的实测数据和归因整理清楚。第二天上午，一个用户看了报告，说了一句话：

"那是不是该拆一下Agent？一个负责搜索找素材，另一个推进故事？"

这句话让我愣了一下。我做了三个实验，全在"修补"——改上下文、改过滤、改prompt。每个实验的假设都是"让LLM少调Tool"，区别只在用什么方式告诉LLM"不要调"。用户建议是"重构"——不是让LLM少调Tool，是让LLM看不到这些Tool。

为什么这个建议有效？因为它换了一个约束层。

前三次实验，约束在语言层：prompt说"不要调"，filter说"调了也白调"，prefetch说"信息够了"。LLM要么不听，要么听了反而更想探索，要么听了但状态不一致。

用户建议的约束在结构层：把6个查询类Tool从DM Agent移走，由game_loop直接调用（Wiki Agent），结果注入DMContext。DM Agent只绑4个决策类Tool。LLM看不到查询类Tool，自然不调。

**不是约束LLM的行为，是改变LLM能看到什么。**

3处代码改动，LLM#1调Tool从2-3次降到0-1次，平均耗时降43%。52个端到端测试通过，narrative质量未受影响。

```
v0（拆分前）                        v4（拆分后）

game_loop._run_round()              game_loop._run_round()
  ├─ engine.search_wiki()             ├─ Wiki Agent.run() [Python, <5ms]
  │   [Python, <1ms]                  │   6个查询类tool由game_loop直接调完
  └─ dm.run() [DM Agent, LLM]        │   结果注入DMContext
        ├─ LLM#1: bind ALL 10 tools   └─ dm.run() [DM Agent, LLM]
        │   6个查询类 + 4个决策类           ├─ LLM#1: bind 只4个决策类
        │   LLM反复调查询类 2-3次 ← 问题    │   LLM看不到查询类，调0-1次 ← 解决
        └─ LLM#2: narrative               └─ LLM#2: narrative
```

三次修补失败，一次拆分成功。区别不在技术难度——拆分比修补更简单，3处改动vs每个实验十几处。区别在约束放在哪一层。

但这一篇的重点不是"约束该放哪一层"——第六篇已经讲过了。这一篇的重点是：**怎么发现问题，怎么归因，怎么避免修错方向。**

## 三个教训

回头看整个过程，三个教训。

**教训1：归因要精准——你以为的问题是A，实际是B，甚至C。**

玩家说"服务不可用"，我猜"LLM慢"。加计时器一测，53.9秒——确实慢。但"慢"的归因就错了：不是代码慢，是SSL冷启动。修timeout、加缓存、优化代码，全没用——问题根本不在你写的代码里。

继续测，发现稳定态11-30秒。归因再次修正：不是SSL的问题了，是LLM#1反复调Tool。

再翻，还有隐藏的LLM#3——兜底逻辑藏的，代码里没有显式调用，性能剖析才把它揪出来。每次3秒，占22%的耗时。

四层归因，每一层推翻上一层：LLM慢→SSL冷启动→LLM#1反复调Tool→还有隐藏的LLM#3。如果我在第一层就停下来修timeout，后面三层问题一个都发现不了。

AI产品的性能瓶颈往往不在你写的代码里。你以为的"慢"可能是外部服务冷启动，你以为的"2个LLM"实际有3个，你以为的"LLM慢"实际是兜底逻辑慢。**归因要精准，修错方向比不修更糟。**

**教训2：修补的代价不只是"没修好"，是"越修越烂"。**

v1：prefetch注入。LLM调Tool次数反增，总耗时从15-30秒涨到17-50秒。没修好，还更慢了。

v2：过滤tool_calls。LLM#1确实少调了，但LangGraph状态不一致导致HTTP 500，上下文暴增导致LLM#2慢5-10倍。修了一个问题，制造了两个更大的问题。

v3：改prompt。LLM行为完全无变化。1处"不要调"对抗7处"应该调"。零效果，但改prompt本身有风险——你不知道加了一句话会不会让LLM在其他地方也变保守。

每次修补都制造了新问题，而且新问题比原来的更难定位。v1的问题还能从计时日志看出来，v2的上下文暴增要翻LangGraph的messages累积才能发现，v3的"零效果"甚至没有明确的失败信号——LLM只是照常运行，你不确定它听没听。

**修补不是免费的。** 每加一层逻辑，就多一个可能出错的地方。v2的filter逻辑本身是对的——它确实过滤了查询类tool_calls。但它跟LangGraph的状态管理冲突了，这个冲突在设计时完全预料不到。修补的副作用往往比原问题更隐蔽。

**教训3：归因有盲区——你以为找到了所有问题，其实没有。**

性能剖析最让我意外的不是LLM#1反复调Tool——这个加计时器就能看到。最让我意外的是LLM#3——代码里没有显式调用，藏在兜底逻辑里，日志里不单独打印。如果不是逐段计时把每个节点的耗时都摊开，我永远不会知道还有第3个LLM调用。

这暴露了一个更普遍的问题：**AI产品里有多少隐藏的LLM调用？** 你写代码的时候只调了2次LLM，但兜底逻辑又调了1次，重试逻辑可能再调1次，后处理提取可能再调1次——你以为2次，实际4次。每次多3秒，4次就是12秒。你以为的"LLM慢"，实际是"你不知道自己调了几次LLM"。

归因的盲区不只是"隐藏调用"。还有：你以为瓶颈在LLM推理，实际在上下文长度（v2的prefetch让messages膨胀）；你以为瓶颈在代码逻辑，实际在外部服务（SSL冷启动）；你以为修好了，实际修补制造了更大的问题（v2的HTTP 500）。

**归因不是一次性的动作，是逐层剥洋葱。** 你找到了一层问题，修了，再测——可能又暴露出下一层。如果修完第一层就停下来，你永远不会看到后面的。

## 性能归因的设计检查清单

**归因层**

- 性能瓶颈的归因靠实测还是靠猜？有没有逐段计时数据？
- 冷启动的延迟来自代码还是外部服务？修代码能解决吗？
- 一次完整调用有几个LLM？有没有隐藏的（藏在兜底逻辑、后处理、重试里）？

**隐藏调用排查**

- 你的系统里有没有藏在兜底/重试/后处理里的LLM调用？你知不知道一次完整请求到底调了几次LLM？
- 兜底逻辑的延迟占比是多少？花在兜底上的时间值不值得？
- 哪些兜底可以合并到主LLM调用？哪些可以前置约束替代？

**修补层**

- 修补前后有没有对比数据？修补让整体变好了还是变差了？
- 修补有没有制造新问题？新问题比原来的更容易定位还是更难？
- 约束放在语言层还是结构层？语言层约束有没有实测验证过效果？

**决策层**

- 做了2-3个修补都失败时，有没有停下来问"问题本质是什么"？
- 有没有问用户？用户视角通常比技术视角更接近本质。
- 沉没成本有没有绑架判断？继续错误方向的成本 vs 换方向的成本，哪个更高？

这套检查清单的核心问题只有一个：**你的性能优化是在精准归因后动刀，还是在猜完就改、改完更糟？** 如果是前者，3处代码改动就能降43%平均耗时；如果是后者，每个修补都在制造新的问题，而新问题比原来的更隐蔽。
