## 第九章 起点：20个Agent是怎么来的

我的Agent系统跑起来了。任务板显示一切正常，49/50任务完成率98%，5个SOP覆盖率80%。但7天内（2026年7月8日-14日），对memory目录下21个教训文件做关键词grep，"反思≠实证/失职/诚实度偏差"关键词出现了**152次**——我的系统在假装成功。

任务板说32个pending，实际只有1个。文件写入报size 4205字节，stat一看实际不是。跨Agent转述丢精度，路径描述模糊到PM和QA找不到同一个文件。66小时无新动作，节奏全靠deadline拉，deadline一松就停滞。

这不是"我的Agent不靠谱"——这是**概率性系统缺少确定性护栏**时必然产生的问题。Agent执行是概率性的，但管理界面（任务板、文件size、报告）也依赖Agent自己报告——概率性输出没有确定性校验，两者之间的接口在骗人。

这一篇，是我们踩完这些坑之后的复盘。先说项目是怎么来的，再说坑在哪、怎么修。

### 9.1 一个人管多条产品线：从困境到Agent

在一家消费金融公司里，一个人负责整个数据产品条线：6个产品域，23个Epic，300+功能点。底层是数据基础设施——数据发现、数据管理、数据探索；上层是业务应用——数字营销、数字风险，再加一个通用门户。每条线都有自己的一摊事——数据管理在搭元数据和变量中心，数字营销在跑客户分群和触达策略，数字风险在管风控变量和消保合规。

日常状态是这样的——每天在四个场景之间来回切换：

**需求诊断场景**：业务方带着一个模糊想法来——"我们想用AI做智能客服"。你得在30分钟内判断：这个场景的AI成熟度够不够？数据就绪了吗？ROI能算过来吗？这需要的是评估框架和行业对标数据。

**需求细化场景**：诊断完"值得做"，接下来要把模糊想法拆成可执行的需求。客户分群用什么标签体系？触达策略用规则引擎还是模型驱动？这需要的是产品拆解能力和PRD写作。

**技术预演场景**：方案定下来，不能直接开干——得先出一个Demo。Demo的目的不是验证技术可行性，而是两件事：一是**对齐期望**，前面聊的方案做出来是不是业务真正想要的？经常是聊的时候双方都觉得懂了，Demo一出来才发现理解偏差；二是**暴露细节**，流程跑一遍才知道哪些环节卡住、哪些交互可以优化。这需要的是快速原型能力和用户视角。

**落地澄清场景**：Demo跑通了，真正落地时又冒出一堆问题。风控变量怎么接入？消保合规怎么过？和现有数据中台的接口怎么对？这需要的是架构治理和跨系统协调能力。

四个场景，四种专业语言。诊断聊的是"该不该做、能不能做"，细化聊的是"怎么拆、谁来干"，预演聊的是"跑不跑得通"，澄清聊的是"怎么接、怎么管"。context来回切换，每切一次要花15分钟重新加载。

最难受的不是忙，是**每个产品线都只能做到60分**。需求追问不够深，字段映射review只能看关键路径，PRD写完没时间打磨。一个人分身乏术，不是能力不够，是带宽不够。

**第一个破局点：vibe coding demo。** 诊断器客户问"这个场景值不值得用AI"，我先用vibe coding的方式快速出一个Demo——不搭架构，不拆Agent，一个prompt搞定五步流程（需求追问→场景诊断→快速Demo→能力定义→落地路线图）。Demo能跑，客户买单，但一个prompt做五件事的代价是：context污染严重，追问阶段的用户对话和Demo阶段的代码生成混在一起，两件事都做不好。

**第二个破局点：拆成7只虾。** 既然一个Agent做不好五件事，那就拆——调度虾（总编排）、萃取虾（需求追问）、诊断虾（五维打分）、Demo虾（代码生成）、结构化虾（能力定义）、Roadmap虾（路线规划）、校准虾（质量校验）。每个虾只做一件事，context干净，注意力集中。

7只虾是典型的**编排者-执行者**模式——调度虾是编排者，其他6只是Worker。每个Worker有独立的SOUL.md（角色说明书）、MEMORY.md（经验笔记本）、工具集和知识域。

**从vibe coding到7只虾，本质是从"一个人硬扛"到"一个人指挥一个团队"。** 但踩完坑之后我们发现，**问题不在团队有没有，在脚手架到不到位**。20个Agent不配Harness，就是20个各自为政的Demo。

### 9.2 从7只虾到20个Agent：膨胀与分层

7只虾跑通诊断器之后，其他产品线也想要Agent。数字社区需要PM、架构师、开发、QA、文档五个角色；个人主页和问小数需要内容创作和数据分析能力；投资分析需要财务和行业研究能力。Agent数量从7膨胀到20——原因不是"多Agent更先进"，而是每条产品线都需要自己的专业角色。但这次膨胀不是简单的数量增加——它形成了**两个团队+一个共享层**的分层架构：

```
                    ┌─────────────────────┐
                    │   文博 (User / P0)   │  ← 飞书直聊
                    └──────────┬──────────┘
                               │ (决策 / 拍板)
                               ▼
                    ┌─────────────────────┐
                    │   派蒙 (大总管)       │  ← 跨团队协调
                    │   model: MiniMax-M3  │     派单 + 跨agent调度
                    └──────────┬──────────┘
               ┌───────────────┼───────────────┐
               ▼               ▼               ▼
       ┌──────────────┐ ┌──────────────┐ ┌──────────────┐
       │   团队 1      │ │   团队 2      │ │   共享层      │
       │  钟离 (CTO)   │ │   数字社区    │ │  云端 + 工具  │
       │  全程设计     │ │   PM 主导     │ │              │
       └──────┬───────┘ └──────┬───────┘ └──────┬───────┘
              │                │                │
              ▼                ▼                ▼
       AI诊断器          数字社区平台        Nick Fury KB
       问小数            6子应用            派蒙main
       个人主页          41万行业务代码      5共享专家
       Portal Shell     200+路由           30+字段映射
```

**团队1（钟离管）**：AI诊断器、问小数、个人主页、Portal Shell。钟离全程设计+兼任PM。

**团队2（PM管）**：数字社区（数据/营销）。PM主导日常，钟离每周≤1h终审。

**共享层**：Nick Fury知识库、派蒙云端分身、问小数项目、5个AI诊断器专家（clarifier/requirement-definer/interaction-designer/diagnostician/agent-architect）。

**20个Agent的4大分类**：


| 分类           | 数量  | Agent                      | 活跃度 |
| ------------ | --- | -------------------------- | --- |
| 核心4人（治理层）    | 4   | 派蒙/钟离/Nick Fury/Tony Stark | 高   |
| 团队2数字社区（执行层） | 5   | PM/arch/dev/QA/doc         | 中   |
| 内容创作（能力补全）   | 4   | Agatha/老六/内容专家/交互测试专家      | 候选  |
| 知识财务（私域服务）   | 3   | 麦麦/小二子/Smith               | 候选  |
| 共享层（云端跨域）    | 4   | 派蒙云端/文博云端/问小数/备用模型         | 中   |


**关键发现**：20个Agent不是扁平的"17个Worker+1个编排者"，而是**两层编排+一个共享层**。派蒙（大总管，跨团队协调）是全局编排者，钟离（研发CTO，团队1全程设计）是团队1的编排者+团队2的终审者。这种分层架构在光谱上的位置更复杂——团队1内部是编排者-执行者，团队2内部也是编排者-执行者，两个团队之间通过派蒙协调是**多Agent编排**。

### 9.3 框架选型：为什么选了OpenClaw

选型时对比了三个框架：


| 维度       | LangChain    | AutoGen  | OpenClaw   |
| -------- | ------------ | -------- | ---------- |
| 多Agent支持 | 弱（Agent抽象不够） | 强（但配置复杂） | 原生支持       |
| 定时任务     | 需外部cron      | 需外部cron  | 原生cron     |
| 通信集成     | 需自己接         | 需自己接     | 原生lark-cli |
| 契约机制     | 无            | 无        | 5契约        |
| 调度中心     | 无内置          | 无内置      | 派蒙         |


**选OpenClaw的理由**：不是它功能最多，而是它的Harness起点最接近我们的需求——原生cron、原生飞书集成、5契约机制、派蒙调度。如果选LangChain，我们需要自己搭cron、接飞书、设计契约机制——这些Harness工作可能比业务逻辑花更多时间。

**回头看**：这个选型决策是对的，但有一个盲区——OpenClaw的cron投递配置比预期复杂（L-34/L-35/L-36三条教训都和cron有关）。框架的Harness起点高，不等于没有坑。

### 9.4 我们已有的确定性组件

说"问题在脚手架"，不是说我们什么脚手架都没有。实际上，20个Agent已经跑着一套**确定性组件和概率性组件的混合架构**：

**5契约机制**（每个Agent启动时必须声明）：

- 输入契约：我需要什么格式的输入
- 边界契约：我做到哪一步为止
- 输出契约：我返回什么格式的结果
- 失败处理契约：出错了怎么办
- 经验回写契约：做完之后往MEMORY.md（经验笔记本）存什么

**4套已锁版SOP**：

- v15-2.0 24条硬约束：核心原则"任何数据必实测，不凭印象报告"
- 空闲状态驱动SOP：Agent检测到连续N分钟无新输入时进入空闲态，按预设优先级队列取下一个任务
- 跨Agent路径描述规范：路径必用绝对路径，含workspace中间层
- 候选编号管理规范：写候选前必先ls查可用编号

**5层调度机制**：

1. Standing Orders（常驻指令，最高优先级）
2. Cron+心跳检测（5分钟/30分钟/1小时三档）
3. Tasks（任务板，50个任务，98%完成率）
4. sessions_send（跨Agent点对点通信）
5. Hooks（事件触发，如文件变更自动smoke测试）

这些不是"缺Harness"——是有Harness，但**确定性护栏没有覆盖概率性输出的关键接口**。5契约是确定性的，但Agent执行是概率性的，两者之间的接口（任务板、文件size、跨Agent报告）没有确定性校验层——概率性输出直接暴露给确定性界面，中间缺了"确定性的壳"。152次诚实度偏差，大部分就出在这些没有护栏的接口上。

## 第十章 用光谱审视我们的实践

### 10.1 我们的架构在光谱上的位置

把文博Agent小队的架构放到综述篇的光谱上：

```
确定性 ←————————————————————————————————————————————→ 概率性

提示链  路由  并行化  评估器-优化器  编排者-执行者  ReAct  Plan&Exec  Reflection  多Agent编排  共识投票  Swarm
                                          ↑                              ↑
                                    团队1/团队2内部                   两个团队之间
                                    （编排者-执行者）                （多Agent编排）
```

**团队1和团队2内部**：光谱中左段——编排者-执行者模式。钟离/PM做任务分解和委派，Worker各做各的。确定性中等。

**两个团队之间**：光谱中右段——多Agent编排。派蒙统一调度，但团队1和团队2的Agent之间不直接通信。

**关键发现**：我们的架构不是"一种模式"，而是两种模式的叠加。这和综述篇6.5的数据直接对应——88%的Agent试点止步于POC，原因排第一的是"评估缺口（64%）"。两种模式的确定性程度不同，评估方式也应该不同——但我们一开始没有区分，用同一套5契约管理所有Agent，导致团队1的Worker和团队2的业务专家被同等对待，管理粒度过粗。

### 10.2 对标详细篇：已有组件 vs 缺失组件

架构模式选型是对的，Harness也已经有了一大半——但缺失的部分恰好卡在"确定性组件和概率性组件的接口"上：


| 组件         | 状态   | 说明                                             |
| ---------- | ---- | ---------------------------------------------- |
| 5契约机制      | ✅ 已有 | 输入/边界/输出/失败处理/经验回写                             |
| 4套SOP      | ✅ 已有 | 24条硬约束+空闲驱动+路径规范+编号管理                          |
| 5层调度       | ✅ 已有 | Standing Orders→Cron→Tasks→sessions_send→Hooks |
| 产品域评测体系    | ✅ 已有 | 三位一体交叉检查（Demo代码↔需求文档↔业务需求），MECE+一致性两层评估        |
| 效果评估Agent  | ✅ 已有 | Evaluator配置，三类指标（业务/产品/成本），行业基准值               |
| MCP标准化工具调用 | ❌ 缺失 | 每个Agent自己造工具轮子                                 |
| Agent系统评测  | ❌ 缺失 | 产品域有评测，但Agent系统本身没有——诊断器五维分数的可信度无法量化           |
| 中断恢复       | ❌ 缺失 | 网络抖动=从头再来                                      |
| 降级策略       | ❌ 缺失 | 模型限速=全线崩溃                                      |


**最关键的缺口是Agent系统评测**。注意，我们不是没有评测体系——产品域治理有三层评估（MECE审视+文档vs需求+代码vs文档），效果评估Agent有完整的三类指标和行业基准值，AI实践日志里也有具体数据：评审从3-5轮降到1-2轮，PM时间从90%维护降到40%，560个用户故事可验证。

但这些评测覆盖的是**产品域**，不是**Agent系统本身**。诊断器给客户打了五维分数——场景成熟度、数据就绪度、技术可行性、ROI预期、组织适配度——但无法回答"这个分数可信吗"。客户追问时，钟离只能凭印象解释。这和11.1的诚实度偏差是同一条线：**确定性界面（五维分数）掩盖了概率性现实（分数的置信度未知）**。

如果Agent系统评测到位，152次诚实度偏差中至少有一部分会被提前拦截——不是靠"更认真"，是靠"有数据可查"。这就是Harness的本质：不是让人更靠谱，是让系统不需要人靠谱也能出靠谱的结果。

**完成度判断**：已有组件覆盖了"日常运行+产品域评测"，缺失组件卡在"Agent系统自评测+从Demo到生产"——产品域能评了，但Agent系统自己评不了自己。

### 10.3 编排价值公式验证

用编排价值公式算一下20个Agent是否值得：

**领域隔离收益**：高。情报分析、产品管理、架构设计、内容创作、数字社区——五个领域的知识和方法论完全不同。单Agent的context会被严重污染。

**Token膨胀**：中等。20个Agent不是同时运行——派蒙按需调度，同一时刻活跃的通常3-5个。Token膨胀是单Agent的3-5倍，不是20倍。

**延迟累积**：中等。串行任务延迟是各步之和；并行任务延迟取决于最慢的Agent。

**N²冲突成本**：低。20个Agent之间不直接通信，冲突通过派蒙中转解决。N²问题被中心化调度规避了。

**结论**：编排价值 = 高 − (中 + 中 + 低) = **正**。20个Agent值得——但前提是派蒙调度可靠。

## 第十一章 踩过的坑：从"反思≠实证"到"静默失败"

知识库实践篇已经复盘了13个INC的根因。这一章从架构视角重新审视，结合7月14日钟离写的团队运行问题评估，看到更深一层。

### 11.1 第一大问题：诚实度偏差——"反思≠实证"出现152次

**数据**：7天内（2026年7月8日-14日，统计口径：memory目录下21个教训文件关键词grep）"反思≠实证/失职/诚实度偏差"关键词出现**152次**。钟离端占比70%——CTO自己的诚实度偏差是系统最大的风险源。

**架构视角**：这不是一个"态度问题"，是一个**确定性系统试图管理概率性系统时必然产生的偏差**。综述篇说"Workflow是确定性系统，Agent是概率性系统"——我们的Agent是概率性的，但我们对Agent的管理方式是确定性的：任务板显示"32 pending"，实际只有1 pending；write tool报size，但文件最终size可能不同；跨Agent转述不带"原话："前缀，信息在传递中失真。

**对应详细篇**：第六章评测体系——"只看最终成功率会系统性误导"。我们的版本更隐蔽：不是评测指标在骗人，是**管理界面在骗人**。任务板、文件size、跨Agent报告——这些"确定性界面"掩盖了底层的概率性。

**教训沉淀**：我们锁版了24条硬约束，核心原则是"任何数据必实测，不凭印象报告"——比如任务板显示的pending数必须逐个get验证，文件size必须stat确认，跨Agent转述必须带"原话："前缀。这本质上是给概率性系统加了一层确定性校验——Harness工程中"可观测性"组件的变体。

### 11.2 第二大问题：节奏失守——66小时无动作

**数据**：7/10 14:08到7/14 09:00，**66小时52分钟**跨度无新动作（判定标准：派蒙无调度记录、所有Agent无输出、任务板无状态变更）。

**架构视角**：节奏失守的根因是"日期驱动"——任务按deadline强制排，节奏被deadline拉。但Agent系统不应该依赖外部deadline来驱动节奏，应该有**自主驱动机制**。

**对应详细篇**：2.1 ReAct循环的"停止条件"——"必须硬编码最大步数。没有硬限制，模型可能无限循环。"我们的版本是反过来的：不是无限循环，是无限停滞——没有外部触发就不动。两种问题的根因一样：**缺少显式的驱动条件**。

**修复**：空闲状态驱动SOP——Agent检测到连续N分钟无新输入时进入空闲态，按预设优先级队列（P0/P1/P2/P3）取下一个任务做，不需要等deadline。这本质上是给Agent系统加了一个"心跳"机制——Harness工程中"状态管理"组件的变体。

### 11.3 第三大问题：路径描述模糊——跨Agent通信的确定性缺失

**数据**：候选#141+#142+#143（钟离端）= 模糊词"钟离tmp/"/"工作目录"；候选#146+#147（QA端）= 漏`memory/`中间层。

**架构视角**：路径描述模糊是**Agent间通信协议不精确**的表现。详细篇第四章讲A2A协议的Agent Card——精确描述"我能做什么、我需要什么输入、我返回什么输出"。我们的Agent之间没有这样的精确描述，路径靠"默认理解"——但每个Agent对目录结构的理解不同。

**对应详细篇**：4.3 A2A——"Agent Card是Agent的能力描述"。我们缺的不是A2A协议本身，而是A2A协议背后的精确性原则——Agent间通信必须用绝对路径，不能用模糊描述。

### 11.4 第四大问题：5个诊断器专家闲置

**数据**：clarifier/requirement-definer/interaction-designer/diagnostician/agent-architect，5个AI诊断器专家基本未启动。98%的任务是钟离单干+subagent完成。

**架构视角**：这是**编排价值公式为负**的典型案例。5个专家的领域隔离收益存在（每个专家只做一件事），但Token膨胀和调度复杂度超过了收益——跨session调用需sessions_spawn复杂配置，钟离自身的subagent能力足够，不主动派给5个专家。

**对应详细篇**：3.5编排价值公式——"价值为负时，单Agent+更多工具为最优解。"钟离+subagent就是"单Agent+更多工具"，5个专家就是"多Agent"。当前阶段，单Agent更高效。

**判断**：5个专家不是"浪费"，而是"时机未到"。随着诊断器项目进入商业化阶段，需要同时服务多个客户时，5个专家的并行能力才有价值。

### 11.5 问题模式总结（架构视角）


| 问题     | 频次     | 对应光谱位置 | 对应详细篇          | 核心教训          |
| ------ | ------ | ------ | -------------- | ------------- |
| 诚实度偏差  | 152次   | 全光谱    | 评测体系/可观测性      | 确定性界面掩盖概率性现实  |
| 节奏失守   | 66h    | 全光谱    | 状态管理/停止条件      | 缺少自主驱动=无限停滞   |
| 路径描述模糊 | 跨Agent | 中右段    | A2A/Agent Card | 通信协议不精确       |
| 专家闲置   | 长期     | 中右段    | 编排价值公式         | 价值为负时单Agent更优 |


**核心洞察**：4大问题可以归结为同一句话——**概率性系统缺少确定性护栏**。5契约是确定性的，Agent执行是概率性的，但两者之间的接口（任务板、文件size、跨Agent报告）没有确定性校验层——概率性输出直接暴露给确定性界面，没有"确定性的壳包裹概率性的核"。诚实度偏差是"概率性输出缺少确定性校验"，节奏失守是"概率性驱动（Agent自主）缺少确定性护栏（心跳检测）"，路径模糊是"概率性描述缺少确定性协议（绝对路径强制）"，专家闲置是"确定性架构（5个专家）和概率性需求（按需调度）不匹配"。

这和综述篇6.5的数据完全对应——88%止步于POC，第一原因是"评估缺口（64%）"。评估缺口的本质就是：概率性系统的输出没有确定性护栏来校验，Demo到生产的鸿沟就跨不过去。Mitchell Hashimoto的定义最精准："构建一个确定性的壳，来包裹概率性的核"——不是"没有Harness"，是"确定性护栏没有覆盖概率性输出的关键接口"。

## 第十三章 给同路人的三个建议

### 建议一：先试单Agent+多Skill，再考虑多Agent

Anthropic的核心原则是：默认从单Agent开始，只有当引入复杂性可以明显改善结果时，才去引入它。Google DeepMind的180组实验也印证了这一点——在顺序推理任务上，所有多Agent配置都比单Agent差39%-70%。

所以选型不是"单Agent还是多Agent"的二选一，而是**三步递进**：

**第一步：单Agent够不够？** 一个Agent+一套好工具，能搞定大部分任务。智能客服查订单→退换货→发通知，每一步都是确定性的工具调用，不需要拆成三个Agent。Skill是确定性工具，不需要独立context，通信成本为零，调试简单。

**第二步：单Agent+多Skill够不够？** 如果任务需要不同领域的专业能力，但不需要独立的context隔离——加Skill就行。Skill像npm包一样安装组合，Agent按需调用，不需要设计通信协议。我们的5个诊断器专家（clarifier/requirement-definer/interaction-designer/diagnostician/agent-architect），当前阶段就是Skill而不是独立Agent——钟离一个Agent调用5个Skill，比5个独立Agent更高效。

**第三步：单Agent+多Skill不够了，再从编排者-执行者开始。** 只有当context真的被污染了——追问阶段的用户对话和Demo阶段的代码生成混在一起，两件事都做不好——才需要拆。编排者-执行者是"半只脚踏进Agent"的最安全起点——编排者是单点，出了问题至少知道找谁。对等协作和Swarm连"找谁"都做不到。

选型口诀：轻量用Skill，强控用编排者-执行者，不要上来就搞对等协作或Swarm。

### 建议二：概率性系统必须用确定性护栏来校验

我们的4大运行问题，根因都是同一个：概率性Agent系统缺少确定性护栏。任务板显示"32 pending"实际只有1个——任务板是Agent自己报告的（概率性），没有独立的确定性校验；write tool报size和实际size不同——输出是Agent声称的（概率性），没有stat验证（确定性）；跨Agent转述丢失精度——转述是Agent理解的（概率性），没有"原话："前缀保留（确定性）。

Harness Engineering的核心思想，用Mitchell Hashimoto的比喻来说：模型是野马，潜力无穷但不可控；Harness是缰绳、笼头、马鞍——Spec（要做什么）、Boundary（边界在哪）、Verification（怎么确认做对了）——三个确定性组件包裹在概率性的模型外面，它才能真正为你工作。

Maestro Order论文用数学证明了确定性护栏的效果：一道验证门把可靠性从0.55提升到0.98，四道提升到0.999。LangChain的实验更直观：只改Harness不改模型，TerminalBench排名从30名外跃升到第5名——确定性护栏对可靠性的影响，可以超过换一代模型。

我们的24条硬约束（"任何数据必实测，不凭印象报告"）就是确定性护栏的实践——任务板pending数逐个get验证、文件size必须stat确认、跨Agent转述必须带"原话："前缀。这些不是"概率性校验"，是确定性护栏——Harness工程中Guardrails组件的变体。

**落地方法**：给每个概率性输出加一层确定性护栏。任务板显示的数据，逐个get实证；文件size，stat验证；跨Agent报告，带"原话："前缀。这不是"多此一举"，是概率性系统的必要成本——你在光谱上容忍的概率性越多，确定性护栏的"保费"就越贵。

### 建议三：编排价值公式算不出来的东西

> 编排价值 = 领域隔离收益 − (Token膨胀 + 延迟累积 + N²冲突成本)

公式能告诉你"值不值得拆"，但算不出来三件事：

**1. 时机。** 我们5个诊断器专家，公式算出来编排价值为负——领域隔离收益存在，但Token膨胀和调度复杂度超过了收益。但"时机未到"这个判断公式给不了。当诊断器进入商业化阶段，需要同时服务5个客户时，5个专家的并行能力才有价值。**公式算的是"现在值不值得"，算不了"什么时候会值得"。**

**2. 边界。** 公式假设"领域隔离收益"是确定的——要么隔离、要么不隔离。但实践中边界是模糊的。我们的团队1和团队2之间，钟离的CTO角色横跨两个团队，每周1h终审团队2的关键决策——这个"跨域监督"在公式里算领域隔离还是算N²冲突？**公式算的是"理想边界"，算不了"真实边界"。**

**3. 人的因素。** 152次诚实度偏差，70%来自钟离端——CTO自己是系统最大的风险源。这不是架构问题，是人的问题。但公式里没有"人的可靠性"这个变量。**公式算的是"系统值不值得拆"，算不了"拆了之后人能不能管住"。**

所以：用公式算一遍，再决定上不上多Agent。但算完之后，还要问自己三个公式算不出来的问题——时机到了吗？边界划清了吗？人能管住吗？
