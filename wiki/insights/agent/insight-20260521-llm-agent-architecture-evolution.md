## 核心洞察

> **TL;DR**: Agent架构建设顺序应该是：Harness → Skill → Memory → Multi-agent Protocol，先建立系统"脊梁"，再逐步扩展能力。

### 落地建议：先后顺序很关键

| 顺序 | 组件 | 职责 | 说明 |
|:---:|:---|:---|:---|
| **1** | **Harness** | 系统"脊梁" | 确保故障可观测、可阻断、可回滚 |
| **2** | **Skill** | 执行能力 | 优先降低执行方差，提升系统可预测性 |
| **3** | **Memory** | 记忆存储 | 避免过早记忆噪声，待执行路径稳定后再持久化关键状态 |
| **4** | **Multi-agent Protocol** | 协作规范 | 多Agent共享，需显式权限控制 |

## 各组件职责详解

### 1. Harness（框架）

| 要素 | 说明 |
|:---|:---|
| **定位** | 系统"脊梁"，差异化核心 |
| **核心能力** | 流程控制、审批、观测、回溯 |
| **职责** | 系统级治理，全局协调 |
| **建设目标** | 故障可观测、可阻断、可回滚 |

### 2. Skill（技能）

| 要素 | 说明 |
|:---|:---|
| **定位** | 执行能力封装 |
| **核心能力** | 跨任务复用，需版本管理 |
| **职责** | 工具接口定义、Agent交互规范 |
| **建设目标** | 降低执行方差，提升可预测性 |

### 3. Memory（记忆）

| 要素 | 说明 |
|:---|:---|
| **定位** | 外部认知基础设施 |
| **核心能力** | 状态持久化，跨任务记忆 |
| **职责** | 固定执行流程、决策规则封存 |
| **建设目标** | 避免过早记忆噪声 |

### 4. Multi-agent Protocol（协作协议）

| 要素 | 说明 |
|:---|:---|
| **定位** | 协作规范 |
| **核心能力** | 多Agent共享，显式权限控制 |
| **职责** | 共享状态、冲突处理、版本化 |
| **建设目标** | 解决"持续协作"问题 |

## 建设顺序的原因

### 为什么Harness先行？

| 原因 | 说明 |
|:---|:---|
| **建立基线** | 确保系统可观测、可控 |
| **降低风险** | 故障不会导致系统崩溃 |
| **为后续奠基** | Skill/Memory需要Harness支撑 |

### 为什么Memory靠后？

| 原因 | 说明 |
|:---|:---|
| **避免噪声** | 执行路径未稳定时，过早记忆会固化错误 |
| **降低复杂度** | 等其他组件稳定后再管理记忆 |
| **聚焦核心** | 先把执行做好，再考虑记忆 |

### 为什么Multi-agent最后？

| 原因 | 说明 |
|:---|:---|
| **成本最高** | Agent Team需要共享状态层 |
| **协调复杂** | 节点间通信协议、Lead Agent仲裁 |
| **其他先行** | Harness/Skill/Memory稳定后再引入 |

| **治理（Governance）** | Harness |

## 架构师核心能力

> **来源**: Agent时代架构师核心能力框架

| 能力 | 说明 |
|:---|:---|
| **跨框架能力** | 不追逐框架，关注底层工程能力 |
| **跨模型能力** | 模型会变，底层能力半衰期长 |
| **系统沉淀** | 建立筛选机制，评估技术优先级 |

### 优先沉淀的能力

| 优先级 | 能力 | 说明 |
|:---:|:---|:---|
| **P0** | 上下文管理 | 上下文是Agent的"生命线" |
| **P1** | 工具设计 | 工具是Agent的"四肢" |
| **P2** | 状态保存 | 长任务需要状态持久化 |
| **P3** | 权限控制 | 安全运行的基础 |
